## §2 Объём деплоя — ДВА объекта, а не один

Строка таблицы мандата (`07_STATE.md:1517`) называет объём «деплой `cf-facts` и `cf-finance`».
Это **устарело**: подготовка (`reference/ingest_moment_zone_fix_2026-08-08.md`, шаг 1) установила,
что расходная ветка несётся `cf-loss-commission`, дефекта в её ингесте нет, а настоящий дефект
сидит в SQL витрины. Фактический объём:

**Объект A — Cloud Function `cf-facts`**, три файла, ветка `deploy/cf-facts-2026-08-09-moment-zone`:
- `helpers.py` — новая функция `parse_moment_to_bishkek_date`;
- `fetch_returns.py` — импорт плюс тело `_parse_moment_kgt` (`return_date` в `core.fact_returns`);
- `fetch_purchases.py` — импорт плюс тело `_parse_date_kgt` (`order_date` и
  `planned_delivery_date` в `core.fact_purchases`, `fetch_purchases.py:96,104`).

**Объект B — Scheduled Query `sq_marts_expenses`**, `transferConfig`
`6a22a243-0000-20fd-a458-883d24f4cad4` (`11_INFRA_FACTS.md:112`), две строки:
`CAST(l.moment AS DATE)` / `CAST(c.moment AS DATE)` → `DATE(…, 'Asia/Bishkek')`
(`sq_marts_expenses.sql:20,44`).

Объекты независимы: разные системы, разные откаты, разные окна проявления. Каждый объявляется
владельцу **отдельным сообщением до подтверждения** (`ADR-077 §6`, `05_CONVENTIONS §Процедура
деплоя` п.5); объединять их в один паст запрещено (`ADR-055 §2`).

### Ловушка объекта A, названная заранее

Снапшот `reference/code/cf-facts/bq_ops.py` **несёт готовый, но не задеплоенный патч
`SALES-REFRESH-WINDOW`** (узкая форма, `07_STATE.md:1481`), у которого мандат НЕ выдан и не
выполнено собственное предусловие (`ADR-145 §4/§5` — защита от рассогласования окна staging и окна
`MERGE`). Перенос снапшота в ветку деплоя «целиком» вывез бы этот патч в прод без мандата.
**Условие: в ветку переносятся ровно три файла выше; `bq_ops.py` в ветке обязан быть побайтово
равен `master` код-репо, проверка `sha256` печатается до `push`.**

## §3 Откат — по каждому объекту отдельно

**Объект A.** Код — повторный деплой именем текущей живой ревизии `cf-facts-00010-mog`
(`generation 1786194676108292`, `MANIFEST.md`). Данные — откат кода сам по себе даты НЕ
возвращает: `core.fact_purchases` грузится полным refresh (`main.py:10` «fetch ALL purchaseorders»),
`core.fact_returns` — режимом `returns` с окном; поэтому после отката кода обязателен повторный
прогон соответствующих режимов. Откат **полон**, но двухшаговый, и это надо сказать до, а не после.

**Объект B.** Возврат прежнего текста запроса из git (`reference/sql/sq_marts_expenses.sql` на
родителе патч-коммита `a45837b`). Витрина `marts.expenses` пересобирается ежедневно
`WRITE_TRUNCATE` в `11:10 UTC` (`11_INFRA_FACTS.md:112`), то есть и правка, и откат проявляются
целиком на первом же следующем прогоне — данными откат полон, руками таблица не трогается.
Второй путь пересборки марта (`cf-finance.trigger_marts()`, `ADR-038`) в замере
`reference/bq_jobs_2026-07-28.md` за пятнадцать суток не проявился ни разу — но правило `ADR-038`
требует закрывать оба пути, поэтому read-back витрины после первого прогона обязателен.

## §4 Условия приёмки

**Условие 1 — шаг 0, замер ожидаемого сдвига ДО деплоя (read-only, класс A).**
`05_CONVENTIONS` Часть I ★ «Критерий приёмки выводится из формулы, не из свойства данных»
(`ADR-075 §3`) требует предъявить разницу двух формул числом **до** прогона. Подготовка
`2026-08-08` этого не сделала: её проверка синтетическая (`reference/ingest_moment_zone_fix_2026-08-08.md`,
шаг 2) — она доказывает, что формула умеет двигать дату на полосе `UTC [18:00; 24:00)`, и ничего
не говорит о том, сколько строк и денег в наших таблицах на этой полосе лежит.

Замер исполним одним read-only заходом и обязан дать:
- `core.fact_loss` и `core.fact_commissionreportin` — число строк с `TIME(moment) >= '18:00:00'`
  (UTC) и разность месячных сумм `DATE(moment,'Asia/Bishkek')` против `CAST(moment AS DATE)`
  отдельно для мая-2026 (зона паритета) и для июля-2026 (текущая клиентская картина);
- `core.fact_returns` / `core.fact_purchases` — в ядре хранится уже `DATE`, исходного времени там
  нет, поэтому величина сдвига **из ядра не выводится**; источником замера может быть только
  ответ МойСклада (живой `GET`, класс B) либо GCS-архив ответов. Что именно взято — называется
  явно; «не измерено» пишется как «не измерено», а не как «сдвига нет» (★ «Успех инструмента ≠ факт»).

**Условие 2 — до/после по трём парам реестра паритета, объявленным сошедшимися.** Патч меняет
числа задним числом ровно на трёх из семи поверхностей финиша Epic-1:
- «Расходы П&Л» → `marts.expenses` (пара сошлась `0,00`, эталон май-2026 `10 232 903,20`, `ADR-006`);
- «Возвраты покупателей» → `core.fact_returns` (пара сошлась `570 = 570`, май-2026, `ADR-114 §2`);
- «Заказы поставщикам в пути» → `core.fact_purchases` (пара сошлась `Δ = 0` точно, `ADR-124`).

Замер `COUNT(*)`/`SUM(...)` до и после по каждой — обязателен. Ненулевая разность **не есть регресс
по умолчанию** (у патча ровно та цель — подвинуть неверно поставленные даты), но уходит архитектору
числом, а не оценкой. Прецедент формы — условие 3 мандата `ADR-146 §5`.

**Условие 3 — гигиена деплоя объекта A** (`ADR-040`, `05_CONVENTIONS §Процедура деплоя` п.1/3/4/7/8):
свежий снапшот живой ревизии сверяется с `master` ДО правки; `.gcloudignore` чист; сплошной поиск
секретов по патчу с печатью совпавших строк; read-back архива после деплоя, соответствие
«ревизия ↔ коммит» пишется в `reference/code/cf-facts/MANIFEST.md`; при неуспехе ветка не сливается.

**Условие 4 — `bq_ops.py` не едет** (см. §2, ловушка).

## §6 Остаточные риски, названные до деплоя

1. **Вариант (a) `Q-92` формально не исключён.** Если эталонными сутками паритета когда-нибудь
   объявят московские (`DATE(M+3ч)`), этот патч придётся переделывать, а `core.fact_sales_profit`
   пересчитывать. Рекомендация архитектора (`ADR-101 §6`) — исключить (a); вероятность мала, цена
   ошибки — один повторный деплой той же формы.
2. **Сдвиг увидит клиент.** Часть документов переедет на соседние сутки; суточные и, возможно,
   месячные числа на страницах изменятся. Это ожидаемое поведение фикса, а не регресс — но сказать
   об этом надо ДО правки, иначе первую верную правку откатят как поломку (тот же класс риска, что
   `R1`, `ADR-140 §5`).
3. **Объект B бьёт по всей истории сразу** (`WRITE_TRUNCATE` ежесуточно), объект A по закупкам —
   тоже (полный refresh). Промежуточного состояния «только вперёд» у этого патча нет по построению.
