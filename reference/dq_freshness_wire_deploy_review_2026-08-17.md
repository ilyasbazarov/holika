## §1. Вердикт

**Мандат класса B не рекомендуется к выдаче в текущем состоянии патча.** Найден дефект, при
котором шесть из двенадцати подключаемых проверок **могут остановить весь конвейер** — ровно то,
чего подключение обязано было избежать по собственной постановке.

Дефект чинится одной правкой класса A (перенос уже существующей формы с шести функций на шесть
других), после чего готовность подтверждается повторным ревью. Задержка — одна сессия.

Отдельно: **мандат класса B архитектор не выдаёт вообще, ни при каком вердикте** — это решение
владельца (`ADR-076 §2`; форма разделения — `ADR-146` §1 владелец / §2-§6 архитектор, `ADR-159`,
`ADR-163`, `ADR-173 §5`). Настоящий документ готовит объект, откат и приёмку и даёт вердикт
готовности; выдача остаётся за владельцем.

## §2. Дефект: шесть проверок из двенадцати могут заблокировать промоут

### §2.1 Механизм

`main()` оборачивает вызов КАЖДОЙ проверки собственным `except`, который превращает любое
исключение в **провал** (`reference/code/cf-dq/main.py`, цикл `for name, fn in CHECKS`):

```python
try:
    passed, detail = fn(bq)
except Exception as e:
    passed, detail = False, f"EXCEPTION: {e}"
...
if not passed:
    all_passed = False
```

`all_passed=False` — это `DQ Gate FAILED`, то есть `step_promote` конвейера не исполняется.

Значит утверждение «проверка структурно не может вернуть `False`» верно **только если функция
сама ловит всё внутри себя**. Наружу отдавать исключение нельзя — снаружи оно означает блокировку.

### §2.2 Замер покрытия по всем двенадцати

Проверено программно по тексту каждой функции (`verify_2026-08-17.log §3`):

| Функция | `try` | `except` | Может ли заблокировать конвейер |
|---|---|---|---|
| `check_freshness_purchases_technical` | ДА | ДА | нет |
| `check_freshness_purchases_business` | **НЕТ** | **НЕТ** | **ДА** |
| `check_freshness_returns_technical` | ДА | ДА | нет |
| `check_freshness_returns_business` | **НЕТ** | **НЕТ** | **ДА** |
| `check_freshness_inventory_technical` | ДА | ДА | нет |
| `check_freshness_inventory_business` | **НЕТ** | **НЕТ** | **ДА** |
| `check_freshness_payments_technical` | ДА | ДА | нет |
| `check_freshness_payments_business` | **НЕТ** | **НЕТ** | **ДА** |
| `check_freshness_commissionreportin_technical` | ДА | ДА | нет |
| `check_freshness_commissionreportin_business` | **НЕТ** | **НЕТ** | **ДА** |
| `check_freshness_invoices_technical` | ДА | ДА | нет |
| `check_freshness_invoices_business` | **НЕТ** | **НЕТ** | **ДА** |

Ровно шесть технических проверок защищены; ровно шесть бизнес-проверок — нет. Форма
существует и применена, но применена наполовину.

### §2.3 Путь исключения подтверждён до конца, не предположен

`run_row` (`reference/code/cf-dq/helpers.py:18`) исключения НЕ глотает:

```python
def run_row(bq: bigquery.Client, sql: str) -> dict | None:
    rows = list(bq.query(sql).result())
    if not rows:
        return None
    return dict(rows[0])
```

`bq.query(sql).result()` без обёртки. Цепочка замкнута: ошибка BigQuery → `run_row` →
незащищённая `*_business` → `except` в `main()` → `passed=False` → `all_passed=False` →
`DQ Gate FAILED` → промоут заблокирован.

### §2.4 Чем это может выстрелить на практике

Бизнес-проверки читают `MAX(order_date)`/`MAX(return_date)`/аналоги из шести таблиц ядра.
Штатно такой запрос не падает. Падает он в трёх случаях, и все три реальны:

1. **Транзиентная ошибка BigQuery** (таймаут, лимит) — редко, но на горизонте суток при `24`
   прогонах в день и шести новых запросах в каждом это `144` дополнительных запроса в сутки,
   каждый из которых есть новая точка отказа.
2. **Изменение схемы или имени таблицы** — а это ровно тот класс события, ради наблюдения за
   которым проверки и подключаются. Проверка, которая падает от поломки наблюдаемого объекта,
   превращает наблюдение в остановку.
3. **Права/квоты** — любой сдвиг в IAM для `cf-dq` роняет запрос.

### §2.5 Почему это критично именно сейчас, а не «маловероятно и ладно»

Комментарий самого патча (`main.py`, блок над проверками свежести) формулирует основание
наблюдающей формы дословно: «DQ Gate есть единый выключатель всего конвейера, блокирующее
подключение шести новых условий перед передачей клиенту повторило бы класс отказа, который
чинила переделка метрики дрейфа». То есть автор патча назвал риск верно и защитился от него —
на шести функциях из двенадцати. Выложить патч как есть означает сделать ровно то, против чего
он написан.

Проект уже платил за этот класс дважды: `ADR-122`/`ADR-153` (метрика `drift_check`
останавливала конвейер на `8,9 %` суток без продаж) и `ADR-152` (fail-open фикс). Третий раз —
за неделю до передачи клиенту.

### §2.6 Побочное следствие: одно записанное утверждение неверно

`reference/dq_gate_block_bounded_2026-08-17.md §1` утверждает: «Остальные тринадцать
(`drift_zero_docs` и шесть пар `freshness_*_technical`/`freshness_*_business`) структурно не
могут вернуть `False` — **они читают код каждой функции**: все обёрнуты так, что возвращают
`(True, ...)` при любом исходе, включая исключение».

Утверждение верно для семи из тринадцати и неверно для шести. Это тот самый класс, ради которого
существует правило `★ Успех инструмента ≠ факт` (`ADR-021 §2`, `ADR-044`): вывод сделан по образцу
(«все написаны по образцу `check_drift_zero_docs`»), а не по построчной проверке каждой функции.
Сама операционная процедура `DQ-GATE-BLOCK-BOUNDED` от этого не рушится — список блокирующих
проверок в её §1 пополняется шестью именами, диагностический запрос и порог не меняются.
Правка текста — [задачей], вместе с фиксом.

## §3. Что чинить (форма назначена, вариантов нет)

Перенести на шесть `*_business`-функций ровно ту форму, которая уже стоит на шести
`*_technical`: тело целиком в `try`, `except Exception as e: return True, f"EXCEPTION
(notify-only, не блокирует): {e}"`. Никакой новой логики, никаких порогов, поведение при
успехе не меняется.

Запреты: не трогать шесть блокирующих проверок (`not_empty`, `drift_check`, `fk_integrity`,
`freshness`, `margin_sanity`, `currency_normalization`) — они обязаны блокировать; не трогать
`check_drift_zero_docs` (`ADR-153`, уже выложена); не менять `main()` — внешний `except` там
корректен и есть последняя линия для блокирующих проверок; не менять пороги и тексты `detail`
сверх добавляемой ветки.

## §5. Приёмка деплоя, когда он будет разрешён

Первые два пункта — обычные; **третий обязателен и не подлежит замене**.

1. `sha256` всех файлов архива новой ревизии совпадает с веткой деплоя побайтово.
2. Обслуживающая ревизия равна новой (`status.traffic`, `percent=100`).
3. **Состав живого механизма после деплоя, не факт выкладки.** Из записи `audit.dq_runs`
   первого естественного часового прогона предъявить СПИСОК ИМЁН исполненных проверок: их
   обязано быть `19`, и двенадцать имён `freshness_*` обязаны присутствовать поимённо.
   Основание — `Q-111`: приёмка прошлого выезда `DQ-CFDQ-DEPLOY` прошла полностью (`sha256`
   совпал, прогон состоялся, всё зелёное) и при этом **объект приёмки достигнут не был** —
   сверялся выложенный ФАЙЛ, а не исполняемый СОСТАВ. Повтор той же приёмки повторит ту же
   ошибку.
4. Все шесть блокирующих проверок в том же прогоне — `passed=true` (деплой не должен совпасть
   с реальной остановкой конвейера по посторонней причине).
5. Ни одна из двенадцати `freshness_*` не несёт `passed=false`. Любое `false` здесь есть
   немедленный откат и вопрос архитектору: значит §3 исполнен не полностью.
