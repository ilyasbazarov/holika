## 1. Два сверяемых числа, с адресом каждого

**A — сторона МойСклад (уровень (i)):** `report/profit/bycounterparty.returnSum`, минорные
единицы ÷100, за период и в разрезе контрагента; агрегируется до итога за период дашборда для
текущей поверхности пары (`ADR-114 §2`). Контрольный путь (ii) — та же величина через
`entity/salesreturn` + `entity/retailsalesreturn` тем же `moment`-фильтром; расхождение двух путей
уровня одного и того же API есть сигнал, не выбор одного из них (`ADR-098 §3` вариант (c)).

**B — наша сторона:** `SUM(core.fact_returns.sum_kgs)` за тот же период, **ограниченная
документами, привязанными к документу продажи** («основание»/basis) — не все строки таблицы.
Это сужение относительно буквального прочтения `ADR-085 §1` («сумма возвратов за период») —
основание сужения и его пределы см. §2.

## 2. Находка июля: у эталона есть неявный периметр «с основанием», у нас его не было

Замер `reference/parity_client_july_recheck_2026-08-13.md` (шаг 2, живой `GET
report/profit/bycounterparty`) разложил `returnSum` июля (`64 190,13`) на два документа:

| Документ | Сумма | Есть у нас |
|---|---|---|
| Эргешева Алтынай (`0d9650b7…`, `has_basis=true`) | `62 709,00` | да, до копейки |
| UMAI WB (Договор КР) | `1 481,13` | **нет** |

`core.fact_returns` за июль несёт четыре документа, `334 185,66`: помимо Эргешевой — три документа
«Неман Фарм» (`110 783,04` + `92 661,33` + `68 032,29` = `271 476,66`), все три с `has_basis=false`
(ни у одного нет ключа `demand` в сыром теле). Сумма ДОКУМЕНТА С ОСНОВАНИЕМ (`62 709,00`) совпадает
с оракулом до копейки; три документа БЕЗ основания в оракуле не отражены вовсе.

**Вывод: `returnSum` МойСклада считает только возвраты, привязанные к продаже того же контрагента;
возвраты без такой привязки в него не попадают.** Это факт о СЕМАНТИКЕ отчёта МойСклада (`ADR-067
§2`: расхождение entity-агрегации/полного множества с отчётом закрывается правилом соответствия,
не подгонкой нашей стороны под наблюдение без объяснения). Май-2026 не проявил это различие
случайно: все восемь майских возвратов несли ключ `demand` (`ADR-098 §5`), то есть в мае множество
«все возвраты» и «возвраты с основанием» совпадали буквально — совпадение оракула `570,00=570,00`
было совпадением этих двух множеств, не проверкой периметра.

**Оговорка о надёжности признака.** Поле `core.fact_returns.has_basis` реализует проверку
`"demand" in doc` — по НАЛИЧИЮ ключа, а не по его значению (`ADR-098 §5`, `Q-101`, статус `DEFER`).
Классификация трёх июльских документов как «без основания» опирается на буквальное отсутствие
ключа `demand` в их сырых телах (это надёжно — при отсутствующем ключе значения не бывает), а
классификация Эргешевой как «с основанием» подтверждена НЕ полем, а внешней сверкой: сумма
документа совпала с оракулом до копейки. Это n=1 положительное подтверждение, не доказательство
корректности поля на общем случае (у него может быть ложноположительный класс — присутствующий, но
пустой ключ `demand` — этим замером не проверенный). **Правило моста ниже не полагается на само
поле `has_basis`**, оно полагается на установленный ФАКТ семантики оракула; будущие месяцы обязаны
верифицировать периметр «с основанием» сверкой суммы с оракулом, а не слепым доверием полю, до
починки `Q-101`.

## 3. Критерий сходимости — инвариант разложения (форма `ADR-157 §1`, не порог на разность)

```
Δ = P − O + ε
```

- **`Δ`** — наблюдаемая разность «все строки core.fact_returns за период» минус `A` (эталон); это
  диагностическая величина, НЕ объект приёмки сама по себе.
- **`P`** — легитимное отступление: сумма документов core.fact_returns БЕЗ привязки к продаже
  (basis отсутствует) — оракул их не считает по своей семантике (§2), наша сторона их несёт
  корректно (`ADR-085 §1`: пара BI-поверхности показывает ВСЕ возвраты периода, это разные вопросы
  — прецедент `parity_client_july_recheck_2026-08-13.md §2`, развилка формы показа на холде
  владельца). **Закрывающее решение — настоящий ADR** (аналог периметровых исключений расходов,
  `ADR-002`/`ADR-005 п.1`): до этого решения сужение объекта паритета нигде не было записано.
- **`O`** — сирота на стороне эталона: сумма документов, присутствующих у оракула и отсутствующих
  в `core.fact_returns`. Знак учитывается вычитанием (`O` — величина недостачи нашей стороны).
- **`ε`** — остаток округления, допуск `|ε| < 1 KGS` (форма `ADR-157 §1`).

**Пара остаётся сошедшейся, пока `Δ` раскладывается без свободного остатка на названные `P`/`O`;
переоткрывается только при появлении суммы, не отнесённой ни к одному компоненту** — тот же
критерий, что `ADR-157 §1`/`ADR-119 §2`: рост `Δ` сам по себе не есть регресс, пока инвариант
держится.

## 4. Замер июля-2026 закрывает инвариант точно

```
Δ = 334 185,66 − 64 190,13 = 269 995,53
P = 271 476,66   (три документа «Неман Фарм», без основания)
O =   1 481,13   (документ UMAI WB, отсутствует в core.fact_returns)
P − O = 271 476,66 − 1 481,13 = 269 995,53 = Δ
ε = 0,00
```

Разложение точное, свободного остатка нет.

**Май-2026 — частный случай той же формулы:** `P=0` (возвратов без основания не было), `O=0`
(все восемь документов загружены), `Δ=0,00`.

## 5. Ответ на вопрос брифа: непогруженный документ — внутри разложения, не вне правила

**Документ UMAI WB (`1 481,13` KGS) относится к СВОБОДНОМУ ОСТАТКУ разложения (компонент `O`), а
не лежит вне объекта паритета.**

Основание — это не решённое периметровое исключение того же типа, что `P`. `P` закрывается
установленным ПРАВИЛОМ (оракул структурно не считает такие документы — то же самое произойдёт с
любым будущим возвратом без основания, механизм известен и воспроизводим). `O` — прямо
противоположный случай: документ ЕСТЬ у эталона, но отсутствует в нашей загрузке по причине,
которая не есть решённое правило, а есть незакрытый дефект полноты ингеста (`RETURNS-INGEST-
COMPLETENESS`; `K1`/`K2`/`K3` опровергнуты живым вызовом, `K4` — тип документа вне периметра
загрузчика `fetch_returns.py:63` (`salesreturn`/`retailsalesreturn`) — подтверждён методом
исключения, точный тип не идентифицирован). Владелец решил не тратить дальнейший бюджет discovery
на установление точного типа (`ADR-181 §2`, вариант 2а) — **это решение останавливает
РАССЛЕДОВАНИЕ механизма, оно не исключает сумму из объекта паритета.** Компонент `O` входит в
разложение как ИМЕНОВАННЫЙ (не безымянный) остаток: сумма точна (`1 481,13` KGS), природа —
«тип документа вне периметра загрузчика (класс `K4`), конкретный тип не идентифицирован по решению
о бюджете, а не потому что мост его прячет». Это тот же приём, каким `ADR-157 §1` определил `O`
для продаж («сумма строк ядра без соответствия в эталоне… независимо от триггера осиротения») —
точная атрибуция суммы к НАЗВАННОМУ КЛАССУ механизма достаточна для замыкания инварианта;
поштучная идентификация каждого документа этим критерием не требуется.

Свободным остатком (который переоткрыл бы пару) была бы сумма, не отнесённая НИ к `P`, НИ к `O`.
На июльском замере такой суммы нет (`ε=0,00`).

## 6. Вердикт

**Пара «Возвраты покупателей» остаётся СОШЕДШЕЙСЯ** — существующий статус (`ADR-114 §2`) не
переоткрывается; счётчик реестра паритета не двигается (`7/7` не пересматривается, знаменатель
остался тем же ещё с `ADR-085 §3`). Рост наблюдаемого `Δ` с `0,00` (май) до `269 995,53` (июль) не
есть регресс — прецедент формы `ADR-157 §2`: «сошлась» означает «объяснена», а не «разность мала».

Разрез возвратов по контрагенту остаётся вне финишной черты (`ADR-114 §3`, не пересматривается
настоящим решением); правило-мост выше относится к ИТОГУ за период — текущей поверхности пары.

**Остаток (i) строки `PARITY-CLIENT-JULY-RECHECK` (правило-мост возвратов) закрыт настоящим
решением.** Остаток (ii) той же строки (настройки графика Топ-20, интерфейс Looker Studio) этим
решением не затрагивается — на владельце.
