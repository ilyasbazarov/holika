## 2. Код `cf-dim`: таблица только читается, не пишется

`main.py` (`preflight_checks`, строки 50-55) и `helpers.py` (`load_uuids`, строки 121-129)
обращаются к `dim_metadata_mappings` единственным способом — `SELECT field_name, current_uuid
FROM core.dim_metadata_mappings` (`helpers.py:124`), результат используется как справочник UUID
для фильтрации ответов МойСклада внутри `dim_products`/`dim_counterparties`/`dim_employees`.

Ни один из трёх модулей записи (`dim_products.py`, `dim_counterparties.py`, `dim_employees.py`)
не упоминает `dim_metadata_mappings` (`grep -rn "metadata_mappings"` по всему каталогу снапшота
даёт ровно 4 совпадения — все в `main.py`/`helpers.py`, все на чтение; см. таблицу выше). В самой
`cf-dim` **нет модуля записи** для этой таблицы — набор файлов ограничен `dim_products.py`,
`dim_counterparties.py`, `dim_employees.py`, `helpers.py`, `config.py`, `main.py`.

**Вывод:** заявление топологии (`01_ARCHITECTURE.md:64`) — «`cf-dim` грузит… `dim_metadata_mappings`»
— смешивает «читает как вход» с «пишет как выход». По коду задеплоенной функции `cf-dim`
`dim_metadata_mappings` **не пишет никогда** — ни ежечасно, ни при любом другом триггере. Это не
регрессия и не потеря загрузчика — структурно `cf-dim` не заявляет себя писателем этой таблицы.

## 3. Документированный писатель — человек, по `RUNBOOK_v8.md §9`

`RUNBOOK_v8.md §9` называет процедуру прямо: `dim_metadata_mappings` хранит соответствие
`имя_поля → UUID` кастомных полей МойСклад. UUID меняются только когда владелец аккаунта
МойСклад пересоздаёт кастомное поле (редкое административное действие на стороне ERP, не
операционное событие пайплайна). Процедура §9: проверить актуальные UUID запросом к таблице,
**вручную выполнить `UPDATE`** при расхождении, затем вручную перезапустить CF-Dim. Автоматического
триггера на эту процедуру раннер не документирует.

Это отвечает на исходный вопрос реестра прямо: писателя, который «должен» писать таблицу и не
пишет (сломанный/потерянный загрузчик), **не существует** — заявленный в топологии писатель
(`cf-dim`) по коду её не пишет никогда, а единственный документированный писатель — ручная
операция человека по редкому триггеру (смена UUID кастомного поля в МойСкладе), не
периодический процесс.

## 4. Содержимое таблицы актуально — сверка по трём UUID из `RUNBOOK_v8.md §9`

`RUNBOOK_v8.md §9` называет «актуальные UUID» для трёх полей на дату последнего обновления рантайм-дока. Live-сверка (эта сессия):

| Поле | UUID по `RUNBOOK_v8.md §9` | UUID в живой таблице (`field_name`) | Совпадение |
|---|---|---|---|
| Срок годности (товар) | `c8ae21e9-64a1-11ef-0a80-0bba00013abb` | `shelf_life` = `c8ae21e9-64a1-11ef-0a80-0bba00013abb` | **да** |
| Страна (контрагент) | `6d6cca1e-ed85-11f0-0a80-0b1a00a4547c` | `country` = `6d6cca1e-ed85-11f0-0a80-0b1a00a4547c` | **да** |
| Статус «В пути» (заказ поставщику) | `491d6da5-8b37-11ef-0a80-0762000253a8` | `status_in_transit` = `491d6da5-8b37-11ef-0a80-0762000253a8` | **да** |

Все три сходятся дословно. Дополнительно: `preflight_checks` (`main.py:50-55`) требует именно эти
три ключа (`{"shelf_life", "country", "status_in_transit"}`) как обязательные для старта `cf-dim`
— и `cf-dim` по независимому замеру (`core_freshness_sweep_2026-08-02.md`) отрабатывает без
пропусков ежечасно все 94 суток заморозки `dim_metadata_mappings`. Если бы содержимое таблицы
устарело относительно реальных UUID МойСклада, `preflight_checks` не сломался бы формально (ключи
на месте), но `dim_products`/`dim_counterparties` начали бы фильтровать по несуществующим/сменившимся
UUID — то есть скрытая деградация без падения функции. Три сверенных ключа не показывают такой
деградации на дату этой сессии. Остальные 16 строк (`avito`, `instagram`, `telegram_id`,
`is_exclusive` и т.д.) кодом `cf-dim` не потребляются (не входят в `required`, `main.py:52`) —
живых потребителей этих 16 полей эта сессия не искала (вне мандата: `preflight_checks` — единственное
место кода, читающее эту таблицу, во всех трёх задействованных CF).

## 5. Вердикт

**Заморозка `dim_metadata_mappings` — ожидаемое поведение справочника с редким ручным триггером
обновления, не потеря/повреждение загрузчика.** Три независимых факта сходятся:

1. Код `cf-dim` структурно не пишет эту таблицу ни при каком триггере (только читает) — §2.
2. Единственная документированная процедура записи — ручная, по `RUNBOOK_v8.md §9`, привязана к
   редкому административному событию (смена UUID кастомного поля в МойСкладе), не к расписанию.
3. Содержимое таблицы на дату этой сессии дословно совпадает с «актуальными UUID» из того же
   рантайм-дока по всем трём проверяемым ключам — то есть 94 суток без изменений отражают
   94 суток без смены UUID в МойСкладе, а не молчаливое устаревание данных.

**Расхождение, оставленное незакрытым (не в мандате этой сессии):** `01_ARCHITECTURE.md:64` относит
`dim_metadata_mappings` к строке «загрузка cf-dim» рядом с тремя таблицами, которые `cf-dim`
действительно пишет ежечасно — формулировка стирает разницу между «читает как вход» и «пишет как
выход» и была прямой причиной того, что справочник попал в список заморозок `CORE-FRESHNESS-SWEEP`
как подозрительный. Правка топологии — документная правка `01_ARCHITECTURE.md` (STABLE, только через
ADR, `CLAUDE.md §Дисциплина документации`) — не решается и не исполняется этой сессией, только
называется как находка.
