## 1. Вход и метод

Ни один снапшот кода в `reference/code/` не содержит парсинга `entity/invoiceout`
(`grep -rln invoiceout reference/code/` → 0 совпадений) — ожидаемо, загрузчика счетов как
элемента конвейера никогда не существовало (`ADR-110 §0`). Форма ответа API восстановлена
**живым read-only `GET`** (шаги 2-3 брифа, класс A по `ADR-091 §1`):

- Секрет `msklad-token` резолвлен inline через `gcloud secrets versions access` (`11_INFRA_FACTS §секреты`).
- Запрос 1: `GET https://api.moysklad.ru/api/remap/1.2/entity/invoiceout?limit=1` → `HTTP 200`, тело
  несёт 28 top-level полей (полный список — `step1_run.log`).
- Запрос 2: `GET .../entity/invoiceout?limit=5&expand=state,agent,salesChannel` → `HTTP 200`, для
  проверки формы `state`/`agent`/`salesChannel` с раскрытым `.name` и разброса значений `rate` на
  5 документах.
- `grep -rF "$TOKEN" reference/_scratch_INVOICES-FIELD-MAP_2026-08-02/` перед коммитом → 0 совпадений
  (токен не закоммичен).
- Оба сырых тела ответов лежат в `reference/_scratch_INVOICES-FIELD-MAP_2026-08-02/` (`invoiceout_sample.json`, `invoiceout_expand.json`).

**Стилевой образец** `load_payments_cloudshell_2026-06-18.py` (тот же автор/период) использован
ТОЛЬКО как образец формы парсинга href (`parse_href`) и структуры записи — не как источник правила
валюты (см. §4, находка о его конвертере).

## 3. Правило суток документа (`ADR-088 §3`, функция UTC)

Источник (`entity/invoiceout`) отдаёт `moment`/`paymentPlannedMoment` в UTC — тот же общий факт API,
установленный `ADR-088 §1` (интерфейс МойСклад рендерит в зоне аккаунта, Москва UTC+3; ответ API —
UTC) и подтверждённый для документов продаж/возвратов (`ADR-088 §3/§4`). Для `entity/invoiceout`
независимо этот факт не переизмерялся (в отличие от `entity/salesreturn`, где сверка с интерфейсом
проведена, `ADR-088 §Контекст`) — переносится по общности API, не по отдельному замеру.

**Целевое правило для `core.fact_customer_invoices.moment`** — то же, что уже работает верно на
продажах (`bq_ops.py:158`, `02_ERP_CONTRACTS.md:41`), **не** дефектный паттерн `moment[:10]`
(`cf-finance/main.py:57`, `load_payments.py` — тот же паттерн среза первых 10 символов без учёта
зоны, применяемый к `paymentout`/`cashout`, где сутки не были предметом ADR-088, но правило то же:
это защита от повторения ИЗВЕСТНОГО дефекта, а не гипотеза):

```
moment_bishkek_date = DATE(PARSE_TIMESTAMP('%Y-%m-%d %H:%M:%E3S', moment), 'Asia/Bishkek')
```

Эквивалент формулировки `ADR-101 §6`: бишкекские сутки = `DATE(M+6ч)`.

**`payment_planned` — пониженная уверенность.** Формат таймстампа идентичен `moment`, но зонная
природа ИМЕННО этого поля (плановая дата платежа, не факт документа) независимо не проверялась ни
на одном из уже адъюдицированных полей `ADR-088`. Рекомендация — применить то же правило по аналогии
(общий факт «API отдаёт UTC» не привязан к конкретному полю), но это **не** покрыто отдельным
замером. Называется здесь явно, не примиряется молча (`05_CONVENTIONS.md` `★ Успех инструмента ≠
факт`, тот же принцип: аналогия не факт).

## 4. Правило пересчёта валюты для `sum_kgs` / `payed_sum_kgs` / `unpaid_sum_kgs`

### 4.1 Наблюдённая форма поля `rate` на живой выборке (5 документов, `invoiceout_expand.json`)

| # | `sum` (минорные ед.) | `rate.value` | валюта (`rate.currency.meta.href`, id) |
|---|---|---|---|
| 0 | 21 525,0 | 90.0 | `3ea7aa1b-…` |
| 1 | 82 305,0 | 90.0 | `3ea7aa1b-…` |
| 2 | 1 310 820,0 | `null` | `1fb4954e-…` |
| 3 | 7 852 494,0 | 1.18 | `9ac2585d-…` |
| 4 | 8 950 400,0 | `null` | `1fb4954e-…` |

Документы с валютой `1fb4954e-…` несут `rate.value = null` — это базовая валюта аккаунта (KGS):
контроль по величине — `1 310 820 ÷ 100 = 13 108,20`, порядок величины типичного опта совпадает без
домножения, то есть `rate=null` здесь означает «курс не нужен, валюта уже KGS», а не «данные не
пришли». Документы с валютами `3ea7aa1b-…` (курс ≈90, совпадает с известным курсом USD,
`02_ERP_CONTRACTS.md:417`) и `9ac2585d-…` (курс 1.18 — та же валюта, что фигурирует в майском
разборе продаж, `07_STATE` §Адъюдикация H1/H4) несут `rate.value` явно.

### 4.2 Применимость `ADR-010` — подтверждена, без модификации

Общий inbound-канон (`ADR-010`, скоуп явно включает `sum`/`payedSum` в `invoiceout`):

```
sum_kgs = (minor_units ÷ 100) × rate.value документа, если задан; иначе — текущий курс валюты
```

Наблюдение §4.1 канону не противоречит: `rate=null` встречается только у документов в базовой
валюте (KGS), для которых курс конвертации тождественно равен `1.0` — форма fallback ADR-010 «иначе
текущий курс валюты» и означает для KGS ровно единицу. Случай «валюта не KGS, а `rate.value`
отсутствует» (тот, что требует живого запроса текущего курса валюты через `entity/currency`, как
`cf-loss-commission/main.py:55-94`, `_fetch_current_rate`/`ADR-029`) в выборке из 5 документов
**не встретился** — это не опровергает его существования (прецедент `Q-97`: единственный такой
документ на паре «Продажи» найден не на случайной выборке, а целевым замером). Загрузчик
(`INVOICES-LOADER-DESIGN`, T2) обязан реализовать fallback-ветку, а не полагаться на отсутствие
случая в этой выборке.

**`payed_sum_kgs` конвертируется ТЕМ ЖЕ курсом документа**, что и `sum_kgs` — оба поля принадлежат
одному документу с одним `rate.value`, отдельного курса для оплаченной суммы в API нет.

**`unpaid_sum_kgs = sum_kgs − payed_sum_kgs`** — вычитание выполняется ПОСЛЕ конвертации обеих
величин в KGS (не `(sum − payedSum) ÷ 100 × rate` — арифметически тождественно при одном курсе на
документ, но порядок называется явно, чтобы не завести вычитание разноконвертированных величин при
будущей правке).

### 4.3 Находка о снапшоте-образце: не копировать конвертер `load_payments.py`

`load_payments_cloudshell_2026-06-18.py:38` считает `sum_kgs = (row.get("sum") or 0) / 100.0` —
**без `× rate.value`**. Это тот же класс дефекта, что `ADR-016` установил и `ADR-010 §Enforcement`
предписал исправить в `cf-finance` (дата фикса `2026-06-25`). Снапшот `reference/code/cf-finance/main.py`
в этом репозитории несёт **ту же дефектную форму** (строка 67: `sum_kgs = float((row.get("sum") or 0) / 100.0)`),
но это — устаревший снимок ревизии `cf-finance-00006-piv` (`reference/code/cf-finance/MANIFEST.md`,
`updateTime: 2026-06-25T09:14:37Z`, дата ДО подтверждённого факта исправления). Актуальная
задеплоенная ревизия `cf-finance-00012-cik` **несёт `× rate.value`** — это установлено независимо
`DEPLOY-REVISION-PROBE` (`06_DECISIONS_LOG.md:1946`: «задеплоенная ревизия `cf-finance-00012-cik`,
держащая 100% трафика, несёт `× rate.value`, строка конвертера напечатана целиком»), но текст этой
строки в текущем снапшоте `reference/code/` НЕ обновлён.

**Следствие для `INVOICES-LOADER-DESIGN` (T2):** ни `load_payments.py`, ни снапшот
`reference/code/cf-finance/main.py` НЕ являются образцом конвертера валюты — оба несут
устаревшую/дефектную форму. Образец конвертера — `ADR-010` напрямую (формула §4.2) либо живой
`cf-loss-commission/main.py:79-94` (`_rate_and_currency`, тот же канон с fallback на текущий курс).
Это расхождение снапшота с текущей ревизией не примиряется здесь молча — называется фактом, разбор
причины (почему `reference/code/cf-finance/` не обновлён после `CODE-REPO-STANDUP`) вне scope этой
задачи.
