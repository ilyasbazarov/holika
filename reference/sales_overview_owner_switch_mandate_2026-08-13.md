# Мандат класса B: атрибуция менеджера в `marts.sales_overview` переводится на владельца документа с границей `2026-05-01`

**Дата:** 2026-08-13 (Бишкек) · **Задача:** `SALES-OVERVIEW-OWNER-SWITCH` · **Класс:** B ·
**Мандат:** ВЫДАН поимённо (владелец, чат 2026-08-13: «вариант 3, оформляй мандат»).
**Оформил:** архитектор, без брифа (`ADR-086 §1`). **База:** `47e6511`.
**Провенанс замеров:** `reference/parity_client_july_recheck_2026-08-13.md`,

## §1 Что решено и почему форма именно такая

Витрина отвечает на вопрос «чей это клиент» (менеджер контрагента), отчёт МойСклада — на вопрос
«кто провёл документ». Замер закрыл механизм арифметически: по владельцу документа июль даёт
`74 745 820,28` против эталона клиента `74 745 820,29` (копейка округления).

Простая замена поля отклонена замером: `document_owner_employee_id` заполняется только внутри окна
обновления, а деплой загрузчика был `2026-08-08`. До `2026-05-01` заполнено `4 575 688,59` из
`352 853 922,06` KGS — то есть `98,7 %` ранней истории потеряло бы разрез по менеджерам.
Досев штатным путём невозможен: окно `90` суток, всё старше мая недостижимо.

**Принят вариант (3) — граница по дате.** До `2026-05-01` атрибуция сохраняется прежней
(менеджер контрагента), с `2026-05-01` берётся владелец документа, пустое значение получает
`'Не указан'` (прецедент `ADR-036`/`ADR-032`). Дата стыка не выдумана под задачу: `2026-05-01` —
уже проведённая финишная черта проекта (`ADR-069`), ранняя история официально объявлена вне
паритета.

## §3 Предписанная форма правки (четыре места, локализация подтверждена грепом)

Греп `\be\.|owner_employee_id|manager_` по `reference/sql/sq_marts_sales_overview.sql` даёт ровно
четыре вхождения: строки `53`, `54`, `55`, `118`. Других мест правка не касается.

**Было** (строки 53-55):

```sql
    c.owner_employee_id,
    e.full_name                                     AS manager_name,
    e.position                                      AS manager_position,
```

**Стало:**

```sql
    -- Атрибуция менеджера (SALES-OVERVIEW-OWNER-SWITCH, 2026-08-13):
    -- до 2026-05-01 — менеджер контрагента (историческая семантика, сохраняется байт-в-байт);
    -- с 2026-05-01 — владелец документа, совпадает с разрезом отчёта МойСклад.
    IF(f.transaction_date < DATE '2026-05-01',
       c.owner_employee_id,
       f.document_owner_employee_id)                AS owner_employee_id,
    IF(f.transaction_date < DATE '2026-05-01',
       e_agent.full_name,
       COALESCE(e_doc.full_name, 'Не указан'))      AS manager_name,
    IF(f.transaction_date < DATE '2026-05-01',
       e_agent.position,
       e_doc.position)                              AS manager_position,
```

**Было** (строка 118):

```sql
  LEFT JOIN `msklad-bi-prod.core.dim_employees` e
    ON c.owner_employee_id = e.employee_id
```

**Стало:**

```sql
  LEFT JOIN `msklad-bi-prod.core.dim_employees` e_agent
    ON c.owner_employee_id = e_agent.employee_id

  LEFT JOIN `msklad-bi-prod.core.dim_employees` e_doc
    ON f.document_owner_employee_id = e_doc.employee_id
```

**Запреты формы, проверяемые ревью:**
- `COALESCE(…, 'Не указан')` применяется ТОЛЬКО к ветке «с 2026-05-01». В исторической ветке
  `NULL` обязан остаться `NULL` — иначе апрельский разрез изменится и приёмка `§5(3)` провалится
  законно.
- Алиас `e` не сохраняется: два разных источника сотрудника обязаны иметь разные алиасы, иначе
  соединение молча возьмёт не тот.
- Ничего, кроме четырёх названных мест, не правится. Блок возвратов, `TODO` в шапке, `fx`-джойн
  и остальные колонки не трогаются.

## §5 Приёмка — четыре проверки, все обязательны

Исполняются ПОСЛЕ первой пересборки витрины (дождаться прогона либо запустить вручную).

1. **Июль сходится с эталоном МойСклад.** Разрез июля по `manager_name`: Турдалиева А. М. =
   `74 745 820,28` (эталон клиента `74 745 820,29`, расхождение `0,01` — округление, допустимо).
2. **Суммарная выручка не изменилась ни в одном периоде** (правка трогает только разрез):
   июль `112 324 457,48`, май `95 214 205,79`, апрель `85 085 235,83`, вся история
   `699 657 101,14`. Отклонение любого из четырёх чисел = отказ приёмки и откат.
3. **История до мая не изменилась.** Апрельский разрез по `manager_name` совпадает с базовым
   построчно: Турдалиева `57 406 025,62`; Турсунбекова `19 506 791,28`; Омурбекова `4 582 772,94`;
   `NULL` `2 851 639,89`; Бейшеналиева `652 772,70`; Бактияр кызы `43 689,93`; Казакбаев
   `41 543,47`. Появление корзины `'Не указан'` в апреле = отказ (значит `COALESCE` протёк в
   историческую ветку).
4. **Май соответствует ожидаемому разрезу:** Турдалиева `77 229 469,41`; Турсунбекова
   `11 931 866,13`; `'Не указан'` `5 301 450,08`; Бактияр кызы `751 420,18`.

## §6 Откат

Полный и односоставный: вернуть в `transferConfig` прежний текст запроса (снапшот
`reference/sql/sq_marts_sales_overview.sql` на коммите `47e6511`) и дождаться пересборки.
Данные не откатываются и не могут быть повреждены: витрина строится `CREATE OR REPLACE` из ядра,
ядро правкой не затрагивается. Снимок таблицы перед правкой НЕ требуется — это единственный
деплой очереди с таким свойством, и оно названо здесь явно, чтобы не переносилось на другие.

## §7 Принятые следствия (объявляются клиенту ДО правки, не после)

1. **Разрез по менеджерам меняет смысл на границе `2026-05-01`.** Одна колонка несёт две
   семантики. Это осознанный размен, а не недосмотр; он обязан быть подписан на странице
   Looker Studio — иначе получается ровно та маскировка, которую проект чинит в других местах.
   Подпись — действие владельца, инструменту недоступно (`LS-PERIOD-CONTRACT`, тот же класс).
2. **Май теряет `5 301 450,08` KGS в корзину `'Не указан'`** (`5,6 %` месяца), июнь —
   `6 394 683,37`, июль — `3 334 723,58`. Это розница и комиссия, где владелец документа не
   читается по построению и не появится никогда.
3. **Числа менеджеров за май-июль сдвинутся у всех, не только у Турдалиевой.** Пример по маю:
   Турдалиева `57 406 025,62` → `77 229 469,41` в апреле/мае-логике разрезов, Турсунбекова и
   Омурбекова также меняются. Клиент, помнящий прежние цифры, обязан быть предупреждён.
4. **Пара реестра паритета «Продажи» НЕ затрагивается** — суммарные величины не меняются,
   правка касается только разреза (`ADR-157` в силе, переоткрытия не требует).
5. Сотрудников-сирот нет: все `document_owner_employee_id` находятся в `dim_employees`
   (замер `step7`, `O2`: `0`).
