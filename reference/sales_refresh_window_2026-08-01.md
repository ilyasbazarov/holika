## 0. Открывающий блок — постановка дословно

### 0.1 Строка GAP-реестра `SALES-REFRESH-WINDOW` (`07_STATE.md`, дословно на момент чтения этой сессией)

> `SALES-REFRESH-WINDOW` | (`ADR-097 §5`, 2026-08-01) Окно обновления `cf-facts` (7/90 суток скользящим) не покрывает якорь паритета `2026-05-01`, режима досева у продаж нет | задача | **Класс A:** подготовка ОДНИМ патчем снапшота `reference/code/cf-facts/` по трём дефектам одной и той же операции `MERGE` (`ADR-100 §7`, объединение принято владельцем 2026-08-01): (1) окно — досев отдельным режимом с раздельными окнами выборки и `MERGE`; (2) отсутствие ветки удаления (`bq_ops.py:237-305`) — строки, исчезнувшие в источнике, остаются в `core` навсегда; (3) `transaction_date` не обновляется при матче (`bq_ops.py:240-256`) — документ, перенесённый по дате задним числом, остаётся на дате первой записи. **Класс B, НЕ выдан:** деплой `cf-facts`, дополнительно гейтится `ADR-065`. **Три ловушки, названные заранее, каждая обязана быть снята dry-run до деплоя, а не рассуждением:** (i) при досеве окно выборки и окно `MERGE` совпадают по построению, поэтому строка старше окна уйдёт в `INSERT` и задвоится (`ADR-097 §5`); (ii) ветка удаления опасна ровно тем же условием окна внутри `ON` (`bq_ops.py:238`): строка вне окна не матчится и под «не найдено в источнике» подпадает формально, поэтому ветка удаления без собственного явного ограничения по дате рискует снести историю за пределами окна; (iii) допустимость обновления `transaction_date` (колонка партиционирования) внутри `MERGE` этой адъюдикацией НЕ установлена и предположением не закрывается.

### 0.2 `ADR-097 §5` (полный текст решения, дословно)

> §5 **Отдельная структурная находка, не зависящая от причины `Q-98`.** У `cf-facts` есть только
> скользящие окна 7 и 90 суток (`config.py`, `HOURLY_WINDOW_DAYS`/`WEEKLY_WINDOW_DAYS`) и нет режима
> досева для продаж; `MERGE` дополнительно ограничивает целевую таблицу тем же окном
> (`T.transaction_date >= DATE_SUB(CURRENT_DATE(), INTERVAL window_days DAY)`, `bq_ops.py`). Якорь
> паритета `2026-05-01` (`ADR-069 §2`) перестал попадать в самое широкое окно `2026-07-30`; весь май
> выходит из него к `2026-08-29`. Пока досева нет, паритет мая не может быть «поддерживаемым
> состоянием» (`ADR-067 §5c`) — только датированным снимком. Ловушка досева называется здесь, чтобы
> не быть открытой заново: окно выборки и окно `MERGE` совпадают по построению, поэтому строка
> старше окна, поданная в staging, не найдёт пары по `ON` и уйдёт в `WHEN NOT MATCHED THEN INSERT`,
> то есть задвоится. Досев повторным вызовом `mode=promote` с прежними параметрами запрещён.
> Заводится задачей `SALES-REFRESH-WINDOW`. accepted.

### 0.3 Расширение объёма — `ADR-100 §7` (полный текст, дословно) и явное подтверждение владельца

> §7 **Правка загрузчика идёт одним патчем с задачей об окне обновления.** Три дефекта (окно без
> досева, отсутствие удаления, замороженная дата) живут в одной и той же операции `MERGE`;
> разнесение их по разным правкам дороже и рискованнее. Объединение принято владельцем (чат
> 2026-08-01). Три ловушки названы заранее и обязаны сниматься dry-run, а не рассуждением: задвоение
> при досеве (`ADR-097 §5`); ветка удаления, которая из-за условия окна внутри `ON` (`bq_ops.py:238`)
> формально считает «исчезнувшей» любую строку за пределами окна; неустановленная допустимость
> обновления колонки партиционирования внутри `MERGE`. accepted (владелец).

## 1. Вариант 1 — досев отдельным режимом (`topoff`) с раздельными окнами выборки и `MERGE`

### 1.1 Идея

Новый `mode="topoff"`, принимающий явные `date_from`/`date_to` (не rolling `window_days`). Текущая
пара `_build_merge_sql`/`promote_to_core` несёт ОДНО число `window_days`, которое одновременно
задаёт (а) окно выборки из API — нет, на самом деле окно выборки сейчас управляется отдельно в
`_run_load`/`_run_weekly_load` (`date_to - timedelta(days=window_days)`) — и (б) окно `ON`-фильтра
`MERGE`. Ловушка `ADR-097 §5` в том, что при досеве старого диапазона (например, мая) через
существующий `mode=promote` подставляется `window_days=7` или `90`, окно `ON` не покрывает май,
`MERGE` не находит существующую майскую строку по `ON`, и она задваивается через
`WHEN NOT MATCHED THEN INSERT`.

**Снятие ловушки:** заменить `window_days: int` на явные границы диапазона `merge_date_from`/
`merge_date_to`, которые ВСЕГДА равны границам выборки (`select_date_from`/`select_date_to`) для
режима `topoff` — не «шире по построению», а РАВНЫ, что и есть минимальное достаточное покрытие:
любая существующая в `core` строка с `transaction_date` внутри диапазона выборки гарантированно
входит в `ON`-фильтр и находит пару, вместо того чтобы задвоиться.

```python
def promote_to_core(
    bq: bigquery.Client,
    cogs_source: str,
    merge_date_from: date,
    merge_date_to: date,
    include_delete_branch: bool = True,
) -> dict:
    """
    cogs_source больше не выводится внутри функции из window_days — вызывающая
    сторона обязана назвать его явно (см. §COGS ниже, открытый вопрос для
    диапазона шире 7/90 суток).
    """
    count_row = next(
        bq.query(f"SELECT COUNT(*) AS cnt FROM `{STG_FACT_SALES}`").result()
    )
    staging_count = count_row.cnt
    if staging_count == 0:
        raise ValueError("promote_to_core: staging table is empty — refuse to MERGE")

    merge_sql = _build_merge_sql(cogs_source, merge_date_from, merge_date_to, include_delete_branch)
    job = bq.query(merge_sql)
    job.result()

    return {
        "staging_rows":  staging_count,
        "merge_date_from": merge_date_from.isoformat(),
        "merge_date_to":   merge_date_to.isoformat(),
        "cogs_source":   cogs_source,
        "affected_rows": job.num_dml_affected_rows,
    }
```

```python
def _run_topoff(run_id: str, select_date_from: date, select_date_to: date, cogs_source_name: str) -> dict:
    """
    Досев произвольного исторического диапазона. НЕ является rolling-режимом:
    date_from/date_to — обязательные явные параметры запроса, defaults запрещены
    (anti-improvisation — угадывать диапазон запрещено).

    merge_date_from/merge_date_to РАВНЫ select_date_from/select_date_to — это и есть
    снятие ловушки ADR-097 §5 (окно MERGE гарантированно покрывает окно выборки,
    ни шире, ни у́же).
    """
    token, bq, gcs, session = get_token(), bigquery.Client(project=GCP_PROJECT), storage.Client(project=GCP_PROJECT), requests.Session()
    ensure_staging_tables(bq)

    records = fetch_demand_positions(token, select_date_from, select_date_to, run_id, session=session)
    if not records:
        raise ValueError(f"topoff: 0 demand positions for {select_date_from}→{select_date_to}")

    blob_path = f"{GCS_PREFIX_DEMAND}/topoff_run_{run_id}.ndjson.gz"
    upload_ndjson_gz(gcs, GCS_RAW, blob_path, records)
    load_staging(bq, records)

    cogs_source_table = {"STG_BYVARIANT": STG_BYVARIANT, "CORE_BYVARIANT_BCK": CORE_BYVARIANT_BCK}[cogs_source_name]
    merge_stats = promote_to_core(bq, cogs_source_table, select_date_from, select_date_to, include_delete_branch=True)

    return {
        "select_date_from": str(select_date_from),
        "select_date_to":   str(select_date_to),
        "demand_positions_fetched": len(records),
        "merge_stats": merge_stats,
    }
```

`_run_promote` (существующий hourly/weekly путь) правится минимально — вычисляет
`merge_date_from = date.today() - timedelta(days=window_days)`, `merge_date_to = date.today()` и
передаёт их в `promote_to_core` вместе с прежней логикой выбора `cogs_source` — то есть для
существующих режимов поведение тождественно текущему (окно выборки и окно `MERGE` для hourly/weekly
и так всегда совпадали, это не новый риск).

### 1.3 Три ловушки — разбор на уровне этого варианта

- **(i) Задвоение при досеве (`ADR-097 §5`).** Снято: `merge_date_from`/`merge_date_to` в `topoff`
  равны `select_date_from`/`select_date_to` по конструкции сигнатуры — числа выборки и `MERGE`
  физически один и тот же параметр, а не два независимых, которые можно рассинхронизировать вызовом.
- **(ii) Ветка удаления шире выборки (`bq_ops.py:238`, `ADR-100 §7`).** Снято тем же равенством:
  `WHEN NOT MATCHED BY SOURCE` ограничена ровно `[merge_date_from; merge_date_to]` = ровно диапазону,
  который был запрошен у API. Строка `core` с датой ВНЕ этого диапазона не попадает под условие
  удаления вообще (SQL `AND T.transaction_date >= ... AND <= ...` перед `THEN DELETE`), то есть
  ветка удаления физически не видит ничего за пределами свежепромотированного диапазона.
- **(iii) Обновление `transaction_date` внутри `MERGE` (партиционирующая колонка) — ОТКРЫТО.**
  Строка `T.transaction_date = S.transaction_date` добавлена в `WHEN MATCHED THEN UPDATE SET`, но
  допустимость такой операции в BigQuery для DATE-партиционированной (не ingestion-time) таблицы ЭТОЙ
  сессией не проверена — сессия класса A не имеет доступа к `bq query` против прод-таблиц (вне scope).
  **Требование к сессии-исполнителю патча:** первой командой прогнать `EXPLAIN`/dry-run именно этого
  `UPDATE SET T.transaction_date = ...` на непустой копии/тестовом диапазоне ДО применения к
  `core.fact_sales_profit`; если BigQuery это запрещает или недопустимо дорого (полное перекладывание
  партиции), назвать альтернативную форму — например, вместо `UPDATE` делать `DELETE` совпавшей по
  `transaction_id` строки плюс `INSERT` новой (расширение ветки удаления на этот случай), не обходя
  вопрос молча.

### 1.4 Открытый вопрос — источник COGS для произвольного диапазона

Текущая логика `promote_to_core` (`window_days >= 90 → STG_BYVARIANT`, иначе `CORE_BYVARIANT_BCK`)
рассчитана ровно на два случая — 7 суток (backup) и 90 суток (свежий staging). Для `topoff`
произвольного исторического диапазона (например, май, вне текущих 7/90-дневных окон) не установлено,
какой из двух источников COGS корректен, и есть ли третий вариант (например, отдельная историческая
выгрузка `byvariant` за нужный период). **Это открытый вопрос, не закрывается предположением.** В
патче параметр `cogs_source_name` сделан ОБЯЗАТЕЛЬНЫМ без default именно поэтому — исполнитель
следующей сессии обязан либо получить ответ явно, либо провести отдельную discovery по `fetch_byvariant.py`
(форма запроса COGS для произвольного диапазона дат) прежде чем задавать значение.

## 2. Вариант 2 — разовый пересев мая (`2026-05-01…2026-05-31`)

### 2.1 Идея

Не постоянный режим — один прогон, покрывающий ровно май, с использованием ТОЙ ЖЕ механики
раздельных окон варианта 1 (переиспользуется `_run_topoff`, не изобретается вторая MERGE-конструкция —
меньше поверхности для второго независимого бага).

### 2.3 Три ловушки — разбор на уровне этого варианта

- **(i) Задвоение.** Тем же механизмом §1.3(i): `merge_date_from = 2026-05-01`,
  `merge_date_to = 2026-05-31` — `ON`-фильтр `T.transaction_date >= '2026-05-01' AND
  T.transaction_date <= '2026-05-31'` покрывает ровно диапазон выборки, ни один майский документ не
  промахивается мимо `ON` и не задваивается через `INSERT`. Это ИМЕННО та форма, которую собственный
  текст задачи (`07_STATE.md`) требует явно: не `DATE_SUB(CURRENT_DATE(), INTERVAL window_days DAY)`.
- **(ii) Ветка удаления.** Тем же механизмом §1.3(ii), с диапазоном `[2026-05-01; 2026-05-31]`:
  удаление коснётся только майских строк без пары в свежей майской выборке — ничего за пределами мая
  не затронуто, что для одноразового пересева мая и есть корректная семантика («май из МойСклада
  сейчас» замещает «май, как он был записан ранее»).
- **(iii) `transaction_date`-UPDATE.** Тот же открытый вопрос §1.3(iii), тот же список действий при
  запрете — актуален и здесь: майский документ, перенесённый на другую майскую (или соседнюю) дату
  задним числом, попадает под ту же самую строку `T.transaction_date = S.transaction_date`.

### 2.4 Источник COGS для мая

Тот же открытый вопрос §1.4, без переоткрытия — единственное отличие от варианта 1 в том, что
диапазон здесь известен заранее и фиксирован (не произвольный), что может упростить discovery
(искать конкретно майский `byvariant`), но не снимает вопрос как таковой.

## 3. Вариант 3 — май объявляется датированным снимком (без правки кода)

### 3.1 Идея

Без единой строки правки `cf-facts` зафиксировать текстом, что данные мая в
`core.fact_sales_profit` — снимок на дату последней загрузки (наблюдение `Q-98`/`ADR-097`), а не
поддерживаемое состояние. Это единственный вариант, у которого класс исполнения — работа с текстом
доков, не с кодом.

### 3.2 Текст-кандидат плашки

**Кандидат размещения A — `02_ERP_CONTRACTS.md §core.fact_sales_profit`** (рядом со схемой таблицы,
после строки `revenue_kgs`):

```markdown
> **Датированный снимок для периодов вне скользящего окна (ADR-097 §5).** `cf-facts` промоутит
> `core.fact_sales_profit` только в скользящем окне `HOURLY_WINDOW_DAYS`/`WEEKLY_WINDOW_DAYS`
> (7/90 суток от даты прогона, `config.py`). Данные ЗА ПРЕДЕЛАМИ этого окна на момент чтения —
> НЕ поддерживаемое состояние: они остаются такими, какими были записаны в момент, когда диапазон
> ещё попадал в окно, и не обновляются последующими правками документов в МойСкладе (изменение
> суммы, переоформление, перенос даты и т.д. молча не долетают). Якорь паритета `2026-05-01`
> (`ADR-069 §2`) вышел из самого широкого окна к `2026-08-29` — все майские строки датированы этим
> ограничением. Снятие ограничения — задача `SALES-REFRESH-WINDOW`, статус на `2026-08-01`: три
> варианта патча подготовлены (`reference/sales_refresh_window_2026-08-01.md`), не выбраны, не
> задеплоены.
```

**Кандидат размещения B — `reference/parity_registry.md`** (как примечание к паре
«Продажи», без изменения самих строк 18–20 — правка формы моста вне scope этой сессии по
`ADR-100 §7` последствиям):

```markdown
> **Ограничение датированного снимка.** Число `core.fact_sales_profit` за май-2026, использованное
> в этой паре реестра, зафиксировано снимком на дату загрузки, а не живым состоянием источника —
> см. плашку `02_ERP_CONTRACTS.md §core.fact_sales_profit` и `ADR-097 §5`. Пересверка этой пары
> после досева мая (если он будет выбран, `SALES-REFRESH-WINDOW`) даст другое число по построению,
> это не регресс проверки.
```

### 3.3 Явное ограничение варианта

Этот вариант **НЕ требует деплоя** и **НЕ снимает находку `ADR-097 §5` по существу** — он
документирует ограничение, а не устраняет его. Он также **НЕ устраняет дефекты (2) и (3)**
(`ADR-100 §7`, сироты и замороженная дата), потому что не трогает `MERGE` вообще — сироты остаются в
`core` навсегда, а перенесённые документы остаются на дате первой записи, независимо от того, стоит
плашка или нет. Если выбран этот вариант, дефекты (2)/(3) требуют отдельного решения владельца/архитектора
(patch-текст для них уже готов в §1.2 и может быть применён отдельно от досева).
