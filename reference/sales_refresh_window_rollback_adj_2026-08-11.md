## §1 Подтверждение находки исполнителя (меньший дефект)

Верно по коду. `main.py:96` — `mode == "weekly"` вызывает `_run_weekly_load(run_id)` БЕЗ
`window_days`; внутри (`main.py:166-208`) окно жёстко `date.today() - WEEKLY_WINDOW_DAYS` (`90`).
`mode == "hourly"` — то же (`window_days=HOURLY_WINDOW_DAYS`, тело запроса игнорируется).
Параметром управляются только `promote`, `perimeter_promote`, `returns` и `perimeter`
(последний — и на выборке: `_run_perimeter_load(run_id, window_days)`).

Следствие: шаг 5 мандата (`ADR-159 §4`) — «загрузка staging и `MERGE` одним прогоном с одним
`window_days`» — для ветки продаж неисполним без нового кода. Остановка исполнителя правильна.

## §2 Второй дефект: ветка удаления не ограничена происхождением строки

Обе ветки (`bq_ops.py`, продажи `:379`, периметр `:647`) написаны так:

```
WHEN NOT MATCHED BY SOURCE
  AND T.transaction_date >= DATE_SUB(CURRENT_DATE(), INTERVAL {window_days} DAY)
THEN DELETE
```

В `core.fact_sales_profit` пишут ДВА независимых загрузчика: обычные продажи (`entity/demand`,
исключая комиссионных агентов) и периметр (`entity/retaildemand` + `entity/commissionreportin`),
у каждого своя staging. Ветка удаления корректна только если источник содержит ВСЕ строки окна;
здесь каждый источник содержит свою половину. Значит для слияния периметра все оптовые строки
формально «исчезли из источника», и наоборот.

**Признака происхождения в таблице нет:** `entity_type` у всех строк — `product` (это тип позиции,
не тип документа). Различает происхождение только `sales_channel_name`.

**Объём под удалением, окно 90 суток (замер `scope_check.sh`, 2026-08-11):**

| Канал | Кто снёс бы | Строк | Сумма, KGS |
|---|---|---|---|
| Оптовая торговля | `perimeter_promote` | `6 922` | **`269 440 872,10`** |
| Комиссия | `promote` | `4 024` | `11 509 770,29` |
| Розница | `promote` | `1 441` | `1 188 422,00` |

**Срок срабатывания.** Недельный конвейер (`workflow_weekly.yaml:216,243`) вызывает
`promote window_days=90`, затем `perimeter_promote window_days=90` — воскресенье
`2026-08-16 01:00 UTC`. Часовой (`workflow_hourly.yaml:140`) вызывает `promote window_days=7`
ежечасно; сегодня он безвреден только потому, что строки периметра в семисуточное окно не
попадают (их максимум — `2026-08-03`), после воскресной загрузки периметра начнёт удалять их
ежечасно.

## §4 Почему это не поймали три проверки подряд

Названо прямо, чтобы не повторилось. (i) `--dry_run` проверяет синтаксис и типы, а не полноту
источника — семантику «источник обязан содержать все строки окна» он не выражает вовсе.
(ii) Проверка архитектора (`sales_refresh_window_mandate_adj_2026-08-11.md §1`) шла по списку
«окно, предохранитель, места вызова, импорты» — список не содержал вопроса «полон ли источник для
ветки удаления». (iii) Предохранитель `ADR-145 §4` меряет ПОКРЫТИЕ staging по датам и по построению
слеп к тому, ЧЬИ строки в ней лежат. Форма «ветка удаления в обоих `MERGE`» принята `ADR-144 §7/§8`
и с тех пор не пересматривалась.

## §6 Форма настоящего фикса — три варианта, решение владельца ПОСЛЕ отката

**Вариант 1 — ограничить каждую ветку удаления своим каналом.** Периметр удаляет только строки с
каналом «Розница»/«Комиссия»; продажи удаляют всё остальное, включая строки без канала (они —
демандовые, `SALES-CHANNEL-NULL-DEMAND`). Две строки на каждую ветку. Проверяется тем же приёмом,
что сработал с предохранителем: read-only подсчёт того, что попало бы под каждый предикат, ДО
деплоя. Опора на смысловое поле — но метки периметра пишутся константой по типу документа
(`ADR-134`), то есть разделение устойчиво по построению, а не по данным.
Плюс: дёшево, одна сессия подготовки и один деплой. Минус: `sales_channel_name` меняем при
промоуте (`WHEN MATCHED THEN UPDATE SET`), значит предикат обязан читать канал ЦЕЛИ, а не источника.

**Вариант 2 — явная колонка происхождения.** Каждый загрузчик пишет свой маркер; ветки режут по
нему. Надёжнее и не зависит от смысла канала. Цена: новая колонка, правка обоих загрузчиков, досев
истории, отдельный деплой — многосессионная работа против одной.

**Вариант 3 — отказаться от ветки удаления.** Июльское завышение `127 621,20` KGS в месяц и майский
перевес `3 610 239,81` KGS уходят в известные ограничения пакета передачи с числами и причиной.
Цена: клиент получает витрину, которая помесячно расходится с МойСкладом на величину сирот.

**Рекомендация архитектора — вариант 1**, с обязательной read-only проверкой обоих предикатов до
деплоя и с тем же снимком таблицы перед прогоном. Вариант 2 правильнее по инженерии, но он есть
ровно тот хвост, который закрытие проекта запрещает наращивать (`scope_close_freeze_2026-08-10.md`);
вариант 3 оставляет клиенту известный дефект денежных величин.

**Строки списка закрытия это не добавляет:** пересмотр формы идёт внутри строки `1`, счётчик
остаётся `8` из `9`.

- Откат не исполнялся: класс B, исполняет деплойная сессия по тексту `§5` после решения владельца.

  по-прежнему нужно, значит правка `_run_weekly_load` войдёт в тот же патч.
