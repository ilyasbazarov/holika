### 4.2 Схема

### 4.3 Дифф USD по месяцам (staging минус прод)

Полная таблица — `run_step4.log`. Наблюдения:
- Май-2026: `staging=117 053,73` / `прод=117 014,30`, дельта `+39,43`. Число строк одинаково (149=149). Объяснение — см. §«Отношение курсов» ниже.
- Месяцы `2025-06…2026-04`, `2026-06` несут малые дельты (`0,02…16,19`) при **равном** числе строк staging/прод в каждом месяце — согласуются с месяцами, где `core.dim_fx_rates` несёт больше одного значения курса (проверено отдельно, `run_step4c.log`: список месяцев с `distinct_rates > 1` совпадает с месяцами с ненулевой дельтой). `2026-02` и `2026-05` — единственное значение курса за месяц, дельта `0,00`.
- **Июль-2026 — особый случай, требует пояснения (НЕ дефект политики):** `staging=128 строк / 222 356,22 USD`, `прод=119 строк / 213 284,74 USD`. Расхождение чисел строк вызвано тем, что прод пересобирается раз в сутки в `11:10 UTC` (одноканально, `ADR-073 §5`) — последняя сборка прода состоялась **вчера**, `2026-07-27 11:10 UTC`; сегодняшний прогон (`2026-07-28 11:10 UTC`) ещё не состоялся на момент этой сессии (~09:05 UTC). За прошедшие ~22 часа в `core.fact_payments`/`fact_loss`/`fact_commissionreportin` приехали новые июльские документы, которые staging (считает по живым данным) уже видит, а прод — ещё нет. Это разница дат сборки, не разница политики конвертации; после планового прогона прода расхождение по числу строк должно исчезнуть.

**Ни одна строка не появилась и не исчезла из-за смены политики курса** — единственное расхождение состава строк (июль) объясняется свежестью источника, не запросом.

### 4.4 Воспроизводимость

Два прогона `marts.expenses_staging` с интервалом (~1 минуту, между ними — отдельный read-only запрос по количеству значений курса за месяц, `step4c_multi_rate_months.sh`), логи `run_step3.log` (прогон 1) / `run_step3_second.log` + `run_step4d.log` (прогон 2). Для ВСЕХ месяцев, включая те, где курс за месяц принимает больше одного значения (`2025-06…2026-04`, `2026-06`, `2026-07`), `total_sum_usd` между прогонами **идентичен до копейки**. Пример: май-2026 `117 053,73` = `117 053,73`; июль-2026 `222 356,22` = `222 356,22` (число строк тоже не изменилось: `128 = 128`, интервал был слишком короток для нового прогона загрузчиков).

**Содержательная приёмка задачи подтверждена.**

## Отношение курсов и величина сдвига майского USD

- Курс, применённый последней сборкой прода к маю (курс на дату сборки, `2026-07-27`): `87.45`.
- Курс, применяемый новой политикой к маю (курс на дату операции, единственное значение за весь май): `87.4205` (подтверждено делением `SUM(total_sum_kgs)/SUM(total_sum_usd)` по staging = `87.420565`, совпадает с точностью округления `ROUND(...,2)` построчно).
- **Отношение: `87.45 / 87.4205 = 1,000337`.**
- **Сдвиг майского `total_sum_usd`: `+39,43 USD`** (`117 053,73 − 117 014,30`), однократный, ожидаемое следствие политики (`ADR-057 §4`, решение владельца §1 в шапке брифа). Разрыв в KGS остаётся `0,00`.

## Побочный факт (Q-77, зафиксирован одной строкой, вне scope)

`core.fact_loss.moment` и `core.fact_commissionreportin.moment` — TIMESTAMP, приводятся к DATE по UTC при локальной зоне Бишкека UTC+6; теперь от этого приведения зависит и выбранный курс дня для этих источников, не только месяц отнесения (`Q-77`, не гейтит эту задачу).
