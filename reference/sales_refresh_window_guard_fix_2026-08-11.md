# SALES-REFRESH-WINDOW — три правки предохранителя по адъюдикации (2026-08-11)

`reference/sales_refresh_window_mandate_adj_2026-08-11.md §3` (архитектор, ветка

## §1 — правка 1: допуск константой

`GUARD_TOLERANCE_DAYS = 3` вынесен в `config.py` с обоснованием из замера архитектора (§C
адъюдикации: 180 суток, `6,63%` пустых дней, ни одного окна из трёх подряд пустых суток за всю
историю). Условие отказа по нижнему краю — `min_date > window_start + GUARD_TOLERANCE_DAYS`, не
магическое число в теле функции.

## §2 — правка 2: обе даты из одних часов

Раньше нижняя граница окна считалась питоновским `date.today() - timedelta(window_days)` (часы
контейнера Cloud Function), а сам `MERGE` — `CURRENT_DATE()` (часы BigQuery). Теперь ОДИН запрос
BigQuery считает разом `MIN`/`MAX` staging и обе границы окна
(`DATE_SUB(CURRENT_DATE(), INTERVAL n DAY)` / `DATE_SUB(CURRENT_DATE(), INTERVAL 1 DAY)`) — питоновские
`date`/`timedelta` в самом предикате больше не участвуют (остались только для арифметики допуска
`window_start + GUARD_TOLERANCE_DAYS`, где `window_start` уже пришёл из BigQuery).

## §3 — правка 3: проверка верхнего края окна

Найдено адъюдикацией, отсутствовало в исходном тексте: ветка удаления сносит всё, что попало в
окно и отсутствует в staging — устаревший ВЕРХНИЙ край staging так же опасен, как короткий нижний.
Добавлено условие `max_date < CURRENT_DATE() - 1 DAY` → отказ, той же формой сообщения, без допуска
(штатный прогон всегда грузит staging до «сегодня», отставание на день и больше — прямой признак
устаревшего/пропущенного прогона, не статистический шум, допуск здесь не обоснован).

первый боевой прогон грузил staging и исполнял `MERGE` ОДНИМ вызовом — это естественно снимает
устаревание к моменту `promote`.
