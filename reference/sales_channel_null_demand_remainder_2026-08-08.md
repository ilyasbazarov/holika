## 2. Опознание документа — точное совпадение, не догадка

Для `2026-07-02` контрагент `178ba7b4-87c0-11ef-0a80-1568002f4222` дал РОВНО ОДИН документ за
сутки (`cd1f2cac-75d5-11f1-0a80-114600c229cb`), и его `sum` в живом ответе равен `6 193 800.0`
(копейки) = `61 938,00` KGS — **точное совпадение** с `revenue_kgs` строки из
`reference/sales_channel_null_demand_2026-08-07.md §1` (`2026-07-02`, тот же контрагент,
`61938.0`). Уникальность по паре контрагент+сутки и точное совпадение суммы исключают, что это
другой документ: это ТОТ ЖЕ документ, что дал `NULL`-строку при загрузке `2026-07-19 01:08:45`.

Для `2026-07-21` тот же контрагент (`13564a08-…`) дал ТРИ документа за сутки (список несёт больше
одного документа на контрагента в этот день) — прямого поимённого совпадения с одной из 38 строк
`NULL`-корзины по сумме не устанавливается (позиционных сумм у нас нет, только сумма документа
целиком); эти три документа используются как контрольная группа того же контрагента/суток, не как
точное отождествление.

## 3. Различитель `ADR-139 §3` — результат измерения

Для ВСЕХ 4 проверенных документов (1 за `2026-07-02` + 3 за `2026-07-21`) поле `salesChannel`
**присутствует и заполнено СЕЙЧАС** — и в списочном режиме (`rows[]` тех же `GET`, что в §1), и в
одиночном `GET entity/demand/{id}`:

| id | сутки | `salesChannel` в списке | `salesChannel` в одиночном GET | id канала |
|---|---|---|---|---|
| `cd1f2cac-75d5-11f1-0a80-114600c229cb` | 2026-07-02 | есть | есть | `4a07eb32-2e47-11ef-0a80-0f4200606f40` |
| `135560a2-84c0-11f1-0a80-1c8f00262f2c` | 2026-07-21 | есть | есть | `4a07eb32-2e47-11ef-0a80-0f4200606f40` |
| `76a5aecf-84bf-11f1-0a80-1c8f0025ff8b` | 2026-07-21 | есть | есть | `4a07eb32-2e47-11ef-0a80-0f4200606f40` |
| `e4693f61-84bf-11f1-0a80-1c8f0026199d` | 2026-07-21 | есть | (не запрошен, найден списком) | `4a07eb32-2e47-11ef-0a80-0f4200606f40` |

Ни один из 4 документов не даёт исход §3 «поле есть в одиночном и отсутствует в списочном»
(что подтвердило бы систематическую потерю поля list-режимом) и ни один не даёт исход «поле
отсутствует в обоих» (что оставило бы вопрос открытым владельцу). **Наблюдается третий, не
предусмотренный явной развилкой §3 исход: поле присутствует в ОБОИХ режимах СЕЙЧАС**, при том что
эти же документы (как минимум точно опознанный `cd1f2cac-…`) дали `NULL` по обоим полям
(`sales_channel_id` и `sales_channel_name`) при загрузке `2026-07-19`.

## Вердикт

**Гипотеза «list-режим МойСклада систематически не отдаёт `salesChannel`» ОПРОВЕРГНУТА измерением.**
Если бы потеря была систематическим свойством list-режима, она проявлялась бы и сейчас — на тех же
документах, тем же кодом фильтрации по датам. Она не проявилась: список за `2026-07-02` и
`2026-07-21` несёт `salesChannel` на всех проверенных строках, включая точно опознанный документ.

**Подтверждается вторая ветвь `ADR-139 §2`: канал был назначен документу ПОСЛЕ первой загрузки.**
Для точно опознанного документа (`cd1f2cac-75d5-11f1-0a80-114600c229cb`, контрагент
`178ba7b4-87c0-11ef-0a80-1568002f4222`, сумма `61 938,00` KGS, единственный документ этого
контрагента за `2026-07-02`) `NULL` был получен загрузчиком `2026-07-19 01:08:45`; сегодня
(`2026-08-08`) канал у него заполнен и в списке, и в одиночном ответе. Между этими двумя моментами
канал не мог «потеряться в парсинге» (тот же код, тот же list-режим сейчас его отдаёт) — значит он
был проставлен документу владельцем/оператором МойСклад уже ПОСЛЕ того, как загрузчик его прочитал.

Найденный id канала (`4a07eb32-2e47-11ef-0a80-0f4200606f40`) на всех 4 документах один и тот же;
по независимой находке `reference/parity_sales_july_diff_2026-08-05.md §2` эти же 40 строк с
`821 523,00` KGS почти наверняка есть канал «ОФИС» (сходимость остатка `6 748,30` KGS по двум
независимым разложениям). Имя канала по `id` этим замером не подтверждалось отдельным вызовом —
`entity/saleschannel` не входил в разрешённый `ADR-139 §2` состав вызовов, а совпадение сумм и
факт «один и тот же id на всех 4 документах» достаточны для вердикта о МЕХАНИЗМЕ, не требуя имени.

**Форма фикса.** Задача читалась, не правит `reference/code/cf-facts/`. Раз канал назначается
ПОСЛЕ загрузки, а не теряется загрузчиком — правка кода парсинга не нужна; открытый вопрос
переносится в область операционного цикла (переприменение/дозагрузка документов, у которых канал
меняется постфактум), и его форма — отдельное решение владельца/архитектора, не этой сессии.
