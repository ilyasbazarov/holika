## §2 Отступление от буквы различителя — названо явно

Строка `Q-96` назначает различителем «выборка не-KGS документов мая из `core.fact_payments` против
того же множества из **живого API**». Живой `GET` требует секрета `msklad-token` и есть класс B
(`ADR-076 §1`), мандат на него не выдан — строка мандата `Q-96` прямо разводит: read-only часть по
`core` идёт классом A сейчас, живой `GET` требует поимённого мандата.

Взят эквивалентный внутренний различитель: сравнение с **записанными** эталонными значениями по двум
конкретным документам. Он не слабее агрегатного сравнения, а сильнее: расхождение локализовано до
двух сумм, и обе проверены поимённо. Чего он НЕ даёт — свежести эталона: числа слоя A сняты
2026-07-14, а МойСклад пересчитывает историю при правках задним числом (`ADR-067 §3`). Если по этим
двум документам с тех пор были правки в источнике, сегодняшнее совпадение проверяет соответствие
июльскому снимку эталона, а не сегодняшнему состоянию МойСклада. Закрывается только живым `GET`,
то есть классом B.

## §3 Когда именно история переписана

| Замер | Значение |
|---|---|
| Строк `paymentout` за май-2026 в `core.fact_payments` | 244 |
| Σ `sum_kgs` за май-2026 | 8 600 919,01 |
| `MIN(_loaded_at)` | `2026-07-31 21:00:25` |
| `MAX(_loaded_at)` | `2026-07-31 21:11:28` |
| Распределение по суткам загрузки | **все 244 строки — одни сутки, `2026-07-31`** |

То есть весь май переписан целиком одним прогоном 2026-07-31, то есть через 11 дней после деплоя
правки (2026-07-20). Ни одной строки со старым `_loaded_at` не осталось.

Согласуется (но отдельно этим прогоном НЕ проверялось) с документированным расписанием
`finance-daily-update`: `0 3 * * *` `Asia/Bishkek` = `21:00 UTC` предыдущих суток
(`11_INFRA_FACTS §CF`) — окно `21:00:25…21:11:28 UTC` попадает ровно в него. У соседнего джоба
`loss-commission-daily-update` там же задокументировано, что загрузчик берёт окно
`2020-01-01 → завтра`, то есть переписывает всю историю каждым прогоном. Если `finance-daily-update`
устроен так же, полный пересчёт истории происходит ежесуточно и произошёл в первый же прогон после
деплоя. **Тело вызова этого джоба настоящим замером не читалось** — сказанное есть согласующаяся
гипотеза механизма, не факт (`ADR-021 §2`).

## §4 Инвесторская поверхность сходится с эталоном точно

`marts.expenses`, `year_month = '2026-05'`: 149 строк, `SUM(total_sum_kgs)` = **10 232 903,20**.

Записанная целевая величина эталона мая — **10 232 903,20** (`ADR-057 §5`, `ADR-005`,
`/reference/pnl_2026-05.md`). Совпадение точное, до копейки.

## §5 Что НЕ сравнивалось и почему

Агрегат `core.fact_payments` за май (244 документа, 8 600 919,01) с числом слоя B эталона
(25 документов, 3 355 976,16) **не сопоставляется**: замер 2026-07-14 был сужен до статьи «Вывод
прибыли», а сегодняшний покрывает все `paymentout` мая. Разные множества; примирять их числа было бы
подгонкой (`_METHOD §4`). Сопоставимы только поимённые документы §1 и величина марта §4 — обе сошлись.

## §6 Следствие для `E1-T3-MECH-FX` (факт, не переквалификация)

Приёмка задачи записана как «staging dry-compare не-KGS май = 0,00 → прод re-diff `core` vs live API
= 0,00 без остатка». Фактически:

- деплой правки состоялся 2026-07-20 (`reference/deploy_revision_probe_2026-08-01.md`);
- история пересчитана 2026-07-31, оба ранее расходившихся документа сошлись с записанным эталоном;
- инвесторский март мая совпал с записанной целевой величиной точно.

То есть **содержательный результат задачи достигнут**, а формальная приёмка — нет: ни staging
dry-compare (`Q-41`, артефакта нет и уже не будет, стадия пройдена), ни свежий live re-diff не
исполнялись. Переквалификация задачи есть решение архитектора и настоящим замером не производится
(`_METHOD §11`: DISCOVER ≠ CAPTURE ≠ решение). Развилка для владельца: закрыть задачу по
записанному эталону либо потребовать свежий live re-diff, который есть класс B и требует поимённого
мандата.
