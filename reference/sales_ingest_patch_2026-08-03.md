## 1. Шаг 1 — различитель формы фикса отгрузки комиссионеру

**Вердикт: различитель есть среди уже загружаемых полей — `agent_id`. Форма — исключение по
списку контрагентов канала, не фильтр по типу договора/складу.**

Провенанс, не домысел:

- `fetch_demands.py` (снапшот ДО патча) загружает из `entity/demand` ровно эти поля на
  документ/позицию: `agent_id` (из `agent.meta.href`), `sales_channel_id`/`name`,
  `project_id`/`name`, `entity_type` (тип позиции ассортимента — product/variant/bundle),
  `product_id`, `quantity`, `price_kgs`, `discount`, `revenue_kgs`. Ни тип договора
  (`contract`), ни склад (`store`) кодом не читаются и в BQ не попадают —
  `grep -n "contract\|store" reference/code/cf-facts/fetch_demands.py` (снапшот до патча)
  даёт 0 совпадений.
- `agent_id` — уже загружаемое поле, и оно пригодно: `ADR-104 §2` измерил (класс A, один
  read-only запрос к `core.fact_commissionreportin`) три контрагента комиссионного канала
  (`0276f431-…`/`3c080755-…`/`31d135bc-…`), а `ADR-104 §5` измерил (тот же замер, другой
  предикат) — за ВСЮ зону паритета (`2026-05-01…2026-08-01`, 7 120 строк) на этих трёх
  контрагентов приходится ровно ОДИН документ `entity/demand`, и это ровно найденная отгрузка
  комиссионеру (`2026-05-12`, `1 980 000,00` KGS). То есть в измеренном окне фильтр по
  `agent_id` не задевает ни одной легитимной продажи этим же трём контрагентам — ложных
  срабатываний в измеренных данных нет.
- Никакого `CONTEXT GAP` здесь не заявляется: различитель найден, не отсутствует.

**Риск, названный явно (не домысливается как решённый).** Список
`config.py::COMMISSION_CHANNEL_AGENT_IDS` — измеренный факт на зону до `2026-08-01`, не
структурный признак контрагента (в МойСклад нет прочитанного нами поля «это комиссионер»).
Если канал получит нового контрагента, фильтр его не подхватит автоматически — потребуется
повторный замер по образцу `ADR-104 §2`. Это ограничение метода, а не скрытый факт.

## 2. Шаг 2 — патч периметра (текст)

Новый файл `reference/code/cf-facts/fetch_perimeter.py`:
`fetch_retaildemand_positions()` (entity/retaildemand) и
`fetch_commission_sales_positions()` (entity/commissionreportin, поле `sum` документа —
Σ`price × quantity` позиций, **не** `commitentSum`, правило `ADR-104 §4`). Это отдельный
ингест от того, что уже грузит `cf-loss-commission` (тот берёт `reward`/`commissionOverhead`
в `core.fact_commissionreportin`, `ADR-026`) — здесь считается сама продажа.

`config.py` получает `STG_FACT_SALES_PERIMETER`, `PERIMETER_WINDOW_DAYS`,
`COMMISSION_CHANNEL_AGENT_IDS`. `bq_ops.py` получает `PERIMETER_STAGING_SCHEMA`,
`ensure_perimeter_staging_table`, `load_perimeter_staging`, `_build_perimeter_merge_sql`,
`promote_perimeter_to_core` — **отдельная** staging-таблица
(`stg_msklad.fact_sales_perimeter_staging`) и **отдельный** `MERGE` в
`core.fact_sales_profit`, не расширяющий `_build_merge_sql` (тот патчит `SALES-REFRESH-WINDOW`,
`ADR-100 §7` — форма периметра задана входом 6 брифа как раздельная, прецедент `ADR-024`).
`main.py` получает два новых режима: `perimeter` (fetch+load) и `perimeter_promote` (MERGE).

**Соблюдено:**
- `sum`, а не `commitentSum` — `fetch_perimeter.py::fetch_commission_sales_positions`
  считает `price × quantity` по позициям (сумма позиций тождественна `sum` документа,
  `ADR-104 §4`), `commitentSum` нигде не читается.
- Правило суток (`ADR-088 §3`) — `_PERIMETER_PARSE_DATE` в `bq_ops.py` дословно повторяет
  `DATE(PARSE_TIMESTAMP('%Y-%m-%d %H:%M:%E3S', …), 'Asia/Bishkek')`, функцию UTC-момента
  документа; `moment_str[:10]` нигде не используется.
- C1 (`ADR-030`) — `_build_perimeter_merge_sql` несёт явный `INSERT (колонки) VALUES (…)`,
  `INSERT ROW` не используется.
- C2 (`ADR-101 §7`) — ветки удаления в новом `MERGE` нет; причина названа комментарием в
  коде (`bq_ops.py::_build_perimeter_merge_sql` докстринг): периметр новый (без
  исторического мусора на момент постройки), объём мал (~513 док/мес), тот же класс дефекта
  для ОСНОВНОГО ингеста уже адресуется отдельной задачей (`SALES-REFRESH-WINDOW`);
  симметричный фикс периметра — будущая отдельная задача, не изобретается здесь молча.

**Ограничение метода, названное явно (не скрыто).** Позиционная форма `entity/retaildemand`
(`price`/`quantity`/`discount`/`assortment` на уровне позиции) предполагается по аналогии с
`entity/demand` — подтверждено полями ДОКУМЕНТА (`reference/parity_sales_discriminate_step2_2026-08-02.md
§Шаг 2`: `agent`, `rate`, `positions`, `sum`, `store`), но НЕ подтверждено живым запросом
позиций (класс B, не выдан этой сессией). Форма позиций `entity/commissionreportin`
подтверждена измерением (`reference/sales_perimeter_confirm_2026-08-02.md §6`: `price`,
`quantity`, `assortment`, `reward`, БЕЗ `discount` — код это учитывает,
`has_discount=False`). **Перед деплоем обязательна одна проверка** (класс B, отдельный
мандат): живой `GET entity/retaildemand/{id}/positions` на одном документе, чтобы
подтвердить состав полей позиции. Это не блокирует подготовку текста патча (класс A), но
блокирует применение к проду.

## 5. Шаг 5 — обе формулы и ожидаемый сдвиг ДО прогона (`★ ADR-075 §3`)

**Формула ДО патча** (текущий прод, май-2026):

```
core.revenue_kgs(май) = Σ_{entity/demand positions} revenue_kgs
                       = 93 522 995,53 KGS   (включает 7 строк-сирот MERGE, ADR-100 §1;
                                              включает отгрузку комиссионеру 1 980 000,00;
                                              НЕ включает retaildemand и commissionreportin-продажи)
```

**Формула ПОСЛЕ патча** (этот патч; `SALES-REFRESH-WINDOW`/сироты — отдельная задача,
здесь НЕ применяется):

```
core.revenue_kgs(май)_new = core.revenue_kgs(май)_old
                             − Σ отгрузки комиссионерам (исключены Шагом 3)
                             + Σ entity/retaildemand.revenue_kgs (Шаг 2)
                             + Σ entity/commissionreportin.revenue_kgs, по sum (Шаг 2)

                          = 93 522 995,53 − 1 980 000,00 + 1 188 422,00 + 2 133 028,08
                          = 94 864 445,61 KGS
```

Входные величины — измеренные факты, не предположения: `93 522 995,53` (`ADR-097 §1`),
`1 188 422,00` (`reference/parity_sales_discriminate_step2_2026-08-02.md`, 506 док.),
`2 133 028,08` (`reference/sales_perimeter_confirm_2026-08-02.md §7`, часть B, измерено, не
остаток), `1 980 000,00` (`reference/sales_h1h4_adj_2026-08-02.md §1`, документ `04235`).

**Ожидаемое расхождение с оракулом (`report/profit/*` = `93 234 205,80` KGS, май-2026):**

```
Δ_new = 94 864 445,61 − 93 234 205,80 = 1 630 239,81 KGS  (≈ 1,7485 %)
Δ_old = 288 789,73 KGS  (0,3097 %, записанное сейчас в реестре)
```

**Предупреждение, обязательное к записи (риск R1, `ADR-101`):** после ЭТОГО патча (без
`SALES-REFRESH-WINDOW`) видимое расхождение временно ВЫРАСТЕТ с `0,31 %` до `≈1,75 %`. Причина
арифметическая, не дефект патча: `Δ_new` почти точно равен сумме строк-сирот `MERGE`
(`1 630 239,87`, `ADR-100 §1`) — этот патч убирает встречное смещение периметра
(`+1 341 450,14` со стороны отчёта), обнажая ранее скомпенсированный дефект сирот, который
устраняется ДРУГИМ патчем (`SALES-REFRESH-WINDOW`). Ожидаемое поведение, не регресс — не
принимать первую же правку за откат.
