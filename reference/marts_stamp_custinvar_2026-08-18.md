## Инцидент, названный явно (не скрыт формулировкой «приёмка прошла»)

Первый вызов `bq update --transfer_config --params='{"query": ...}'` заменил не только текст
запроса, а **весь** объект `params` целиком — стёр три поля, которых не было у объекта
`weight_flow` (там `params` изначально нёс только `query`, поэтому там дефект не воспроизвёлся):
`destination_table_name_template` (`customer_invoices_ar`), `partitioning_field` (пусто),
`write_disposition` (`WRITE_TRUNCATE`). Первый ручной прогон упал: `errorStatus.message = "A
destination table must be set with SELECT statements"` — таблица назначения бралась именно из
стёртого поля (лог — `step5_run.log`/`run_final_2026-08-18.json`, первая попытка).

Это нарушение мандата (§5: «ничего кроме текста запроса не меняется») формой вызова, не решением
поменять что-то ещё. Инцидент объявлен владельцу отдельным сообщением до исправления; исправление
подтверждено дословным «да, исправляй». Слепой retry не делался: сначала read-only снятие текущего
состояния (`step7`/до вызова — фактически повторная сверка через `bq show`), значения трёх полей
восстановлены из живого снимка, снятого ДО первой правки (`live_transfer_config_2026-08-18.json`).

**Исправление.** Повторный `bq update --transfer_config` с полным объектом `params`: тот же текст
запроса (`reference/sql/sq_marts_customer_invoices_ar_stamped_2026-08-13.sql`), плюс три
восстановленных поля с прежними значениями. Read-back после исправления: все три поля на месте
(`step9_run.log`), текст запроса побайтово равен подготовленному файлу (`diff rc=0`, sha256
`f8d155198bafebabc0e890f8a9645f341083ec99e95f645776458c71320bf377` на обеих сторонах).

ручной прогон (`bq mk --transfer_run`, после исправления) завершился `SUCCEEDED`

## Урок для следующих сессий той же строки

`bq update --transfer_config --params=<json>` заменяет объект `params` ЦЕЛИКОМ, не сливает поля.
Перед подменой `query` у любого следующего объекта (`sq_marts_expenses`) обязательно снять живой
`params` целиком и включить в payload ВСЕ его поля, а не только `query` — иначе тот же класс
дефекта повторится, если у объекта есть поля сверх `query` (что и произошло здесь, но не
воспроизвелось у `weight_flow`).
