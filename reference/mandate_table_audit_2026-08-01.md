## §3 Принцип раздачи мандатов

Резать задачу по линии **«какое действие исполнитель физически может совершить»**, а не по теме.
Основания класса B неравноценны и в `ADR-076 §1` перечислены как разные пункты:

- **живой read-only `GET` с секретом** — инструменту доступен, прецедент `REPORT-FIELDS` отработан
  целиком с провенансом (`reference/_scratch_REPORT-FIELDS_2026-07-31/`);
- **деплой и правка Cloud Functions / Scheduler / Workflows** — инструменту технически доступен,
  но есть настоящая B и дополнительно гейтится `ADR-065`;
- **правка в интерфейсе Looker Studio или МойСклад** — инструменту недоступна физически ни в каком
  классе (`ADR-085 §9`). **Но текст SQL-запроса интерфейсом не является** — его подготовка есть
  запись в `/reference`, то есть класс A по букве `ADR-076 §1`.

Последний пункт — главный источник высвобождаемой работы: четыре задачи Looker Studio сейчас целиком
помечены «инструменту не отдаётся», хотя инструменту не отдаётся только последний шаг каждой.

## §5 Правило парности (закрывает `Q-89` и §1b)

Строка задачи в GAP-реестре `07_STATE` и строка в таблице `§Мандат Claude Code: класс задач` —
**парные**:

- заводится задача-строка в реестре ⇒ ТЕМ ЖЕ коммитом заводится строка мандата;
- задача-строка уезжает в `07_ARCHIVE.md` ⇒ ТЕМ ЖЕ коммитом убирается строка мандата;
- ответственность на проходе сборки (`_ASSEMBLER.md`), потому что именно он применяет обе правки.

Изобретать форму не требуется: ровно такая парность уже механизирована для
`06_DECISIONS_LOG` ↔ `06_INDEX` проверкой №3 хука (`tools/hooks/pre-commit`, самотест
«проверка 3 (ADR-064, 06 без 06_INDEX)»). Механизация парности реестра и мандата тем же приёмом —
отдельная работа, настоящим разбором не исполняется и в задачу не оформляется без решения владельца.

Исключение из правила ровно одно и оно уже существует по факту: строки, где вместо класса стоит
«не отдаётся» или «—», описывают не мандат, а его отсутствие; они остаются в таблице, пока
существует задача-строка.
