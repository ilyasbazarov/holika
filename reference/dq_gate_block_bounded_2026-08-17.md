## 1. Диагностика — «блокирует ли гейт сейчас и сколько»

Каждый прогон `cf-dq` пишет одну строку `audit.dq_runs` на каждый чек (`helpers.py:24-35`,
схема `run_id STRING, check_name STRING, passed BOOL, detail STRING, checked_at TIMESTAMP`).
Прогоны идут раз в час (`msklad-pipeline-hourly`, `asia-east1`, cron `0 * * * *`,
`11_INFRA_FACTS.md:27`) — один `run_id` = один час.

**Блокирует promote не любой `passed=False`.** Из девятнадцати чеков `CHECKS`
(`main.py:215-237`) блокирующих — шесть: `not_empty`, `drift_check`, `fk_integrity`, `freshness`,
`margin_sanity`, `currency_normalization`. Остальные тринадцать (`drift_zero_docs` и шесть пар
`freshness_*_technical`/`freshness_*_business`) структурно не могут вернуть `False` — они читают
код каждой функции: все обёрнуты так, что возвращают `(True, ...)` при любом исходе, включая
исключение (наблюдающая форма, `DQ-FRESHNESS-WIRE`, ревью `ADR-173`). Читать их `detail` для
диагностики полезно (например `VERDICT=EXCEEDED` внутри технической проверки свежести говорит о
реальном отставании загрузчика), но приравнивать их к причине блокировки — ошибка.

**Правка (`DQ-FRESHNESS-WIRE-GUARD-FIX`, 2026-08-17).** Утверждение выше верно только начиная с
этой правки. С момента выката `DQ-FRESHNESS-WIRE` (2026-08-13) и до этой правки шесть функций
`freshness_*_business` НЕ несли `try/except` (парные `freshness_*_technical` несли) — необёрнутое
исключение BigQuery из них доходило до внешнего `except` в `main()`, который превращает его в
`passed=False`, то есть эти шесть на практике МОГЛИ заблокировать промоут, вопреки тексту выше
(найдено `reference/dq_freshness_wire_deploy_review_2026-08-17.md §2`). `DQ-FRESHNESS-WIRE-GUARD-FIX`
перенесла на них ту же форму `try/except Exception: return True, ...`, что уже стояла на
`*_technical`-парах — подтверждено программным обходом всех двенадцати функций
(`reference/_scratch_DQ-FRESHNESS-WIRE-GUARD-FIX_2026-08-17/verify_2026-08-17.log`). После этой
правки утверждение «структурно не может вернуть `False`» верно для всех тринадцати без исключения.

Запрос — последние 30 часовых прогонов, с вердиктом каждого и деталью упавших блокирующих чеков:

```sql
WITH blocking_checks AS (
  SELECT check_name FROM UNNEST([
    'not_empty', 'drift_check', 'fk_integrity',
    'freshness', 'margin_sanity', 'currency_normalization'
  ]) AS check_name
),
runs AS (
  SELECT
    run_id,
    MIN(checked_at) AS checked_at,
    LOGICAL_AND(
      NOT (check_name IN (SELECT check_name FROM blocking_checks) AND NOT passed)
    ) AS run_passed,
    STRING_AGG(
      IF(check_name IN (SELECT check_name FROM blocking_checks) AND NOT passed,
         check_name || ': ' || detail, NULL),
      ' | '
    ) AS blocking_detail
  FROM `msklad-bi-prod.audit.dq_runs`
  GROUP BY run_id
)
SELECT
  ROW_NUMBER() OVER (ORDER BY checked_at DESC) AS rn,
  run_id, checked_at, run_passed, blocking_detail
FROM runs
ORDER BY checked_at DESC
LIMIT 30;
```

**Ожидаемый вывод, штатный случай:** `rn=1` (последний час) несёт `run_passed=true`,
`blocking_detail=NULL` — гейт не блокирует, `step_promote` в `workflow_hourly.yaml` исполнился.

**Ожидаемый вывод, случай блокировки:** одна или несколько верхних строк (начиная с `rn=1`) несут
`run_passed=false` с непустым `blocking_detail` (например `freshness: max_date=2026-08-14,
lag_days=3` при пороге `DQ_FRESHNESS_MAX_DAYS=3`, либо `not_empty: staging_count=0`). **Длительность
блока** читается напрямую: количество ПОДРЯД идущих строк сверху с `run_passed=false`, до первой
строки с `run_passed=true` (или до конца выборки, если блок длится дольше 30 часов — тогда `LIMIT`
увеличить). Один `run_id` = один час, поэтому это число и есть длительность блока в часах.

## 2. Порог эскалации

**24 подряд идущих часовых прогона с `run_passed=false`** (сутки непрерывной блокировки) — порог,
после которого блок обязан быть РАЗОБРАН человеком, а не просто дожидаться следующего часа.
Число — решение владельца, зафиксированное формой `ADR-154`/`dq_gate_form_adj_2026-08-10.md §2.1`
п.2; код его не исполняет (ack-механизм и автоснятие по времени `ADR-154 §2.2` отклонены явно) —
исполняет оператор, читающий запрос §1.

**Что делать при достижении порога:**
1. Прогнать запрос §1, прочитать `blocking_detail` самой ранней из подряд идущих заблокированных
   строк (не последней — она может быть побочным следствием того же первопричинного отказа, что и
   первая) и самой последней (текущее состояние).
2. Определить причину по имени упавшего чека: `not_empty`/`freshness` — остановка загрузки
   (см. §3 п.4 «Данные не свежие» текущей диагностики, источник `cf-facts` шаг `step_facts`, не
   сам гейт); `drift_check` — реальное падение выручки против скользящего среднего (не ложный
   нулевой день — тот класс уже отфильтрован `drift_zero_docs`/`ADR-153`); `fk_integrity` —
   продукт в staging без строки в `core.dim_products` (устарел справочник, см. `cf-dim`);
   `margin_sanity`/`currency_normalization` — искажение данных из источника или ошибка курса
   (см. `cf-fx`).
3. Устранить ПЕРВОПРИЧИНУ выше по конвейеру (`cf-dim`/`cf-fx`/источник МойСклад), не сам гейт —
   гейт корректно отражает состояние данных, «чинить» его вместо источника есть тихое ослабление
   контракта (`00_CHARTER §главный принцип`).
4. После устранения причины блок снимается процедурой §3.

Не разобранный блок дольше `24` часов эскалируется тем же каналом, что и остальные исходы гейта —
телеграм-канал через лог-метрику `msklad_dq_gate_failed`/`cf-alert` (`ADR-149`, подтверждено
read-back 2026-08-09) — это уже штатный сигнал; порог `24` часа добавляет только обязанность
разобрать, а не факт получения сигнала (тот приходит с первого же блокирующего часа).

## 3. Процедура ручного снятия блокировки

**Когда применяется.** Только после того, как первопричина устранена (§2 п.3). Процедура НЕ
является способом «пропустить» гейт при неустранённой причине — блокирующий чек, если причина
жива, провалится на следующем прогоне тем же образом, включая ручной.

**Кто вызывает.** Оператор с доступом `gcloud` к проекту `msklad-bi-prod` — тем же путём, каким
исполняются остальные ручные `gcloud`-операции этого проекта (не запись в живые таблицы напрямую,
а вызов уже задеплоенного конвейера тем же способом, каким его вызывает Cloud Scheduler).

**Явный запрет, который нельзя обойти.** Снятие блокировки НЕ означает прямой вызов
`cf-facts` с `mode=promote` и вручную подобранным `window_days`. Опасность названа
`ADR-145 §4`/`dq_gate_form_adj_2026-08-10.md §2.2(б)`: часовой staging несёт 7 суток данных
(`workflow_hourly.yaml:step_facts`/`step_promote`, `window_days: 7`); вызов `promote` с окном шире
этого (например `window_days=90`, значение из недельного режима) при часовом staging удалил бы
строки вне фактически загрученного окна — ветка `WHEN NOT MATCHED BY SOURCE ... THEN DELETE`
приняла бы их за исчезнувшие в источнике. Это по-прежнему технически возможно набрать руками через
прямой HTTP-вызов `cf-facts`; процедура ниже такого вызова не требует и явно его не рекомендует.

**Параметры — запусти сам конвейер, а не его последний шаг:**

```bash
gcloud workflows run msklad-pipeline-hourly --location=asia-east1
```

Это тот же вход, что использует Scheduler каждый час: `step_dim → step_fx →
step_facts(mode=hourly) → step_dq → [если пройден] → step_promote(window_days=7,
захардкожено в `workflow_hourly.yaml`, не параметр вызова) → step_purchases(non-blocking)`.
Запуск конвейера целиком, а не прямой вызов `cf-facts`, устраняет запрещённый пункт выше
конструктивно: `window_days=7` для `step_promote` зашит в тексте `workflow_hourly.yaml`, оператор
его не выбирает и не может подставить более широкое значение через этот путь. Гейт (`step_dq`)
переоценивается заново на свежих данных — если первопричина действительно устранена, `step_dq`
пройдёт и `step_promote` исполнится тем же прогоном; если нет — прогон остановится на том же шаге
с тем же диагнозом, и это ожидаемо, не сбой процедуры.

Если после устранения причины прогоны всё равно не идут (последняя строка запроса §1 старше часа
и не обновляется) — проверить, не приостановлен ли сам Scheduler-джоб:

```bash
gcloud scheduler jobs describe msklad-pipeline-hourly --location=asia-east1 \
  --format="value(state)"
```

`state=PAUSED` — возобновить: `gcloud scheduler jobs resume msklad-pipeline-hourly
--location=asia-east1`. `state=ENABLED` при этом — не причина остановки, искать в `step_dim`/
`step_fx`/`step_facts` (логи соответствующих Cloud Run функций).

**Чем проверяется результат — три независимых подтверждения, не одно:**
1. Статус самого запуска: `gcloud workflows executions list msklad-pipeline-hourly
   --location=asia-east1 --limit=1 --format="value(state)"` → ожидание `SUCCEEDED`
   (не `FAILED`, не `ACTIVE` дольше нескольких минут).
2. Запрос §1 повторно: верхняя строка (`rn=1`) несёт свежий `checked_at` (в пределах последнего
   часа) и `run_passed=true`.
3. Свежесть данных на самой поверхности, которую защищает гейт:
   ```sql
   SELECT MAX(transaction_date) AS max_txn_date,
          TIMESTAMP_DIFF(CURRENT_TIMESTAMP(), MAX(_loaded_at), MINUTE) AS loaded_minutes_ago
   FROM `msklad-bi-prod.core.fact_sales_profit`;
   ```
   `loaded_minutes_ago` — малое число (минуты, не часы) означает, что `step_promote` этого прогона
   действительно записал в `core`, а не просто прошёл гейт без записи.

Если пункт 1 даёт `SUCCEEDED`, а пункты 2-3 не подтверждаются — это несогласованное наблюдение
(`ADR-021 §2`/`ADR-044`), не факт «всё в порядке»: не примирять половины, эскалировать архитектору
вместо повторной попытки вслепую.
