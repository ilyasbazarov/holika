## 2. Предмет 1 — место жительства: имя режима, точка входа, вызов, соседство

### 2.1 Решение

| Свойство | Значение |
|---|---|
| Функция | `cf-finance` (вариант A, `ADR-110 §5`, решение владельца — не пересматривается) |
| Имя режима | `invoices` |
| Точка входа | существующая `main(request)`; режим читается из тела запроса полем `mode` |
| Умолчание `mode` | `payments` — существующее поведение `run_etl()` |
| Вызов | ОТДЕЛЬНЫЙ Cloud Scheduler job `invoices-daily-update`, тело `{"mode": "invoices"}` |
| Расписание | `0 4 * * *`, `Asia/Bishkek` (= `22:00Z` предыдущих суток) |
| `attemptDeadline` | `1800s` — равен серверному `--timeout` самой CF (`11_INFRA_FACTS.md:18`) |
| `retryConfig` | `maxRetryDuration=0s` — прецедент обоих существующих job'ов (`11_INFRA_FACTS.md:26/27`) |
| Принципал | OIDC `etl-sa@msklad-bi-prod.iam.gserviceaccount.com` (`ADR-110 §1`: сервисный, не личный) |
| Триггер витрин | НЕ вызывается. `trigger_marts()` в `cf-finance` триггерит `sq_marts_expenses` (расходы), к счетам отношения не имеющий |

### 2.2 Форма диспетчера (целевая, не патч)

Образец формы — `cf-facts/main.py:68-86` (напечатан в провенансе, П2):

```python
def main(request):
    body = request.get_json(force=True, silent=True) or {}
    mode = body.get("mode", "payments")
    if mode == "payments":
        run_etl()                      # существующее поведение, не трогается
    elif mode == "invoices":
        run_invoices_etl()             # новый модуль
    else:
        return (f"Unknown mode: {mode!r}. Expected: payments | invoices", 400)
    return "OK", 200
```

**Почему умолчание, а не обязательный параметр.** Тело, которое шлёт существующий
`finance-daily-update`, в репо не задокументировано (`11_INFRA_FACTS.md:26` фиксирует тело только у
`loss-commission-daily-update` — `{}`). Умолчание `payments` делает правку безопасной при ЛЮБОМ
теле, включая пустое и отсутствующее, — то есть снимает необходимость знать этот факт заранее.
Это не обход гэпа, а конструкция, к которой гэп неприложим.

### 2.3 Почему отдельный Scheduler job, а не цепочка внутри суточного прогона платежей

Три довода, каждый проверяемый:

1. **Оговорка `ADR-110 §5(ii)` снимается по построению.** Оговорка требует замерить длительность
   суточного прогона до и после, потому что «функция получает новый объём работы». При отдельном
   job'е прогон платежей не удлиняется ВООБЩЕ — счета едут своим вызовом, своим инстансом Cloud Run.
   Обязанность замера при этом остаётся (§13), но меряется теперь длительность НОВОГО прогона против
   потолка `1800s`, а не деградация существующего.
2. **Изоляция отказа в ту сторону, которая важна.** Падение счетов не роняет платежи и наоборот;
   при цепочке внутри одного вызова падение второго шага оставляет непредсказуемое частичное
   состояние. Прецедент разнесения — `loss-commission-daily-update` при живом `finance-daily-update`
   на той же минуте (`11_INFRA_FACTS.md:26/27`).
3. **Цена — ноль дополнительных действий класса B против уже запланированных.** Строка
   `07_GAPS.md:91` определяет `INVOICES-LOADER-DEPLOY` как «деплой загрузчика **и постановка на
   суточное расписание**» — создание расписания уже внутри T4. Отдельный job не добавляет ни новой
   единицы деплоя, ни новых прав (тот же URI, тот же OIDC-принципал), то есть довод `ADR-110 §5`
   («наименьшее число действий класса B») не нарушается.

### 2.4 Почему `0 4 * * *` по Бишкеку

Витрина-потребитель `sq_marts_customer_invoices_ar` пересобирается **ежедневно, якорь `10:00Z`**
(`11_INFRA_FACTS.md:113`; подтверждено живым замером `2026-08-02 10:00:10`,
`reference/core_freshness_sweep_2026-08-02.md:124`). Загрузчик обязан отработать ДО неё.
`04:00` по Бишкеку = `22:00Z` предыдущих суток — двенадцать часов запаса при потолке прогона
`1800s` (полчаса). Сдвиг на час от общей отметки `03:00`, где уже стоят два job'а, оставлен
намеренно: он делает читаемыми и логи, и замер длительности §13.

Точное время — рекомендация проекта, а не выведенное из документа значение: владелец вправе
сдвинуть его при T4, инвариант один — **строго раньше `10:00Z` и не одновременно с двумя
существующими job'ами**.

### 2.5 Взаимодействие с существующими режимами

- Общие ресурсы: секрет `MSKLAD_TOKEN` (`11_INFRA_FACTS.md:19`), клиент BigQuery, форма заголовка
  авторизации. Переиспользуются как есть.
- Общих ТАБЛИЦ нет: платежи пишут `core.fact_payments_stg` → `core.fact_payments`, счета — свою
  staging (§6) → `core.fact_customer_invoices`. Пересечения записи нет, одновременный прогон
  безопасен.
- `DELETE`-постфильтр системных статей (`cf-finance/main.py:121-131`, `ADR-011`) к счетам НЕ
  применяется: `EXCLUDE_EXPENSE_IDS` — статьи расходов, у счетов покупателям таких полей нет.

### 2.6 Наблюдение о публичном доступе `cf-finance` (называется, не чинится)

`ADR-110 §5(i)` называет оговоркой «публичный доступ `cf-finance` (`allow-unauthenticated`, помечен
предупреждением в `01_ARCHITECTURE.md §топология`)». Репо по этому поводу расходится сам с собой:

- `01_ARCHITECTURE.md:25` — `cf-finance (daily 03:00 KGT) ⚠️ allow-unauthenticated`
- `11_INFRA_FACTS.md:149` — `**cf-finance (ADR-022, 2026-07-20):** … привязка allUsers → run.invoker
  снята. Верификация 2026-07-20: анонимный запрос → 403; вызов Scheduler (OIDC через тот же SA) → 200`
- `11_INFRA_FACTS.md:28` — `⚠️ TD-SEC-01 — подтверждённый инцидент 2026-07-20, устранён IAM-lockdown (ADR-022)`

То есть пометка в `01_ARCHITECTURE.md` описывает состояние ДО `2026-07-20` и с тех пор не
обновлялась. Из этого следует, что оговорка `ADR-110 §5(i)` **вероятно уже погашена решением
`ADR-022`**, и «ценность поверхности» растёт у поверхности, которая анонимно недоступна.

**Настоящим документом это НЕ решается и `01_ARCHITECTURE.md` не правится:** файл STABLE, правка
только через ADR (`05_CONVENTIONS.md:126`), а живой IAM этой сессией не переспрашивался — устная
согласованность двух документов не есть замер. Пункт назван для архитектора; блокирует он
ровно ничего (§11, п. 7).

## 3. Предмет 2 — пагинация, профиль запроса, поведение при ошибках

### 3.1 Профиль запроса

```
GET https://api.moysklad.ru/api/remap/1.2/entity/invoiceout
    ?limit=100
    &offset=<N>
    &expand=state,agent,salesChannel,rate.currency
Заголовки: Authorization: Bearer <msklad-token>
           Accept-Encoding: gzip
           (Content-Type НЕ ставится)
```

Правила поднятые, не выдуманные — `02_ERP_CONTRACTS.md §поведение МойСклад API`, дословно:

> - `time.sleep(0.25)` обязателен в цикле пагинации — иначе 429/5xx от МойСклад. *(строка 296)*
> - При `expand=` (например `expand=expenseItem`) `limit` НЕ должен превышать 100 — иначе API молча
>   игнорирует `expand` и возвращает `NULL` вместо вложенного объекта. *(строка 297)*
> - `timeout` в сетевой обёртке (`_api_get`/`helpers.py`) = 90 (не 30) для тяжёлых эндпоинтов…
>   Декораторы ретраев (`tenacity`) не спасают от низкого базового `timeout`. *(строка 298)*
> - GET-запросы: только `Authorization: Bearer $TOKEN`, без `Content-Type`. *(строка 301)*
> - `invoiceout` и `paymentout`: `expand=agent,state` … — статус и агент приходят expanded без
>   отдельного резолва. *(строка 303)*

**`limit=100` — не выбор, а следствие.** Все четыре `expand` нужны по карте полей
(`reference/invoices_field_map_2026-08-02.md §2`: `agent_name`, `state_name`, `sales_channel_name`
требуют `expand`), значит потолок `limit ≤ 100` применяется. При `4526` документах источника
(`ADR-109 §3`) это `~46` страниц × `0.25 с` ≈ `12 с` сетевого времени — при потолке прогона
`1800 с` запас трёхзначный.

**`rate.currency` в списке `expand` — добавление этого проекта к трём, названным в тексте запуска.**
Основание: `currency_code` обязан заполняться из `rate.currency.isoCode`, буквенного ISO
(`ADR-027`, `02_ERP_CONTRACTS.md:425`), а выборка T1 наблюдала у `rate.currency` только
`meta.href` с UUID (`reference/invoices_field_map_2026-08-02.md §4.1`, колонка «валюта
(`rate.currency.meta.href`, id)»), то есть без `expand` буквенного кода нет и fallback-ветка §8
не сможет назвать валюту, для которой запрашивает курс. Прецедент того же `expand` в живом коде —
`cf-loss-commission/main.py:103/130` (`expand="expenseItem,agent,rate.currency"`,
`expand="agent,rate.currency,positions"`), напечатано в провенансе, П5.

### 3.2 Форма обхода — явный `offset`/`limit`, НЕ `meta.nextHref`

```
offset = 0
while True:
    page = GET(..., limit=100, offset=offset, expand=<полный список>)
    rows = page["rows"]; собрать
    if offset == 0: meta_size_first = page["meta"]["size"]
    if len(rows) < 100: break
    offset += 100
```

**Почему не `nextHref`** (которым пользуется `cf-finance/main.py:70`): `nextHref` — строка,
сформированная сервером, и сохранность в ней параметра `expand` в репо ничем не подтверждена.
Цена ошибки здесь несимметрична: при потере `expand` API отвечает `200` и отдаёт `NULL` вместо
вложенных объектов (`02_ERP_CONTRACTS.md:297/425`) — отказ ТИХИЙ, ровно того класса, что
`05_CONVENTIONS.md ★ Успех инструмента ≠ факт`. При явном `offset` параметры собираются нами на
каждой странице, и предположение не требуется вовсе. Образец формы — `cf-facts/helpers.py:71-99`
(`paginate_entity`).

### 3.3 Контроль полноты обхода (вход для готовности-условия 2 и предохранитель ветки удаления)

После обхода, ДО записи в staging:

| Проверка | Условие | Действие при провале |
|---|---|---|
| G1 полнота | `len(collected) >= meta_size_first` | `raise` — staging не пишется, `MERGE` не запускается |
| G2 непустота | `len(collected) > 0` | `raise` — то же |

`G1` печатает оба числа, не метку (`ADR-044`). `>=`, а не `==`, намеренно: документы, созданные
в источнике во время обхода, легитимно увеличивают набор; уменьшить его может только оборванный
обход. Прецедент `raise` на нуле записей — `cf-facts/main.py:118-122`
(«API returned 0 demand position records… Possible: no shipments in window, or API issue»).

`G1`/`G2` — единственные предохранители ветки удаления (§7.3); порогов, требующих калибровки, в
проекте нет намеренно (§7.4).

### 3.4 Ошибки и повторы

**Уровень кода** (образец — `cf-facts/helpers.py:50-68`, `tenacity`):

| Код | Поведение загрузчика |
|---|---|
| `429` | ретрай с экспоненциальной задержкой (`multiplier=1, min=1, max=60`), до 5 попыток, `reraise=True` |
| `5xx` | то же |
| `401` | НЕ ретраится — токен истёк; исключение наверх, прогон падает |
| `4xx` прочие | `raise_for_status()`, прогон падает |
| сетевой таймаут | `timeout=90` на запрос, далее общий ретрай |

Исчерпание ретраев = падение прогона ДО записи в staging. Частичного состояния не возникает по
построению: staging пишется одним `load_table_from_json` после полного обхода (§6.3).

**Уровень оператора** — `02_ERP_CONTRACTS.md:306-309` (RB-18), не переписывается:
`429` — подождать 5 минут, перезапустить CF; `503/502/504` — проверить статус МойСклада;
`401` — обновить токен через Secret Manager; `415` — GET через Python `requests`, не `curl`.

**Ретраев на уровне Scheduler нет** (`maxRetryDuration=0s`, §2.1) — падение проглатывается тихо,
и это ровно та дыра наблюдаемости, которую закрывает §10.

## 4. Предмет 3 — правило суток

### 4.1 `moment` — канон, процитирован дословно

`reference/invoices_field_map_2026-08-02.md §3`, дословно:

> **Целевое правило для `core.fact_customer_invoices.moment`** — то же, что уже работает верно на
> продажах (`bq_ops.py:158`, `02_ERP_CONTRACTS.md:41`), **не** дефектный паттерн `moment[:10]`
> (`cf-finance/main.py:57`, `load_payments.py` …):
>
> ```
> moment_bishkek_date = DATE(PARSE_TIMESTAMP('%Y-%m-%d %H:%M:%E3S', moment), 'Asia/Bishkek')
> ```
>
> Эквивалент формулировки `ADR-101 §6`: бишкекские сутки = `DATE(M+6ч)`.

Основание — `ADR-088 §3` (`06_DECISIONS_LOG.md:1718`), дословно:

> Мост обязан называть правило суток каждой сверяемой таблицы явно, как функцию от UTC-времени
> документа. … На текущей фактуре: интерфейс и ручные выгрузки из него = `DATE(M+3ч)`;
> `core.fact_sales_profit` = `DATE(M+6ч)`; `core.fact_returns`, `core.fact_purchases`,
> `core.fact_loss`, `core.fact_commissionreportin` = `DATE(M)`.

**Правило `core.fact_customer_invoices` настоящим проектом назначается `DATE(M+6ч)`** — то же, что
у продаж, единственная сегодня недефектная ветка (`ADR-088 §4`: «Ветка продаж НЕ дефектна»).

### 4.2 Где вычисляется — в SQL, не в Python

Преобразование живёт в `USING`-подзапросе `MERGE` (§6.2/§6.4), staging несёт СЫРУЮ строку
`moment_raw STRING`.

Довод не стилистический. Дефект четырёх веток (`ADR-088 §4`) имеет ровно одну форму — срез строки
в Python (`moment_str[:10]`, `row.get("moment")[:10]`), где зона не называется вообще и потому
не видна при чтении. В SQL правило стоит одним выражением с явной зоной `'Asia/Bishkek'` и
проверяется чтением текста `MERGE`. Прецедент правильной ветки — `bq_ops.py:158` — устроен именно
так. Побочно: сырое значение остаётся в staging, то есть правило можно перепроверить запросом,
не обращаясь к источнику.

### 4.3 `payment_planned` — решение принято: рабочая гипотеза принимается, отдельный замер НЕ требуется

Текст запуска требует решить, а не оставить висеть. **Решение: применить то же правило
`DATE(M+6ч)`.** Три довода, по возрастанию силы:

1. **Общность факта.** `ADR-088 §1` устанавливает свойство СЕРИАЛИЗАЦИИ API («интерфейс рендерит
   время в зоне аккаунта … следовательно возвращённое API `15:33` есть UTC»), а не свойство
   конкретного поля. Формат таймстампа у обоих полей идентичен.
2. **Структурное наблюдение из выборки T1, поднимающее аналогию выше аналогии.** В образце
   (`reference/invoices_field_map_2026-08-02.md §2`): `moment = "2025-10-22 19:13:00.000"`,
   `paymentPlannedMoment = "2025-11-05 19:13:00.000"`. Это ровно `+14 суток` при **том же
   времени суток до миллисекунды**, то есть плановая дата порождается из `moment` прибавлением
   срока и наследует его часы. Поле не имеет собственных часов, которые могли бы жить в другой
   зоне. Это уже не «по аналогии» — это наблюдение над данными.
3. **Цена ошибки ограничена и измерима.** Единственный потребитель поля — витрина
   `sq_marts_customer_invoices_ar` (`reference/sql/sq_marts_customer_invoices_ar.sql:15-16`):
   `payment_planned IS NOT NULL AND payment_planned < CURRENT_DATE()` в счётчике `overdue_count`.
   Ошибка зоны сдвигает дату на одни сутки только у документов с `M ∈ [18:00; 24:00)` и меняет
   лишь момент, когда счёт становится просроченным, на один день. Ни `sum_kgs`, ни
   `unpaid_sum_kgs`, ни строка 23 реестра паритета от этого не зависят.

**Почему не заказан замер.** Замер здесь означал бы живой `GET` плюс взгляд на экран МойСклада;
взгляд на экран инструменту недоступен ни в каком классе (`ADR-101 §7`), то есть замер стоил бы
хода владельца. Вопрос, который снимается наблюдением над уже лежащими в репо данными, владельцу
не задаётся (`05_CONVENTIONS.md §Язык`, п. 5).

**Остаток назван явно:** правило для `payment_planned` не проверено против интерфейса МойСклада.
Проверка стоит нуля, если пристёгнута к `INVOICES-PARITY-RECHECK` (T6), где сверка с источником
идёт всё равно, — там и снимается. Отдельная строка реестра не заводится (`ADR-051 §2`: тот же
объект, что `Q-92`).

## 6. Предмет 4 — схема staging и стратегия загрузки

### 6.1 Место и имя

`msklad-bi-prod.stg_msklad.fact_customer_invoices_staging`

**Почему `stg_msklad`, а не `core.<table>_stg`.** У проекта два несовпадающих обычая: `cf-facts`
кладёт staging в задокументированный слой `stg_msklad` (`01_ARCHITECTURE.md:29` — `stg_msklad
(TTL 14d)`; `02_ERP_CONTRACTS.md:11` — `stg_msklad.fact_sales_staging (TTL 14 дней)`), а
`cf-finance` держит `core.fact_payments_stg` (`cf-finance/main.py:10`), то есть промежуточную
таблицу внутри витринного датасета. Задокументирован в контрактах первый; второй — местная
привычка одной функции. Новый код рождается по контракту, существующий не ретрофитится (`ADR-030`
scope: «Scope — только новый `MERGE`-код»). Имя `fact_customer_invoices_staging` повторяет форму
`fact_sales_staging`.

**Цена решения, названная:** внутри `cf-finance` появятся два разных обычая расположения staging.
Это осознанное расхождение, а не недосмотр; приведение `core.fact_payments_stg` к контракту —
не эта задача.

### 6.2 Схема staging — 19 колонок

| # | Колонка | Тип | Источник / назначение |
|---|---|---|---|
| 1 | `invoice_id` | STRING | `id` — ключ строки |
| 2 | `invoice_name` | STRING | `name`, через `str()` |
| 3 | `moment_raw` | STRING | `moment` КАК ЕСТЬ, `'YYYY-MM-DD HH:MM:SS.mmm'` UTC |
| 4 | `payment_planned_raw` | STRING | `paymentPlannedMoment` как есть, может быть `NULL` |
| 5 | `agent_id` | STRING | `parse_href(agent)` |
| 6 | `agent_name` | STRING | `agent.name` (требует `expand`) |
| 7 | `state_id` | STRING | `parse_href(state)` |
| 8 | `state_name` | STRING | `state.name` (требует `expand`) |
| 9 | `sales_channel_id` | STRING | `parse_href(salesChannel)`, `NULL` легитимен |
| 10 | `sales_channel_name` | STRING | `salesChannel.name`, `NULL` легитимен |
| 11 | `applicable` | BOOL | `applicable` — флаг проведённости, см. §6.5 |
| 12 | `currency_code` | STRING | `rate.currency.isoCode` (`ADR-027`), не числовой `.code` |
| 13 | `rate_value` | FLOAT64 | применённый курс: `rate.value` документа либо fallback (§8) |
| 14 | `sum_minor` | FLOAT64 | `sum` КАК ЕСТЬ, минорные единицы валюты документа |
| 15 | `payed_sum_minor` | FLOAT64 | `payedSum` как есть |
| 16 | `sum_kgs` | FLOAT64 | результат конвертации (§8) |
| 17 | `payed_sum_kgs` | FLOAT64 | результат конвертации тем же курсом |
| 18 | `unpaid_sum_kgs` | FLOAT64 | `sum_kgs − payed_sum_kgs` ПОСЛЕ конвертации обеих |
| 19 | `_loaded_at` | TIMESTAMP | одна отметка на прогон, §6.4 |

**Колонки 11–15 — не украшение, а закрытие названного структурного дефекта.** `ADR-101 §4`
(`06_DECISIONS_LOG.md`, разбор `Q-20`) установил дословно: «Ни `core.fact_sales_profit`
(22 колонки), ни `core.fact_payments` (15 колонок) не несут ни валюты документа, ни исходной суммы
в минорных единицах, ни применённого курса — конвертация происходит в загрузчике, в таблицу
ложится только результат в KGS. Значит внутри хранилища сравнивать не с чем, любая проверка там
есть агрегатная эвристика, а ошибка „забыли умножить на курс“ построчная». Держа исходную сумму,
курс и код валюты В STAGING, новая ветка получает построчно проверяемую конвертацию, НЕ трогая
живую схему `core`. Прямая проверка становится однострочной:

```sql
SELECT COUNT(*) AS bad_rows
FROM `msklad-bi-prod.stg_msklad.fact_customer_invoices_staging`
WHERE ABS(sum_kgs - sum_minor / 100.0 * rate_value) > 0.01
   OR ABS(payed_sum_kgs - payed_sum_minor / 100.0 * rate_value) > 0.01
   OR ABS(unpaid_sum_kgs - (sum_kgs - payed_sum_kgs)) > 0.01;
```

Это готовый вход для `INGEST-CURRENCY-ASSERT` (шаги 1-2, класс A) по ветке счетов; настоящая
задача его не исполняет и строки под него не заводит.

**Типы минорных единиц — `FLOAT64`, не `INT64`:** выборка T1 (§4.1) показывает значения вида
`21 525,0`, `1 310 820,0` — JSON-числа с дробной частью в сериализации. `INT64` дал бы отказ
загрузки на первом же таком значении.

### 6.3 Стратегия загрузки в staging

```
bigquery.LoadJobConfig(
    write_disposition = "WRITE_TRUNCATE",
    schema            = <явные 19 SchemaField>,
)
bq.load_table_from_json(records, STG_INVOICES, job_config=job_config).result()
```

- **`WRITE_TRUNCATE`** — идемпотентность staging по построению: повторный прогон замещает
  содержимое целиком, дублей не бывает. Прецеденты: `cf-finance/main.py:76`, `cf-facts` load_staging.
- **Схема передаётся ЯВНО каждый прогон, никогда не выводится из данных.** У датасета `stg_msklad`
  срок жизни таблиц 14 суток (`02_ERP_CONTRACTS.md:11`); при простое дольше двух недель таблица
  исчезает и создаётся заново загрузочным заданием. Явная схема делает пересоздание корректным;
  автовывод типов дал бы `INTEGER` вместо `FLOAT64` на удачном наборе данных — то есть молчаливую
  порчу того же класса, что закрывает `C1`.
- Запись выполняется ОДНИМ заданием после полного обхода и после проверок `G1`/`G2` (§3.3).
  Частичной staging не бывает — и это единственное, на чём держится безопасность ветки удаления.

### 6.4 `_loaded_at` — одна отметка на прогон

Стамп берётся ОДИН раз в начале прогона (`run_started_at = datetime.now(timezone.utc)`) и
проставляется всем записям; в `MERGE` он переносится из staging, а не подменяется
`CURRENT_TIMESTAMP()`.

Два следствия, оба нужны дальше: (i) готовность-условие 1 (`ADR-110 §4`) проверяется одним
запросом `SELECT COUNT(DISTINCT _loaded_at)` — после двух суточных прогонов ровно `2`, без
разброса по микросекундам, который дал бы `datetime.now()` внутри цикла (форма
`cf-finance/main.py:68`); (ii) значение читается как «когда строка последний раз подтверждена
присутствующей в источнике» — прямой признак, которым `ADR-100 §1` ловил сирот на продажах.

### 6.5 Проведённость документа (`applicable`) — фильтруется в базе, НЕ на выгрузке

Решение диктуется `ADR-034`, дословно (`06_DECISIONS_LOG.md`):

> **Решение:** поведение `cf-loss-commission` признано соответствующим ADR-011 (тянуть всё без
> исключений, фильтровать в базе; **никогда не `if/continue` на выгрузке** — иначе смена статуса
> документа не приедет и в таблице зависнет фантом). Правило нарушает `cf-finance`, не новый
> загрузчик.

Из чего следует для нового загрузчика:

- **Фильтра на выгрузке нет.** Ни `if row.get("applicable") is False: continue`
  (`cf-finance/main.py:47`, названный `ADR-034` нарушителем), ни серверного
  `filter=applicable=true` (`cf-facts/fetch_returns.py:48`). Тянется всё.
- **`applicable` едет в staging колонкой** (образец — `cf-loss-commission/main.py:121/165`) и
  фильтруется одной строкой в `USING`-подзапросе `MERGE`: `WHERE applicable IS NOT FALSE`.
- **Живая схема `core` не меняется**: колонки `applicable` там нет и настоящим проектом не
  добавляется. `ADR-034` требует фильтровать «в базе», не «в целевой таблице»; `USING`-подзапрос
  и есть база.
- **`IS NOT FALSE`, а не `= TRUE`** — намеренно: `NULL` (поле отсутствует у документа) трактуется
  как проведённый, повторяя умолчание `d.get("applicable", True)` в
  `cf-loss-commission/main.py:121`. Тихо терять документы из-за отсутствующего поля нельзя.

**Побочная выгода, названная явно:** staging держит ПОЛНЫЙ набор документов источника, включая
черновики. Значит недостачу `468` документов из `4526` (`ADR-109 §3`, задача
`INVOICES-PERIMETER-DIFF`) после первого же прогона можно разложить по статусам и по флагу
проведённости ЗАПРОСОМ К СВОЕЙ STAGING, без живого `GET` к МойСкладу — то есть частично классом A
вместо класса B. Настоящая задача этого не делает и строку `INVOICES-PERIMETER-DIFF` не трогает;
факт назван, потому что меняет цену той задачи.

### 6.6 Окно выборки — полная история, без фильтра по дате

Загрузчик каждый прогон тянет ВСЕ документы `entity/invoiceout` без `filter` по `moment`.

Довод 1 — прецедент дома. `03_PIPELINE_SPEC.md:45`, дословно: «`run_etl()` при КАЖДОМ запуске
делает полный re-fetch всей истории `paymentout`+`cashout`, без инкрементального окна (в отличие
от `cf-facts`, где есть `window_days`). Надёжно при малом объёме, но линейно растёт по времени и
риску таймаута». Объём счетов того же порядка: `4526` документа против `4732` строк
`core.fact_payments` (`07_STATE.md §Контрольные цифры`), то есть режим, который уже работает на
платежах, применим один в один.

Довод 2 — это предусловие ветки удаления. Предикат «не найдено в источнике» истинен корректно
только тогда, когда «источник» есть его полный набор. Ловушка (ii) `ADR-100 §7` (условие окна в
`ON` делает исчезнувшей всю историю за пределами окна) при отсутствии окна не возникает вовсе.

Довод 3 — досев становится побочным продуктом. Первый же успешный прогон подтягивает
`2026-06-05 … сегодня` целиком, потому что берёт всю историю. То есть `INVOICES-BACKFILL` (T5,
класс B, `07_GAPS.md`) сводится к проверке, а не к отдельной операции досева. **Настоящий документ
статус T5 не меняет** — это решение архитектора/владельца; факт назван, потому что меняет её цену.

Цена решения: время прогона растёт линейно с историей. При сегодняшних `~46` страницах запас до
потолка `1800 с` трёхзначный; наблюдаемость роста обеспечивает замер §13.

## 7. Предметы 5 и 6 — текст `MERGE` и поведение при удалении счёта

### 7.1 Решение по удалению, названное явно

**`WHEN NOT MATCHED BY SOURCE THEN DELETE` — строка, исчезнувшая в источнике, физически удаляется
из `core.fact_customer_invoices`.**

Основание — `C2` (`05_CONVENTIONS.md:170-183`, `ADR-101 §7`), дословно:

> **Правило:** в новом `MERGE`-коде проекта либо есть ветка удаления, либо в коде рядом стоит
> комментарий с причиной её отсутствия. **Если ветка удаления есть, она обязана нести собственное
> явное ограничение по дате, независимое от окна выборки:** условие окна, стоящее в `ON`, делает
> предикат «не найдено в источнике» истинным для всей истории за пределами окна, поэтому наивная
> ветка удаления опаснее исходного дефекта.

и `ADR-100 §1` (механизм, который эта ветка предотвращает), дословно:

> **Сироты.** `MERGE` (`bq_ops.py:237-305`) не имеет ветки удаления; позиция, удалённая в
> источнике задним числом, остаётся в `core` навсегда. За май-2026 таких строк ровно семь …
> Их сумма `1 630 240,60` покрывает всю целевую разность `1 630 239,87`.

### 7.2 Как выполняется требование `C2` об «ограничении по дате, независимом от окна выборки»

Требование `C2` адресует конкретную ловушку: окно в `ON` превращает «вне окна» в «исчезло».
В настоящем проекте **окна нет ни в выборке, ни в `ON`** (§6.6, §7.4) — предикат «не найдено в
источнике» вычисляется против ПОЛНОГО набора документов источника, и ложных срабатываний по
построению давать не может.

Отдельное ограничение по дате в ветку удаления **не вносится сознательно**, и вот почему его
внесение было бы вредно: любая дата-граница здесь означала бы «строки старше границы не удалять
никогда», то есть возвращала бы ровно тот дефект накопления сирот, против которого `C2` написан,
только на другом отрезке. `C2` требует, чтобы ветка удаления не опиралась на окно выборки; здесь
она не опирается ни на какое окно вообще, что есть более сильное выполнение того же требования.

**Инвариант, от которого зависит корректность, назван и защищён механически:** «staging содержит
полный текущий набор документов источника». Держат его `G1` и `G2` (§3.3) плюс запись staging
одним заданием после обхода (§6.3). Если инвариант нарушен, `MERGE` не запускается вовсе.

### 7.3 Что эта ветка стоит — цена, названная

1. **Удаление необратимо за пределами машины времени BigQuery** (7 суток по умолчанию). Массовое
   удаление на стороне источника доедет в ядро в тот же прогон. Это ЖЕЛАЕМОЕ поведение (ядро
   обязано отражать источник, `00_CHARTER §главный принцип`), но обратной операции у него нет.
2. **Витрина реагирует немедленно.** `sq_marts_customer_invoices_ar`
   (`reference/sql/sq_marts_customer_invoices_ar.sql`) агрегирует по всей истории без фильтра
   периода — удалённые счета исчезают из задолженности контрагента на следующем прогоне витрины.
   Это тоже желаемое, но оно видимо клиенту, и назвать это заранее дешевле, чем объяснять потом.
3. **Отличить «удалён в источнике» от «не доехал» после факта нельзя** — строки уже нет.
   Компенсация: staging предыдущего прогона живёт 14 суток и содержит полный набор, то есть
   вопрос «был ли счёт вчера» отвечается запросом, пока staging не истёк.

**Отвергнутая альтернатива — мягкое удаление** (колонка-флаг вместо `DELETE`): требует правки
живой схемы `core.fact_customer_invoices` и правки текста витрины, то есть выводит работу за
рамки восстановления загрузки — ровно то расползание, которое `ADR-110 §4` запрещает перечнем
«чем работа расползаться не должна».

### 7.4 Ключ строки и `ON`-клауза

**Ключ — `invoice_id`**, единственная `REQUIRED`-колонка схемы (`ADR-110 §1`, подтверждено живой
схемой §5). Суррогатный ключ не строится: у счёта, в отличие от позиции отгрузки
(`transaction_id = MD5(demand_id + position_id)`), зерно строки совпадает с документом.

```
ON T.invoice_id = S.invoice_id
```

и НИЧЕГО больше. Никакого `AND T.moment >= DATE_SUB(...)` — именно эта добавка
(`bq_ops.py:238`) названа ловушкой (ii) `ADR-100 §7` и делает ветку удаления опасной.

### 7.5 Текст `MERGE` целиком

```sql
MERGE `msklad-bi-prod.core.fact_customer_invoices` T
USING (
  SELECT
    invoice_id,
    invoice_name,
    -- ADR-088 §3 / ADR-101 §6: бишкекские сутки как функция UTC-времени документа, DATE(M+6ч).
    -- НЕ moment_raw[:10] — это дефект четырёх существующих веток ингеста.
    DATE(PARSE_TIMESTAMP('%Y-%m-%d %H:%M:%E3S', moment_raw), 'Asia/Bishkek')  AS moment,
    agent_id,
    agent_name,
    state_id,
    state_name,
    sum_kgs,
    payed_sum_kgs,
    unpaid_sum_kgs,
    -- то же правило суток; NULL допустим (поле есть не у всех документов)
    CASE
      WHEN payment_planned_raw IS NULL THEN NULL
      ELSE DATE(PARSE_TIMESTAMP('%Y-%m-%d %H:%M:%E3S', payment_planned_raw), 'Asia/Bishkek')
    END                                                                        AS payment_planned,
    sales_channel_id,
    sales_channel_name,
    _loaded_at
  FROM `msklad-bi-prod.stg_msklad.fact_customer_invoices_staging`
  -- ADR-034: черновики фильтруются в базе, не на выгрузке; NULL читается как «проведён»
  WHERE applicable IS NOT FALSE
) S
ON T.invoice_id = S.invoice_id

WHEN MATCHED THEN UPDATE SET
  T.invoice_name       = S.invoice_name,
  -- ADR-100 §2: дата документа ОБЯЗАНА обновляться при матче.
  -- Её отсутствие в UPDATE SET и есть второй дефект MERGE продаж.
  T.moment             = S.moment,
  T.agent_id           = S.agent_id,
  T.agent_name         = S.agent_name,
  T.state_id           = S.state_id,
  T.state_name         = S.state_name,
  T.sum_kgs            = S.sum_kgs,
  T.payed_sum_kgs      = S.payed_sum_kgs,
  T.unpaid_sum_kgs     = S.unpaid_sum_kgs,
  T.payment_planned    = S.payment_planned,
  T.sales_channel_id   = S.sales_channel_id,
  T.sales_channel_name = S.sales_channel_name,
  T._loaded_at         = S._loaded_at

-- C1 / ADR-030: только явный INSERT (колонки) VALUES (...).
-- WHEN NOT MATCHED THEN INSERT ROW ЗАПРЕЩЁН (позиционное сопоставление колонок).
WHEN NOT MATCHED BY TARGET THEN INSERT (
  invoice_id,
  invoice_name,
  moment,
  agent_id,
  agent_name,
  state_id,
  state_name,
  sum_kgs,
  payed_sum_kgs,
  unpaid_sum_kgs,
  payment_planned,
  sales_channel_id,
  sales_channel_name,
  _loaded_at
) VALUES (
  S.invoice_id,
  S.invoice_name,
  S.moment,
  S.agent_id,
  S.agent_name,
  S.state_id,
  S.state_name,
  S.sum_kgs,
  S.payed_sum_kgs,
  S.unpaid_sum_kgs,
  S.payment_planned,
  S.sales_channel_id,
  S.sales_channel_name,
  S._loaded_at
)

-- C2 / ADR-101 §7 + ADR-100 §1: ветка удаления присутствует.
-- Предикат корректен, потому что staging несёт ПОЛНЫЙ набор документов источника (§6.6),
-- а окна нет ни в выборке, ни в ON (§7.2). Инвариант держат проверки G1/G2 (§3.3).
WHEN NOT MATCHED BY SOURCE THEN DELETE
```

### 7.6 Порядок операций прогона

```

2. полный обход entity/invoiceout (§3.2)
3. G1: len(collected) >= meta.size первой страницы  → иначе raise

4. конвертация валюты построчно (§8)
5. load_table_from_json → stg_msklad.fact_customer_invoices_staging (WRITE_TRUNCATE, явная схема)

```

Шаг 6 не запускается, если упал любой из 1–5. Витрины не триггерятся (§2.1).

## 8. Предмет 7 — правило валюты и обязательная fallback-ветка

### 8.1 Канон, процитирован дословно

`ADR-010` (`06_DECISIONS_LOG.md:119`), дословно:

> **Решение:** канон конвертации — `minor_units ÷ 100 × rate` документа (`rate.value` документа,
> **если задан; иначе — текущий курс валюты**) до суммирования в KGS; `÷100 без ×rate` запрещён.
> **Скоуп: все входящие мультивалютные суммы (`price`/`sum` позиций, `sum`/`payedSum` в
> `invoiceout`, `sum` в `paymentout`/`cashout`) — глобальный inbound-канон.**

`reference/invoices_field_map_2026-08-02.md §4.2`, дословно:

> ```
> sum_kgs = (minor_units ÷ 100) × rate.value документа, если задан; иначе — текущий курс валюты
> ```
>
> **`payed_sum_kgs` конвертируется ТЕМ ЖЕ курсом документа**, что и `sum_kgs` — оба поля
> принадлежат одному документу с одним `rate.value`, отдельного курса для оплаченной суммы в API
> нет.
>
> **`unpaid_sum_kgs = sum_kgs − payed_sum_kgs`** — вычитание выполняется ПОСЛЕ конвертации обеих
> величин в KGS.

Код валюты — `ADR-027` (`02_ERP_CONTRACTS.md:425`): `rate.currency.isoCode`, буквенный ISO 4217;
числовой `rate.currency.code` запрещён.

### 8.2 Fallback-ветка — обязательна, реализуется, а не выводится из выборки

`reference/invoices_field_map_2026-08-02.md §6` требует дословно:

> **Fallback «не-KGS документ без `rate.value`»** для `entity/invoiceout` не пронаблюдён ни разу
> (выборка 5 документов), хотя предусмотрен каноном `ADR-010`/`ADR-029`. `INVOICES-LOADER-DESIGN`
> обязан реализовать fallback-ветку (`_fetch_current_rate`-эквивалент), не полагаясь на «в выборке
> не встретилось».

`ADR-029 §2` то же основание: обязательство «НЕ гейтится замером не-KGS документов в выборке».

**Целевая логика (три ветви, ни одной неявной):**

| Условие | Курс | Лог |
|---|---|---|
| `rate.value` задан | `float(rate.value)` | — |
| `rate.value` пуст И `currency_code == 'KGS'` | `1.0` | — |
| `rate.value` пуст И валюта не KGS | текущий курс из `entity/currency` по `isoCode`, с кэшем на прогон | `WARNING` с id документа, кодом валюты и применённым курсом |

Третья ветвь при невозможности прочитать курс **падает исключением**, не подставляет `1.0`:
хардкод `1.0` в этом месте есть в точности дефект, который `ADR-029 §1` объявил подлежащим
исправлению.

**Образец реализации — `reference/code/cf-loss-commission/main.py:55-94`** (`_fetch_current_rate` +
`_rate_and_currency`), тот же канон с fallback и с кэшем `_CURRENCY_RATE_CACHE`. Дословно оттуда
предупреждение автора, которое T3 обязан перенести вместе с кодом:

> ВАЖНО: точная форма поля 'rate' в ответе entity/currency не была проверена на живых данных на
> момент этой правки … Код обрабатывает и объектную {"value": ...}, и скалярную форму, но при
> первом реальном срабатывании этой ветки — проверь лог ниже глазами, не доверяй молча.

### 8.3 Запрет, который уже стоил проекту денег

**НЕ брать конвертер из `reference/code/cf-finance/main.py` и из `load_payments.py`.**
Провенанс — `reference/invoices_field_map_2026-08-02.md §4.3`: оба несут
`sum_kgs = (row.get("sum") or 0) / 100.0` без `× rate.value`
(`reference/code/cf-finance/main.py:67` — проверено чтением файла в этой сессии).
Снапшот `reference/code/cf-finance/` соответствует ревизии `00006-piv`
(`reference/code/cf-finance/MANIFEST.md`), тогда как живая — `00012-cik`
(`11_INFRA_FACTS.md:22`), и в живой `× rate.value` ЕСТЬ. То есть дефект существует только в
снимке; копирование снимка воспроизвело бы уже починенную в проде ошибку.

Полный разбор — `reference/architect_review_queue_2026-08-02-3.md`. T2 этим не блокируется:
формула взята из `ADR-010` напрямую.

### 8.4 Где хранится результат

`sum_kgs`, `payed_sum_kgs`, `unpaid_sum_kgs` — в `core` (14 колонок неизменны).
`currency_code`, `rate_value`, `sum_minor`, `payed_sum_minor` — только в staging (§6.2), где и
становятся построчно проверяемыми.

## 9. Предмет 8 — покрытие проверкой свежести

### 9.1 Факт, от которого строится решение

`reference/dq_source_capture_2026-08-02.md §1-2`, дословно:

> **Проверка свежести (`check_freshness`, `main.py:70-86`) читает ТОЛЬКО
> `stg_msklad.fact_sales_staging`** …
> **Вывод периметра:** сторож видит один домен — продажи … Возвраты, закупки, инвентарь, платежи,
> счета покупателям, списания, комиссии контрагентов … — вне периметра **любого** из шести чеков,
> не только свежести.
>
> **Ответ: нет.** … `check_freshness` не адресует эту таблицу вовсе … **Даже если бы адресовала** —
> колонка, по которой чек считает возраст, `transaction_date_raw` …, в таблице счетов
> **отсутствует структурно**.

Это и есть причина, по которой таблица простояла 58 суток незамеченной.

### 9.2 Что проектируется ЗДЕСЬ: текст проверки и различение двух свежестей

Проверок нужно ДВЕ, и путать их нельзя — `ADR-007` / `03_PIPELINE_SPEC.md:82-86` уже развёл эти
роли для продаж (техническая `_loaded_at` = «запускался ли прогон» против бизнес-даты =
«устаревание данных»).

**(A) Техническая свежесть загрузчика — СТОРОЖ. Именно она поймала бы заморозку.**

```sql
SELECT
  TIMESTAMP_DIFF(CURRENT_TIMESTAMP(), MAX(_loaded_at), HOUR) AS load_lag_hours,
  COUNT(DISTINCT _loaded_at)                                 AS distinct_load_stamps,
  COUNT(*)                                                   AS n_rows
FROM `msklad-bi-prod.core.fact_customer_invoices`
```

Условие прохождения: `load_lag_hours <= 48`.

**Откуда `48`, а не выдумано.** `03_PIPELINE_SPEC.md:86` задаёт для ЧАСОВОГО пайплайна порог
liveness `≤ 2 часа` по `_loaded_at`, то есть «два пропущенных прогона». Тот же способ построения
для СУТОЧНОГО загрузчика даёт `≤ 48 часов`. Число выведено из формы уже принятого правила, а не
подобрано.

Контроль на сегодняшних данных (не гипотетический): на момент замера
`reference/invoices_staleness_probe_2026-08-02.md §5` разрыв составлял 58 суток ≈ `1392` часа —
проверка была бы красной с `2026-06-07` и осталась бы красной до сих пор.

**(B) Бизнес-свежесть — ДИАГНОСТИКА, НЕ блокирующая.**

```sql
SELECT DATE_DIFF(CURRENT_DATE('Asia/Bishkek'), MAX(moment), DAY) AS business_lag_days
FROM `msklad-bi-prod.core.fact_customer_invoices`
```

Порог **настоящим документом НЕ назначается**, и это осознанный отказ, а не пропуск: счета
выставляются неравномерно, эмпирического распределения пауз между документами в репо нет, а порог,
выведенный из ничего, есть ровно тот дефект, который `ADR-101 §4` описал у `Q-20` («гейт назван,
исполнителя у гейта нет»). Величина печатается каждый прогон (§10.1); порог назначается после
2–3 недель наблюдения, и это работа T3/T4, а не догадка T2.

### 9.3 Что уходит в `DQ-GATE-SCOPE-SPLIT` — и почему именно это

**Уходит: место исполнения проверки (A) и её блокирующая семантика.**

Довод не про чистоту разделения, а про вред. Строка `07_GAPS.md:87` (`DQ-GATE-SCOPE-SPLIT`)
описывает дословно:

> `drift_check` считает по выручке ПРОДАЖ, а `check_dq`/`raise_dq_failed` в `workflow.yaml`
> останавливает выполнение до `step_promote`, `step_purchases` И `step_returns` — одна слабая
> суббота по продажам гасит на неделю загрузку данных, к продажам отношения не имеющих.

Если проверку (A) добавить седьмым чеком в `cf-dq` СЕЙЧАС, симметрия сработает в обратную сторону:
провал по счетам погасит промоут продаж, закупки и возвраты. То есть добавление корректной
проверки до разделения гейта **расширило бы уже известный радиус поражения**, а не уменьшило.
Поэтому размещение ждёт `DQ-GATE-SCOPE-SPLIT`, а текст проверки готов заранее и лежит здесь.

**Тоже уходит туда (или в отдельную задачу оповещения): путь сигнала.** Даже корректная и
корректно размещённая проверка сегодня никого не уведомит —
`reference/dq_source_capture_2026-08-02.md §1-2` установил, что специфичный алерт
`msklad-dq-gate-failed` структурно не может сработать (лог-метрика ждёт `service_name="cf-dq"` +
`severity>=ERROR`, а провал логируется CRITICAL на ресурсе Workflow; 0 совпадений за 90 суток).
Настоящий проект этого не чинит и задачи под это не заводит.

**Остаётся здесь (T2/T3, класс A):** текст обеих проверок (§9.2), обоснование порога `48 часов`,
инвариант «один стамп `_loaded_at` на прогон» (§6.4), без которого проверка (A) неоднозначна.

### 9.4 Следствие для готовности программы, которое надо сказать вслух

`ADR-110 §4` объявляет пятым обязательным условием готовности: «**Наблюдаемость.** Проверка
свежести покрывает эту таблицу и подала бы сигнал, если бы загрузка встала снова».

Из §9.3 следует: **пятое условие НЕ достигается задачами `T2`–`T4` и гейтится
`DQ-GATE-SCOPE-SPLIT`**, у которой сегодня «форма фикса не назначена» (`07_GAPS.md:87`). Программа
`ADR-110` этой зависимости не называет — её декомпозиция (`§3`, `T1→T6`) внешних гейтов знает
ровно один, код-репозиторий для `T4`. Это не возражение против программы, а недостающее ребро
графа; решение о нём — архитектора, не T2.

## 10. Наблюдаемость самого прогона (обработка ошибок, часть вторая)

### 10.1 Что печатает прогон — числа, не метки

`ADR-044` требует от вердикта печатать данные, а не метку. Прогон обязан вывести:

```
INVOICES: fetched=<N> meta_size=<M> applicable_false=<K>
INVOICES: staged=<N> merged_inserted=<I> merged_updated=<U> merged_deleted=<D>
INVOICES: load_lag_hours=<H> business_lag_days=<B> distinct_load_stamps=<S>
INVOICES: currency_fallback_hits=<F>
```

`merged_deleted` — отдельной цифрой намеренно: это единственный необратимый эффект прогона (§7.3),
и он обязан быть виден в логе без запроса к BigQuery. `currency_fallback_hits` — счётчик третьей
ветви §8.2: её первое в истории проекта срабатывание должно быть замечено, а не пройти молча
(`Q-51`/`ADR-031 §5`: не-KGS документ без курса за всю историю не встречался ни разу).

### 10.2 Порог-предохранитель на удаление НЕ вводится — и почему это решение, а не пропуск

Напрашивается автоматический выключатель вида «отменить прогон, если удаляется больше X %».
Он не вводится по двум причинам:

1. **Ему нечем быть откалиброванным.** Сколько счетов удаляется в источнике за сутки — в репо не
   измерено ни разу. Число, взятое из головы, есть тот же класс дефекта, что `ADR-101 §4` назвал
   у `Q-20`.
2. **Он избыточен по построению.** Единственный сценарий ложного массового удаления — оборванный
   обход источника, и его перехватывает `G1` (§3.3) ДО записи в staging. Остаётся сценарий
   настоящего массового удаления на стороне источника — и его загрузчик обязан пропустить, а не
   гасить.

**Открытый пункт для T3, названный:** после 2–3 недель прогонов величина `merged_deleted`
становится измеренной, и тогда предохранитель можно назначить числом, а не догадкой. До этого
защита — `G1`, `G2` и печать §10.1.

## 11. `CONTEXT GAP` — названы, ни один не обойдён подстановкой

Ни один из семи не блокирует программу целиком; каждый — открытый пункт для названной задачи.

1. **Структура живого `cf-finance/main.py` неизвестна.** Снапшот в репо — ревизия `00006-piv`
   (`reference/code/cf-finance/MANIFEST.md`) против живой `00012-cik` (`11_INFRA_FACTS.md:22`),
   разница минимум шесть ревизий. В снапшоте диспетчера режимов НЕТ вовсе: `grep -n "mode"
   reference/code/cf-finance/main.py` → **0 совпадений**, а точка входа —
   `def main(request): run_etl(); return "OK", 200` (`main.py:138-140`, напечатано в провенансе, П1).
   Есть ли `mode` в живой ревизии — не установлено.
   *Следствие:* §2.2 задаёт диспетчер как ЦЕЛЕВУЮ форму, а не как патч по номерам строк.
   **T3 обязан снять свежий снапшот `cf-finance` ДО написания патча** и строить патч против него.
   Кому: `INVOICES-LOADER-BUILD`, первым шагом.
2. **Тело запроса, которое шлёт `finance-daily-update`, не задокументировано**
   (`11_INFRA_FACTS.md:26` фиксирует тело только у `loss-commission-daily-update`).
   *Обойдено конструктивно, не подстановкой:* умолчание `mode="payments"` (§2.2) корректно при
   любом теле. Гэп остаётся, цены не имеет.
3. **Приём `expand=state,agent,salesChannel,rate.currency` (четыре) при `limit=100` не
   пронаблюдён.** T1 наблюдал три (`reference/invoices_field_map_2026-08-02.md §1`). Прецедент
   трёхкомпонентного `expand` с `rate.currency` есть (`cf-loss-commission/main.py:130`), но на
   другой сущности.
   *Кому:* T3, одним read-only `GET` в начале сухих прогонов; проверка — что `agent.name`,
   `state.name`, `salesChannel.name` и `rate.currency.isoCode` пришли непустыми хотя бы на одном
   документе каждый. Провал = тихая деградация `expand` (`02_ERP_CONTRACTS.md:297`), лечится
   разбиением на два прохода.
4. **Что именно составляет недостачу `468` документов** (`4058` наших против `4526` источника,
   `ADR-109 §3`) — не установлено; загрузчик первой ручной загрузки не найден (`Q-82`,
   `SOURCE-MAP-REST`), поэтому неизвестно, фильтровал ли он что-нибудь.
   *Следствие:* настоящий проект НЕ воспроизводит неизвестный фильтр и НЕ объявляет своё правило
   объяснением недостачи. Правило периметра публикуется одно и явное: `applicable IS NOT FALSE`
   (§6.5). Разложение недостачи — `INVOICES-PERIMETER-DIFF`, и §6.5 удешевляет его до запроса к
   собственной staging.
5. **Зона поля `payment_planned` не проверена против интерфейса МойСклада.** Решение принято
   (§4.3) на структурном наблюдении, не на замере; остаток снимается попутно в
   `INVOICES-PARITY-RECHECK` (T6).
6. **Бизнес-порог свежести (§9.2 B) не назначен** — нет эмпирики пауз между счетами.
   *Кому:* T3/T4 после 2–3 недель наблюдения.
7. **Расхождение двух документов о публичном доступе `cf-finance`** (§2.6): `01_ARCHITECTURE.md:25`
   против `11_INFRA_FACTS.md:28/149`. Живой IAM этой сессией не перепроверялся.
   *Кому:* архитектор. Не блокирует ничего.
