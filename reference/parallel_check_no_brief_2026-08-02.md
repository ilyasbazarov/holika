# FILE: parallel_check_no_brief_2026-08-02.md

**Сессия:** `PARALLEL-CHECK-NO-BRIEF` (2026-08-02, класс A — правка инструмента в репо, коммит
локальный; облачных вызовов ноль).
**База:** `git rev-parse HEAD` = `0cc54b1` на момент заведения дерева.
**Повод:** дефект, найденный проверками после сборки 2026-08-02 — сессии, исполняемые без брифа
(`ADR-086 §1`), выпадают из механической проверки параллельности целиком.

---

## 1. Дефект: что именно не работало

`tools/parallel_check.sh` читал набор файлов на запись ТОЛЬКО из поля «Файлы на запись» в
`briefs/<TASK>.md`. Для задачи без брифа скрипт печатал `ПРОВЕРКА: нет файла briefs/<TASK>.md` и
возвращал `RC 3`.

Проверено фактом на живой задаче (сессия `UNGATED-QUEUE-ADJ`, 2026-08-02):

```
$ bash tools/parallel_check.sh UNGATED-QUEUE-ADJ PARITY-SALES-DISCRIMINATE-2NDSTEP
ПРОВЕРКА: нет файла briefs/UNGATED-QUEUE-ADJ.md
```

Исполнение без брифа — законный режим (`ADR-086 §1`), и таких сессий в проекте уже несколько
(`SALES-ORPHAN-CONFIRM`, `STATE-COMPACT`, `UNGATED-QUEUE-ADJ`). То есть правило параллельности
(`ADR-082 §1`: перед одновременным запуском обязателен прогон проверки) для целого класса сессий
не имело исполняющего механизма — ровно тот дефект «правило есть, механизма нет», который
`ADR-093` разобрал для языка, а `ADR-099` для канала запуска сборки.

## 2. Поправка к собственной рекомендации

В чате 2026-08-02 сессия `UNGATED-QUEUE-ADJ` рекомендовала «научить скрипт читать набор файлов не
только из брифа, но и из блока сессии». **Рекомендация неверна по механизму и здесь не
исполняется:** session-блок пишется В КОНЦЕ сессии, а проверка нужна ДО её запуска. Читать нужно
то, что лежит в репо заранее.

Такое место уже существует и заполняется по действующему правилу: колонка «Основание» таблицы
`07_STATE §Мандат Claude Code` несёт у задач класса A поле `Пишет: <пути>`, а парность строки
реестра и строки мандата обязательна (`ADR-090 §1`). То есть данные уже есть, их просто никто не
читал машинно.

## 3. Что сделано

Правка `tools/parallel_check.sh`, три изменения:

1. **Второй источник набора.** Приоритет прежний — бриф; при его отсутствии набор берётся из
   поля `Пишет:` строк таблицы мандата. Берутся ВСЕ строки задачи, включая шаговые
   («`<TASK>`, шаг 2a»), потому что набор задачи есть объединение наборов её шагов. Источник
   печатается в выводе по каждой задаче, чтобы вердикт был проверяем.
2. **Класс задачи читается из той же таблицы.** Задача, все строки которой класса B, не
   параллелится никогда (`ADR-082 §1`) — теперь это возвращает `RC 1` механически, а не остаётся
   ручной проверкой «отдельно по `07_STATE`», как было написано в прежнем вердикте. Смешанный
   класс (`A/B`) печатает предупреждение и разбирается по файлам. Класс, который установить не
   удалось, печатается как неустановленный и на вердикт не влияет: отсутствие данных фактом не
   является (`ADR-021 §2`).
3. **Два подавления ложных срабатываний.** Плейсхолдер `<TASK>` раскрывается в имя задачи (иначе
   любые две задачи ложно пересекались бы на общем шаблоне `reference/_scratch_<TASK>_<date>/`);
   из хвоста `Пишет:` отбрасываются токены со пробелом или знаком параграфа — рядом с путями там
   стоят ссылки вида `` `ADR-081 §8` ``, и две задачи, цитирующие один ADR, дали бы ложное
   пересечение, то есть заблокировали бы законный запуск.

Отказ остаётся отказом: нет ни брифа, ни строк мандата — `RC 3`; источник найден, но набор пуст —
`RC 3`. Тихого пропуска ни в одной ветке нет.

## 5. Побочная находка: пять строк мандата класса A без объявленного набора

Новый механизм сразу показал, что данные заполнены не везде. Из 18 строк мандата класса A поле
`Пишет:` отсутствует у пяти:

- `CODE-REPO-STANDUP, шаг 1` — задача DONE, дозаполнение смысла не имеет;
- `INGEST-MOMENT-ZONE-FIX, подготовка патча` — набор выводится из собственного текста строки
  (`правка снапшота reference/code/`), дозаполняется этой сессией;
- `CC-READONLY-PRINCIPAL, шаг 1 (замер D1-D3)` — набор назван в строке реестра
  (`артефакт → /reference/cc_readonly_principal_<date>.md`), дозаполняется этой сессией;
- `ORACLE-AUTOMATION, написание скрипта` — **не дозаполняется**: где живёт сам скрипт посева, в
  репо не сказано, подстановка правдоподобного пути была бы импровизацией (`_METHOD §6`);
- `CC-READONLY-PRINCIPAL, шаги 2-3, подготовка патча` — **не дозаполняется**: строка говорит
  «патч `.claude/settings.json` и скрипт выдачи ролей готовятся», но где лежит подготовленный
  патч, не сказано.

Две последние обязаны получить набор при взятии задачи — до того проверка по ним честно
откажет, а не пропустит молча.

## 6. Процессное отклонение этой сессии, названное явно

Задача заведена из разговора: строки `PARALLEL-CHECK-NO-BRIEF` в `07_STATE` на момент старта не
было, а `ADR-086 §3` требует, чтобы определение задачи было свойством репо. Формально работа
должна была идти после появления строки, то есть после отдельной сборки.

Это **третий зафиксированный инстанс класса** (`INVOICES-LOADER-PROBE`, 2026-07-31, строки нет ни
в `07_STATE`, ни в `07_ARCHIVE`; замер, поднятый сессией `DEPLOY-TRUTH-ADJ`, `07_STATE §Подробности`).
Отдельный `Q` не заводится (`ADR-051 §2`). Но повторяемость сама по себе есть факт: инстанс
возникает каждый раз, когда владелец поручает работу репликой в чате, и разорвать цикл
«строка появляется только сборкой, а сборка идёт после сессии» дисциплиной не удаётся — правило
удовлетворимо только тем, что сессия заводит строку СВОИМ блоком, что и делается здесь.
Наблюдение адресовано архитектору как кандидат на уточняющее прочтение `ADR-086 §3`, а не как
основание нарушать его дальше.
