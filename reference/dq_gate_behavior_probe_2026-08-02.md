`2026-08-02→03` (`2026-08-02T18:00:02Z`, execution `5a36322f-76fa-428f-b2be-62bc2e1b98d5`) дал

загружается через `WRITE_TRUNCATE` (`reference/code/cf-facts/bq_ops.py:7,115` — комментарий явно
называет это; комментарий там же: «hourly (7d)… weekly (90d)») — то есть КАЖДЫЙ прогон полностью

`07-25…07-31`: к моменту замера скользящее окно staging уже частично съехало вперёд. Это
дополнительно, независимо от прямого совпадения чисел, исключает staging как источник `ma7`.
**Источник гейта — `core.fact_sales_profit`.**

Подтверждает документированное поведение `03_PIPELINE_SPEC.md:72,78` независимой сверкой с

### Разбор восстановления `2026-07-26`

Тела `drift_check` внутри блока (`step2c_recovery_bodies_v2_run.log`, 14 захваченных `CRITICAL`-записей): `target_date`
не меняется (`2026-07-25`) на протяжении ВСЕГО блока, при этом соседний чек `freshness` показывает
смену `max_date` `2026-07-25→2026-07-26` (`lag_days` 1→0) в середине блока — это ожидаемо: `target_date`
= T-1 от бишкекского «сегодня» и должен оставаться постоянным весь бишкекский календарный день,
меняясь только на следующей полуночи; `freshness` при этом читает `MAX(DATE(transaction_date_raw))`
именно из STAGING (`03_PIPELINE_SPEC.md:74` привязывает freshness к сырой колонке), а staging
(`WRITE_TRUNCATE`, живая выгрузка из МойСклад) не блокируется гейтом и продолжает получать свежие
календарные даты независимо от промоута — отсюда несовпадение динамики `target_date` (стоит) и
`max_date` (растёт) внутри одного и того же блока.

Восстанавливающий прогон — `2026-07-26T18:00:02Z`, execution `cdf2cea8-1a3b-4bdc-b174-a5d2b21c4e91`
(`step2g_run.log`): `promote_result` `{"status":"ok","merge_stats":{"affected_rows":691,...},
"coverage_stats":{"total_revenue_kgs":23266271.13,...}}` — DQ пройден полностью, промоут исполнен.
Тело ПРОХОДЯЩЕГО (`passed=true`) `drift_check` этим методом не снимается: `cf-dq`, судя по обеим
попыткам (`step2d_recovery_success_body_run.log`, `step2e_success_body_run.log` — оба `[]` при `rc=0`), пишет детальное `CRITICAL`-тело
только при отказе, не при успехе. Пустая выдача при `rc=0` — гэп наблюдения (`ADR-021 §2`), не факт
«лога нет вообще».

**Ответ на «каким из трёх объяснений (а)/(б)/(в) объясняется восстановление `2026-07-26`»:**
- **(в) ручной промоут — ОПРОВЕРГНУТО фактом**, не догадкой: ни одного задания от личного аккаунта
  за весь период.
- **(б) источник — промежуточная таблица — ОПРОВЕРГНУТО Замером 1.**
- **(а) часовой/недельный считают по-разному — НЕ ПОДТВЕРЖДЕНО.** Оба режима в один день дали
  идентичные цифры одним механизмом; разница только в частоте опроса (известно и раньше).
- **Что осталось необъяснённым (`CONTEXT GAP`):** если `target_date` при восстанавливающем прогоне
  сменился на `2026-07-26` (следующий бишкекский день), то `core.fact_sales_profit` на МОМЕНТ
  проверки (ДО шага `step_promote` того же прогона, порядок DAG `step_dq → check_dq → step_promote`,
  `01_ARCHITECTURE.md:84`) физически не содержала ни одной строки за `2026-07-26` — промоут для этого
  дня исполнился только ПОСЛЕ прохождения чека, в этом же прогоне. Строгое чтение «только уже
  промёрженный `core`» не может механически объяснить прохождение чека в этот момент, каким бы ни
  было число `yesterday_rev`. Не разрешается без чтения `cf-dq` — закрывается `DQ-SOURCE-CAPTURE`,
  вне scope этой сессии.

## Ответ владельцу одной фразой

**Блокировка сама не снимется.** `yesterday_rev` останется `0`, пока промоут заблокирован — данные
за день, который надо оценить, физически не попадают в ядро без прохождения самого чека, который их
блокирует. Нужен один внешний шаг (класс B, мандат не выдан этой сессией): либо ручной промоут
конкретного прогона, либо правка/калибровка `drift_check`/порога в `cf-dq` с передеплоем. Вариант
«подождать, пока выручка сама вернётся к норме» отпадает — она физически не может вернуться, пока
данные не пропущены в ядро. Из трёх ранее обсуждавшихся объяснений прошлого восстановления отпадает
ручной промоут (журнал заданий чист) и отпадает версия «источник — промежуточная таблица» (числа
совпадают с ядром); версия «часовой и недельный режимы считают по-разному» не нашла подтверждения,
но и не была нужна — само по себе восстановление `07-26` содержит техническую деталь, которую можно
объяснить только чтением кода `cf-dq` (отдельная задача).

## Что этой сессией НЕ сделано (вне scope)

- Ни одного действия над живым конвейером — ручной промоут, перезапуск, правка порога, деплой не
  выполнялись (класс B, мандат не выдан).
- Код `cf-dq` не читался — граница `DQ-SOURCE-CAPTURE`. (Код `cf-facts`, `bq_ops.py`, прочитан —
  он в контексте задачи через `02_ERP_CONTRACTS.md`/бриф и не относится к запрету.)
- Реальность падения выручки `2026-08-01` (снижение продаж в выходной день vs ошибка вычисления) не
  оценивалась — требует независимой сверки с МойСклад, класс B.
- `07_STATE`, `06_DECISIONS_LOG`, `06_INDEX`, `07_GAPS`, `11_INFRA_FACTS`, `03_PIPELINE_SPEC` не
  правились.

## `CONTEXT GAP` (поимённо)

1. **Точный технический механизм восстановления `2026-07-26T18:00:02Z`** — прохождение
   `drift_check` для `target_date=2026-07-26` не может быть строго объяснено чтением уже
   промёрженного `core` (промоут этого дня исполнился ПОСЛЕ проверки, в том же прогоне). Не
   разрешается без чтения `cf-dq` — закрывается `DQ-SOURCE-CAPTURE`.
2. **Тело прохождения (`passed=true`) `drift_check`** ни разу не найдено этим методом (`cf-dq`,
   судя по всем попыткам, логирует детальное `CRITICAL`-тело только при отказе). Пустая выдача при
