## §1. Почему у этих двух задач нет брифа, а у деплоя он был

`ADR-086 §1` разрешает исполнение без брифа только классу A, и на деплое я на этом настаивал.
Здесь настаиваю на обратном, и разница не в удобстве, а в свойствах объекта:

- **деплой** был многошаговой не-идемпотентной операцией с пятью предусловиями, необратимой

Прецеденты класса B, исполненного по поимённому мандату без отдельного брифа: `ADR-149`

## §2. Мандат 1 — откат кода `cf-facts`

**Основание:** владелец, чат 2026-08-12. Рекомендация архитектора — `…defect_adj…§7`.

**Объект — ровно одна команда:**

```
gcloud run services update-traffic cf-facts --to-revisions=cf-facts-00011-mab=100 \
  --region=asia-east1 --project=msklad-bi-prod
```

**Три ревизии, которые нельзя путать** (все существуют в Cloud Run):

| Ревизия | Что несёт | Роль |
|---|---|---|
| `cf-facts-00011-mab` | код БЕЗ ветки удаления, `INGEST-MOMENT-ZONE-FIX` | **цель отката**, обслуживала прод до `2026-08-11T16:42Z` |
| `cf-facts-00012-ber` | первый заход, откачен `2026-08-11` | трафика не несёт, не трогать |
| `cf-facts-00014-doh` | патч варианта 1, **несёт 100 % сейчас** | источник отката, не удалять |

**Приёмка — три read-back, форма прецедента `2026-08-11`:**
1. `gcloud run services describe cf-facts` → `status.traffic` = `cf-facts-00011-mab`, `100 %`.
2. Сопоставление `core.fact_sales_profit` со снимком `core.fact_sales_profit_snap_20260811_163306`
   по каналам СРАЗУ после перевода — фиксируется как отсечка, ожидание: расхождение равно уже
   известным `36` удалённым строкам и **ни одной новой**.
3. То же сопоставление ПОСЛЕ первого естественного часового `promote` на откаченной ревизии
   (расписание `0 * * * *`, прогон не вызывать вручную) — ожидание: **новых удалённых строк `0`**.
   Дополнительно подтвердить по `resource.labels.revision_name` в Cloud Logging, что запросы
   обслужены `cf-facts-00011-mab`, а не `00014-doh`.

**Откат отката** (если понадобится): та же команда с `--to-revisions=cf-facts-00014-doh=100`.
Пересборка не требуется ни в одну сторону.

**Что НЕ разрешено:** трогать данные `core.fact_sales_profit`; удалять снимок
`snap_20260811_163306` (`ADR-161`); удалять любую из трёх ревизий; сливать ветку код-репо
`deploy/cf-facts-2026-08-11-refresh-window-v2` в `master`; править `transferConfig`, Scheduler,
Workflows; запускать любые `mode=*` прогоны вручную.

**Побочный факт для понимания эффекта:** после отката ветка удаления в коде отсутствует, поэтому
недельный прогон `2026-08-16T01:00Z` пройдёт по прежней логике и удалений не сделает. Именно это
и есть цель шага — снять безнадзорный широкий прогон с повестки.

## §3. Мандат 2 — `SALES-REFRESH-WINDOW-SOURCE-PROBE`, запрос к источнику

**Основание:** владелец, чат 2026-08-12. Постановка — `…defect_adj…§5`.

**Объект:** живые `GET` к `api.moysklad.ru` с секретом `msklad-token`. **Только чтение.** Ни
одной записи ни в одну таблицу, включая `*_staging`. Выход — файлы в `reference/`.

**Вопрос:** живы ли сейчас в МойСклад `29` позиций, удалённых прогоном
`job_id=1e698e3d-35c5-44c2-b90f-fbe852cf39a7`.

**Форма запроса — ВПЕРЁД, и это не стилистика.** Спросить источник про удалённую позицию по её
идентификатору нельзя: в ядре лежит `TO_HEX(MD5(CONCAT(demand_id,'|',position_id)))`
(`bq_ops.py:261`), обратно `demand_id` не достаётся. Поэтому:

1. по каждой паре «дата + контрагент» запросить `entity/demand` этого контрагента за эту дату
   с `expand=positions`;
2. пересчитать `TO_HEX(MD5(CONCAT(demand_id,'|',position_id)))` по каждой полученной позиции;
3. проверить вхождение `29` удалённых идентификаторов в полученное множество:
   - **найден** ⇒ позиция в источнике жива ⇒ выгрузка её потеряла ⇒ **дефект (b1)**;
   - **не найден** ни в одном документе пары ⇒ позиции в источнике нет ⇒ **удаление законно (b2)**.

**Ловушка суток, обязательная к учёту (`ADR-088`).** `transaction_date` есть `DATE(moment + 6ч)`
(Бишкек). Фильтровать `moment` по бишкекской дате напрямую нельзя — потеряются документы
вечерней полосы. Для бишкекской даты `D` окно фильтра по `moment` есть
`[D−1 18:00:00Z ; D 18:00:00Z)`. Наивный фильтр по `D 00:00…23:59` даст ложное «документа нет»,
то есть ложный вывод «удаление законно».

**Ограничения API (`02_ERP_CONTRACTS §поведение API`):** `limit ≤ 100` и обязательная
пагинация — документ с числом позиций больше лимита обязан дочитываться, иначе получим ту же
неполноту, которую расследуем; `sleep 0.25` между вызовами, обработка `429`, `timeout=90`.
Пустой ответ и `401` — гэп наблюдения, не факт (`★ Успех инструмента ≠ факт`).

### Два контроля — условие доверия к выходу, а не пожелание

**Положительный.** В тот же прогон включаются три группы семи сирот `ADR-100 §1`:
`(2026-05-07, b2c49334-f066-11f0-0a80-0c49000a9f1e)`,
`(2026-05-09, deb32c34-990c-11ef-0a80-19eb00083704)`,
`(2026-05-26, b2c49334-f066-11f0-0a80-0c49000a9f1e)`.
Их семь идентификаторов обязаны вернуться **«не найдено»** — их отсутствие в источнике доказано
независимо тремя признаками. Найдётся хоть один ⇒ метод неверен, вердикт по `29` НЕ выносится.

**Отрицательный.** Не менее `10` заведомо ЖИВЫХ позиций, взятых из архива
`archive_106b.ndjson` по тем же парам, обязаны **найтись**. Не нашлись ⇒ запрос собран неверно
(скорее всего окно суток или пагинация), вердикт не выносится.

Оба контроля печатаются в артефакт до вердикта по `29`. Это ровно то, чего не хватило прошлому
ходу и что стоило ложной картины «дефект подтверждён на двух третях остатка».

**Состав пар:** `13` рабочих из `…delete_adj…§4` (`G1`…`G13`) плюс `3` контрольных. Полный
список `29` идентификаторов с датой, контрагентом и суммой — `deleted_29.csv` в
`reference/_scratch_SALES-REFRESH-WINDOW-DELETE-DISCRIMINATE_2026-08-12/`; архив источника
`archive_106b.ndjson` (`7690` записей) там же и переиспользуется без обращения к облаку.

**Что НЕ разрешено:** любая запись в BigQuery; восстановление данных; деплой; слияние ветки;
`POST`/`PUT`/`DELETE` к МойСклад любого вида; расширение объёма за пределы `16` пар.

**Приёмка:** вердикт по каждому из `29` идентификаторов с доказательством (найден/не найден,
в каком документе, сколько позиций получено), плюс результат обоих контролей, плюс поимённый
список строк, удалённых ОШИБОЧНО (кандидаты на восстановление шагом 3). Гипотеза, не
различённая данными, объявляется неразличённой, а не правдоподобной.

## §6. Порядок и что после

Шаги независимы; рекомендую шаг 1 первым — он снимает срок `2026-08-16T01:00Z` и делает
остальное неспешным. Между сессиями — проход сборки (буфер непуст есть стоп-условие старта).

После шага 2 архитектор получает поимённый список ошибочно удалённых строк и ставит шаг 3
(селективное восстановление, класс B, мандат отдельно) и шаг 4 (проверка полноты выгрузки как
предусловие повторного деплоя, класс A).
