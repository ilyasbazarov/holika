## §4. Механизм найден в коде, а не предположен

`helpers.py::paginate_entity` (строки `87-99`) — **обход по `offset`**:

```
offset = 0
while True:
    page_params = {**params, "limit": PAGE_SIZE, "offset": offset}
    ...
    if len(rows) < PAGE_SIZE: break
    offset += PAGE_SIZE
```

Вызов из `fetch_demands.py:71-73` идёт с `order: "moment,asc"`.

Отсюда два факта, каждый проверяем чтением:

1. **Смещение окна при вставке.** Обход по `offset` устойчив только если набор не меняется
   между страницами. Документ, появившийся в наборе НИЖЕ текущего `offset` во время обхода,
   сдвигает всё после себя на одну позицию, и ровно один документ проскакивает мимо страниц.
   При сортировке `moment,asc` новый документ «сегодняшним» временем встаёт в конец и вреда не
   делает — а вот документ с задним числом (создан или отредактирован задним `moment`) встаёт в
   СЕРЕДИНУ. Прогон шёл `04:53:35Z…05:02:08Z`, около девяти минут — окно для такой вставки
   реально. Наблюдение согласуется: пропал ровно ОДИН документ.
2. **Проверки полноты нет вовсе.** `paginate_entity` не читает `meta.size` — число, которое сам
   МойСклад возвращает как общее количество под фильтр. Поэтому недобор страниц **не
   детектируется ничем**: обход завершается «успешно», отдаёт `638` документов вместо `639` и
   рапортует `rc=0`. Это ровно класс `★ Успех инструмента ≠ факт`.

Предохранитель `_assert_staging_covers_merge_window` этого не ловит и по построению не может:
он проверяет КРАЯ окна (`MIN`/`MAX` даты), а здесь края целы — дыра в середине
(`…defect_adj…§6`, теперь подтверждено инстансом).

## §5. Лекарство не изобретается — оно уже работает в этом же репозитории

`cf-finance/invoices.py` (загрузчик счетов, построен по контракту `ADR-110`) делает ровно то,
чего нет у продаж:

```python
if offset == 0:
    meta_size_first = page.get("meta", {}).get("size")
...
def check_completeness(collected, meta_size_first):
    n = len(collected)
    print(f"INVOICES: G1 fetched={n} meta_size_first={meta_size_first}")
    if n == 0:
        raise RuntimeError("G2 FAILED: fetched=0 documents …")
    if meta_size_first is not None and n < meta_size_first:
        raise RuntimeError(f"G1 FAILED: fetched={n} < meta_size_first={meta_size_first} — обход оборван")
```

Три свойства, каждое к месту:
- сравнение `n < meta_size` **отказом**, не предупреждением;
- **`<`, а не `≠`** — документы, созданные во время обхода, законно увеличивают набор; уменьшить
  его может только оборванный обход (докстринг там же);
- оба числа печатаются независимо от исхода (`ADR-044`).

Проверено в бою: `ADR-117` фиксирует `fetched = meta_size = 4526` на боевом прогоне досева.

**Сработала бы эта проверка на нашем случае?** Документ «04235» существовал в источнике задолго
до прогона (он лежал в ядре с мая), значит был учтён в `meta.size` на нулевом смещении, а
пропал в ходе обхода ⇒ `638 < 639` ⇒ **отказ, `MERGE` не исполняется, удаления нет**. Одна
посылка здесь непроверенная — что `meta.size` действительно вернул `639`; она снимается замером
на первом же прогоне с проверкой, а не рассуждением.

**Ключевое следствие:** с этой проверкой ветка удаления становится безопасной по построению —
неполная выгрузка падает ДО `MERGE`. Это и есть тот недостающий предохранитель, который
`…defect_adj…§6` назвал структурно необходимым.

## §6. Что это делает с решением о повторном деплое

Узкая форма фикса (`ADR-144 §8`, решение владельца: «только ветка удаления, режим досева не
строится») **оказалась у́же необходимого**. Ветка удаления опирается на полноту выгрузки как на
предпосылку, а предпосылка не обеспечена и не проверяется. Инцидент это измерил ценой
`1 980 000,00` KGS.

Поэтому порядок меняется: **сначала проверка полноты, потом ветка удаления.** По отдельности
первое безопасно и полезно само по себе (ловит обрывы обхода во всех режимах, включая нынешний
часовой), второе без первого — нет.

Это расширение утверждённого объёма, то есть **решение владельца, а не моё** (§8, развилка 2).

## §8. План: четыре шага и две развилки владельцу

| Шаг | Что | Класс | Состояние |
|---|---|---|---|
| 1 | Откат кода | B | **ИСПОЛНЕН** `2026-08-12`, три read-back чисты |
| 2 | Запрос к источнику | B | **ИСПОЛНЕН** `2026-08-12`, оба контроля пройдены |
| **3** | **Восстановить 2 строки `1 980 000,00` KGS из снимка** | **B** | **мандат нужен — развилка 1** |
| **4** | **Проверка полноты выгрузки по образцу загрузчика счетов** | **A** | **объём нужен — развилка 2** |
| 5 | Повторный деплой ветки удаления вместе с проверкой полноты | B | после `3` и `4`, мандат отдельно |

**Развилка 1 — восстановление двух строк.** Что решаем: возвращать ли в ядро две строки,
удалённые ошибочно. Вариант (a) восстановить из снимка `core.fact_sales_profit_snap_20260811_163306`
точечно по двум идентификаторам — восстанавливает майский паритет, риск минимален, состав
поимённый и проверяемый read-back. Вариант (b) дождаться повторного деплоя и позволить
загрузчику вставить их самому — дешевле по действиям, но неопределён по сроку (документ старше
`7`-суточного часового окна, попадёт только в недельный `90`-суточный прогон) и оставляет
инвесторскую витрину неверной всё это время. **Рекомендую (a)**, потому что срок при (b) не мы
назначаем, а нарушенный паритет — объявленное состояние проекта.

**Развилка 2 — расширение объёма фикса.** Что решаем: остаётся ли в силе «узкая форма, только
ветка удаления» (`ADR-144 §8`). Вариант (a) добавить проверку полноты как обязательного
спутника ветки удаления и деплоить их вместе — устраняет причину, а не следствие; цена — один
небольшой патч по готовому образцу из соседнего загрузчика. Вариант (b) деплоить ветку удаления
как есть — сохраняет утверждённый объём, но осознанно оставляет ту же мину: следующий пропуск
документа снова станет потерей данных, и ловить его будет нечем. Вариант (c) деплоить только
проверку полноты, ветку удаления отложить — устраняет риск и даёт наблюдаемость, но не решает
исходную задачу (сироты продолжают копиться). **Рекомендую (a)**; при нежелании расширять
объём приемлем (c), но не (b).

## §9. Остаточный риск, который заводить задачей нельзя, но назвать обязательно

Значит теоретически возможны документы, которые не доехали в ядро вовсе — пропущенные и часовым

подхватывается следующим (окна перекрываются), а реестр паритета сходился `7/7` на измерениях
против источника. Установить это точно можно только сверкой количеств документов с источником —
работой того же класса, что `ORACLE-AUTOMATION`.

Заводить это отдельной строкой **нельзя**: объём закрытия проекта закрыт к дополнению
(`ADR-156 §1`), новая находка идёт текстом в реестр известных ограничений. Так и поступаю —
текст выше предназначен для `HANDOVER-PACKAGE`, реестр известных ограничений. Проверка полноты
(шаг 4) снимает этот риск вперёд, но не задним числом.
