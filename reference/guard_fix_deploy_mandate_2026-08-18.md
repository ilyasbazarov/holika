Пересечение наборов пусто, но `--source` деплоит каталог целиком: чистота разделения по файлам
не защищает сама по себе. Правило — `ADR-152 §3`, прецедент цены — `ADR-147 §3`.

**Проверка перед деплоем:** `git diff --stat master` в ветке деплоя обязан показать **ровно два
файла**. Три и больше — стоп, не «уточнить по ходу».

## §3. Предусловия (все read-only, ДО деплоя; каждое печатает строки, `ADR-044`)

- **П1 — контракт `run_id` в живых конвейерах (новое, `ADR-188 §2`).** Снять живые
  `sourceContents` обоих Cloud Workflow (`msklad-pipeline-hourly`, `msklad-pipeline-weekly`) и
  предъявить строками с номерами, что `step_promote` **и** `step_perimeter_promote` несут
  `run_id: ${run_id}` в `body`. **Отсутствие хотя бы в одном месте есть СТОП:** фикс
  fail-closed, и деплой остановил бы конвейер на каждом прогоне. Снапшот `2026-08-07` контракт
  подтверждает, но снапшот живым объектом не является.
- **П2 — обслуживающая ревизия.** `gcloud run services describe cf-facts
  --format="yaml(status.traffic)"` — ожидание `cf-facts-00017-jon, percent=100`. Расхождение с
  откатной ревизией есть стоп.
- **П3 — дрейф.** Скачать архив обслуживающей ревизии, распаковать, сверить `sha256` каждого
  файла с `master` код-репо (свежий клон). Любое расхождение есть дрейф и стоп
  (`05_CONVENTIONS §Процедура деплоя` п.1).
- **П4 — гигиена ветки.** Ветка заведена от `master`; `git diff --stat master` — ровно два файла
  (§2); `.gcloudignore` исключает `*.bak`, `__pycache__/`, `*.pyc`, разовые `patch_*.py`
  (`ADR-040`); сплошной поиск секретов по диффу с печатью совпавших строк, пустая выдача фактом
  не является (п.7).
- **П5 — объявление действия.** ОТДЕЛЬНЫМ сообщением в чат до подтверждения владельца: что
  исполняется, на каком объекте, чем откатывается (`ADR-077 §6`, п.5 процедуры).

## §4. Приёмка выкладки

1. **Read-back архива** развёрнутой ревизии: два файла совпадают с веткой по `sha256`,
   посторонних файлов в архиве нет (`ADR-040`). Успех команды деплоя фактом чистоты архива не
   является (`ADR-021 §2`).
2. **Запись «ревизия ↔ коммит»** в `reference/code/cf-facts/MANIFEST.md` по результату read-back
   (п.3 процедуры). Неудачная попытка, если она случится, записывается наравне с удачной (п.8).
3. **Обслуживающая ревизия** после деплоя снята живым съёмом и несёт `percent=100` на новой
   ревизии.
4. **Ручную проверку `promote` не делать** (`ADR-188 §4`): без `run_id` в теле фикс откажет по
   свежести, с произвольной строкой — по разбору. Если проверка всё же нужна, `run_id` обязан
   быть разбираемым (эпоха либо `%Y%m%dT%H%M%S`) И не позже последней загрузки staging.
5. **Ступень 3** закрывается прогоном `2026-08-23`, не этой сессией. Сессия деплоя фиксирует
   ожидание, а не выдаёт его за результат.
6. **Слияние ветки в `master`** — только после успешного read-back (п.1 приёмки). При неуспехе
   ветка не сливается (п.8 процедуры).
