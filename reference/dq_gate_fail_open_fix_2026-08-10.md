## 1. Разбор дефекта (ссылка, не пересказ)

Полный разбор — `reference/dq_gate_fail_open_adj_2026-08-03.md §1/§6`. Требование этой задачи —

первое — ограничение блокировки по длительности — вне scope этой задачи, см. §5 ниже).

Дефект (§6 адъюдикации, дословно): «сторож самоРАЗОРУЖАЕТСЯ. Ветка `ma7 == 0 → passed=True` при
замороженном ядре означает, что после восьми суток блокировки проверка перестаёт проверять и
пропускает данные, ставшие причиной блокировки». `ma7` считается по фактически присутствующим
суткам окна `T-8…T-2` в `core.fact_sales_profit` (`main.py:57-65` до правки); если промоут в это
ядро стоит достаточно долго, окно вычерпывает исторический хвост и `ma7` схлопывается в `0`,
после чего старая ветка возвращала `passed=True` безусловно — именно тогда, когда проверять
нужнее всего.

## 2. Оба случая `ma7 == 0` (§1 брифа)

Число `ma7 == 0` **одним значением** не различает два структурно разных состояния:

1. **Заморозка ядра.** `core.fact_sales_profit` ИМЕЕТ историю (строки в таблице есть), но окно
   `T-8…T-2` относительно текущей даты опустело, потому что промоут остановлен на восемь и более
   суток. Именно этот случай описан в адъюдикации: `MAX(transaction_date)=2026-08-01`
   (`dq_gate_fail_open_adj_2026-08-03.md §1`), таблица не пуста, но со временем окно вычерпывает её
   хвост.
2. **Первый запуск проекта.** `core.fact_sales_profit` НЕ ИМЕЕТ ни одной строки вообще (по
   построению — проект только начал грузиться, базы для сравнения ещё никогда не было). Это
   легитимное состояние, не авария.

Старая ветка не различала эти два случая — оба давали `ma7=0` и оба пропускались молча.

## 3. Выбранная форма и почему отклонены альтернативы

**Выбрано:** различитель — дополнительный `SELECT COUNT(*) FROM core.fact_sales_profit` (без
оконного фильтра, то есть по ВСЕЙ таблице, не по `T-8…T-2`).

- `COUNT(*) == 0` → таблица никогда не имела строк → случай «первый запуск» → `passed=True` с
  явным сообщением-обоснованием (не тихий пропуск: причина названа в `detail`).
- `COUNT(*) > 0` → таблица имеет историю, но окно `T-8…T-2` пусто → случай «заморозка» →
  `passed=False` с явным сообщением, отличным от прежнего «нет истории → пропуск».

**Почему не «просто заменить `True` на `False`» (первый вариант из брифа §2, п.1).** Такая замена
закрывает случай заморозки, но создаёт новый немой тупик у случая «первый запуск»: свежепосеянный
проект без единой строки в `core.fact_sales_profit` начал бы получать перманентный
`passed=False` без возможности отличить эту ситуацию от аварии — то же самое немое поведение,
которое конституция проекта (`00_CHARTER §главный принцип`, `_METHOD §11`) запрещает как замену
одного тихого блока другим. Бриф прямо требовал проверить эту альтернативу и решить, если тупик
создаётся — он создаётся, поэтому взят различитель, а не безусловный `False`.

**Почему не оставить как есть / не звать `DQ-GATE-METRIC-REDESIGN`.** Задача `DQ-GATE-METRIC-REDESIGN`
(`07_GAPS.md:76`) решает другую проблему — метрика `drift_check` отождествляет «почти не продавали»
(легитимные тихие дни) с «данные испорчены»; это калибровка метрики на НЕПУСТЫХ данных. Эта же
задача — не про калибровку значения, а про структурно иное состояние (`ma7` буквально
неопределимо, делить не на что), решение которой не пересекается с переделкой метрики (форма той
задачи не назначена и не предрешается этой правкой).

**Почему различитель — `COUNT(*)` по всей таблице, а не что-то другое.** Это самый дешёвый и точный
сигнал «была ли хоть одна строка когда-либо» — не требует дополнительных источников (сравнивать
staging с core через уже читаемый `CORE_FACT`), не вводит новых зависимостей, не трогает остальные
пять чеков. Альтернатива «проверить `MAX(transaction_date) IS NULL`» эквивалентна по смыслу
(`COUNT(*)=0 ⟺ MAX(transaction_date) IS NULL` для этой таблицы), выбран `COUNT(*)` как более прямой
для читателя кода.
