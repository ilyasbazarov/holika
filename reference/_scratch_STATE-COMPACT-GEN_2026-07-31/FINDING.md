# Проба «где скрипт-загрузчик 2026-06-05 для core.fact_customer_invoices» — результат

**Дата:** 2026-07-31 (Бишкек) · **Замер:** `2026-07-31T13:48:25Z…13:52:54Z` (см. `run.log`, `run2.log`)
**Повод:** `07_STATE §Текущий фокус` ставил это прямым вопросом владельцу; вопрос частично снимаем
замером (`ADR-056`: вопрос, снимаемый замером, не задаётся). Класс A: read-only, ничего не пишет.

## Установлено фактом

1. **На локальной машине владельца (macOS) загрузчика нет.** Файлов `*.ndjson`/`*.jsonl` во всём
   домашнем каталоге (кроме служебных логов Claude Code) — ноль. Поиск по содержимому `Desktop`,
   `Downloads`, `Documents` по `invoiceout` / `fact_customer_invoices` даёт только документацию
   проекта и `sq_marts_customer_invoices_ar.sql` (витринный SQL, не загрузчик).

2. **На диске Cloud Shell загрузчика нет.** Файлов `*.ndjson`/`*.jsonl` во всём `$HOME` — ноль
   (вывод `find` пуст, `run.log`). Файлов с mtime `2026-06-05` — только четыре debug-лога npm.
   Файлов со словом `invoice` в имени — один, витринный SQL. В `.bash_history` (576 строк) ни одной
   строки с `bq load`, `ndjson`, `invoice`, `load_`.

3. **Найден СОСЕДНИЙ загрузчик того же класса — `~/load_payments.py` (Cloud Shell, mtime 2026-06-18),**
   полный текст сохранён в `load_payments_cloudshell_2026-06-18.py`. Он воспроизводит ровно ту
   последовательность, которую `SOURCE-MAP-INVOICES` восстановила по истории заданий BigQuery:
   - `GET api.moysklad.ru/api/remap/1.2/entity/<type>?expand=…&limit=1000` с пагинацией по `nextHref`;
   - сборка плоских записей в память, `_loaded_at` проставляется в Python ДО загрузки;
   - `bigquery.Client.load_table_from_json(records, core.fact_*_stg,
     source_format=NEWLINE_DELIMITED_JSON, write_disposition=WRITE_TRUNCATE)`;
   - `MERGE` из `_stg` в `core.fact_*` с ЯВНЫМ списком колонок в `INSERT` (соответствует `C1`/`ADR-030`).

   **Это объясняет наблюдение `source_map_invoices_2026-07-30.md §4` точнее прежней трактовки.** Там
   отсутствие `sourceUris` в конфигурации `LOAD`-задания было прочитано как «`bq load` локального
   файла». `load_table_from_json` даёт ту же картину (нет `sourceUris`, `inputFiles=1`), но NDJSON
   при этом **никогда не существует как файл на диске** — клиентская библиотека сериализует список
   словарей и грузит его потоком. Если счета грузились этим же приёмом (а форма задания совпадает),
   то **искать файл NDJSON бессмысленно по построению: его не было**. Пункты 1–2 выше согласуются
   с этим объяснением.

## Что НЕ установлено

Сам скрипт-загрузчик счетов (`entity/invoiceout` → 14 колонок) не найден ни на одной из двух
проверенных машин. Проверены только эти две; другие устройства владельца, Colab и Google Drive
не проверялись. `.bash_history` Cloud Shell ограничен по длине и события начала июня в него не
попадают — отсутствие следа там не есть доказательство отсутствия события.
