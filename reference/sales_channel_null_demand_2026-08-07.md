## 3. Проверка ветки `entity/demand` — метки периметра отсутствуют

Все 40 строк дают `sales_channel_name = NULL` в группировке; ни одна строка не несёт метку
`«Розница»` или `«Комиссия»`:

```
sales_channel_name | n_rows
NULL                | 40
```

Метки периметра (`ADR-134`) — константы, которые `bq_ops.py:527` (`MERGE_PERIMETER`,
`WHEN MATCHED THEN UPDATE SET T.sales_channel_name = S.sales_channel_name`) проставляет ВСЕГДА
из staging и никогда не оставляет `NULL` (сам патч не читает реальный `salesChannel`, но
записывает константу безусловно). Следовательно `NULL` у этих 40 строк не мог прийти из ветки
периметра (`entity/retaildemand`/`entity/commissionreportin`) — они лежат в основной ветке
`entity/demand`, как и требует приёмка.

## 4. `fetch_demands.py` — как извлекается `salesChannel` и где поле окажется пустым

Файл: `reference/code/cf-facts/fetch_demands.py`.

```
104:        sc_href = demand.get("salesChannel", {}).get("meta", {}).get("href", "")
105:        sc_id   = parse_href(sc_href) if sc_href else None
106:        sc_name = channel_map.get(sc_id) if sc_id else None
```

`channel_map` строится ОДИН раз до цикла по документам (строки 23–26, 56):

```
23:def _fetch_sales_channel_map(token: str, session: requests.Session) -> dict:
24:    """Build {uuid: name} map for all sales channels."""
25:    rows = paginate_entity(token, "entity/saleschannel", session=session)
26:    return {row["id"]: row.get("name") for row in rows}
```

Список продаж (`entity/demand`) читается БЕЗ `expand` (строки 68–76) — поле `salesChannel`
приходит (или не приходит) как есть, тем же ответом list-режима, которым приходит и заголовок
документа; список-запрос не запрашивает и не ограничивает состав полей явно.

**Два теоретически различимых механизма потери, и они РАЗЛИЧЕНЫ измерением (§5 ниже):**
(a) `sc_href` пуст → строка 104 не находит `demand["salesChannel"]["meta"]["href"]` — сам ключ
`salesChannel` отсутствует в ответе МойСклада на данный документ, ЛИБО присутствует без `meta`;
(b) `sc_href` непуст, но `sc_id` не резолвится в `channel_map` (строка 106) — `entity/saleschannel`
не вернул этот канал (устаревший кэш, гонка пагинации, архивный канал вне выдачи).

## 5. Различитель (a) vs (b) — измерением, не рассуждением

`sales_channel_id` у ВСЕХ 40 строк тоже `NULL`, не только `sales_channel_name`:

```
id_state    | n_rows
id_NULL     | 40
```

Если бы дефект был механизмом (b) (пропуск в `channel_map`), `sales_channel_id` был бы заполнен
(строка 105 резолвит `sc_id` из `sc_href` независимо от `channel_map`), а пустым оказался бы
только `sales_channel_name`. Наблюдается обратное: `sc_id` тоже `NULL`, что по построению строки
104–105 означает `sc_href` был пуст изначально — **механизм (b) опровергнут, механизм (a)
подтверждён**: у этих 40 строк объект `demand`, полученный из ответа списка `entity/demand`, не
нёс поля `salesChannel` (либо не нёс вложенного `meta.href`) на момент загрузки.

## Вердикт

**Точка потери названа частично: механизм внутри нашего кода определён (`fetch_demands.py:104`,
`sc_href` пуст → `sales_channel_id`/`sales_channel_name` оба `NULL`, кэш `channel_map` из
рассмотрения исключён измерением §5), но ПОЧЕМУ ответ list-режима `entity/demand` не нёс поле
`salesChannel` для именно этих 40 строк — с нашей стороны неразличимо оставшимся способом.**

Источник (`/reference/oracle_july_2026_2026-08-07.md §1`) подтверждает: канал у этих документов
заполнен (корзины «канал не указан» за июль нет, канал «ОФИС» имеет нулевой оборот) — то есть на
стороне МойСклада поле не пусто. Значит расхождение не в парсинге (парсер отработал правильно на
том, что получил) и не в кэше справочника каналов (опровергнуто §5) — а в том, что именно вернул
`GET entity/demand` в момент загрузки. Различить «список-режим МойСклада систематически не
отдаёт `salesChannel` для части документов» от «канал был назначен ПОСЛЕ первой загрузки, а
повторный забор эти сутки не задел» нашими данными нельзя: у нас нет истории изменений документа,
только текущий срез `channel_map` и разовый снимок `demand`.

**Требуется одно из:** живой `GET entity/demand/{id}` на одном из 40 документов с текущим
состоянием канала (класс B, мандат не выдан) — совпадёт с `NULL` сейчас же, значит поле пусто и
у источника ПРЯМО СЕЙЧАС (хотя за июль оборот был), не совпадёт — подтвердит, что список-режим
терял поле на моменте загрузки; **либо** взгляд владельца на один конкретный документ в
интерфейсе МойСклад (любой транзакции из §1, например `transaction_id`
`d0b83f495f4580647aa83c403a7cce6e`, `2026-07-02`, контрагент `178ba7b4-87c0-11ef-0a80-1568002f4222`)
— поле «Канал продаж» в карточке документа.

**Оговорка приёмки удержана:** отчёт МойСклада мог бы не показывать пустую группу вовсе — тогда
вывод «теряется у нас» не следует из одного лишь замыкания итога. Настоящий вердикт на эту
оговорку не опирается единолично: он строится на разнице `sales_channel_id` vs
`sales_channel_name` внутри НАШИХ данных (§5), которая не зависит от полноты отчёта источника.
Форма фикса НЕ назначается этим документом (правка — отдельная задача по факту вердикта, как
требует приёмка).
