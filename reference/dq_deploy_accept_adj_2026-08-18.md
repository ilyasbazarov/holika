## §7 Гэп по `weight_flow` ЗАКРЫТ входом владельца — третий мандат разгейчен

**Вход (владелец, чат 2026-08-18).** Источник `weight_flow` в Looker Studio несёт ровно восемь
измерений — `flow_date`, `flow_direction`, `month_start`, `positions_total`,
`positions_with_weight`, `week_start`, `weight_coverage_pct`, `weight_kg` — плюс автоматическую
метрику `Record Count`.

**Сверка с живой схемой.** `reference/schema_dump_2026-07-28.md:537-548` даёт у `marts.weight_flow`
ровно восемь колонок теми же именами и в том же составе. **Список полей источника совпадает со
схемой таблицы один в один.**

**Вывод.** Источник хранит ЯВНЫЙ поимённый список полей, а не позиционный доступ и не «все поля
схемы». Отсюда три следствия, каждое снимает свою часть гэпа
(`marts_build_stamp_prep_2026-08-13.md §3`):

- (а) **Подхватываются ли новые колонки автоматически** — вопрос перестаёт быть блокирующим:
  какой бы ни был режим, две новые колонки могут только ДОБАВИТЬСЯ к списку из восьми. Ни одно из
  восьми имён от этого не меняется, не сдвигается и не исчезает.
- (б) **Сломается ли элемент страницы** — нет: все восемь полей адресуются по имени, элемент,
  чувствительный к появлению новых полей, требовал бы позиционного доступа либо агрегации «по
  всем полям», а `Record Count` считает строки и от состава колонок не зависит.
- (в) **Нужен ли ручной снимок графиков по прецеденту `msklad_inventory_latest`** — не нужен:
  тот прецедент опасен именно `SELECT *`, здесь список полей предъявлен и он закрытый.

**Возражение архитектора снимается. Условие владельца («нет критических возражений») выполнено и
по третьему объекту.**

- **`7г3` — `sq_marts_weight_flow`, Config ID `6a1f9418-0000-276f-a1e4-d4f547ee7418`: мандат ВЫДАН**
  (владелец, чат 2026-08-18; условие выполнено после закрытия гэпа входом владельца).
  Форма, предусловия, приёмка и откат — те же, что §5, без изменений.

**Отдельное предупреждение по этому объекту, не отменяющее мандата.** Финальная строка живого
запроса — `SELECT * FROM outbound UNION ALL SELECT * FROM inbound`, то есть склейка ПОЗИЦИОННАЯ.
Две колонки обязаны быть добавлены в ОБА CTE в одинаковом порядке, иначе склейка либо не
соберётся, либо сложит разные величины. Подготовленный текст это условие выполняет — доказательство
не в чтении, а в том, что `bq query --dry_run` прошёл (`marts_build_stamp_prep_2026-08-13.md §2`):
BigQuery проверяет арность и типы `UNION ALL` на этапе валидации. Исполнителю: не пересобирать
текст самостоятельно, применять подготовленный файл как есть.

## §8 Наблюдение по данным владельца: `weight_coverage_pct` агрегируется суммой

В присланных настройках у поля `weight_coverage_pct` (доля позиций с заполненным весом, проценты)
стоит агрегирование по умолчанию **«Сумма»**. Сумма процентов по строкам величины не имеет: при
двух строках по `60 %` источник отдаст `120 %`. Поле рассчитывается в запросе построчно
(`sq_marts_weight_flow.sql:24,42`), поэтому корректная агрегация — среднее, а лучше взвешенное
(`SUM(positions_with_weight)/SUM(positions_total)`).

Дефект предметный и предшествует нашей правке: отметка времени сборки его не создаёт и не чинит.
По `ADR-156 §2/§5` он НЕ заводит строку реестра и уходит текстом в
`reference/handover_limitations.md` вместе с проверкой владельца, использует ли хоть один элемент
страницы «Склад» это поле напрямую. Записано наблюдением (`ADR-107 §4`).
