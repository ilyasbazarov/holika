## (2) Контроль полноты построчного эталона `reference/oracle_july_2026_employees_2026-08-07.pdf`

**Метод.** Текстовый слой страниц `1–7` извлечён утилитой `pdftotext` (не ручная транскрипция,

результат. Скрипт и код разбора — `_scratch/parse_pdf.py`, сырой текстовый слой —
`_scratch/pdf_pages_1-7.txt` и `_scratch/pdf_pages_1-7_raw.txt`.

**Контроль А — число строк.**

|---|---|---|
| Строк-отгрузок | `243` | `243` |
| Строк-возвратов | `1` | `1` |
| Итого строк | `244` | `244` |

**Контроль А: СОШЁЛСЯ.** Независимая перепроверка построчным `grep -c` по каждой из 7 страниц
отдельно: `29 + 40 + 40 + 40 + 40 + 40 + 15 = 244` — совпадает.

**Контроль Б — сумма отгрузок.**

| Величина | Требуется (`ADR-138 §3`, `oracle §1`) | Получено из PDF |
|---|---|---|
| Сумма отгрузок, KGS | `108 989 733,88` | **`108 989 733,92`** |

**Контроль Б: НЕ СОШЁЛСЯ.** Расхождение `+0,04` KGS (`108 989 733,92 − 108 989 733,88`).

**Сумма возвратов, для справки (не часть двух обязательных контролей, но независимая
перекрёстная проверка):** `62 709,00` KGS — совпадает с `oracle §1` (канал «Оптовая торговля»,
возвраты) и с `oracle §3` (документ `№ 00008`) **точно**, расхождения нет.

**Проверка на артефакт парсинга.** Расхождение `0,04` KGS воспроизведено ДВУМЯ независимыми
методами извлечения текста (`pdftotext -layout` и `pdftotext` без флага, разный алгоритм
раскладки колонок) и суммированием через `Decimal` (не `float`, чтобы исключить погрешность

аномальным форматом числа (пробел как разделитель тысяч, слипшиеся колонки) не найдена: парсер
сообщил `0` нераспознанных строк, похожих на строки данных. Само по себе воспроизведение на двух
методах не доказывает, что ошибки нет в PDF или в отчёте-источнике `§1` — только что ошибки нет
в извлечении текста.

## Промежуточный стоп и его снятие

**СТОП по тексту задачи (`ADR-138 §3`, дословно): «Расхождение любого из двух контролей есть
СТОП с предъявлением чисел, а не повод округлить или продолжить.»**

- Контроль числа строк — сошёлся (`244 = 244`).
- Контроль суммы отгрузок — **не сошёлся**: `108 989 733,92` (PDF) против `108 989 733,88`
  (`oracle §1`), разница `+0,04` KGS.

**Снято владельцем в чате 2026-08-08:** «0,04 сом это округление отчёта, продолжай на этом же
PDF». Причина расхождения этой сессией не установлена (не парсинг — воспроизведено двумя
независимыми методами извлечения текста), решение принято владельцем как есть. Шаги (3)/(4)
ниже исполнены на том же PDF без повторной выгрузки.

## (4) Вердикт: локализация по суткам и проверка кандидатов K1–K4

**Двадцать пять из тридцати суток дают Diff в пределах `±0,01` KGS** (округление отчёта/`FLOAT`,
не предмет разбора). **Весь содержательный остаток сидит на пяти сутках:**

| Дата | Diff, KGS | Доля остатка |
|---|---|---|
| 2026-07-30 | 100 601,997 | 56,5 % |
| 2026-07-21 | 27 019,20 | 15,2 % |
| 2026-07-27 | 22 543,92 | 12,7 % |
| 2026-07-13 | 15 180,00 | 8,5 % |
| 2026-07-11 | 4 950,00 | 2,8 % |
| 2026-07-29 | 3 833,98 | 2,2 % |
| 2026-07-02 | 2 538,01 | 1,4 % |
| 2026-07-20 | 1 457,30 | 0,8 % |

### K1 (сироты в слепом окне 19 суток) — ПОДТВЕРЖДЁН, объясняет ровно три сутки

Даты кандидатов из шага (1) (`_loaded_at < 2026-07-19`, `_scratch/step1b_run.log`) —
`2026-07-02`/`2026-07-11`/`2026-07-13` — **совпадают день-в-день** с тремя сутками локализации
выше, и их суммы совпадают **до цента**: `2 538,0108` = `2 538,01`; `4 950,0000` = `4 950,00`;
`15 180,00` = `15 180,00`. Итого К1 закрывает `22 668,0108` KGS — те же `8` строк, что и на шаге
(1). **Это независимое подтверждение К1 вторым методом** (первый — принадлежность ветке
`entity/demand`, `SALES-JULY-RESIDUAL-SPLIT` шаг (3); второй — точное совпадение суточной суммы с
PDF-эталоном день-в-день). accepted как факт.

### Проверка K1-остатка: пять оставшихся суток (`155 456,41` KGS) НЕ являются сиротами

Ни одна из пяти дат (`07-20`, `07-21`, `07-27`, `07-29`, `07-30`) не входит в список кандидатов
шага (1) (`_scratch/step1b_run.log` содержит только 8 строк на трёх датах выше). Следовательно К1
исчерпан этими тремя сутками и дальше не расширяется — оставшиеся `155 456,3693` KGS (`178
124,3801 − 22 668,0108`) требуют другого механизма.

### Поиск документа/пары документов PDF, дающих разницу суток (обязательный пункт приёмки)

**Метод** (`_scratch/step4c_doc_match_search.py`): для каждой из пяти дат искомая величина Diff
ищется (допуск `±0,05` KGS) среди суммы ОДНОГО документа PDF (по всему июлю, не только этой дате
— проверка гипотезы «документ учтён на другую дату») и среди суммы ЛЮБОЙ ПАРЫ документов PDF (по
всему июлю, `C(243,2) ≈ 29 千`).

**Результат: ни для одной из пяти дат совпадение не найдено** — ни одиночное, ни парное.
`155 456,3693` KGS не собирается ни из одного, ни из двух документов, присутствующих где-либо в
эталоне за июль.

### K3 (замороженная дата, `transaction_date` не обновляется при `MATCH`) — не подтверждён и не опровергнут этим методом

Если бы K3 объяснял пять дат сдвигом документа МЕЖДУ сутками ВНУТРИ июля, соответствующий документ
нашёлся бы в PDF на другой дате того же месяца тем же поиском — он не нашёлся. Но K3 также
предсказывает случай, когда документ `moment` сдвинулся ЗА пределы июля (в август), — тогда его
не будет в июльском PDF вовсе, и поиск внутри месяца в принципе не мог бы его найти. **Оба
исхода поиска (документ найден внутри месяца / документ отсутствует в PDF) совместимы с разными
ветвями K3**, поэтому этот замер K3 не различает. Различитель требует истории `moment` документа
или прямого обращения к источнику (класс B, живой вызов) — вне границ этой задачи («живых вызовов
к МойСкладу нет»).

### K2 (черновики без фильтра `applicable`) — не подтверждён и не опровергнут этим методом

`core.fact_sales_profit` не несёт поля `applicable`/`moment` (проверено `bq show --schema`,
полный список 22 колонки — `_scratch/` истории вызовов сессии). Документ, отсутствующий в PDF
целиком (не найденный ни на одной дате поиском выше), одинаково хорошо объясняется ЛИБО
черновиком, не попадающим в отчёт «Прибыльность» (K2), ЛИБО документом K3, чей `moment` ушёл в
август. **Различитель между K2 и K3 недоступен в `core.fact_sales_profit`** — нужен join по
`demand_id`/`applicable`, которого таблица не несёт (`ADR-104 vi`: `transaction_id` есть
`MD5(demand_id + position_id)`, сам `demand_id` не хранится отдельно).

### K4 (`COMMISSION_CHANNEL_AGENT_IDS` неполон для июля) — ослаблен на самой крупной дате, не проверен на прочих

Разбивка по `agent_id` для всех пяти дат (`_scratch/step4b_agent_breakdown.sh` →
`step4b_run.log`) не даёт ни одного контрагента, чья сумма за день совпадает с Diff этого дня.
На `2026-07-30` (крупнейший Diff, `100 601,997` KGS) выручка размазана по `12` контрагентам, у
крупнейшего — `1 986 390,00` KGS (не совпадает и не является видимой долей остатка). Гипотеза
«один контрагент, ставший комиссионным в июле» ПРЕДСКАЗЫВАЕТ концентрацию на одном `agent_id`
величиной около Diff — этого не наблюдается на самой крупной дате. **K4 ослаблен как ЕДИНСТВЕННОЕ
объяснение крупнейшей даты**, но не проверялся как частичный вклад на остальных четырёх, и полное
опровержение потребовало бы сопоставления `agent_id` с живым списком комиссионных контрагентов
июля (класс B, вне границ задачи).
