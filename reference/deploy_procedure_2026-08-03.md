# `DEPLOY-PROCEDURE` — процедура деплоя Cloud Function «только из код-репо»

**Дата:** 2026-08-03 (Бишкек) · **Роль:** архитектор · **Класс задачи:** A (текст процедуры, ничего не
исполняет и не деплоит)
**Основание:** `ADR-065` объявил инвариант «деплой любой CF — только из код-репо; ревизия ↔ коммит» и
оставил форму процедуры owner-gated. Форма выбрана владельцем 2026-08-03 — **вариант Б** (отдельная
ветка, слияние в основную только после успешной проверки развёрнутого архива). Разбор развилки и
альтернатив — `reference/deploy_order_adj_2026-08-03.md §3`.
**Статус:** текст готов, ни разу не применён. Первое применение — `INVOICES-LOADER-DEPLOY`, оно же
приёмка процедуры.

---

## §1 Что фиксируется и зачем

**Инвариант:** основная ветка код-репо в любой момент равна тому, что стоит в проде. Не «должна быть
равна», а равна — потому что коммит попадает в неё только после того, как развёрнутый архив прочитан и
сверен.

Причина выбора формы: проект уже дважды платил за расхождение документов с продом (`Q-44`: доки несли
`00006-piv` против живой `00012-cik`; `Q-45`: два независимых подтверждения одного и того же фикса).
Вариант «коммит сразу в основную ветку, потом деплой» узаконивает это расхождение на время между
коммитом и удачным деплоем, а при неудачном деплое — до ручного отката. Вариант Б делает состояние
основной ветки проверяемым свойством, а не обещанием.

**Что процедура НЕ решает:** она не заменяет провенанс-снапшоты `/reference/code/` (`ADR-017`) и не
отменяет гигиену архива (`ADR-040`) — оба встроены в шаги ниже.

## §2 Факты об объекте, от которых процедура построена

| Факт | Значение | Провенанс |
|---|---|---|
| Код-репозиторий | `https://github.com/ilyasbazarov/holika-prod` | `reference/code_repo_2b_confirm_2026-08-03.md` |
| Ветка по умолчанию | **`master`**, не `main` | там же, `§(v)` |
| Видимость | публичный (решение отложено владельцем) | строка реестра `CODE-REPO-VISIBILITY` |
| Раскладка | каталог на функцию: `cf-finance/`, `cf-facts/`, `cf-dq/` | `reference/code_repo_seed_rest_2026-08-03.md §5` |
| Текущее содержимое | seed из архивов ЗАДЕПЛОЕННЫХ ревизий, ни одного недеплоенного патча | там же |
| Регион всех функций | `asia-east1` | `11_INFRA_FACTS`, подтверждён замерами |

**Наблюдение, а не назначение:** в снапшоте `cf-facts` лежит рабочий деплой-скрипт
`reference/code/cf-facts/deploy_and_workflow.sh`, и форма команды в нём такова:

```
gcloud functions deploy cf-facts \
  --gen2 --runtime=python312 --region=asia-east1 \
  --source=cf/cf_facts --entry-point=main \
  --service-account=etl-sa@msklad-bi-prod.iam.gserviceaccount.com \
  --memory=2048MB --timeout=540s ...
```

Значение `--source` в нём указывает на раскладку рабочего каталога Cloud Shell (`cf/cf_facts`), а не на
раскладку код-репо (`cf-facts/`). **Процедура ниже требует, чтобы `--source` указывал на каталог функции
в выкаченной ветке код-репо, и ни на что другое** — иначе инвариант «ревизия ↔ коммит» не выполняется,
как бы аккуратно ни был сделан коммит. Прочие параметры команды берутся из существующего скрипта и этой
процедурой не переопределяются: их источник — задеплоенная конфигурация, а не догадка.

## §3 Процедура

Шаги 0–3 и 6–8 — класс A. Шаг 5 (собственно деплой) — класс B, требует поимённого мандата и
подтверждения владельца. Шаг 4 обязателен и предшествует подтверждению.

### Шаг 0 — предусловия

- Мандат класса B на этот деплой выдан поимённо отдельным ADR (форма — `ADR-092`/`ADR-108`).
- Известна текущая задеплоенная ревизия функции и её `generation`.
- Рабочее дерево сессии чистое, буфер разобран (`bash tools/session_status.sh`).

### Шаг 1 — свежий снапшот задеплоенного и сверка с основной веткой

Снять архив исходников ЖИВОЙ ревизии и сверить его с `master` код-репо побайтово:

```
gcloud functions describe <cf> --gen2 --region=asia-east1 --project=msklad-bi-prod
gsutil cp gs://<bucket>/<cf>/function-source.zip#<generation> <scratch>/
shasum -a 256 <файлы>
```

- Совпало — идём дальше.
- **Не совпало — СТОП.** Это дрейф: в проде стоит не то, что записано в основной ветке. Деплой поверх
  дрейфа затрёт чужую правку молча. Расхождение разбирается отдельно, до деплоя.

Основание отдельным шагом: успех команды деплоя фактом чистоты не является (`ADR-021 §2`), и ровно
этим приёмом уже было поймано, что снапшот `cf-finance` отставал на шесть ревизий.

### Шаг 2 — ветка и перенос патча

```
git checkout master && git pull
git checkout -b deploy/<cf>-<YYYY-MM-DD>-<тема>
```

Патч переносится **по diff, а не копированием файлов** подготовленного снапшота: подготовка могла
делаться против более старой ревизии. Проверяется `.gcloudignore` — `*.bak`, `__pycache__/`, разовые
patch-скрипты исключены (`ADR-040`, условие деплоя, не пожелание).

### Шаг 3 — коммит в ветку и выкладка ветки

Коммит с сообщением вида `<cf>: <что меняет> (задача <ID>)`. `git push` ветки — исходящее действие,
подтверждается владельцем (`ADR-076 §1`). **Основная ветка на этом шаге не трогается.**

### Шаг 4 — объявление действия отдельным сообщением

До любого подтверждения исполнитель отдельным сообщением в чат называет три вещи (`ADR-077 §6`):
**что именно исполняется, на каком объекте, чем откатывается.** Откат называется конкретной
предыдущей ревизией по имени, а не словом «откатим».

### Шаг 5 — деплой *(класс B)*

Одна команда, отдельным пастом, не в связке с диагностикой (`ADR-055 §2`). Доставка — файлом, запуск с
редиректом в лог (`ADR-055 §1`). `date -u` и `gcloud auth list` — первой И последней командой скрипта
(`ADR-055 §4`, `ADR-063 §4`), чтобы деградация авторизации посреди прогона была детектируемой.
`--source` указывает на каталог функции в выкаченной ветке.

Обрыв или timeout — **слепой retry запрещён** (`05_CONVENTIONS` Часть I): сначала read-only
`describe`/`list`, затем доисполнение только недостающего хвоста.

### Шаг 6 — read-back развёрнутого архива

Не «команда вернула OK», а чтение того, что реально развернулось:

1. `describe` новой ревизии — имя ревизии, `generation` архива;
2. архив скачивается и распаковывается, `shasum -a 256` по всем файлам;
3. сверка с содержимым ветки — побайтово;
4. проверка отсутствия мусора в архиве (`ADR-040`).

Любое расхождение — деплой считается неуспешным, ветка НЕ сливается.

### Шаг 7 — функциональная проверка

Определяется задачей, а не этой процедурой: прогон функции и чтение лога, либо проверка целевой
таблицы. Задача не считается выполненной без подтверждённого лога реального прогона
(`05_CONVENTIONS` Часть I, модель исполнения).

### Шаг 8 — слияние в основную ветку и запись соответствия

**Только теперь:**

```
git checkout master && git merge --no-ff deploy/<cf>-<YYYY-MM-DD>-<тема>
git push origin master
```

Тем же шагом в `reference/code/<cf>/MANIFEST.md` записывается: имя ревизии, `generation` архива,
sha256 файлов, дата в UTC, SHA коммита код-репо. **Это и есть фиксация «ревизия ↔ коммит»** — запись
по результату проверки, а не сообщение команды деплоя.

### Шаг 9 — неуспех

Ветка не сливается. Откат — деплой предыдущей ревизии, названной на шаге 4. Неудачная попытка
записывается в `MANIFEST.md` наравне с удачной: ревизия, время, что пошло не так. Ветка сохраняется
как провенанс, не удаляется.

## §4 Инварианты и запреты

1. **В основной ветке нет ни одного коммита, не прошедшего шаг 6.** Это единственный смысл варианта Б;
   нарушение обесценивает процедуру целиком.
2. **`--source` — только каталог функции выкаченной ветки.** Деплой с рабочего каталога машины
   нарушает `ADR-065` независимо от аккуратности коммита.
3. **Секреты в репозиторий не попадают.** Репозиторий публичный; функции читают секреты из Secret
   Manager, и сегодня это верно по факту — правило записывается здесь, чтобы оставаться верным дальше.
   Проверка перед шагом 3 — сплошной поиск по патчу; пустая выдача поиска фактом не является
   (`05_CONVENTIONS` Часть I), поэтому печатаются совпавшие строки, а не метка.
4. **Один скрипт на шаг, диагностика и действие раздельно** (`ADR-055 §2`).
5. **Провенанс-снапшот `/reference/code/` не отменяется** (`ADR-017`): он остаётся копией для чтения в
   `holika`, код-репо остаётся источником деплоя.

## §5 Чек-лист (короткая форма для брифа)

```
[ ] 0  мандат класса B выдан поимённо; дерево чистое
[ ] 1  снапшот живой ревизии снят и побайтово сверен с master (расхождение = СТОП)
[ ] 2  ветка deploy/<cf>-<дата>-<тема>; патч перенесён по diff; .gcloudignore чист
[ ] 3  коммит в ветку; push ветки подтверждён владельцем; master не тронут
[ ] 4  объявление в чат: что / на каком объекте / чем откатывается
[ ] 5  деплой одной командой, отдельным пастом, лог в файл, UTC-якорь в начале и в конце
[ ] 6  read-back архива: ревизия, generation, sha256 всех файлов, мусора нет
[ ] 7  функциональная проверка по задаче, лог подтверждён
[ ] 8  merge --no-ff в master; запись ревизия↔коммит в MANIFEST.md
[ ] 9  при неуспехе: ветка не слита, откат на названную ревизию, запись в MANIFEST.md
```

## §6 Что этой задачей НЕ сделано

- Процедура ни разу не применена; её приёмка — первый деплой (`INVOICES-LOADER-DEPLOY`).
- Параметры команды деплоя для `cf-finance` и `cf-dq` не снимались: в репо есть готовый скрипт только
  для `cf-facts`. Перед первым деплоем каждой функции её параметры берутся из задеплоенной
  конфигурации (`describe`), а не переносятся с соседней функции.
- Автоматизация процедуры (скрипт, оборачивающий шаги 1–8) не пишется: сначала процедура должна пройти
  один живой цикл, иначе автоматизируется непроверенное.
