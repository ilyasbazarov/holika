## 2. Находка: Custom Query — источник, а не поверхность

Владелец сообщил состав графика, сидящего на источнике `msklad_counterparty_returns` (страница
«Операционка», единственный график на этом источнике — «Топ контрагентов»):

> Контрагент · Страна · Развернуть · Показатель · Выручка (KGS) · Маржа (KGS) · % от общего дохода

**Колонок возвратов среди отображаемых нет.** Запрос считает `return_sum_kgs`, `net_revenue_kgs` и
`return_rate_pct` — ни одна из трёх не выведена ни на один график дашборда. То есть **возвраты в
разрезе по контрагенту не имеют видимой поверхности вообще.**

**Что из-за этого было записано неверно.** `reference/parity_registry.md` строка 20 и
`07_GAPS.md` строка `Q-79` называли поверхностью BI этой пары **Custom Query**
`msklad_counterparty_returns`. Custom Query есть источник данных; поверхностью является график.
Состав полей графика ни разу не снимался — инвентарь `reference/ls_custom_queries_2026-07-30.md`
снимал поля только для `msklad_inventory_latest` (семь графиков страницы «Склад») и прямо
оговаривал, что поля остальных не снимались.

**Класс дефекта тот же, что у `CODE-REPO-2B-CONFIRM` сутками ранее:** в реестре записан заместитель
факта, а не факт, и никто не проверил заместителя на соответствие. Там — «действие за владельцем»
вместо состояния объекта; здесь — «источник данных» вместо нарисованной поверхности. Второй инстанс
за двое суток; наблюдение дописывается в уже заведённую строку `GATE-STATE-VERIFIABILITY`, отдельная
строка не заводится (`ADR-051 §2`, плюс заморозка `ADR-107 §4`).

## 3. Адъюдикация (архитектор)

**Поверхность пары «Возвраты покупателей» переназначается** с `msklad_counterparty_returns`
(«Операционка») на блок возвратов в Executive summary, источник `fact_returns`, **на уровне итога за
период дашборда**.

Основание. Финишная черта (`ADR-067`/`ADR-068`) определена как числовой паритет **сверяемых
поверхностей BI** с тем, что рисует интерфейс МойСклад. Поверхность, которую ничто не рисует,
сверяемой поверхностью не является — сверять её можно было бы только с самой собой. Величина,
выбранная владельцем объектом паритета 2026-08-01 (вариант (c), число отчёта МойСклада в разрезе по
контрагенту), остаётся эталоном СТОРОНЫ ИСТОЧНИКА; наша сторона сравнивается с ней на том уровне
агрегации, который реально выведен на дашборд. Итог за период есть сумма того же разреза, и он
совпал точно.

**Пара объявляется СОШЕДШЕЙСЯ. Счётчик реестра 1/7 → 2/7.**

**Разрез по контрагентам остаётся вне финишной черты** до появления графика, который его рисует.
Расширение реестра паритета есть решение владельца, не тихое расползание scope (`04_ROADMAP`,
«Финиш Epic-1»). Владельцу предложено добавить две колонки в «Топ контрагентов» (данные уже лежат в
запросе, стоимость — минуты); **владелец отказался (чат 2026-08-03)**. Решение зафиксировано как
принятое, не как отложенное: вопрос закрыт, к нему не возвращаться без нового повода.

## 4. Проверка регресса «Топ контрагентов» — исполнена чтением, не вопросом владельцу

Вопрос «не изменились ли числа графика после правки» был задан владельцу и отозван как негодный:
он требует помнить вчерашние значения дашборда. Правильный способ — сравнение двух формул
(`05_CONVENTIONS` Часть I, `★ Критерий приёмки выводится из формулы, не из свойства данных`).
Прежний текст поднят из истории git (коммит `e0d3659`, снимок `LS-QUERY-SNAPSHOT`).

| Что | Прежний текст | Новый текст |
|---|---|---|
| `WHERE` по продажам | `f.transaction_date BETWEEN @DS_START_DATE AND @DS_END_DATE` | **идентично** |
| `GROUP BY` | `c.name, f.agent_id, r.return_sum_kgs, c.country, f.sales_channel_name, f.project_name` | `c.name, f.agent_id, r.return_sum_kgs, c.country` |
| Подзапрос возвратов | окно `CURRENT_DATE() − 365 суток`, `GROUP BY agent_id` | период дашборда, `GROUP BY agent_id` |
| `counterparty_count` | литерал `1` | `COUNT(DISTINCT f.agent_id)` — тождественно `1` на строке |
| поле счётчика дней | `transaction_date` (имя-обманка) | `active_days_count` |

**Вывод: `Выручка (KGS)`, `Маржа (KGS)` и `% от общего дохода` измениться не могли.** График
группирует по контрагенту; прежний текст отдавал тот же набор строк, разбитый дополнительно по
каналу и проекту, и Looker Studio складывал эти части обратно. Сумма по разбиению равна сумме без
разбиения. Подзапрос возвратов присоединён по `agent_id` и отдаёт не более одной строки на
контрагента, поэтому строки продаж не размножались ни в одной из версий — то есть выручка не была
завышена и раньше.

Изменилось ровно одно: `return_sum_kgs` больше не повторяется на каждом срезе канал×проект. Поскольку
это поле ни на одном графике не выведено (§2), завышение было невидимым, и его устранение тоже
невидимо.

**Остаточный риск, названный и не снятый:** из вывода запроса исчезли поля `sales_channel_name` и
`project_name`, а поле `transaction_date` переименовано. Любой фильтр, элемент управления или второй
график, ссылавшийся на эти три имени, после правки сломается — в Looker Studio это видно как ошибка
на элементе. Владелец сообщил ровно один график на этом источнике и об ошибках не сообщал; проверка
интерфейса инструменту недоступна ни в каком классе (`ADR-085 §9`), поэтому отсутствие ошибок здесь
принимается как свидетельство владельца, а не как замеренный факт.
