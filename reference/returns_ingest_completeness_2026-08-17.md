## Факты о каденции и окне

- Возвраты грузятся ТОЛЬКО из недельного workflow, шаг `step_returns`
  (`workflow_weekly.yaml:113-135`), с явным `window_days: 90` в теле запроса. Ручной запуск с
  произвольным `window_days` тоже возможен (`main.py:315`), но не задокументирован как рабочий
  канал — расписание Scheduler в этот артефакт не входит (вне scope шага 1).
- `_run_returns` считает окно от `date.today()` на момент запуска (`main.py:327-328`):
  `date_from = date_to - timedelta(days=window_days)`. При `window_days=90` окно всегда захватывает
  весь июль, пока прогон происходит не позже конца сентября — то есть на 2026-08-17 окно НЕ
  исключает июль структурно, при условии что прогон вообще состоялся после появления документа.
- Загрузка — `WRITE_TRUNCATE` целиком по окну (`load_returns`, `bq_ops.py:878-901`,
  `main.py:311`: «full window refresh, no MERGE needed»). Ветки удаления/MERGE здесь нет вообще —
  весь класс дефектов `ADR-100`/`C2` (05_CONVENTIONS) к этой таблице неприменим.
- Порог свежести `DQ_FRESHNESS_RETURNS_MAX_HOURS = 336` (`cf-dq/config.py:30`, комментарий строки
  32: «недельная каденция → 2 × 168ч = 336ч») — допуск на два пропущенных недельных прогона.
  Подтверждает недельную (не часовую) каденцию ветки возвратов, отдельный факт от механизма пропажи
  документа.

## Классификация четырёх кандидатов

### K1 — документ проведён/изменён после последнего недельного прогона, покрывающего июль

**НЕ РАЗЛИЧИМ без живого вызова.**

`_run_returns` фильтрует по `moment` документа (`fetch_returns.py:57-61`: `moment>=...;moment<=...`),
взятому НА МОМЕНТ запроса к API, а не по времени последнего успешного прогона CF. Если документ
UMAI WB был проведён (`applicable=true`) уже ПОСЛЕ того как в последний раз отработал `step_returns`
с окном, покрывающим июль, WRITE_TRUNCATE следующего прогона его подхватит; если между тем моментом
и сейчас прогонов ещё не было — документ отсутствует не из-за дефекта, а потому что следующий
недельный цикл ещё не наступил. Различитель — сопоставление `moment` документа (только живым `GET`,
шаг 2) с временем последнего фактического запуска `step_returns` (лог Workflows/Scheduler, класс A,
но не входит в состав этого шага — репо не содержит журнала прошлых прогонов `step_returns` с
таймстампами в обязательном контексте). Ни один из двух фактов не поднят в рамках шага 1.

### K2 — фильтр `applicable=true` отсекает документ, не проведённый на момент выгрузки

**НЕ РАЗЛИЧИМ без живого вызова.**

Код (`fetch_returns.py:57-61`):
```
base_filter   = (
    f"moment>={date_from_str};"
    f"moment<={date_to_str};"
    f"applicable=true"          # TD-11: defensive — исключаем черновики
)
```
Фильтр реален и действует одинаково для всех документов запроса — не специфичен для одного
контрагента. Если документ UMAI WB на момент любого прошлого прогона имел `applicable=false`
(черновик/не проведён) и стал `applicable=true` позже, фильтр законно исключил бы его на прошлых
прогонах; следующий WRITE_TRUNCATE-прогон (после того как документ стал проведён) забрал бы его.
Это частный случай того же наблюдения, что и K1 — различитель тот же (текущий `applicable`-статус
и история его смены доступны только живым `GET` конкретного документа, шаг 2).

### K3 — потеря страницы в `paginate_entity` (тот же класс, что `ADR-167`)

**ОПРОВЕРГНУТ как действующий в этой копии кода.**

`ADR-167` (`06_INDEX.md:179`) зафиксировал именно этот класс дефекта в ветке `SALES-REFRESH-WINDOW`
(`helpers.py:87-99` на момент инцидента — обход по `offset` без проверки `meta.size`) и предписал
лекарство: перенос `check_completeness` из `cf-finance/invoices.py:109-122`. Текущая копия
`helpers.py`, читаемая в этой сессии, уже несёт эту проверку — `paginate_entity`
(`helpers.py:71-122`), строки 117–120:
```
if meta_size is not None and len(all_rows) < meta_size:
    raise RuntimeError(
        f"PAGINATE_PROBE FAILED: path={path} fetched={len(all_rows)} < meta_size={meta_size} — обход оборван"
    )
```
`fetch_return_positions` вызывает `paginate_entity` и для списка документов, и для позиций каждого
документа (`fetch_returns.py:66-71`, `84-88`) — оба обхода защищены этой же функцией. Обрыв обхода
списка `entity/salesreturn`/`entity/retailsalesreturn` дал бы громкий `RuntimeError`, валящий весь
прогон `_run_returns` (и тогда `07_STATE`/логи Workflows несли бы след ошибки шага `step_returns`, а
не тихое отсутствие одного документа). Молчаливая частичная потеря именно этого документа этим
конкретным механизмом исключена ПРИ УСЛОВИИ что `meta.size` в ответе API не был `null` — единственная
оговорка: guard пропускает проверку, если `meta_size is None` (строка 117, `if meta_size is not None`).
Различить «ответ содержал `meta.size=null`» без живого вызова нельзя, но это уже не тот механизм,
что `ADR-167` (там `meta.size` проверки не было вовсе) — здесь пришлось бы совпасть отдельному,
более редкому и не описанному в GAP-строке условию. Вывод по буквальной формулировке K1 из
GAP-строки: опровергнут.

### K4 — тип документа вне периметра загрузчика

**НЕ РАЗЛИЧИМ без живого вызова** (репо не даёт закрывающего факта).

Загрузчик обходит ровно два типа (`fetch_returns.py:63`): `for entity_type in ("salesreturn",
"retailsalesreturn")`. GAP-строка утверждает, что «оба присутствуют в данных» — это означает, что в
`core.fact_returns` УЖЕ есть документы обоих типов вообще (июньский возврат того же контрагента,
`761,00` от `2026-06-24`, загружен — упомянут в `07_GAPS.md`), но не доказывает, что документ UMAI WB
на `1 481,13` относится к одному из этих двух типов, а не к третьему типу, отсутствующему у
загрузчика. Ни один прочитанный файл (`02_ERP_CONTRACTS.md §поведение МойСклад API`,
`09_GLOSSARY.md`) не содержит исчерпывающего перечня типов документов домена «возврат» в API
МойСклад — такого факта в обязательном контексте нет, и утверждать его означало бы гэп, закрытый
догадкой (запрещено `★ Anti-improvisation`). Различитель — тип документа в ответе на живой `GET`
конкретного возврата контрагента UMAI WB за июль (шаг 2, класс B, мандат не выдан).

## Итог шага 1

Из четырёх кандидатов один (**K3**) опровергнут чтением кода этой провенанс-копии: защита от
тихой потери страницы (`ADR-167`) в файле уже присутствует и дала бы громкий отказ прогона, а не
молчаливое отсутствие одного документа — за исключением узкой, не встречающейся в этой GAP-строке
оговорки про `meta.size=null`. Остальные три (**K1, K2, K4**) требуют живого вызова API
(момент/статус `applicable` конкретного документа UMAI WB, либо его точный тип) — репо не несёт
факта, который бы их разрешил, и подставлять «наиболее правдоподобный» из трёх запрещено
`★ Anti-improvisation`/`ADR-021 §2`. Различитель шага 2 — один живой `GET` `entity/salesreturn` с
фильтром по контрагенту UMAI WB за июль (класс B, мандат НЕ выдан, `07_STATE.md:1809`) — способен
закрыть K1/K2/K4 одним ответом: он вернёт `moment`, `applicable` и подтвердит/опровергнет сам тип
документа.

Правка кода и деплой в объём этого шага не входят (см. приёмку строки `RETURNS-INGEST-COMPLETENESS`,
`07_GAPS.md:88`).
