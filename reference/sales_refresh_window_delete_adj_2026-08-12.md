## §1. Главный факт: семь из тридцати шести удалённых строк — это подтверждённые сироты,
## ради удаления которых патч и строился

`ADR-100 §1` (accepted, владелец) измерил и записал сирот продаж за май-2026 **двумя
независимыми признаками**:

> За май-2026 таких строк ровно семь, что подтверждается двумя независимыми признаками:
> разностью числа строк по суткам (`2 + 2 + 3` на `2026-05-07` / `2026-05-09` / `2026-05-26`)
> и распределением `_loaded_at`… Их сумма `1 630 240,60`…

Сверка со списком удалённых (`…deploy_v2…§8`), пересчёт мой, не из чужого текста:

| Признак | `ADR-100 §1` | Фактически удалено | Совпадение |
|---|---|---|---|
| Число строк | `7` | `6` без канала + `1` оптовая (`33 701,25`, `2026-05-26`) = **`7`** | **да** |
| Сумма | `1 630 240,60` (`ADR-119`) / `1 630 239,81` (после `SALES-INGEST-PATCH`) | `1 596 538,5585` + `33 701,25` = **`1 630 239,8085`** | **да**, до копейки против `1 630 239,81`; разница с `1 630 240,60` есть известные `0,79` (`ADR-101 §1`) |
| Подпись по суткам | `2 + 2 + 3` на `05-07` / `05-09` / `05-26` | **`2 + 2 + 3`** на тех же трёх датах | **да** |

**Три независимых признака сошлись одновременно.** Это не правдоподобие — это опознание.
Патч удалил ровно тот набор строк, который проект нашёл целевой сверкой с источником
(`ADR-100`), включил в правило-мост пары «Продажи» (`ADR-119`) и объявил причиной, ради
устранения которой заведена сама задача `SALES-REFRESH-WINDOW`.

**Следствие для приёмки:** по этим семи строкам удаление есть НЕ дефект, а исполнение
назначенной работы. Их восстановление откатом данных было бы регрессом закрытой пары реестра
паритета.

## §2. Третье число приёмки было мис-специфицировано — мной

Мандат (`…deploy_mandate…§4`, пункт приёмки 3) требовал: «удалённых строк оптовой торговли
`0` штук / `0,00` KGS. Ненулевое значение есть немедленный откат».

**Этот критерий неверен, и ошибка моя.** Узкая форма фикса (`ADR-144 §8`) есть **ровно ветка
удаления** — её единственная работа состоит в том, чтобы удалять строки, исчезнувшие из
источника. Критерий «удалено ноль» требует от работающего патча ничего не делать. Он совместим
с исправностью только при условии «за 106 суток из источника не исчез ни один документ» — а
проект располагает измерением, что за ОДИН май исчезло семь (`ADR-100 §1`).

Число `0` перенесено мной из приёмки ОТКАТА `2026-08-11` (`ADR-161`), где оно было верным:
там удаление было чистым ущербом межзагрузчикового дефекта, и ноль означал «ущерба нет».
В контексте работающей ветки удаления то же число означает «работа не сделана». Это
буквально класс, на который у проекта есть правило — `05_CONVENTIONS` Часть I
**★ Критерий приёмки выводится из формулы, не из свойства данных** (`ADR-075 §3`): я вывел
приёмку из свойства данных под другой формулой.

**Верный критерий** — не «удалено ноль», а «**каждая удалённая строка отсутствует в
источнике**». Ирония в том, что это дословно содержание `Q-107` (`proposed`, ждёт апрува
владельца): «для любой операции, УДАЛЯЮЩЕЙ строки, назвать, чьи строки представляет источник,
и доказать, что он полон для окна операции». Правило было написано, но не применено к тексту
приёмки, который я писал в том же документе.

**Вывод по остановке:** исполнитель поступил правильно. Он исполнил мандат буквально,
остановился на ненулевом числе и не стал править приёмку под факт (`ADR-047` — приёмка
сессией не переписывается). Ошибка лежит в мандате, не в исполнении. Решение владельца
задержать откат сохранило доказательную базу, без которой опознание §1 было бы невозможно.

## §3. Что этим НЕ доказано

Опознаны `7` строк из `36`. **Остаются `29` строк на `2 407 220,42` KGS без атрибуции:**

| Группа | Строк | Сумма, KGS |
|---|---|---|
| оптовая торговля (за вычетом одной опознанной) | `27` | `427 220,42` |
| «К Глобал РФ Маркетплейсы» | `2` | `1 980 000,00` |

По ним вопрос исполнителя остаётся открытым и правомерным: исчезли ли эти документы из
МойСклад (тогда удаление корректно) или выборка на длинном окне их потеряла (тогда это дефект
патча). Опознание §1 **повышает** правдоподобие первой гипотезы, но не переносится на остаток
автоматически: сироты `ADR-100` измерялись только по маю, а `27` из `29` остаточных строк
лежат в июне-июле.

**Заметная величина:** пара строк маркетплейса `2026-05-12` на `1 980 000,00` KGS (одна из них
с суммой `0,00`) — это `82 %` неатрибутированной суммы в двух строках. Их проверка окупает
себя одна.

## §4. Дешёвый различитель, которого никто не назвал: он не требует класса B

Исполнитель отверг гипотезу дефекта выборки доводом «нет кластеризации на границе
страницы/даты» — но проверял кластеризацию по дате. Информативный разрез — **пара
дата + контрагент**, то есть признак ДОКУМЕНТА. Пересчёт остатка (`29` строк):

| Дата | Контрагент | Строк | Сумма, KGS |
|---|---|---|---|
| 2026-05-12 | `31d135bc` | 2 | 1 980 000,00 |
| 2026-06-03 | `b3667c34` | 2 | 128 520,00 |
| 2026-07-13 | `4d4bb3c6` | **6** | 15 180,00 |
| 2026-07-21 | `356fb156` | **8** | 27 019,20 |
| 2026-07-30 | `b3667c34` | 3 | 100 602,00 |
| прочие 8 групп | — | по 1 | 155 899,22 |

`13` групп, из них `5` многострочных. Строки удалялись **пачками по документу**, а не
поодиночке вразброс.

**Различитель, исполнимый классом A, без единого живого вызова:** для каждой из `13` групп
сравнить число удалённых строк с ПОЛНЫМ числом строк этой группы в снимке
`core.fact_sales_profit_snap_20260811_163306`.

- Удалено **все** строки группы → из ядра исчез документ целиком → это поведение источника,
  а не потеря позиций выборкой. Гипотеза (a).
- Удалено **часть** строк группы, часть осталась → выборка вернула документ, но не все его
  позиции → дефект выборки. Гипотеза (b).

Этот тест разделяет две гипотезы одним запросом к двум таблицам BigQuery, обе из которых уже
существуют, и **не требует ни секрета, ни обращения к МойСклад**. Он должен идти ПЕРВЫМ.
Прямой запрос к `api.moysklad.ru` (класс B) нужен только если тест даст «часть» — либо как
подтверждение по паре маркетплейса.

### §4a. Уточнение формы теста (найдено после написания §4): есть точный инструмент вместо
### приблизительного

Группировка по паре дата + контрагент есть ПРИБЛИЖЕНИЕ документа: один контрагент может иметь
за сутки несколько документов. Точного разреза по документу в `core.fact_sales_profit` нет —
идентификатор документа в таблицу не попадает вовсе, он зашит в хеш:
`transaction_id = TO_HEX(MD5(CONCAT(s.demand_id, '|', s.position_id)))` (`bq_ops.py:261`).
Обратно из хеша `demand_id` не достаётся.

**Но точный инструмент существует и он уже на диске облака.** `_run_weekly_load` архивирует
СЫРОЙ ответ источника в GCS до всякой загрузки в staging (`upload_ndjson_gz`), и этот архив
неизменяем. В нём есть и `demand_id`, и `position_id` по каждой позиции — то есть по нему
восстанавливается ровно то, что выгрузка вернула на 106-суточном окне. Прецедент опоры на
этот архив как на снимок источника — `ADR-143` («снимок источника на момент загрузки
существует»).

Отсюда точный трёхступенчатый различитель, весь класса A:

1. **Пересчитать хеш по каждой записи архива** и проверить, присутствуют ли в этом множестве
   `29` удалённых `transaction_id`. Ветка удаления по построению сносит то, чего нет в
   staging; поэтому:
   - удалённый идентификатор **найден** в сыром архиве → выгрузка его вернула, а до `MERGE` он
     не дошёл → дефект между архивом и staging, гипотеза (b) подтверждена **без всякого
     обращения к складу**;
   - **не найден** → выгрузка его не вернула, вопрос смещается на границу «выгрузка или
     источник», шаг 2.
2. **Для ненайденных — искать в архиве записи того же `agent_id` за ту же
   `transaction_date`.** Есть такие записи → документ в выгрузку попал, а конкретная позиция
   нет → потеря позиций, гипотеза (b). Нет ни одной → документ отсутствует в выгрузке целиком,
   гипотеза (a) правдоподобна, шаг 3.
3. **Только для остатка и обязательно для пары маркетплейса** (`1 980 000,00` KGS) — прямой
   `GET` к `api.moysklad.ru`, класс B, мандат выдаётся поимённо, объём — единицы чтений.

Форма §4 (сравнение со снимком по группам) остаётся годной как быстрая прикидка и как
перекрёстная проверка шага 2, но решающим считается архив: он есть снимок ИСТОЧНИКА, а снимок
таблицы есть снимок НАШЕЙ стороны, и подменять первое вторым — ровно та ошибка, против которой
стоит `00_CHARTER §главный принцип` (реконсиляция — только против источника, никогда против
собственных таблиц).

## §5. Поправка к срочности: она преувеличена

Исполнитель сообщил владельцу, что «снимок таблицы и 7-дневное окно восстановления — оба
способа отката данных — доступны, но не бесконечны». **Первая половина утверждения неверна.**

`core.fact_sales_profit_snap_20260811_163306` — это ТАБЛИЦА BigQuery, а не окно. Она не
истекает и живёт, пока её не удалят; `ADR-161` прямо запрещает её удалять. Все `36` удалённых
строк лежат в ней. Значит **восстановить их можно в любой момент, а не до четверга**.

Истекает только time travel (`maxTimeTravelHours = 168`, замерено сессией) — но это
резервный путь, дублирующий снимок, а не единственный.

**Реальный срок один и он не про откат:** следующий широкий прогон — недельный конвейер
`msklad-pipeline-weekly`, расписание `0 1 * * 0` (`11_INFRA_FACTS.md:27`), то есть
**`2026-08-16T01:00Z`**, воскресенье. Он пройдёт с окном `90` суток и снова задействует ветку
удаления. До него — трое с половиной суток. Этого времени достаточно на §4 с большим запасом;
паническое решение сегодня ночью ничего не покупает.

## §6. Почему откат данных не является безопасным действием по умолчанию

Обычно откат — консервативный выбор. Здесь не так, и это надо сказать прямо: **восстановление
`36` строк из снимка вернёт в ядро семь строк, про которые проект отдельной работой доказал,
что их в источнике нет** (`ADR-100 §1`), и которые входят в разложение, закрывшее пару
«Продажи» (`ADR-119`, счётчик реестра `7/7`, финиш Epic-1 объявлен `ADR-140`).

То есть откат данных — это не «вернуться в известное хорошее состояние», а «вернуть известный
дефект вместе с неизвестным». Рекомендация исполнителя («откат независимо от результата, если
причина не выяснена быстро — данные важнее диагностики») исходит из посылки, что откат
нейтрален. Посылка неверна, и это единственное место, где я с исполнителем расхожусь по
существу; вся его фактура принята без правок.

Откат **кода** этой оговоркой не затронут: он нейтрален, обратим, проверен исполнением.

## §7. Варианты и рекомендация

Общее для всех: снимок не удаляется; ветка код-репо в `master` не сливается до решения.

**Вариант 1 — полный откат сейчас (код и данные).**
Плюсы: одно действие, состояние системы становится полностью описанным.
Минусы: возвращает семь подтверждённых сирот, то есть регресс закрытой пары паритета;
уничтожает единственный полученный урожай — знание о том, что ветка удаления РАБОТАЕТ и
находит именно то, что должна; следующий заход упрётся ровно в тот же вопрос с нуля.
**Не рекомендую.**

**Вариант 2 — откат только кода, данные не трогать.**
Плюсы: снимает живой риск полностью и немедленно; семь корректных удалений сохраняются.
Минусы: оставляет `29` необъяснённых удалений в проде; таблица оказывается в состоянии,
которое ни один документ не описывает. Это худший из вариантов по документированности —
именно то состояние, из которого рождаются будущие «расхождения непонятного происхождения».
**Не рекомендую как первый шаг; годится как страховка, см. ниже.**

**Вариант 3 — сначала различитель §4 (класс A), решение по его результату.**
Плюсы: единственный вариант, отвечающий на настоящий вопрос; не требует ни секрета, ни живых
вызовов, ни нового мандата; исполним за одну короткую сессию; укладывается в срок до
`2026-08-16T01:00Z` с запасом; сохраняет все опции открытыми.
Минусы: патч остаётся на трафике ещё несколько часов. Риск этого ограничен: штатный часовой
режим работает с окном `7` суток, единственный наблюдавшийся прогон дал `deleted=0`, и по
построению в семисуточном окне сирот почти не бывает — но это одно наблюдение, не
доказательство.
**РЕКОМЕНДУЮ.**

**Вариант 4 — приостановить расписание, потом расследовать.**
Плюсы: снимает и живой риск, и спешку, ничего не откатывая.
Минусы: пауза Scheduler — сама по себе класс B и требует мандата; останавливает поступление
свежих данных во все витрины; при запасе в трое суток цена выше пользы.
**Не рекомендую.**

### Рекомендация целиком

**Вариант 3 с жёсткой страховкой по времени.** Именно:

1. **Сейчас** — сессия класса A исполняет различитель §4 по `13` группам. Результат бинарен:
   «во всех группах удалено всё» → гипотеза (a), патч исправен; «хотя бы в одной удалено
   частично» → гипотеза (b), дефект выборки подтверждён.
2. **Если (b)** — немедленный откат кода (не данных), дефект выборки чинится отдельной
   задачей, восстановление данных решается после того, как станет известно, что именно
   потеряно.
3. **Если (a)** — подтвердить парой живых `GET` к МойСклад две строки маркетплейса
   (`1 980 000,00` KGS, `82 %` неатрибутированной суммы) — это класс B, мандат придётся
   выдать поимённо, объём ровно два чтения. Затем переписать третье число приёмки на верное
   («каждая удалённая строка отсутствует в источнике») и закрыть деплой штатно.
4. **Жёсткая страховка:** если к `2026-08-15T12:00Z` вопрос не закрыт ни в одну сторону —
   откат кода без дальнейшего обсуждения, до недельного прогона остаётся более двенадцати
   часов. Данные при этом не трогаются в любом случае.

Ни на одном шаге не требуется решение «прямо сейчас, ночью».

## Вердикт

Третье число приёмки ненулевое не потому, что патч сломан, а потому, что критерий требовал от
исправного патча бездействия; ошибка критерия моя. Семь из тридцати шести удалений опознаны
тремя совпавшими признаками как подтверждённые сироты `ADR-100 §1` — по ним патч сделал ровно
свою работу. Двадцать девять строк остаются неатрибутированными и разделяются дешёвым
различителем класса A, не требующим ни секретов, ни живых вызовов. Срочность преувеличена:
снимок-восстановление не истекает, единственный реальный срок — недельный прогон
`2026-08-16T01:00Z`. Откат данных безопасным действием по умолчанию не является.
