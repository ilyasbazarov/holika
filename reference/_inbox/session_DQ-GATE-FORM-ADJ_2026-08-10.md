- ADR-0XX: Форма метрики `drift_check` принята — разделение по наличию документов; механизм
  реализации две функции; канал `notify` существующий; кандидат 3 отложен с триггером
  Контекст: `ADR-122 §4` завёл задачу без формы; исполнительская сессия 2026-08-10 спроектировала
  три кандидата и оставила четыре развилки (`reference/dq_gate_metric_redesign_2026-08-10.md §5`),
  адъюдикация вне её мандата.
  Решение: (1) принимается кандидат 1 — `target_rev == 0` даёт исход `notify` и не блокирует
  промоут, `target_rev > 0` при `ratio < threshold` остаётся блокирующим, `freshness` остаётся
  независимым блокирующим бэкстопом; (2) механизм — ДВЕ функции по образцу пары
  `technical`/`business` блока свежести, вариант с состоянием из трёх значений отклонён, потому что
  менял бы контракт агрегации `main()` для всех шести существующих чеков ради одного;
  (3) канал исхода `notify` — существующий телеграм (решение владельца, чат 2026-08-10);
  (4) пороги `0,10`/`0,03` не меняются; (5) кандидат 3 (persistence-gating) — `DEFER`, триггер
  назван: два и более подряд идущих провала блокирующего класса, разобранных человеком и признанных
  ложными. Полное обоснование — `reference/dq_gate_form_adj_2026-08-10.md §1`.
  Последствия: [задачей `<подготовка DQ-GATE-METRIC-REDESIGN, класс A>`] правка
  `reference/code/cf-dq/main.py` — сужение `check_drift` и новая диагностическая функция рядом.
  [задачей `<деплой cf-dq, класс B, мандат не выдан>`] выкладка вместе с проверками свежести, один
  выезд. [задачей `<вторая лог-метрика, класс B, мандат не выдан>`] доставка исхода `notify` в
  существующий канал: диагностический чек даёт `passed=True` и под фильтр `msklad_dq_gate_failed`
  не попадает. [задачей `<деплой cf-dq>`] `03_PIPELINE_SPEC.md §DQ` — строка `drift_check`
  дописывается вторым исходом. [без правок] `reference/code/cf-dq/config.py` — пороги не меняются.
  Статус: accepted (архитектор — §1/§2/§4/§5; владелец — §3 канал и отсрочка кандидата 3,
  чат 2026-08-10)

- ADR-0XX: Ограниченность блокирующего действия DQ Gate закрывается операционной формой;
  механизм подтверждения-и-пропуска и автоснятие по времени отклонены
  Контекст: требование `dq_gate_fail_open_adj_2026-08-03.md §7` пункт 1 не имело формы; строка
  `DQ-GATE-BLOCK-BOUNDED` заведена `ADR-152 §7` с явно принятым риском неограниченной блокировки.
  Решение: ack-механизм в коде НЕ строится и автоснятие по времени НЕ вводится. Четыре основания:
  (а) автоснятие есть fail-open под другим именем — ровно эта дыра закрыта `ADR-152` 2026-08-10;
  (б) «пропустить» физически означает прямой вызов живой `cf-facts` в обход гейта, у которого уже
  известна мина рассогласования окон (`ADR-145 §4`) — после деплоя `SALES-REFRESH-WINDOW` тот же
  вызов с `window_days=90` при часовом staging удаляет порядка 83 суток продаж; (в) причина,
  породившая требование (никто не замечает остановки), закрыта другими средствами — рабочий
  адресный сигнал (`ADR-149`), закрытый самопропуск (`ADR-152`), снятие самого частого класса
  ложных блокировок (решением выше); (г) кнопка в один клик при частых срабатываниях нажимается
  рефлекторно, после передачи её будет нажимать тот, у кого нет контекста разбора. Вместо кода:
  длительность блока извлекается запросом к `audit.dq_runs` (данные уже пишутся каждым прогоном),
  порог эскалации `24` часовых прогона назначается человеку, ручное снятие получает написанную
  процедуру. Задача переопределена как документная, класс A.
  Последствия: [сейчас] строка `DQ-GATE-BLOCK-BOUNDED` — `OPEN` → `READY`, форма назначена, состав
  работы `reference/dq_gate_form_adj_2026-08-10.md §2.3`. [сейчас] строка мандата
  `DQ-GATE-BLOCK-BOUNDED` заводится (её не было, `ADR-090 §1` нарушен при приземлении `ADR-152`).
  [задачей `DQ-GATE-BLOCK-BOUNDED`] пункт про параметры ручного снятия гейтится появлением
  предохранителя `ADR-145 §4/§5` — того же, что стоит предусловием мандата `SALES-REFRESH-WINDOW`;
  предохранитель делается один раз на две задачи. [задачей `HANDOVER-PACKAGE`] строка реестра
  известных ограничений: блокировка не ограничена по времени автоматически, это названный выбор.
  [без правок] `reference/code/cf-dq/main.py` — этим решением не трогается.
  Статус: accepted (архитектор; владелец делегировал выбор явно, чат 2026-08-10)

- ADR-0XX: Дефект построчного `_loaded_at` снят с критического пути `DQ-FRESHNESS-COVERAGE`;
  посылка «проверка не может быть написана» разобрана и признана верной только для условия
  готовности
  Контекст: `reference/dq_freshness_coverage_2026-08-09.md §3/§7-§8` оставил 2 из 6 таблиц без
  технической проверки, назвав причиной построчный вызов `datetime.now()` в двух загрузчиках, и
  адресовал форму фикса архитектору.
  Решение: (1) обе недостающие проверки пишутся сейчас, классом A, с порогом `48` часов по той же
  формуле `2 x` суточная каденция — пропускное условие всех четырёх уже написанных функций есть
  `lag <= порог` от `MAX(_loaded_at)`, и от единственности стампа оно не зависит; неисполнимым
  построчный стамп делает только условие готовности «`COUNT(DISTINCT _loaded_at)` равен числу
  прогонов»; (2) `MAX` по построчным стампам равен моменту окончания прогона, отличается от единого
  стампа на длительность прогона (минуты против порога в 48 часов), направление ошибки безопасное;
  (3) поле `distinct_load_stamps` для этих двух таблиц обязано быть помечено в тексте детали как
  неинформативное — иначе следующая сессия прочитает его как число прогонов; (4) сам дефект реален
  и выносится строкой `LOADER-LOADED-AT-STAMP`, фикс-форвард едет попутно при следующем деплое этих
  функций, своего выезда не получает.
  Последствия: [сейчас] строка `DQ-FRESHNESS-COVERAGE` — формулировка «2/6 блокированы» снимается
  как опровергнутая чтением кода. [сейчас] заводятся строка `LOADER-LOADED-AT-STAMP` и три строки
  таблицы мандата (`ADR-090 §1`). [задачей `<подготовка DQ-FRESHNESS-COVERAGE, класс A>`] две
  функции в `reference/code/cf-dq/main.py` и два порога в `config.py`. [без правок]
  `reference/code/cf-finance/`, `reference/code/cf-loss-commission/` — этим решением не трогаются.
  Статус: accepted (архитектор)
