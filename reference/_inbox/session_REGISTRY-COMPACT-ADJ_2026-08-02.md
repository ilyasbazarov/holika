## NEW_DECISIONS

- **ADR-0NN: GAP-реестр разрезается на индекс и полный текст; колонка «Как закрывается»
  перестаёт быть лентой дописок.**

  **Контекст.** После `ADR-105` реестр стал крупнейшим разделом `07_STATE`: 70 023 симв.,
  54,2 % файла, 62 строки. Объём сидит в одной колонке — `Как закрывается` даёт 73,9 %, сам
  вопрос 23 %. Причина: колонка делает две работы — метод закрытия (короткое, стабильное) и
  ленту дописок (растёт, не убывает); 23 строки из 62 несут маркеры дописки и дают 59 % объёма
  колонки, 20 строк несут внутри две и более даты. `ADR-064` этого не лечит: пункт назначения
  срабатывает только при полном закрытии, до тех пор строка растёт неограниченно —
  канал уже назван `ADR-105 §4`. Побочно: 39 строк из 62 не называют статус в начале, то есть
  реестр перестал быть приборной панелью. Полный разбор с тремя вариантами —
  `reference/registry_compact_adj_2026-08-02.md`; выбор — за владельцем.

  **Решение (предлагается, двумя шагами).**

  §1 **Шаг 1 — разрез на индекс и полный текст (вариант C).** Заводится `07_GAPS.md`, куда
  **дословно** переезжают все 62 строки. `07_STATE §Открытые вопросы` оставляет индекс:
  `ID · статус · вопрос одной фразой · есть ли гейт`. Приём не новый — `ADR-064` уже сделал это
  с журналом решений (`06_INDEX` вместо полного `06_DECISIONS_LOG` в обязательном контексте);
  настоящий параграф расширяет `ADR-064`, не отменяет его. Замер: индекс 7 165 симв. против
  70 023; `07_STATE.md` 129 106 → 66 248 симв. (−49 %).

  §2 **Статус называется первым словом.** У 39 строк, где статуса в начале нет, он выносится в
  начало из уже написанного текста. Это вынесение, а не переформулировка: содержание строки не
  меняется.

  §3 **Шаг 2 — разрез колонки (вариант A), отдельным ADR, после шага 1.** `Как закрывается`
  оставляет метод, статус и гейт; лента дописок уезжает в артефакт вопроса либо в архив, в
  строке — ссылка. Порядок именно такой: шаг 1 снимает стоимость чтения немедленно и дословно,
  после чего разрез делается по одной строке, не блокируя Epic-1.

  §4 **Жёсткая форма строки с проверкой хуком (вариант B) НЕ принимается сейчас.** Единственный
  вариант, требующий переписать все 62 строки, то есть единственный с реальным риском потери
  смысла. Его главная выгода — механический предел длины — уже входит в объём задачи
  `STATE-DETAILS-BUDGET` (`ADR-105 §4`). Возврат к B — только если после шага 2 строки продолжат
  расти, и уже с фактами.

  §5 **Защитные механизмы, обязательные для обоих шагов.** (i) Ничего не удаляется — только
  перемещается. (ii) Перенос бинарный: строка либо остаётся как есть, либо уезжает дословно;
  переписывание при переносе запрещено. (iii) Там, где переформулировка неизбежна, старая
  редакция уезжает в архив дословно тем же коммитом. (iv) Применение — скриптом с
  предохранителями по образцу `ADR-105 §5`: привязка к `git hash-object` целевого файла (не к
  `HEAD`), отказ при изменении файла, при неполном совпадении границ строки и при повторном
  применении; режим `--check` печатает дельту до применения. (v) Проверка №4 хука
  (`4-bad-gone` / `4-good-archive`) распространяется на нового адресата, чтобы исчезновение
  строки заваливало коммит. (vi) Счётчик строк реестра в стенд-апе печатается каждой сборкой.
