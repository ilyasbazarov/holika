* ADR-0XX: Время документа МойСклад: API отдаёт UTC, интерфейс рендерит в зоне аккаунта; правило моста называет правило суток по каждой сверяемой таблице; выбор эталонных суток гейтится замером, а не задаётся вопросом
Контекст: `Q-77` заведён `E1-T1-MECH-CUTOVER` (2026-07-27) как две неразличённые гипотезы — «настоящий UTC» против «местного времени без пересчёта». Карта происхождения продаж (`reference/source_map_sales_2026-07-29.md §5`) вскрыла, что внутри одного архива `cf-facts` ветки трактуют зону противоположно: `bq_ops.py:158` конвертирует, полагая `moment` временем в UTC (фактический сдвиг +6ч), а `fetch_returns.py:115-122`/`fetch_purchases.py:41-50` не конвертируют, полагая `moment` уже местным временем; карта отказалась выбирать правдоподобную версию и назначила различителем сверку с интерфейсом. Сессия `REPORT-FIELDS` (2026-07-31) сверку исполнила через владельца: документ `entity/salesreturn` №00008 (`id = 0d9650b7-7549-11f1-0a80-19c400103fb5`), API `2026-07-01 15:33:00.000`, интерфейс `01.07.2026 18:33`, сдвиг +3 часа — не подтвердилась ни одна из двух гипотез. Второй факт владельца (2026-07-31, чат): часовой пояс аккаунта МойСклад = Москва. Два факта вместе гипотезы различают.
Решение: §1 Причина установлена, `Q-77` закрывается фактом. Интерфейс рендерит время в зоне аккаунта (Москва, UTC+3), показанное `18:33` есть московское, следовательно возвращённое API `15:33` есть UTC. Гипотеза «API отдаёт московское время» отвергнута. `Q-77` закрывается: его вопрос (какая зона) имеет ответ; его последствие (состояние слоя загрузки) переходит в задачу `INGEST-MOMENT-ZONE-FIX` и отдельной `Q`-строкой не дублируется (`ADR-051 §2`). Строка `Q-77` переносится в `07_ARCHIVE.md` дословно тем же коммитом (`ADR-064`). accepted (архитектор). §2 Эталонные часы паритета есть часы интерфейса МойСклад. Основание: `ADR-068 §3` определяет мост как правило, по которому клиент воспроизводит нашу цифру руками со своей страницы; процедура воспроизведения и есть контракт, а клиент видит интерфейс, не ответ API. Существенное уточнение, вскрытое настоящим ADR: эти часы — настройка аккаунта, а не константа. Их изменение меняет эталон паритета ретроспективно и есть решение владельца, а не техническая деталь (`§7`). accepted (архитектор). §3 Мост обязан называть правило суток каждой сверяемой таблицы явно, как функцию от UTC-времени документа. Окно запроса к API выводится из этого правила, а не назначается по виду периода. На текущей фактуре: интерфейс и ручные выгрузки из него = `DATE(M+3ч)`; `core.fact_sales_profit` = `DATE(M+6ч)`; `core.fact_returns`, `core.fact_purchases`, `core.fact_loss`, `core.fact_commissionreportin` = `DATE(M)`. Расширение `ADR-079 §2` (мост описывает core-слой): правило суток входит в обязательный состав описания моста наравне с полем-источником, правилом конвертации в KGS, фильтром периода и зерном строки. accepted (архитектор). §4 Дефект локализован и сужен. Ветка продаж НЕ дефектна: `DATE(PARSE_TIMESTAMP(...), 'Asia/Bishkek')` при UTC на входе даёт истинные бишкекские сутки, `02_ERP_CONTRACTS.md:41` подтверждён фактом и правки не требует. Дефектны четыре ветки, берущие дату UTC и объявляющие её местной: возвраты и закупки в `cf-facts` (`moment_str[:10]` при комментарии «МойСклад отдаёт в UTC+6»), списания и комиссии в `cf-finance` (приведение к дате по UTC, исходная формулировка `Q-77`). Дефект не зависит от `§7`: по UTC неверно при любом выборе эталонных суток. Заводится `INGEST-MOMENT-ZONE-FIX` (класс B: правка и деплой Cloud Functions, дополнительно гейтится `ADR-065`); мандат настоящим ADR НЕ выдаётся, целевое правило суток гейтится `§7`. Про `core.fact_payments.moment` (приходит уже DATE) правило суток не установлено и не предполагается — при постановке задачи фикса устанавливается отдельно. accepted (архитектор). §5 Экспозиция названа количественно и входит в приёмку первой сверки. Полосы, на которых календари расходятся: интерфейс против продаж — `M ∈ [18:00; 21:00)`, по Бишкеку ночь 00:00–03:00; интерфейс против возвратов и закупок — `M ∈ [21:00; 24:00)`; продажи против возвратов — `M ∈ [18:00; 24:00)`, по Бишкеку 00:00–06:00. Задача сверки обязана посчитать документы этих полос ОТДЕЛЬНО и ДО общего вердикта: иначе ненулевая разница неатрибутируема и повторяется класс ошибки, наблюдавшийся на расходах до `ADR-006` (разрыв ~33 %, `ADR-005 §Контекст`). accepted (архитектор). §6 Замер ночных полос — первый шаг задачи сверки, до содержательных замеров. Считаются документы мая-2026 в полосах `§5` по каждому типу (продажи, возвраты). Основание приоритета: от результата зависит, имеет ли развилка `§7` цену вообще; вопрос, снимаемый замером, владельцу не задаётся (`ADR-056`). accepted (архитектор). §7 Выбор эталонных суток (`Q-92`) — owner-gated, решается ПОСЛЕ `§6`, не раньше. Варианты и их цена, зафиксированы заранее, чтобы решение принималось не в спешке: (a) московские сутки интерфейса как есть — паритет в строгом смысле достижим, клиент воспроизводит цифру руками, но бишкекский бизнес отчитывается по московским суткам, а `core.fact_sales_profit` придётся пересчитать и перезалить, поскольку он хранит бишкекские; (b) переключить часовой пояс аккаунта на Бишкек — один календарь во всём контуре, ветка продаж уже корректна, кода на большой таблице не меняется; цена: отображение истории в интерфейсе меняется, ручная выгрузка `reference/pnl_2026-05.md` сделана в московском отображении и её период смещается, единственная сошедшаяся пара «Расходы» (`0,00`) требует перепроверки; (c) объявленное отступление `ADR-068 §2` — ничего не меняется ни в МойСкладе, ни в коде продаж, сверка идёт по окну, выведенному из наших суток; цена: уровень паритета (b) по `ADR-068 §1` ослабляется — клиент не воспроизведёт наш месячный итог, просто выбрав «май» у себя, и отступление живёт постоянно на дашборде. Гэп внутри варианта (b), из репо не снимается: меняет ли переключение пояса отображение УЖЕ существующих документов или только новых. Не предполагается ни в какую сторону (`_METHOD §6`). Исполнять различитель ДО `§6` не рекомендуется: при пустой ночной полосе вариант (b) может не понадобиться. proposed (решение владельца). §8 `Q-93` — зона границ запроса. Предположение «в той же зоне, в которой отдаётся `moment`» правдоподобно и фактом не является (`ADR-021 §2`). Различитель: запрос узким окном вокруг документа с известным `M`, исполняется первым шагом задачи сверки вместе с `§6`. accepted (архитектор). §9 `ADR-085 §1` уточняется, не отменяется.
