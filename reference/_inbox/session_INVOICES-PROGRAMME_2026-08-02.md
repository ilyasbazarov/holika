## NEW_DECISIONS

- **ADR-0NN: Программа постройки загрузчика счетов покупателям — контракт, декомпозиция из шести
  задач, определение готовности из пяти условий; разбиение работ на параллельные проходы.**
  Контекст: `INVOICES-STALENESS-PROBE` (2026-08-02) подтвердила, что `core.fact_customer_invoices`
  не пополнялась с `2026-06-05` (58 суток, единственное значение времени загрузки на всех 4058
  строках), при том что витрина поверх неё пересобирается ежедневно и выглядит живой. Загрузчик
  как элемент конвейера никогда не строился: таблица заполнена ручным прогоном от личного аккаунта
  (`11_INFRA_FACTS §Ручные/разовые загрузки`). Владелец потребовал проект в согласии с
  архитектурой, декомпозицию на задачи и определение готовности, исключающее бесконечную разработку.
  Решение:
  §1 **Контракт загрузчика** зафиксирован девятью свойствами с провенансом каждого
  (`reference/invoices_loader_programme_2026-08-02.md §1`); ключ `invoice_id`, приём
  staging→`MERGE`, форма `MERGE` — явный `INSERT (колонки)` (`C1`, `ADR-030`), принципал —
  сервисный аккаунт конвейера, не личный.
  §2 **Три унаследованных правила обязательны и названы явно**, потому что лежат в других
  документах и легко пропускаются: сутки документа как функция UTC-времени (`ADR-088`) — новый
  загрузчик НЕ повторяет дефект четырёх существующих веток; правило пересчёта валюты есть ВХОД
  задачи, а не деталь реализации; поведение при удалении счёта в источнике обязано быть названо
  явно, иначе воспроизводится механизм строк-сирот (`ADR-100`).
  §3 **Декомпозиция из шести задач** с единственной жёсткой последовательностью
  `T1 → T2 → T3 → T4 → T5 → T6`; внутри программы параллелить нечего, вся программа параллелится
  с работами вне её. Деплойная часть дополнительно гейтится первым выгрузом код-репозитория
  (`ADR-065`).
  §4 **Определение готовности — пять проверяемых условий, все обязательны:** автоматичность (два
  суточных прогона дают два разных времени загрузки без ручного запуска); полнота (число счетов
  равно источнику либо разность объяснена правилом); идемпотентность (два прогона подряд не
  меняют числа); паритет (строка 23 реестра — `0,00` либо закрыта правилом); наблюдаемость
  (проверка свежести покрывает таблицу). Пятое условие обязательно потому, что без него программа
  воспроизводит исходный дефект: молчаливая заморозка возможна ровно там, где её некому заметить.
  Перечень того, чем работа расползаться НЕ должна, зафиксирован тем же параграфом.
  §5 **Место жительства загрузчика вынесено владельцу** отдельным вопросом
  `INVOICES-LOADER-HOME`: режим внутри функции финансов (рекомендация архитектора — наименьшее
  число действий класса B на пути к работающей загрузке) либо отдельная функция. Публичный доступ
  функции финансов есть дефект, существовавший до программы; связывать его с восстановлением
  данных значит блокировать одно ради другого — чинится своей задачей.
  §6 **Разбиение работ на проходы.** Сплошной прогон свежести таблиц (`CORE-FRESHNESS-SWEEP`) и

  оба класса A, оба параллелимы, наборы файлов на запись не пересекаются, брифы собраны.
