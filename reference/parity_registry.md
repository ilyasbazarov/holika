# /reference/parity_registry.md — Реестр паритета (страница/отчёт МойСклад ↔ витрина/страница Looker Studio)

**Задача:** `PARITY-REGISTRY`, discovery-часть (класс B, мандат `ADR-076 §3a`).
**Основание:** `ADR-067 §5a/§5b`, `ADR-068 §3`, `ADR-069 §1/§4`.
**Что покрывает этот файл:** инвентарь пар из обоих сидов (`01_ARCHITECTURE.md §потребители` таблица PR-39; `reference/client_concerns_2026-07.md` треки A/Б), правило-мост там, где оно выводится из уже принятых ADR/SQL репо, endpoint report-API (Шаг 2, детали — `reference/parity_report_api_2026-07-28.md`), покрытие-с-даты, статус сходимости по существующим артефактам.
**Чего этот файл НЕ делает** (`ADR-076 §4`): не адъюдицирует НОВЫЕ правила моста. Где правило не выводится напрямую из принятого ADR/SQL — строка помечена «требуется», не заполнена предположением.
**Мост** — только уровень (b) паритета (`ADR-068 §1`): совпадение итогов/строк через опубликованное правило, не пиксельное совпадение страниц.
**DERIVED вне паритета** (`ADR-067 §4`): `total_sum_usd`/`revenue_usd`/`cogs_usd`/`margin_usd`/`gmroi`/ABC-XYZ и прочие производные от `dim_fx_rates`-конвертации в реестр НЕ включаются как объект сверки; сверка — только на KGS-величинах до производных.
**Якорь глубины паритета:** `2026-05-01` (`ADR-069 §2`) — используется во всех строках, где иное не обосновано фактом репо.

## Датированный снимок и каденция пересъёма эталона

**Что зафиксировано.** Зона паритета есть **датированный снимок**, а не непрерывно обновляемая область
(решение владельца 2026-08-02, `ADR-101 §10`). Причина структурная: `cf-facts` промоутит
`core.fact_sales_profit` только внутри скользящего окна (`HOURLY_WINDOW_DAYS`/`WEEKLY_WINDOW_DAYS` =
7/90 суток от даты прогона, `config.py`). Данные за пределами окна — не поддерживаемое состояние: они
остаются такими, какими были записаны, когда диапазон ещё попадал в окно, и последующие правки
документов в МойСкладе (изменение суммы, переоформление, перенос даты) до них не долетают молча.

**Каденция пересъёма — решение владельца 2026-08-03, вариант 1** (`reference/deploy_order_adj_2026-08-03.md §10`):

> Эталон месяца снимается **один раз** — в последнее воскресенье, при котором весь месяц ещё целиком
> внутри окна 90 суток. Наша сторона снимается **в тот же день**, сразу после недельного прогона.
> Пересъём после этого не производится: месяц закрыт окончательно, потому что наша сторона физически
> перестаёт меняться.

Календарь правила (дата съёма = последнее воскресенье, при котором `дата − 90 суток ≤ первый день месяца`):

| Месяц зоны | Предел (первый день + 90 суток) | Воскресенье съёма |
|---|---|---|
| май-2026 | `2026-07-30` | `2026-07-26` — **упущено**, см. ниже |
| июнь-2026 | `2026-08-30` | `2026-08-30` |
| июль-2026 | `2026-09-29` | `2026-09-27` |
| август-2026 | `2026-10-30` | `2026-10-25` |

**Основание — замер, не оценка.** По 127 майским документам `entity/demand` кривая застывания
(`updated − moment`): `30,71 %` документов перестали меняться через 7 суток после конца месяца,
`81,89 %` — через 30, `95,28 %` — через 45, `99,21 %` — к `2026-07-26`; медиана `29,39` суток, максимум
`80,10`. Возвраты застывают в день создания (`lag = 0,00` у всех 8 майских). Расчёт и скрипты —
`reference/deploy_order_adj_2026-08-03.md §9`, `reference/_scratch_DEPLOY-ORDER-ADJ_2026-08-03/`.
Предел замера: поле `updated` отражает состояние на `2026-08-01`, поэтому кривая есть нижняя оценка
дрейфа; замерен один месяц и два типа документов из семи пар реестра.

**Почему именно эта точка.** Каденция зажата между двумя измеренными границами: снизу — скоростью
застывания документов в источнике, сверху — окном обновления, после которого выравнивать стороны уже
нечем. Между ними остаётся практически одна точка в месяц, и правило её называет. Только в ней правило
одновременности снимка (`ADR-079 §3`) выполняется буквально, а не декларируется.

**Запасной путь (обязателен).** Если целевой воскресный прогон сорван, окно уходит безвозвратно. Тогда
месяц закрывается одним из двух способов, и выбор называется явно в строке пары: либо датированным
снимком по последнему успешному прогону с поимённо названной потерей документов, либо досевом после
постройки постоянного режима (`SALES-REFRESH-WINDOW`, вариант 1, целевой по `ADR-101 §10`).

**Май-2026 — ЗАКРЫТ датированным снимком (решение владельца 2026-08-03, вариант 1).** Целевая точка
`2026-07-26` упущена: это ровно тот прогон, который первым провалился в аварии DQ Gate. Применён
запасной путь — снимок по последнему успешному недельному прогону `2026-07-19T01:11:56Z`.

- **Снимок:** `core.fact_sales_profit` за май — `1363` строки, `93 522 995,53` KGS; сторона источника
  на `2026-08-01` — `127` документов, `91 892 755,66` KGS; разность `1 630 239,87` KGS. Посуточная
  таблица всех 26 суток, три рассинхронизированных документа поимённо, доказательство и границы —
  `reference/may_zone_close_2026-08-03.md` (артефакт самодостаточен).
- **Потеря неденежная.** Три документа (`№04195`, `№04456x`, `№04227`) правились в источнике после
  `2026-07-19`, имеют дату раньше `2026-05-11` и штатным путём не догонятся никогда — но денежного
  эффекта эти правки не имели: двое соответствующих суток сходятся на уровне копеек, третьи
  расходятся ровно на позицию, атрибутированную строкам-сиротам ещё `ADR-100 §1`, и суммарная
  арифметика замыкается с остатком `−0,73` KGS. Рассинхронизированы неденежные поля; что именно в них
  изменено — не устанавливалось.
- **Разность `1 630 239,87` KGS этой записью НЕ закрывается** — она есть отдельный предметный дефект
  (`MERGE` без ветки удаления, `ADR-100 §1`, конвенция `C2`), патч подготовлен текстом, не выбран и не
  задеплоен.
- **Сходимость пар реестра эта запись не объявляет:** фиксируется состояние данных, статусы пар не
  менялись.

**Примечание к парам, опирающимся на `core.fact_sales_profit` (строки 18–19).** Число за май-2026
зафиксировано снимком на дату загрузки, а не живым состоянием источника. Пересверка этих пар после
досева мая, если он будет выбран, даст другое число **по построению** — это не регресс проверки.
