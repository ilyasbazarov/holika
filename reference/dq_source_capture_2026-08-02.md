## 1. Что проверяет `cf-dq` — периметр по коду, дословно

`main.py` определяет ровно шесть чеков (`CHECKS`, строки 106–113) и три таблицы-константы (строки 9–11):

```
STAGING     = f"{GCP_PROJECT}.stg_msklad.fact_sales_staging"   (main.py:9)
CORE_FACT   = f"{GCP_PROJECT}.core.fact_sales_profit"           (main.py:10)
DIM_PRODUCT = f"{GCP_PROJECT}.core.dim_products"                (main.py:11)
```

**Ни одна другая таблица ядра нигде в `main.py` не упоминается.** Все шесть чеков читают исключительно
эти три идентификатора:

| Чек | Строки | Таблица(ы) |
|---|---|---|
| `not_empty` | 13–15 | `STAGING` |
| `drift_check` | 17–60 | `STAGING` (вчерашняя выручка) + `CORE_FACT` (MA7) |
| `fk_integrity` | 62–68 | `STAGING` × `DIM_PRODUCT` |
| `freshness` | 70–86 | `STAGING` |
| `margin_sanity` | 88–98 | `CORE_FACT` |
| `currency_normalization` | 100–104 | `STAGING` |

**Проверка свежести (`check_freshness`, `main.py:70-86`) читает ТОЛЬКО `stg_msklad.fact_sales_staging`**,
по колонке `transaction_date_raw` (строка 73/77), порог `lag_days ≤ DQ_FRESHNESS_MAX_DAYS = 3`
(`config.py:17`). Это дословно совпадает с `03_PIPELINE_SPEC.md:76`.

**Вывод периметра:** сторож видит один домен — продажи (`fact_sales_staging`/`fact_sales_profit`) и
их внешний ключ на товары (`dim_products`). Возвраты, закупки, инвентарь, платежи, счета покупателям,
списания, комиссии контрагентов, справочники контрагентов/сотрудников, все марты и `audit.*` — вне
периметра **любого** из шести чеков, не только свежести.

## 2. Счета покупателям (`core.fact_customer_invoices`) — не проверяются, дважды не могли бы

**Ответ: нет.** Двойное обоснование, оба — из кода/схемы, не из документации:

1. **`check_freshness` не адресует эту таблицу вовсе** — единственная таблица в запросе (`main.py:81`,
   `FROM \`{STAGING}\``) резолвится в `stg_msklad.fact_sales_staging` (`main.py:9`), не в
   `core.fact_customer_invoices`. Ни в одном из шести чеков идентификатор таблицы счетов не встречается.
2. **Даже если бы адресовала** — колонка, по которой чек считает возраст, `transaction_date_raw`
   (`main.py:73/77`), в таблице счетов **отсутствует структурно**: полный список 14 колонок
   `core.fact_customer_invoices` (`reference/invoices_staleness_probe_2026-08-02.md §2`) не содержит
   `transaction_date_raw` — дата документа там называется `moment` (тип `DATE`, не строка с
   `PARSE_TIMESTAMP`-форматом). Формулировка задачи предполагала именно это несовпадение
   (`briefs/DQ-SOURCE-CAPTURE.md:66`) — код подтверждает её напрямую.

Это не совпадение и не забытая колонка — это два независимых структурных факта, каждого из которых
по отдельности достаточно, чтобы исключить покрытие.

**Более широкий факт (не только счета).** Из семи материальных фактовых таблиц `core.*`
(`fact_sales_profit`, `fact_returns`, `fact_purchases`, `fact_inventory`, `fact_payments`,
`fact_customer_invoices`, `fact_commissionreportin`) под наблюдением `cf-dq` в любой форме — только
`fact_sales_profit` (через `drift_check`/`margin_sanity`) и его staging-предшественник. Заморозка,
подобная счетам (58 суток без загрузки), на любой из оставшихся пяти таблиц ядра прошла бы так же
незаметно для этого сторожа.

## 3. Откуда берётся вчерашняя выручка и MA7 — совпадает ли деплой с докой

`check_drift` (`main.py:17-60`) в задеплоенной ревизии `cf-dq-00007-hot`:

```python
WITH target_d AS (
    SELECT DATE_SUB(CURRENT_DATE('Asia/Bishkek'), INTERVAL 1 DAY) AS d
)
SELECT ... COALESCE(SUM(s.revenue_kgs), 0) AS target_rev
FROM target_d
LEFT JOIN `{STAGING}` s ON DATE(PARSE_TIMESTAMP(...), 'Asia/Bishkek') = target_d.d
GROUP BY target_d.d
```
— **вчерашняя выручка считается из `STAGING` (`fact_sales_staging`)**, не из `CORE_FACT`.

```python
ma7 = ... SELECT COALESCE(AVG(daily_rev),0) FROM (
    SELECT transaction_date, SUM(revenue_kgs) AS daily_rev
    FROM `{CORE_FACT}`
    WHERE transaction_date >= DATE_SUB(CURRENT_DATE('Asia/Bishkek'), INTERVAL 8 DAY)
      AND transaction_date  <  DATE_SUB(CURRENT_DATE('Asia/Bishkek'), INTERVAL 1 DAY)
    GROUP BY 1)
```
— **MA7 считается из `CORE_FACT` (`fact_sales_profit`), окно T-8…T-2** — совпадает с
`03_PIPELINE_SPEC.md:78` дословно («MA7 за период T-8…T-2 из CORE_FACT»).

**Совпадение с докой — частичное.** `03_PIPELINE_SPEC.md:78` называет источник MA7 (`CORE_FACT`)
явно, но не говорит явно, что вчерашняя выручка берётся из ДРУГОЙ таблицы (`STAGING`), а не из того же
`CORE_FACT`. Это не ошибка кода — сравнение «свежие данные (ещё не промоутнутые) против исторической
базы (уже промоутнутой)» логически корректно для чека, который должен сработать ДО промоута. Но это
асимметрия, которую доковая формулировка не проговаривает явно, и следующая сессия, читающая только
`03_PIPELINE_SPEC.md`, её не увидит. Порог, будни/выходные, метод T-1 (не T-0) — всё остальное
совпадает с `03_PIPELINE_SPEC.md:72,78` буквально.

## 4. Порог для субботы — разумен ли `0,03`

**Метод:** реконструкция чужими глазами кода. Формула `check_drift` воспроизведена read-only запросом
к `core.fact_sales_profit` для каждой субботы за последние 70 суток (`step12` скрипт, обвязка та же:
`AVG(daily_rev)` по 7 суткам ДО, T-8…T-2). Для двух суббот, где сторож реально сработал, значения
сошлись с фактически залогированными **до знака после запятой** (07-25: `ma7=3533380` код vs
`3 533 379,92` реконструкция; 08-01: `ma7=4780222` код vs `4 780 221,57`; `yesterday_rev` — те же
цифры) — реконструкция проверена, не гипотеза.

| Суббота | Выручка | MA7 (T-8…T-2) | ratio | Порог `0,03` |
|---|---|---|---|---|
| 2026-05-30 | 586 710 | 4 332 270 | **0,135** | пройден |
| 2026-06-06 | 3 945 003 | 2 743 689 | **1,438** | пройден |
| 2026-06-13 | 1 764 342 | 6 198 273 | **0,285** | пройден |
| 2026-06-20 | 996 030 | 3 066 382 | **0,325** | пройден |
| 2026-07-04 | 1 804 885 | 5 206 924 | **0,347** | пройден |
| 2026-07-11 | 666 570 | 3 205 403 | **0,208** | пройден |
| 2026-07-18 | 1 752 665 | 1 590 245 | **1,102** | пройден |
| 2026-07-25 | 65 386 | 3 533 380 | **0,0185** | **НЕ пройден** |
| 2026-08-01 | 25 921 | 4 780 222 | **0,0054** | **НЕ пройден** |

Из последних трёх суббот в этом окне (07-18/07-25/08-01) — ровно **две не прошли порог, одна прошла**,
что совпадает с наблюдением, переданным владельцем.

**Вывод: порог `0,03` не выглядит неоткалиброванным.** Семь из девяти суббот дают ratio от `0,135` до
`1,438` — весь этот диапазон минимум в 4,5 раза выше порога, то есть обычная суббота (даже самая
слабая из наблюдавшихся, `0,135`) проходит с большим запасом, а не впритык. Обе несработавшие субботы
проваливаются не пограничным значением, а падением до `1,9%` и `0,5%` от нормы — на два порядка ниже
порога, не на проценты. Порог не является узким местом этого эпизода; проблема — в
самоподдерживающемся отказе после первого срабатывания (`ADR-101`, `07_STATE §Волна 1 (1a)`), не в
калибровке `0,03`.

**Предел замера.** Реконструкция подставляет `CORE_FACT` вместо `STAGING` для «вчерашней выручки»
семи ПРОШЕДШИХ суббот, потому что `stg_msklad.fact_sales_staging` эфемерна (TTL 14 дней, `01_ARCHITECTURE.md:20`)
и историю на момент тех дат уже не хранит. На двух субботах, где сторож реально сработал, это
допущение **проверено фактом** (точное совпадение с залогированными числами, см. выше); для семи
прошедших суббот оно не проверено независимо — если `STAGING`/`CORE_FACT` расходятся систематически
(дубликаты, ещё не смёрженные документы), абсолютные ratio могли бы сдвинуться. Направление вывода
(«запас на порядок, не впритык») устойчиво к небольшому сдвигу такого рода.

## 5. Путь сигнала — дошёл бы алерт до человека

**Сам `cf-dq` никого не уведомляет.** `main()` (`main.py:115-144`) на любой исход пишет только в
`audit.dq_runs` (`helpers.py:24-36`) и возвращает JSON HTTP-ответом; вызовов `cf-alert` или Telegram
в `main.py`/`helpers.py` нет ни одного (сплошной `grep`, 0 совпадений).

**Уведомление устроено на уровне оркестрации, не функции.** Оба Cloud Workflow
(`msklad-pipeline-hourly`/`-weekly`, исходники сняты `gcloud workflows describe`, шаг `step2`) на
провале `check_dq` делают ровно одно: `sys.log(severity=CRITICAL, text="[…] DQ Gate FAILED …")`, затем
`raise: "DQ Gate failed — promote blocked"` — то есть роняют исполнение workflow с этой ошибкой
(`step2_hourly_workflow.yaml:99-109`). Ни `cf-alert`, ни Telegram в тексте самого workflow не
упомянуты (тот же сплошной `grep`, 0 совпадений в обоих workflow).

**Дальше — Cloud Monitoring, и здесь есть развилка.** Найдено четыре enabled alert policy, все с
двумя каналами (email `beksultan.aiv@gmail.com` + webhook на `cf-alert` для Telegram):

1. **`msklad-dq-gate-failed`** (специфичная про DQ) — питается log-based метрикой с фильтром
   `resource.labels.service_name="cf-dq" AND jsonPayload.message=~"DQ.*FAILED|…" AND severity>=ERROR`.
   **Эта метрика не может сработать никогда**, по двум независимым причинам, обе проверены не
   предположением, а прямым запросом: (i) реальные записи `service_name="cf-dq"` за последние 7 суток
   несут `severity=INFO` (сэмпл трёх записей, `step6`) — сам `cf-dq` не логирует ни `ERROR`, ни
   `CRITICAL` никогда, включая провал чека; (ii) фраза «DQ Gate FAILED» физически лежит в логе
   ДРУГОГО ресурса — исполнения Workflow, не `cf-dq`. Прямой запрос точным фильтром метрики за
   90 суток вернул **0 совпадений** (`step7`, полный список пуст, не текстовая метка «не найдено»).
2. **`msklad-workflow-execution-failed`** (общая, «workflow упал по любой причине») — метрика читает
   `resource.type="workflows.googleapis.com/Workflow"` + `jsonPayload.state=~"FAILED|CANCELLED"`, то
   есть платформенную запись о завершении исполнения, а не текст ошибки. Этот фильтр **реально
   срабатывает**: запрос тем же фильтром вернул 20 совпадений за последние часы, вплоть до текущего
   часа (`step10`) — оба workflow сейчас в этом состоянии из-за блокировки `drift_check`.

**Вывод.** Специально названный «DQ-алерт» (`msklad-dq-gate-failed`) — мёртвая проводка: канал есть
(email+Telegram настроены и включены), но триггер к нему никогда не приходит, потому что фильтр
метрики ссылается на ресурс и уровень серьёзности, которых реальный лог провала не несёт. Работающий
путь — другая, более общая политика (`msklad-workflow-execution-failed`), которая сообщила бы «workflow
упал», не называя причину, и которая, судя по совпадающим записям, фактически срабатывает прямо
сейчас на каждом часовом провале.

**Предел замера.** Совпадение лог-записей с фильтром политики доказывает, что условие политики
выполняется — это НЕ то же самое, что подтверждение доставки письма/сообщения в Telegram (для этого
нужен доступ к истории инцидентов Monitoring/логам самого `cf-alert`, вне класса A этой сессии).
Отсутствие проверки доставки не есть факт «уведомления не было» (`ADR-021 §2`) — это названный предел,
не вывод.

## 6. Почему задеплоенная ревизия старше правки, которую ей приписывают в документах

**Ответ: правка уже внутри задеплоенной ревизии; дата в документах ошибочна, не код.**

`patch_dq.py`, найденный в самом архиве деплоя, переписывает функцию `check_drift` целиком; тело,
которое он вставляет (`target_d`/`target_rev`/`target_date`, T-1-логика), **побайтово совпадает** с
телом `check_drift` в задеплоенном `main.py` (сравнение текста, не догадка — раздел `MANIFEST.md`).
`mtime` обоих файлов внутри архива — `2026-06-18 10:57`, за две минуты до `createTime` ревизии
`cf-dq-00007-hot` (`10:59:31Z`, `11_INFRA_FACTS.md:76`). То есть патч применён и упакован
непосредственно перед этим деплоем — **T-1-фикс деплоился 2026-06-18, а не 2026-06-24.**

Три вложенных ZIP внутри архива (`src.zip`, `function-source.zip`, `function-source-patched.zip`) —
самореференциальные остатки прежней упаковки; их `main.py` (идентичен во всех трёх) несёт
ДОПАТЧЕВУЮ версию (`max_d`/`today_rev`, T-0), датирован `2026-05-26` — день ревизии `cf-dq-00006-lac`.
Они подтверждают направление патча (до → после), но не исполняются (Python не разворачивает вложенные
zip внутри пакета функции).

**Дата `2026-06-24`, которую несли `11_INFRA_FACTS.md`/`03_PIPELINE_SPEC.md` до сессии
`FACTS-WORKFLOW-STOP-DIAG`, не соответствует ни одной ревизии `cf-dq`** — она датирует ревизию ДРУГОЙ
функции (`cf-facts-00007-xir`, тот же день). Разбор кода в этой сессии подтверждает гипотезу,
названную (но не проверенную) в `reference/facts_stop_diag_adj_2026-08-02.md §6`: T-1-фикс — это
деплой `cf-dq-00007-hot` от `2026-06-18`, а привязка к дате `2026-06-24` в прежней редакции доков была
ошибкой атрибуции (спутана с деплоем `cf-facts` того же дня). Никакого расхождения «код против
деплоя» здесь нет — расхождение было только в тексте документации, и оно уже устранено фактом
предыдущей сессии; эта сессия закрывает его чтением кода, как и требовалось.

## 7. Что осталось непроверенным (пределы этой сессии)

- Доставка алерта до Telegram/почты (см. §5) — не проверялась, вне класса A без доступа к истории
  инцидентов Monitoring.
- Реконструкция ratio по семи прошедшим субботам (§4) использует `CORE_FACT` вместо `STAGING` —
  проверено фактом только для двух сработавших суббот; направление вывода устойчиво, абсолютные
  цифры для остальных — с этой оговоркой.
- Правка кода, деплой, изменение порогов, состав проверок — вне scope (бриф, раздел «Вне scope»).
- Форма фикса покрытия (счета и прочие непроверяемые таблицы) — архитекторское решение, не
  назначается этой сессией.
