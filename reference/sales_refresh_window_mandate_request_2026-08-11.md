# SALES-REFRESH-WINDOW — запрос архитектору: рассмотрение выдачи мандата класса B на деплой (2026-08-11)

**От кого:** сессия-исполнитель `SALES-REFRESH-WINDOW` (класс A, без брифа — `ADR-086 §1`).
**Кому:** архитектор.
**Что запрашивается:** анализ готовности и, если готовность подтверждена, подготовка текста
поимённого мандата класса B (форма `ADR-115 §5`/`ADR-115 §12`, прецедент `ADR-146`) для решения
владельца. Эта сессия мандат не выдаёт и не запрашивает его выдачу от своего имени — только
собирает и предъявляет факты (`ADR-076`: класс A не решает за класс B).

## §1 — что закрыто на момент запроса

1. **Объём и форма патча решены и не переоткрываются.** Узкая форма (только ветка удаления, режим
   `topoff` не строится) в ОБОИХ `MERGE` `cf-facts` (`_build_merge_sql`, `_build_perimeter_merge_sql`)
   — решение владельца `ADR-144 §8`, текст патча подготовлен и `--dry_run`-провалидирован против
   живых таблиц сессией `SALES-REFRESH-WINDOW` (2026-08-08), артефакт
   `reference/sales_refresh_window_2026-08-08.md §5`.
2. **Предусловие `ADR-145 §4/§5` (защита от рассогласования окна staging/`MERGE`) закрыто текстом.**
   Эта сессия (2026-08-11) спроектировала и внесла в снапшот функцию
   `_assert_staging_covers_merge_window` — отказ ДО `MERGE`, если `MIN(transaction_date)` staging
   моложе начала окна `MERGE`. Вызывается из обеих `promote_to_core`/`promote_perimeter_to_core`.
   Форма выбрана владельцем в чате из двух спроектированных вариантов. `python3 -m py_compile` —
   без ошибок; `bq query --dry_run` guard-запроса против ОБЕИХ живых staging-таблиц — validated.
   Артефакт — `reference/sales_refresh_window_2026-08-11.md`. Коммит — `d62c587` (ветка
   `s/SALES-REFRESH-WINDOW`).
3. **Порядок деплоя (`ADR-145 §3`) — предыдущий по очереди объект закрыт.** `SALES-DOCUMENT-OWNER-DEPLOY`
   задеплоена и закрыта `DONE` (2026-08-08, `07_ARCHIVE.md`).
4. **База деплоя подтверждена свежим read-only снимком этой сессией (2026-08-11), не унаследована
   из старого документа.** Живая ревизия `cf-facts-00011-mab` (`generation 11`, `updateTime
   2026-08-09T11:00:22Z`) — деплой `INGEST-MOMENT-ZONE-FIX` (09.08) поверх `cf-facts-00010-mog`.
   `bq_ops.py` этим деплоем НЕ тронут (`MANIFEST.md`: «Незатронутые файлы — sha256 идентичен
   предыдущей ревизии `cf-facts-00010-mog`»), то есть база, на которой `SALES-REFRESH-WINDOW`
   готовился и валидировался `--dry_run` (2026-08-08), остаётся действительной для `bq_ops.py`
   без повторной подготовки патча. Снимок — `reference/_scratch_SALES-REFRESH-WINDOW_2026-08-11/live_revision_check.log`
   (`gcloud run services describe`, обходной путь `functions describe` даёт `403`, тот же приём, что
   у прежних сессий).
5. **Окно деплоя.** `2026-08-25`…`2026-09-29` (`ADR-144 §8(3)`, нижняя граница проверена расширенным
   замером `ADR-157`/`SALES-PARITY-VERDICT-ADJ`, 2026-08-10: самая поздняя майская строка `2026-05-26`,
   пересечения с окном выкладки нет ни в один день).

## §2 — что НЕ закрыто и требует решения архитектора до текста мандата

1. **Функциональная проверка предохранителя не выполнена — только синтаксис.** `--dry_run` не
   исполняет код и не проверяет, что `_assert_staging_covers_merge_window` реально отказывает на
   рассогласованном staging (например, часовой staging + `mode=promote, window_days=90`). Живая
   проверка этого сценария требует вызова функции — то есть уже деплоя или как минимум прогона
   против живого staging, что выходит за класс A. Вопрос архитектору: входит ли эта проверка в
   ПРИЁМКУ мандата (аналог трёх условий `ADR-146 §5`) или закрывается ПОСЛЕ деплоя первым же
   реальным прогоном.
2. **У патча единственного в очереди нет работающего отката (`ADR-145 §5`).** Повторный деплой
   прежней ревизии (`cf-facts-00011-mab`) вернёт код, но не удалённые строки. Восстановление —
   time travel BigQuery (срок хранения в проекте не замерен этой сессией) либо пересбор из
   GCS-архива (не построен, режим `topoff` не строится). Это свойство было предусловием ИМЕННО
   мандата (`ADR-145 §5`), не пунктом внутри него — вопрос архитектору: снимается ли предусловие
   отсутствием отката теперь, когда предохранитель есть, или откат остаётся отдельным пунктом,
   требующим решения владельца отдельно от факта готовности предохранителя.
3. **Открытое свойство метода предохранителя (не домысленное, названо явно).** Сравнение по
   `MIN(transaction_date)` может дать ложный ОТКАЗ (fail-closed), если на первый день окна `MERGE`
   в staging не оказалось ни одной продажи. Вероятность такого дня для проекта не измерена. Если это
   считается приемлемым — не требует действия; если нет — альтернатива (`COUNT DISTINCT` с явным
   параметром покрытия) спроектирована, но шире объёма предусловия (правка HTTP-контракта `main.py`).
4. **Риск `R1` (`ADR-101`, `ADR-140 §5`) остаётся именно риском, не измерением.** Ветка удаления
   двинет видимую разность по маю/июлю в момент первого прогона внутри окна — числа правила-моста
   `ADR-119` могут подлежать переписыванию. Не гейтит мандат по существующему решению `ADR-144`, но
   называется здесь повторно как часть полной картины перед выдачей.
5. **Источник COGS шире 90 суток** (`SALES-MERGE-DRYRUN`) остаётся открытым, гейтит только режим
   `topoff` (не строится этой формой) — без изменений, назван для полноты, не для действия.

## §3 — предлагаемая структура мандата (черновик для архитектора, не текст решения)

По прецеденту `ADR-146`: §1 объект/шаги брифа (здесь брифа нет — объём взять из
`reference/sales_refresh_window_2026-08-08.md §2` + предусловие `reference/sales_refresh_window_2026-08-11.md`),

§3 откат (назвать явно ограничение §5 `ADR-145` — отката данных нет, откат кода есть), §4 готовность
подтверждена архитектором по существу (сверка хунков, `.gcloudignore`, поиск секретов — тот же
протокол, что `ADR-146 §4`), §5 условия приёмки (минимум: функциональный прогон предохранителя на
намеренно рассогласованном staging ДО первого боевого `promote`, если архитектор сочтёт это
обязательным по §2 п.1 выше; замер `COUNT(*)`/`SUM(revenue_kgs)` по маю и июлю до/после первого
боевого `promote`, по прецеденту `ADR-146 §5(3)`).
