## §3. Ветка периметра (`_build_perimeter_merge_sql`, вторая ветка удаления) НЕ исполнилась — снова

Это то самое ограничение, которое сама ступень 2 (`2026-08-12`) назвала явно: «вторая ветка удаления
(периметр) сегодня не исполнялась вовсе — до окна 90 суток дело впервые дойдёт на недельном
прогоне» (`reference/sales_refresh_window_deploy_final_2026-08-12.md §4 п.1`). Первый шанс её
проверить настал `2026-08-16` — и предохранитель `ADR-145 §4` остановил её **до** MERGE, по причине,
не связанной с самим патчем удаления:

```
SELECT MIN(DATE(transaction_date_raw)), MAX(DATE(transaction_date_raw)), COUNT(*), MAX(_loaded_at)
FROM stg_msklad.fact_sales_perimeter_staging
→ min_date=2026-05-18, max_date=2026-08-10, n_rows=5484, last_loaded_at=2026-08-16 01:18:21
```

Staging **свежая** (загружена минуту до падения, в рамках этого самого прогона) — это не протухшие
данные прошлого захода. Запрошенный диапазон выборки правильный: `fetch_perimeter.py::_run_perimeter_load`
считает `date_to = date.today()` (`2026-08-16`), `date_from = date_to - 90` (`2026-05-18`) — ровно
то, что видно в `min_date` результата. Но **фактически полученные документы** (`entity/retaildemand`
+ `entity/commissionreportin`) не тянутся дальше `2026-08-10` — шесть суток разрыва между запрошенным
и полученным верхним краем. Причина разрыва (задержка источника в появлении этих двух типов
документов / дефект пагинации или фильтра запроса) **этой сессией не установлена** — прямая проверка
требует живого `GET` к МойСклад (класс B, мандат не выдан, вне scope read-only сессии).

**Это не повторение уже известного ограничения.** Прогон `2026-08-09` (предыдущая попытка недельного
цикла) упал на другом шаге — `raise_dq_failed` («DQ Gate failed — promote blocked»,
`step1_run.log`), до `step_perimeter_promote` дело не доходило вовсе. Свежесть-предохранитель
периметра сработал в проде **впервые** именно `2026-08-16`.

## §4. Май-2026 — текущее состояние, без реконciliации истории

```
SELECT COUNT(*), SUM(revenue_kgs) FROM core.fact_sales_profit WHERE transaction_date BETWEEN '2026-05-01' AND '2026-05-31'
→ n_rows=3404, total_revenue_kgs=95 214 205,80
```

Поскольку ветка продаж дала `deleted=0` на этом прогоне (§2), **этот** прогон майскую сумму не
трогал вычитанием. Последнее известное репо число (`07_STATE.md:1633`, `2026-08-08`) — `3 300`
строк / `96 471 991,41` KGS; между `2026-08-08` и `2026-08-16` в репо зафиксированы минимум два
independent изменения (`7` сирот удалены `2026-08-12T05:15:55Z`; `2` ошибочно удалённые строки
восстановлены — все три события описаны в `07_STATE.md` до этой сессии) — прямое вычитание
`3300 → 3404` / `96 471 991,41 → 95 214 205,80` НЕ приписывается этому прогону, эта сессия такую
атрибуцию не производит (не её объект). Текущее число фиксируется фактом для следующей сверки.

## §5. Разбиение таблицы (снимок vs живая) — только числа, не построчно

```
SELECT COUNT(*) FROM core.fact_sales_profit_snap_20260811_163306 → 42 995
SELECT COUNT(*) FROM core.fact_sales_profit → 43 270
```

Живая таблица теперь **больше** снимка на `275` строк (снимок снят `2026-08-11`, до деплоя ветки
удаления) — рост объясним пятью днями обычных вставок (`inserted`) поверх снимка, направление
(рост, не падение) согласуется с `deleted=0` на последнем прогоне. Точное построчное сопоставление
снимок↔живая (кто именно вставлен/удалён за пять дней) этой сессией не производилось — вне объёма
read-only проверки одного прогона (мандат ограничивает сравнение «на ОДИН этот прогон»).

## Вердикт

**Ступень 3 НЕ может быть закрыта этой сессией.** Часть критерия — ветка продаж — выполнена
чисто (прогон дошёл до `step_promote`, `deleted=0`, объяснять нечего). Но вторая половина критерия
(«первый недельный прогон» как проверка **обеих** веток удаления, `§4` мандата) не достигнута:
ветка периметра снова не исполнилась, на этот раз ОСТАНОВЛЕНА предохранителем `ADR-145 §4`, а не
пропущена по DAG. Предохранитель сработал корректно по своей логике (отказался удалять на
неполном окне) — это не дефект патча `SALES-REFRESH-WINDOW`, а новая находка: перечень
`entity/retaildemand`+`entity/commissionreportin`, отдаваемый источником на запрошенный диапазон
`2026-05-18…2026-08-16`, обрывается на `2026-08-10`. Природа разрыва не установлена этим read-only
замером. Ступень 3 остаётся **открытой** до одного из двух исходов: (a) причина разрыва найдена и
это не дефект нашей стороны — следующий недельный прогон (`2026-08-23`) станет первым реальным
испытанием ветки периметра; либо (b) разрыв — дефект `fetch_perimeter.py`/пагинации, тогда патч
периметра требует правки до следующей попытки. Решение по маршруту — архитектору/владельцу, не
этой сессии.
