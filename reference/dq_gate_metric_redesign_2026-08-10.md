# Переделка метрики `drift_check` — проектирование формы (без деплоя)

**Дата:** 2026-08-10 (Бишкек) · **Роль:** исполнитель (бриф `briefs/DQ-GATE-METRIC-REDESIGN.md`) ·
**Класс задачи:** A — проектирование, ничего не пишет в облако и не деплоит.
**Основание:** `ADR-122 §4` — «метрика, у которой нормальный и аварийный вход дают одно значение, не
калибруется — она переделывается»; `ADR-122 §8 (1)` — требование «ограниченность блокирующего
действия», переданное в эту задачу.

---

## 1. Дефект своими словами

Задеплоенная формула (`reference/code/cf-dq/main.py:30-84`, воспроизведена
`dq_gate_threshold_calibration_2026-08-04.md §2`):

```
ratio = revenue(T-1) / MA7(T-8…T-2)
passed = ratio >= threshold   (threshold: 0,10 будни / 0,03 выходные)
```

Формула отвечает на вопрос «насколько вчера продали меньше обычного», и не отвечает на вопрос
«почему». Оба класса входа дают один и тот же результат — низкий `ratio`, чек красный:

- **«В этот день почти/совсем не продавали» — нормальный вход для этого бизнеса.** Замер
  (`dq_gate_threshold_calibration_2026-08-04.md §3.3`) показал: **40 из 451** суток истории (**8,9 %**)
  не имеют вообще ни одного документа продажи, причём на **всех днях недели**, не только по
  выходным — 24 будних и 16 выходных. Это не выброс, а регулярное свойство бизнеса (99 % B2B опт,
  Дордой/Джунхай, `00_CHARTER §миссия`).
- **«Данные испорчены» — аварийный вход.** Например остановленный `promote`, оборванная загрузка,
  структурная порча выгрузки — то, ради чего чек вообще существует (`03_PIPELINE_SPEC.md §DQ`,
  строка `drift_check`).

Число порога эту разницу не чинит — три основания замера (`dq_gate_threshold_calibration_2026-08-04.md §4`,
которые дублирую здесь своими словами, не пересказом по памяти):

1. **Разрыва вокруг порога нет** (`§3.2`): ряд `ratio` по выходным непрерывен через `0,03`
   (`…0,02950 │ 0,03130…`), любое число рассекает ту же сплошную полосу.
2. **Доминирующий класс провалов порогу не подчиняется** (`§3.3-§3.4`): при **любом положительном
   пороге** нулевые сутки проваливают чек — снижение порога в 30 раз (`0,03 → 0,001`) убирает 15 из
   31 провала выходных и не может тронуть оставшиеся 16.
3. **Ослабление порога стоит того, ради чего чек существует** (`§4 пункт 3`): если гипотеза владельца
   верна («не заводили документы» — обычная пауза), чек и так сработал правильно; более низкий порог
   в следующий раз пропустил бы реальный обрыв ввода молча в инвесторскую витрину — тихое примирение
   цифр, запрещённое `00_CHARTER §главный принцип`.

Значит дефект — не в числе `0,03`/`0,10`, а в **форме**: одно скалярное сравнение `ratio ≥ threshold`
физически не может нести два разных бита информации («было мало документов» и «было ли это
нормально»).

Эра действующей ревизии `T-1` (`2026-06-18…2026-08-01`, 45 суток, `§3.5`) даёт масштаб проблемы на
практике: **7 провалов за 45 суток** (≈ раз в 6,5 дня). Из них: будни — 3 провала, все 3 нулевые по
документам; выходные — 4 провала, 1 нулевой, 3 с реальной ненулевой выручкой ниже порога
(`0,0295` 05.07 · `0,0185` 25.07 · `0,0054` 01.08), из которых одно (`0,0295`) отстоит от порога всего
на 1,7 % его величины — внутри погрешности допущения «ядро вместо staging» (`§2 предел 1`, `§3.5`).

## 2. Кандидаты формы

Общее ограничение всех кандидатов: они читают только то, что уже есть в репо/пайплайне
(`stg_msklad.fact_sales_staging`, `core.fact_sales_profit`); ничего внешнего (календарь праздников,
ручная разметка «выходной для бизнеса») в проекте не заведено — если кандидату это нужно, это назван
явным недостающим входом, не подставлено.

### Кандидат 1 (рекомендуемый) — разделение по наличию документов + понижение серьёзности

Вместо одного сравнения `ratio ≥ threshold` — сначала классификация по факту наличия документов за
T-1, отдельно от классификации по уровню выручки:

```
if target_rev == 0:                      # документов не было вовсе
    outcome = "notify"                    # НЕ блокирует promote
elif ratio < threshold:                   # документы были, выручка ниже нормы
    outcome = "block"                     # блокирует, как сейчас
else:
    outcome = "pass"
```

Это не изобретение с нуля: в том же файле уже есть работающий прецедент ровно такого разделения —
пара «(A) техническая свежесть — блокирующая ПО ФОРМЕ» / «(B) бизнес-свежесть — диагностика, ВСЕГДА
`passed=True`» для шести таблиц ядра (`main.py:147-151`, форма из
`reference/invoices_loader_design_2026-08-02.md §9.2`). Кандидат 1 — тот же архитектурный ход
(технический сигнал остаётся блокирующим, бизнес-интерпретация — не блокирующим отдельным каналом),
применённый к `drift_check`.

**Адрес реализации.** `check_drift` (`main.py:30-84`) возвращает сегодня `(bool, str)`. Кандидат
требует третьего состояния — либо (i) `check_drift` разбивается на две функции (`check_drift_zero_docs`
notify-only + `check_drift_low_ratio` blocking, только когда `target_rev > 0`), по образцу
разбиения `technical`/`business` в блоке freshness (`main.py:154-301`), либо (ii) чек возвращает
`(passed, severity, detail)` и `main()` (`main.py:303-330`) перестаёт трактовать `passed=False` как
безусловный блок для `severity="notify"`. Выбор (i) vs (ii) — форма, не назначается этим документом
(см. развилки, §5).

### Кандидат 2 — порог по истории того же дня недели (percentile от собственного ряда weekday)

Вместо единого порога 0,10/0,03 — порог, вычисленный из исторического распределения **именно этого
дня недели** (например `p10` ряда), а не общего MA7 по всем дням. Числа для оценки уже посчитаны
замером — `dq_gate_threshold_calibration_2026-08-04.md §3.1`:

| День | `p10` |
|---|---|
| вс | 0,0295 | пн | 0,0389 | вт | 0,1727 | ср | 0,0408 | чт | 0,0967 | пт | 0,0362 | сб | 0,0127 |

### Кандидат 3 — блокировка по устойчивости (persistence-gating), не по одиночному дню

Блокировать `promote` не по одному провалившему T-1, а только если провал повторяется N дней подряд
(например T-1 и T-2 оба ниже порога). Единичный тихий день не блокирует ничего; серия — блокирует.
Идея не завязана на «почему было мало» (документы/выручка) — она завязана на «разово или устойчиво».

**Оценка данными калибровки: недостаточно.** Существующие таблицы (`§3.1-§3.5`) дают агрегаты по дню
недели и по всей истории, но не дают **последовательность провалов по календарным суткам** — то есть
нельзя посчитать, сколько из 31/63 провалов шли подряд, а сколько изолированно. Единственные
датированные точки в артефакте — 4 примера нулевых суток эры `T-1` (`2026-06-23, 06-26, 06-27, 07-06`,
`§3.3`), которые не соседствуют по календарю, и 2 сутки с залогированным реальным провалом
(`2026-07-25`, `2026-08-01`, `§2`), тоже не соседние. Это слишком мало точек для вывода о частоте
серий. **CONTEXT GAP (кандидат 3 неоценим по имеющимся таблицам):** нужен новый разрез по датам
(список провалов `drift_check` с датой, а не агрегат) — существующий замер его не даёт, а повторный
запрос BigQuery вне scope этой задачи (`briefs/DQ-GATE-METRIC-REDESIGN.md §Вне scope`). Кандидат
остаётся зафиксированным как идея, не оцененной количественно.

## 3. Оценка кандидатов по фактам замера

### Кандидат 1 — что он пропускает / ловит

По всей истории (`dq_gate_threshold_calibration_2026-08-04.md §3.4`, выходные, `129` суток, порог
`0,03`): из **31** провала выходных **16** — нулевые сутки → уходят в `notify`, **15** остаются
`block`. По будням (та же логика, числа `§3.3-§3.4`): из **63** провалов **24** нулевые → `notify`,
**39** остаются `block`.

На эре действующей ревизии `T-1` (`§3.5`, 45 суток, 7 провалов): **4 из 7** (все 3 будних + 1
выходной) — нулевые сутки → переходят в `notify`, перестают блокировать `promote`. **3 из 7**
(выходные, `0,0295`/`0,0185`/`0,0054`) остаются `block` — это ровно тот класс, где числовой признак
всё ещё смешивает «реально мало» с «возможно испорчено» (§3.2 — непрерывность у порога никуда не
делась для НЕнулевых суток), но по факту эры `T-1` он на порядок реже (3 события за 45 суток против 7
при нынешней форме).

Кандидат НЕ решает continuum-проблему §3.2 внутри класса «документы есть, выручка ниже порога» — он
решает ровно ту часть дефекта, которая формулируется явно как найденная и посчитанная: смешение
«нуля документов» с «аномалией» (§3.3, доминирующий класс провалов).

### Кандидат 2 — отклоняется как та же патология другим числом

Замена одного порога на семь (по дню недели) не убирает ни одно из трёх оснований `ADR-122 §4`:
continuum вокруг любого `p10` никуда не девается (`p10` по построению оставляет **10 %** истории ниже
себя — те же 8,9 % нулевых суток в это же число попадают, просто перераспределяются по семи корзинам
вместо двух); нулевые сутки как были неустранимы положительным порогом, так и остаются — `p10`
воскресенья (`0,0295`) выше нуля, значит нулевые воскресенья по-прежнему проваливают. Кандидат
переносит калибровку с двух чисел на семь, не меняя её природу — отклоняется по той же арифметике,
что уже закрыла вопрос калибровки в `ADR-122 §2`.

### Кандидат 3 — не оценён (см. §2, CONTEXT GAP)

Не отклонён и не принят: данных для сравнения с текущим `drift_check` по объёму пропуска/поимки нет в
существующих таблицах. Остаётся кандидатом, требующим отдельного замера (новый разрез по датам), если
владелец захочет его развивать.

## 4. Ответ на `ADR-122 §8 (1)` — ограниченность блокирующего действия

**Вопрос:** должен ли новый чек блокировать «вероятно нормальный тихий день» так же, как аномалию?

**Ответ: нет для класса «документов не было вовсе», да для класса «документы есть, выручка ниже
нормы».**

Обоснование через `00_CHARTER §главный принцип` (тихое послабление гейта запрещено — расхождение
закрывается правилом/ADR, не тихим примирением):

- **Понижение серьёзности для нулевого класса — не тихое послабление, а поимённое правило,
  обоснованное числом.** Замер показал: (i) этот класс структурно неустраним никаким положительным
  порогом (`§3.4`, 16/31 и 24/63), (ii) он occurs на всех днях недели, то есть это не аномалия
  выходных, а свойство потока документов вообще, (iii) `ADR-122 §2 пункт 3` уже принял риск того, что
  если гипотеза владельца ошибочна, часть реальных срывов продаж попадёт в этот класс — то же
  решение, принятое архитектором для порога, переносится на форму: понижение до `notify`
  задокументировано этим артефактом, а не сделано молча внутри кода.
- **Это не оставляет дыру без наблюдателя.** Технический бэкстоп остаётся блокирующим отдельным
  механизмом — `freshness` (`lag_days ≤ 3`, `03_PIPELINE_SPEC.md §DQ`, автомат, блокирующий) ловит
  устойчивую остановку потока (несколько суток без свежих данных), а не единичный тихий день. Один
  нулевой T-1 не триггерит `freshness`; серия нулевых суток, дошедшая до 3+ дней лага — триггерит.
  Кандидат 1 не убирает блокировку с этого риска, он убирает её только с ЕДИНИЧНОГО тихого дня,
  для которого `freshness` и не задумывался как наблюдатель.
- **Класс «документы есть, выручка ниже нормы» остаётся блокирующим**, потому что именно там, по
  замеру, живёт необъяснённый остаток (3 события за 45 суток эры `T-1`, `§3.5`) — тот случай, где
  порог мог сработать и правильно, и по совпадению, и разбор требует человека, а не автопропуска.
- **Явный побочный риск, не решаемый этим документом.** Текущая форма (один блокирующий флаг на оба
  класса) создаёт риск привыкания оператора: если чек красный раз в 6,5 дня и в 4 из 7 случаев это
  «ничего страшного», решение о ручном промоуте рискует стать рефлекторным для ВСЕХ случаев, включая
  редкий реальный. Понижение частого класса до `notify` снижает этот риск структурно, но сам риск
  «привыкания к notify» этим документом не измерялся — открытый вход, не гэп-блокер задачи.

## 5. Рекомендация

**Форма: Кандидат 1** — разделение `drift_check` на два наблюдения по факту наличия документов
(«нулевые документы» → `notify`, не блокирует; «документы есть, выручка ниже порога» → `block`, как
сейчас), с сохранением текущих чисел порога `0,10`/`0,03` для оставшегося блокирующего класса (замер
не даёт оснований их менять — `ADR-122 §2` в силе для этого подмножества).

**Кандидат 2 отклонён** обоснованием §3 (та же патология другим числом).

**Кандидат 3 не выбран и не отклонён** — зафиксирован как идея, оценка которой требует нового разреза
данных по датам (CONTEXT GAP, §2), не покрытого существующей калибровкой.

### Развилки владельцу (не решаются этой сессией — класс A, форма вне мандата исполнителя)

1. **Механизм понижения до `notify`.** Два варианта адреса реализации (§2, Кандидат 1): (i) две
   отдельные функции-чека по образцу `technical`/`business` в блоке freshness (`main.py:147-301`),
   или (ii) один чек, возвращающий состояние из трёх значений, с правкой агрегации в `main()`
   (`main.py:303-330`), которая сегодня трактует любой `passed=False` как блок. Оба технически
   реализуемы; выбор — решение архитектора/владельца, не этого документа.
2. **Куда уходит `notify`.** В проекте уже есть уведомляющий канал — `cf-alert`/Telegram
   (`03_PIPELINE_SPEC.md §DQ`, таблица порогов свежести, механизм «автомат, уведомляющий»). Не решено:
   `notify`-исход `drift_check` идёт туда же, или заводит отдельный канал/запись в `audit.dq_runs` без
   Telegram. Не решать в этой сессии.
3. **Порог для оставшегося блокирующего класса.** Рекомендация оставляет `0,10`/`0,03` без изменений
   для класса «документы есть». Замер `§3.5` даёт только 3 точки на этот класс за 45 суток — этого
   достаточно, чтобы не считать порог явно сломанным, недостаточно, чтобы считать его подтверждённым.
   Отдельная задача калибровки этого сузившегося класса — открытый вопрос, не эта сессия.
4. **Кандидат 3 (persistence-gating).** Развивать ли его отдельным discovery-брифом (замер
   последовательности провалов по датам) — решение владельца.
