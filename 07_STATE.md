Сессия `REPORT-FIELDS` (2026-07-31, класс B) сняла имена полей `rows[0]` восьми точек API живым `GET` (`curl --compressed`, `limit=1`), провенанс в `reference/_scratch_REPORT-FIELDS_2026-07-31/` (сырые тела ответов + лог с `date -u`/`gcloud auth list` первой и последней командой). `report/profit/byvariant` и `report/profit/byproduct` дали побайтово идентичный `rows[0]` для товара из первой строки — конкретно потому, что у этого товара нет заведённых модификаций; различие двух эндпоинтов на товаре с реальными вариантами этой сессией не проверено. Первая попытка скрипта (без `curl --compressed`) дала непарсимые gzip-тела — трактовано как untrusted-вывод, не как факт «полей нет»; логи и тела удалены, скрипт исправлен, перезапущен чисто.

**Сессия `PARITY-MOMENT-ZONE` (2026-07-31, архитектор) — адъюдикация правила моста для времени документа, `ADR-088`.** Второй факт владельца (часовой пояс аккаунта МойСклад = Москва, чат, 2026-07-31), сопоставленный с замером `REPORT-FIELDS` (документ `entity/salesreturn` №00008, API `2026-07-01 15:33:00.000` vs интерфейс `01.07.2026 18:33`), различает две гипотезы `Q-77`: интерфейс рендерит в зоне аккаунта (UTC+3), следовательно API отдаёт UTC. Ветка продаж (`bq_ops.py:158`, `core.fact_sales_profit`) корректна — `DATE(PARSE_TIMESTAMP(...), 'Asia/Bishkek')` при UTC на входе даёт истинные бишкекские сутки, `02_ERP_CONTRACTS.md:41` подтверждён. Дефектны четыре ветки, берущие дату UTC и объявляющие её местной: возвраты и закупки в `cf-facts` (`fetch_returns.py:115-122`, `fetch_purchases.py:41-50`), списания и комиссии в `cf-finance` (исходная формулировка `Q-77`). Мост обязан называть правило суток каждой сверяемой таблицы явно, как функцию от UTC-времени документа `M` (`ADR-088 §3`); окно запроса к API выводится из этого правила. Выбор эталонных суток паритета (`Q-92`) — owner-gated, решается ПОСЛЕ замера ночных полос (`ADR-088 §6/§7`), не раньше; три варианта с ценой каждого зафиксированы в тексте `ADR-088 §7`. **Сборка (2026-07-31) — разбор `PARITY-MOMENT-ZONE`, дефект маркера последствий пойман до применения.** Пункт последствий блока нёс маркер `[задачей первой построчной сверки]` — описание, не заведённый task-ID, что нарушает проверяемость правила `ADR-083 §3` (сборщик обязан убедиться, что задача `<ID>` существует строкой в `07_STATE`). Правки внесены в файл буфера ДО применения; расхождений с изложенным здесь текстом решения нет.

**Адъюдикация `PARITY-SCD2-ATTRIBUTION` (`ADR-089`).** Ключевой структурный факт, снявший необходимость дополнительного различителя в интерфейсе МойСклада: `country` документирован как «кастомное поле» сущности контрагента (`02_ERP_CONTRACTS.md:154`), а схемы `core.fact_sales`/`core.fact_returns` не несут колонки `country` вовсе — только `agent_id` (FK). МойСклад структурно не может хранить атрибут контрагента ПО ДОКУМЕНТУ — только по сущности контрагента, одним текущим значением; наше собственное SCD2-версионирование (`scd2_valid_from/to`) — артефакт нашего пайплайна (`cf-dim` детектирует изменение при следующем суточном прогоне и создаёт вторую запись, `01_ARCHITECTURE.md:392`, RB-22), не отражение версионирования, существующего в самом МойСкладе. Отсюда: разрез «страна»/«имя контрагента» оракула (то, что рисует интерфейс МойСклада, `ADR-067`) для ЛЮБОГО периода есть текущее состояние сущности контрагента, потому что оракулу нечем показать иное; правило-мост «снимок на дату сделки» дало бы число, невоспроизводимое клиентом никаким запросом к МойСкладу — то есть нарушило бы главный принцип (`00_CHARTER §главный принцип`) сильнее, чем решает. Действующий JOIN `AND scd2_is_current = TRUE` (`02_ERP_CONTRACTS.md:157/409`) признан корректным по существу. Названо явно ограничение решения (`ADR-089 §5`): аргумент — структурный (custom-поле живёт на сущности, документ несёт только FK), не прямое наблюдение отображения МойСклада; замороженные реквизиты в печатных формах документов — отдельный, более узкий случай, этим решением не покрывается и не отменяется, различитель под него не заводится проактивно.

Бриф `PARITY-CHECK-SALES-RETURNS` требует пяти шагов на исполнении — (1) различитель `Q-93` (зона границ `momentFrom`/`momentTo`, метод: узкое окно вокруг документа `entity/salesreturn` №00008 с известным `moment`); (2) замер ночных полос `ADR-088 §5/§6` за май-2026 по продажам и возвратам отдельно, плюс второй замер сдвига на майском документе (`ADR-088 §10`, факт «+3 часа» пока подтверждён только на одном июльском документе); (3) построчная сверка обеих пар с правилом суток каждой таблицы, документы ночных полос считаются ОТДЕЛЬНО от общего итога; (4) запись правила и результата в `reference/parity_registry.md` строки 18–20 (только эти строки, остальной файл не трогать); (5) вопрос `Q-92` (эталонные сутки паритета) этой сессией НЕ задаётся ни при каком результате замера — он имеет цену только после того, как известно, пуста ли ночная полоса. Мандат класса B выдаётся отдельным ADR поимённо; единственное основание класса B — доступ к секрету `msklad-token` (`ADR-076 §1`), при выдаче действуют без изменений шесть оговорок `ADR-076 §5` и форма логирования `ADR-079 §6` (сессия `PARITY-CHECK-SALES-RETURNS-GEN`, 2026-08-01).

**Ревизия таблицы мандата (`MANDATE-TABLE-AUDIT`, 2026-08-01, архитектор).** Установлены три класса дефектов и один принцип. Дефекты: (i) пять задача-строк реестра не имели строки мандата (`LS-RETURNS-FX-HARDCODE`, `LS-PERIOD-CONTRACT`, `LS-INVENTORY-EXPLICIT-COLUMNS`, остаток `LAUNCH-RUNBOOK`, шаги 2+ `CODE-REPO-STANDUP`); (ii) одна строка мандата не имела строки реестра (`PROCESS-DEBT`, заведена пунктом последствий `ADR-083`, `06_DECISIONS_LOG.md:1384`) — зеркало `Q-89`; (iii) две строки закрытых задач остались в таблице (`Q-4`, `REPORT-FIELDS`), причём `STATE-COMPACT` их не поймал по построению: `Q-4` архивирован до той сессии, `REPORT-FIELDS` после. **Причина систематического нарушения `ADR-056` установлена той же сессией (`ADR-093`).** Правило языка — единственный закон проекта без механической проверки, и оно конкурирует с проверяемым правилом «работа на фактах»: дешевейший способ показать источник есть назвать его код, поэтому в паре «проверяемое против непроверяемого» побеждает проверяемое, и нарушение воспроизводится. Дополнительно найдено расхождение двух документов о составе обязательного чтения архитектора: `CLAUDE.md §Старт` п.2 требует `05_CONVENTIONS.md`, а `_ARCHITECT.md §3/§9` его не называет — сессия пошла по короткому списку и файл с правилом на старте не открыла.
