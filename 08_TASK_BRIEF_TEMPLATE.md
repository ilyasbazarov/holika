# 08 · TASK_BRIEF_TEMPLATE — Пакет-передача для рабочего чата

**Версия:** 2.0 · **Статус:** STABLE
**Как пользоваться:** генератор (роль `_GENERATOR.md`) или человек заполняет шаблон под конкретную
задачу и кладёт его в `briefs/<TASK>.md`. **Один бриф = одна задача = одна сессия.**
**Raw-URL в «context-to-load» НЕ приводятся** (`ADR-082 §2`): бриф исполняется внутри Claude Code,
файлы лежат на диске, `CLAUDE.md` подхватывается сам. Литеральные raw-URL нужны только при запуске
в обычном чате без доступа к диску; такой запуск для исполнения брифов не применяется.
Порядок запуска — `09_RUNBOOK.md`, режим И или П.

````md

<A: чтение, запись только в staging и /reference, коммит без push. B: живые конфиги, деплой CF, секреты,
инвесторские поверхности. При сомнении B. Класс обязан совпадать с таблицей `07_STATE §Мандат Claude Code`,
расхождение есть стоп-условие сессии. Для класса B указать номер и параграф ADR, выдавшего мандат.>

**Параллель (ADR-082 §1, уточнён `ADR-083 §1`):** да | нет
<Это ДОПУСК, а не разрешение. `да` означает ровно: «класс A И полный набор файлов на запись
объявлен ниже». Класс B не параллелится никогда. Достаточное условие — непересечение наборов —
свойство ПАРЫ задач, одной задаче неизвестно и проверяется механически перед запуском:
`bash tools/parallel_check.sh <TASK1> <TASK2>` (`09_RUNBOOK`, режим П). Значение обязано совпадать
с колонкой «Параллель» таблицы `07_STATE §Мандат Claude Code`; расхождение есть стоп-условие
сессии. Поле не заполнено = нет.>

**Файлы на запись** (полный список; на нём МЕХАНИЧЕСКИ проверяется пересечение при параллельном
запуске — `tools/parallel_check.sh`, `ADR-083 §1`):
- `<путь/один/на/строку.md>` — <зачем; путь ПЕРВЫМ токеном строки, в обратных кавычках>
- `<каталог/со/слэшем/на/конце/>` — <каталог объявляется со слэшем; вложенные в него файлы
  отдельно не перечисляются, проверка считает вложенность пересечением>
<Форма ОБЯЗАТЕЛЬНА: заголовок ровно `**Файлы на запись**`, дальше маркированный список.
Инлайновое перечисление в одну строку проверкой не читается и даёт ОТКАЗ (RC 3), а не
«пересечения нет». Поле отсутствует или список пуст = отказ проверки (`ADR-021 §2`), не разрешение.>

## Роль

Модель исполнения: ты исполняешь сам (`ADR-082 §2`). Не-идемпотентное — `deploy`, `run`, `update`,
прод-`bq query`, `git push` — только отдельным действием после явного подтверждения владельца,
никогда в связке с диагностикой. `Done` — только по подтверждённому логу, не по `rc=0`.
Работаешь в СВОЁМ рабочем дереве и коммитишь в СВОЮ ветку (`ADR-081 §6`). `07_STATE`,
`06_DECISIONS_LOG` и `06_INDEX` не правишь: session-блок кладёшь файлом в `reference/_inbox/`.
````

## Вариант: discovery-бриф (обогащение репо)

Тот же шаблон, но задача — **добыть знание**, а не построить прод-артефакт (`_METHOD.md` §11):
- **Цель:** закрыть конкретный гэп из `07_STATE` «Открытые вопросы».
- **Return-this:** обогащение репо — черновой ADR / `/reference`-артефакт + запись в `02_*_CONTRACTS` /
  патч дока. Точно указать, куда что коммитится.
- **Acceptance:** знание зафиксировано и трассируемо к источнику; открытый вопрос помечен на закрытие.
- **Вне scope:** прод-код (пишется отдельной задачей уже поверх закрытого гэпа).

## Правила заполнения

- **Класс задачи обязателен.** Не проставлен или расходится с `07_STATE §Мандат Claude Code: класс задач` → бриф не выдаётся, вопрос владельцу (`ADR-076 §2`).
- «Context-to-load» — по именам файлов, читаемых с диска; **литеральные raw-URL не приводятся** (`ADR-082 §2`, шапка этого документа). Шапка и раздел правил обязаны говорить одно и то же: расхождение между ними есть дефект шаблона, а не выбор исполнителя (`ADR-083 §2`).
- Не раздувать scope: явный раздел «Вне scope» обязателен.
- Приёмка — только **проверяемые** условия (лог / число / сходимость с эталоном), не «работает».
