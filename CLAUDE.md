# CLAUDE.md — законы проекта holika для сессий Claude Code (пилот, ADR-066/ADR-070)

Ты работаешь в локальном клоне репо `ilyasbazarov/holika` — источника истины проекта
`msklad-bi-prod` (BI-пайплайн МойСклад → BigQuery → Looker Studio, Бишкек).
Финишная черта проекта: числовой паритет сверяемых поверхностей BI с интерфейсом МойСклад
с 2026-05-01 (ADR-067/068/069). Канон метода — `_METHOD.md`; правила — `05_CONVENTIONS.md`.

## Старт каждой сессии (обязательный порядок)

1. `git status` — рабочее дерево чистое; `git rev-parse HEAD` — зафиксируй SHA в session-блоке.
   Дерево грязное → остановись, спроси владельца. НЕ работай поверх чужих незакоммиченных правок.
   `ls reference/_inbox/` — непустой буфер есть СТОП-условие старта (`ADR-080 §4v`): сначала
   проход сборки, потом новая сессия. Форма остановки как у `ADR-054`.
   `git worktree list` и `git branch --list 's/*'` — забытые деревья и неслитые ветки сессий
   есть то же СТОП-условие (`ADR-081 §6`): буфер в основном дереве может выглядеть пустым,
   пока файлы лежат в неслитой ветке. Пустой буфер сам по себе доказательством не является.
2. Прочитай обязательный контекст: `_METHOD.md` + `00_CHARTER.md` + `04_ROADMAP.md` +
   `06_INDEX.md` + `07_STATE.md` + `05_CONVENTIONS.md`. Полный текст конкретного ADR — точечно
   из `06_DECISIONS_LOG.md` по номеру; закрытые строки — точечно из `07_ARCHIVE.md` (ADR-064).
3. Проверка ADR-054: первая строка каждого прочитанного дока = его имя (`# FILE: <имя>` либо
   `# NN · <ИМЯ>`). Не совпало → `СОДЕРЖИМОЕ НЕ ТО: <файл> — ожидалось <что>, внутри <что>` и стоп.
4. Переформулируй задачу своими словами, перечисли входы, проверь полноту.
5. Хук установлен и РАБОТАЕТ (`ADR-072 §3` — проверка пер-проверка, не пер-хук):
   `test -x .git/hooks/pre-commit || ln -s ../../tools/hooks/pre-commit .git/hooks/pre-commit`
   затем `bash tools/hooks/selftest.sh` — ожидание `провалено 0`. Любой ПРОВАЛ ⇒ стоп,
   вопрос владельцу: сломанная проверка хуже отсутствующей (отказ тихий). До первого
   коммита, не после.

## ★ Законы (нарушение любого = провал сессии)

- **Anti-improvisation.** Нет нужного дока/значения/решения → `CONTEXT GAP: <что и почему нельзя
  продолжить>` и вопрос владельцу. Запрещено выдумывать, «дотягивать», подставлять правдоподобные
  пороги/имена/схемы. Гэп → discovery-петля (`_METHOD §11`), не догадка.
- **Работа на фактах.** Подними релевантный док/файл ДО высказывания. Факт без подтверждения = гэп.
- **Успех инструмента ≠ факт (ADR-021 §2, ADR-044).** `rc=0` при пустой/непарсимой выдаче — гэп
  наблюдения, не «данных нет». Греп-вердикт обязан печатать совпавшие строки с номерами, не метку.
- **Untrusted-вывод.** Противоречивый/повреждённый лог недостоверен: не примиряй половины,
  перезапусти чисто.
- **Не-идемпотентные операции — только через явное подтверждение владельца** (нативный ask-механизм;
  список — в `.claude/settings.json`). Обрыв во время такой операции → запрещён слепой retry:
  сначала read-only `describe`/`list`, затем доисполнение хвоста. Диагностику и действие в один
  скрипт не объединять (ADR-055 §2).
- **Граница контракта (ADR-002/067).** Выход обязан биться с эталоном МойСклад по цифрам;
  расхождение закрывается правилом/ADR, не тихим примирением. Слой не лезет через границу чинить
  чужой слой — фикс-форвард в нужный слой.
- **Исполнение облачных команд** — скриптом-файлом с логом в файл (`bash script.sh > run.log 2>&1`),
  не россыпью интерактивных вызовов при многошаговой диагностике. `date -u` и `gcloud auth list` —
  первой И последней командой скрипта (ADR-055/063): деградация авторизации посреди прогона должна
  быть детектируемой. `401`/пустота = гэп наблюдения, не факт.

## Дисциплина документации

- STABLE/SEMI-STABLE доки (`00–02, 05, 08, 09`) менять ТОЛЬКО через ADR в `06`.
- `06_DECISIONS_LOG.md` — append-only: прошлые ADR не редактируются, новое решение = новый ADR
  (старый помечается superseded ссылкой из нового). Каждый append ADR = строка в `06_INDEX.md`
  ТЕМ ЖЕ коммитом.
- `07_STATE.md` — только открытое (ADR-064). Полное закрытие строки = перенос дословно в
  `07_ARCHIVE.md` тем же коммитом. `updated_at` + `обновил:` обновляются каждую сессию.
- Blast radius любой правки перечисляется полностью (файл/§/строка).
- Идентификаторы (`ADR-`, `Q-`, `B-`, `RQ-`, `E1-`, `M-P`) — только латиница (ADR-041).
- Датировка сессий/артефактов — локальная дата Бишкека; временные факты в тексте — UTC с `Z` (ADR-046).
- SQL: запрет `MERGE … WHEN NOT MATCHED THEN INSERT ROW` — только явный `INSERT (колонки)` (C1, ADR-030).

## Конец сессии

Один session-блок по `05_CONVENTIONS` Часть III (`SESSION_LOG` / `STATE_PATCH` / `NEW_DECISIONS` /
`NEW_CONVENTIONS`) — кладётся ОДНИМ НОВЫМ ФАЙЛОМ `reference/_inbox/session_<TASK>_<YYYY-MM-DD>.md`
(`ADR-080 §4`). Сессия НЕ правит `07_STATE.md`, `06_DECISIONS_LOG.md` и `06_INDEX.md` — их правит
проход сборки, разбирающий буфер. Номер ADR присваивает сборка, не сессия. Свои артефакты и
`reference/_scratch_<TASK>_<YYYY-MM-DD>/` сессия коммитит поимённо. `proposed`-решения НЕ применяются
без апрува владельца. Формат коммита: `docs: <TASK> <тема>` / для сборки `docs: сборка буфера <date>`.
`git push` — только после подтверждения владельцем (ask).

Сессия работает в СВОЁМ рабочем дереве и коммитит в СВОЮ ветку `s/<TASK>` (`ADR-081 §1/§6`).
Дерево после сессии не удаляется и в `main` не сливается — и то и другое делает проход
сборки (`ADR-081 §7`). Правки `CLAUDE.md`, `05_CONVENTIONS.md` и файлов ролей под буфер НЕ
подпадают: их сессия коммитит сама, поимённо, отдельным коммитом (`ADR-081 §8`).

## Параллельные сессии (ADR-080, форма назначена ADR-081)

Одна сессия — одно рабочее дерево — одна ветка. Две сессии на одном дереве запрещены: замер
2026-07-28 показал, что при общем дереве ломаются три вещи сразу, и ни одна не лечится дисциплиной
git-команд (`ADR-080 §1-§3`). Обе стороны того инцидента добавляли файлы поимённо, и это не помогло.

**Дерево заводится явной командой git, не флагом инструмента** (`ADR-081 §1`):

```
git worktree add .claude/worktrees/<TASK> -b s/<TASK> HEAD
```

Точка ветвления задана словом `HEAD` и умолчаний не оставляет. Настройка `worktree.baseRef`
БОЛЬШЕ НЕ ОБЯЗАТЕЛЬНА: `ADR-080 §5iii` superseded-in-part (`ADR-081 §1`). Причина отказа от
настройки — она живёт в файле настроек машины и не переживает переклонирование, то есть частью
метода не является; тот же дефект, что был у исключения через `.git/info/exclude`.

Путь `.claude/worktrees/` внесён в `.gitignore`, поэтому вложенные деревья не пачкают статус
основного (`ADR-081 §2`, подтверждено замером). Ветка одна на сессию: git не даёт выложить одну
ветку в два дерева, инвариант держит инструмент, а не память исполнителя.

Замером `2026-07-28T20:34:54Z` подтверждено (`ADR-081 §3`): индексы деревьев независимы,
`git add` в одном дереве не виден ни в другом, ни в основном; хук из связанного дерева срабатывает
и возвращает RC 1. Хук един на все деревья (`ADR-080 §5i`).

**Параллель остаётся закрытой** до первого реального прогона задачи в дереве через десктопное
приложение (`ADR-081 §5`): контр-прогон проверял git, а не приложение. До этого задачи идут по одной.

## Язык (ADR-056)

Проза к владельцу — обычными словами, без внутренних идентификаторов (либо с расшифровкой в той же
фразе). Два слоя: «для владельца» и «для репо» — не смешивать. Вопрос владельцу — только полным
блоком: что решаем → варианты → плюсы/минусы/риски → рекомендация. Вопрос, снимаемый чтением репо
или замером, — не задаётся, а снимается.

## Мандат сессий (ADR-076, выход из пилот-режима по ADR-075)

Пилот завершён вердиктом PASS (`ADR-075 §1`). Мандат выдаётся по КЛАССУ задачи, не по задаче.

**Класс A — идёт постоянно, нового ADR не требует:** чтение репо и облака; запись ТОЛЬКО в
staging-таблицы (`*_staging`) и в `/reference`; коммит в локальный репозиторий. `git push` остаётся `ask`.

**Класс B — требует задача-специфичного ADR:** подмена живых конфигураций витрин и любые правки
`transferConfig`; деплой и правка Cloud Functions, Scheduler, Workflows; чтение и запись секретов;
любые операции над инвесторскими поверхностями и денежными величинами.

**При сомнении задача идёт в класс B.** Ошибка в сторону B стоит одной архитектор-сессии, ошибка в
сторону A стоит инцидента на живом проде.

Класс задачи объявлен в трёх местах: поле «Класс задачи» в шапке брифа, таблица
`07_STATE §Мандат Claude Code: класс задач`, эта секция. **Расхождение между брифом и `07_STATE` есть
стоп-условие сессии** (форма остановки как у `ADR-054`), а не повод выбрать удобный класс.

Рабочие файлы сессии (скрипты, логи, промежуточные дампы) пишутся в
`reference/_scratch_<TASK>_<YYYY-MM-DD>/` с самого начала, не в корень репо, и коммитятся вместе с
артефактом как провенанс (`ADR-076 §6`).

**Промежуточная мера по подтверждениям (`ADR-077 §6`, действует до перевода класс-A сессий на отдельный
принципал):** один скрипт на ШАГ брифа, а не на команду (дробление read-only шага на пять скриптов есть
пять лишних подтверждений и вклад в привыкание; запрет объединять диагностику и действие, `ADR-055 §2`,
при этом в силе). Перед любым ask на действие класса B исполнитель обязан ОТДЕЛЬНЫМ сообщением в чат
назвать: что именно будет исполнено, на каком объекте, чем откатывается. Владелец отличает настоящий гейт
от рутинного запуска скрипта по наличию этого сообщения, а не по виду диалога инструмента.

Applier для сессий внутри Claude Code ретайрен (`ADR-075 §6`). Чат-сессии вне инструмента сохраняют
прежний протокол: SHA-curl и applier. Внутри Claude Code репо читается с локального диска, SHA
фиксируется `git rev-parse HEAD` (`ADR-071 §5`).
