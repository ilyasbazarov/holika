## Обязательные оговорки (нарушение = провал прогона)

1. **Только SELECT.** Ни одной команды записи (`bq load`, `bq query` с записью, `bq mk/update/rm`,
   `gcloud … deploy/run`) в `run.log` быть не должно.
2. **Пустой результат = гэп наблюдения, не факт** (`05` Часть I ★, `ADR-021 §2`). «Заданий нет»
   пишется только если запрос вернул содержательный отрицательный ответ (0 строк с ясным диапазоном
   охваченного окна), а не ошибку/`401`/обрезанную выдачу.
3. **Доставка через файл** (`ADR-055 §1`): heredoc-запись скрипта, запуск
   `bash script.sh > run.log 2>&1; cat run.log`. `date -u` и
   `gcloud auth list --filter=status:ACTIVE --format='value(account)'` — **первой И последней**
   командой скрипта (`ADR-055 §3`, `ADR-063 §4`). Расхождение личности между началом и концом ⇒
   выводы прогона считаются неподтверждёнными.
4. **Временные файлы не удалять**, путь печатать последней строкой (`ADR-043`).
5. **ADR не предлагать.** Квалификация находки (закрывает ли она `Q-82` целиком или только продвигает) —
   за архитектором. `NEW_DECISIONS` в session-блоке = «нет».

## Шаги

**Шаг 0 — якорь.** `date -u`; `gcloud auth list --filter=status:ACTIVE --format='value(account)'`;
`gcloud config get-value project`. Все три значения — в артефакт дословно. Пусто или не тот аккаунт →
стоп.

**Шаг 1 — история заданий по `core.fact_customer_invoices`.**
Запрос к `` `region-asia-east1`.INFORMATION_SCHEMA.JOBS_BY_PROJECT `` (образец — `fx_may_window_2026-07-28.md`
§D2(б), адаптировать таблицу):

```sql
SELECT
  job_id,
  job_type,
  statement_type,
  user_email,
  creation_time,
  end_time,
  destination_table.project_id AS dest_project,
  destination_table.dataset_id AS dest_dataset,
  destination_table.table_id AS dest_table,
  error_result.reason AS error_reason,
  query
FROM `region-asia-east1`.INFORMATION_SCHEMA.JOBS_BY_PROJECT
WHERE destination_table.dataset_id = 'core'
  AND destination_table.table_id = 'fact_customer_invoices'
ORDER BY creation_time ASC
```

Без фильтра по дате — горизонт задаёт сам `INFORMATION_SCHEMA` (retention), не выдумывать окно заранее
(anti-improvisation). Если запрос по всему горизонту слишком велик/таймаутит — сузить окном явно и
зафиксировать это отклонение с причиной в артефакте, не молчать.

**Шаг 2 — разбор находок.**
- Если строки есть: для каждого задания — `job_type` (`LOAD` vs `QUERY`), `user_email` (кто/что
  писало — человек, `etl-sa@…`, иной сервис-аккаунт), `creation_time` (разовая вставка или регулярная
  каденция), `query` (для `QUERY`-заданий — полный текст, сверить упомянутые колонки со схемой
  `reference/schema_dump_2026-07-28.md`; для `LOAD`-заданий поле `query` обычно `NULL` — это ожидаемо,
  не гэп).
- Если строк нет: явно зафиксировать это как отрицательный результат горизонта
  `INFORMATION_SCHEMA.JOBS_BY_PROJECT`, а не как «загрузчика никогда не было» — таблица физически
  существует и содержит данные (`reference/schema_dump_2026-07-28.md`), значит запись произошла ДО
  начала видимого окна retention.
- Не выбирать между несколькими гипотезами происхождения — фиксировать то, что показал запрос,
  дословно.

**Шаг 3 — артефакт.** `reference/customer_invoices_load_jobs_<YYYY-MM-DD>.md` (дата — локальная дата
Бишкека, `ADR-046 §1`; временные факты внутри — UTC с суффиксом `Z`, `ADR-046 §3`). Состав:
`git rev-parse HEAD`; `date -u` и аккаунт начала и конца; полный текст SQL-запроса шага 1; сырая выдача
(или её релевантная часть, полная выдача — в `reference/_scratch_LS-QUERY-SNAPSHOT_<date>/`); разбор
шага 2; явный вывод — назван принципал-загрузчик, ИЛИ явный гэп «за пределами видимого горизонта» со
ссылкой на то, что видимость чужих принципалов уже подтверждена (`bq_jobs_2026-07-28.md §6`), то есть
пустой результат не объясняется правами доступа; строка «прод не тронут: ни одной команды записи».

**Шаг 4 — закрытие якоря.** `date -u` и `gcloud auth list --filter=status:ACTIVE` последними командами
скрипта.
