## Цель
Спроектировать (не применить) форму фикса «маскировки свежести» для пяти таблиц `core`/`marts`,
которые не несут колонки времени и потому не проверяемы существующим методом свежести
(`CORE-FRESHNESS-SWEEP`, `reference/core_freshness_sweep_2026-08-02.md`). Форма обязана нести ДВА
раздельных сигнала на таблицу — «когда витрина/таблица была последний раз пересобрана» И «насколько
свежи данные источника, на которых основана эта пересборка» (`ADR-111 §6`, `07_GAPS.md` строка
`MARTS-BUILD-STAMP`) — потому что отметка одной только пересборки не решает найденную маскировку:
`marts.customer_invoices_ar` пересобирается ежедневно (`CREATE OR REPLACE`) поверх `core.fact_customer_invoices`,
который может простаивать (был заморожен 58 суток, `INVOICES-STALENESS-PROBE`), и после пересборки
выглядел бы «свежим» по одной лишь метке времени сборки. Результат — текстовое предложение (варианты
правки SQL/схемы, без ранжирования выбора одного варианта, по прецеденту `SALES-REFRESH-WINDOW`) в
`reference/marts_build_stamp_2026-08-10.md`; выбор варианта и любое применение — отдельная задача
класса B/по решению владельца.

## Шаги
1. Прочитать `07_GAPS.md` строку `MARTS-BUILD-STAMP` и `ADR-111` целиком — переформулировать своими
   словами, что именно называется маскировкой и почему одной отметки времени сборки недостаточно.
2. Для каждой из пяти таблиц прочитать живой SQL-снапшот (где он есть) и определить чтением, а не
   предположением: (а) режим записи (`CREATE OR REPLACE` / `MERGE` / иное), (б) из какой(-их)
   `core.*`-таблицы(-иц) читает, (в) есть ли уже в тексте запроса колонка, отражающая момент
   пересборки или момент источника. `core.dim_fx_rates` — не Custom Query; если код `cf-fx` не найден
   в `reference/code/`, зафиксировать это как `CONTEXT GAP` для этой одной строки и продолжить с
   остальными четырьмя (частичный `CONTEXT GAP` не блокирует всю задачу — по аналогии с
   `SALES-MERGE-DRYRUN`, где вопрос (б) остался гэпом, а вопрос (а) был закрыт).
   Для `marts.expenses_staging`: если ни один живой SQ её не строит (нет адреса в
   `03_PIPELINE_SPEC.md §marts — SQL` и в `11_INFRA_FACTS.md §SQ`), зафиксировать `CONTEXT GAP` по
   этой одной строке (кто её пишет — не установлено репозиторием) и не изобретать источник.
3. Для каждой таблицы (где источник и SQL найдены) спроектировать минимум два независимых варианта
   текста правки — без выбора одного, по прецеденту `SALES-REFRESH-WINDOW`
   (`reference/sales_refresh_window_2026-08-01.md`):
   - Вариант «две колонки»: `_marts_built_at TIMESTAMP` (момент выполнения запроса, `CURRENT_TIMESTAMP()`)
     плюс `_source_max_loaded_at TIMESTAMP` (агрегат `MAX()` соответствующей колонки времени источника
     — назвать конкретную колонку конкретной `core.*`-таблицы, не общим словом «время источника»).
   - Вариант «одна производная колонка»: `_source_lag_seconds` или аналог — разница между моментом
     сборки и максимальным временем источника, посчитанная внутри того же запроса.
   Для каждого варианта — точный SQL-фрагмент (`SELECT`/выражение), куда он вставляется в существующий
   текст, и что теряется/приобретается по сравнению с другим вариантом (как в `SALES-REFRESH-WINDOW`
   — сравнительная таблица без ранжирования).
4. Явно назвать открытые вопросы, которые эта сессия НЕ решает (форма — предметная, гейт снят только
   до уровня подготовки): какая из колонок будет читаться проверкой свежести (`DQ-FRESHNESS-COVERAGE`
   — тот же класс работы, отдельная задача, не сливать); ломает ли добавление колонки существующие
   потребители Looker Studio страниц (состав колонок этих страниц эта сессия не проверяет — вне scope,
   только называется как открытый вопрос); нужно ли `WHEN NOT MATCHED` — форма C1/C2 применима только
   если найден `MERGE`, что должно быть подтверждено чтением на шаге 2, не предположено здесь.
5. Собрать всё в `reference/marts_build_stamp_2026-08-10.md`: по одной секции на таблицу (текущая
   форма с цитатой источника, оба варианта правки, открытые вопросы), плюс сводная таблица в начале.
