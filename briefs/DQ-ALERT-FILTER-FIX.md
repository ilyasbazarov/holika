## Шаги
1. Read-only: снять текущую конфигурацию log-based метрики `msklad-dq-gate-failed` и связанной alert

2. Сформулировать исправленный фильтр метрики, адресующий реальный источник записи (лог исполнения
   Cloud Workflow, `severity=CRITICAL`, текст вида `DQ Gate failed`/`DQ.*FAILED`) — процитировать
   текущий и предлагаемый фильтр дословно, объяснить разницу в терминах ресурса/severity.
3. Не применяя изменение (правка живой policy — за гейтом мандата), составить план проверки: какой
   `gcloud logging read`/`gcloud monitoring` запрос с предложенным фильтром против уже случившегося
   провала `2026-08-01T18:02:01Z` даст ненулевую выдачу — и по возможности прогнать этот запрос
   read-only (без изменения policy) как эмпирическое подтверждение формулы фильтра.
4. Зафиксировать всё найденное и предложенное в `reference/dq_alert_filter_fix_<date>.md`: текущий
   фильтр → диагноз → предложенный фильтр → результат read-only проверки против `2026-08-01T18:02:01Z`
   → явное указание, что применение (`gcloud alpha monitoring policies update` / аналог) не исполнено,
   ждёт мандата класса B.
5. Если владелец в ходе сессии в чате выдаёт мандат явно (форма — отдельный ADR по прецеденту
