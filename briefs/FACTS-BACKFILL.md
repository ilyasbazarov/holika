## Входы — что уже установлено и не переустанавливается
1. Блокировка `drift_check` в `step_dq` весь известный период останавливала ТОЛЬКО
   `step_promote`/`step_perimeter_promote` (продажи). `step_purchases` и `step_returns` в
   `workflow_weekly.yaml` стоят в DAG ДО `step_dq` — блокировкой формально не затрагиваются.
2. `load_purchases`/`load_returns` (`bq_ops.py:680-772`) — оба `WRITE_TRUNCATE`, не `MERGE`:
   `core.fact_purchases` перезаписывается целиком БЕЗ окна дат (`_run_purchases` вызывает
   `fetch_purchase_positions` без `date_from`/`date_to` — полный refresh всех заказов на момент
   прогона); `core.fact_returns` перезаписывается целиком в пределах окна `window_days`,
   переданного явно в теле `step_returns` (`window_days: 90`).
3. Продажи закрыты фактом: `core.fact_sales_profit` не несёт дыры `2026-08-01…2026-08-04`
   (`FACTS-FLOW-RESUME-CONFIRM`, 2026-08-05). Закупки и возвраты этим замером НЕ проверялись —
   явная оговорка того же артефакта.
4. На момент `FACTS-FLOW-RESUME-CONFIRM` (2026-08-05) недельный прогон возвратов
   `2026-08-09T01:00Z` ещё не наступал.

## Гипотеза, которую замер обязан подтвердить или опровергнуть
Из (1)+(2): если недельный workflow исполнялся хотя бы один раз начиная с `2026-08-01` (даже если
итоговый execution упал на `step_dq`/`step_promote`), `step_purchases` и `step_returns` уже успели
отработать ДО падения, и обе таблицы уже не несут дыры — досев не требуется структурно, по
устройству загрузки (полная перезапись, а не накопление). **Гипотеза может быть неверна** —
например, если execution падает раньше `step_purchases` по другой причине, либо
`step_purchases`/`step_returns` сами завершаются ошибкой (в `workflow_weekly.yaml` их `try/except`
всё равно делает `raise: ${e}`, то есть код НЕ гарантирует «не блокирует promote при ошибке»
несмотря на комментарий рядом с `step_purchases` — расхождение комментария и кода само по себе не
факт, проверяется логами). Замер гипотезу ПРОВЕРЯЕТ, не иллюстрирует.

## Шаги

**Шаг 1** (`date -u` первой командой скрипта). Список execution `msklad-pipeline-weekly` за
`2026-07-27T00:00Z…момент замера` (`gcloud workflows executions list`); для каждого — статус, момент
старта/конца и, по логам execution (`gcloud logging read` либо `executions describe`), состояние
шагов `step_purchases`/`step_returns`: исполнились ли они и с каким результатом — НЕЗАВИСИМО от
итогового статуса всего execution. Печатать тела дословно (`ADR-044`).

**Шаг 2.** Для каждого успешно исполнившегося `step_purchases`: момент запуска и фактическое число
загруженных строк в `core.fact_purchases` на этот момент (`INFORMATION_SCHEMA.JOBS_BY_PROJECT`,
`region-asia-east1`, задания с целью `core.fact_purchases`, явный `--max_rows`/`-n`, независимый
`COUNT(*)` для контроля молчаливой обрезки — `ADR-021 §2`, ловушка подтверждена
`PARITY-STOCK-INTRANSIT`). То же для `step_returns`/`core.fact_returns`.

**Шаг 3.** Текущее состояние обеих таблиц на момент замера: признак свежести последней загрузки,
число строк, наличие записей с датой заказа/возврата внутри окна простоя (`2026-08-01…2026-08-04`)
— не как самостоятельный признак дыры (`WRITE_TRUNCATE` не накапливает историю выборочно), а как
подтверждение, что последний успешный прогон в принципе покрывал это окно своей выборкой (для
`fact_purchases` — весь массив заказов; для `fact_returns` — окно 90 суток от момента прогона).

**Шаг 4.** Раздельный вердикт по каждой из двух таблиц: «дыра отсутствует, досев не требуется» (с
обоснованием — какой именно прогон и когда закрыл окно простоя) либо «дыра присутствует / не
установлено» (с точным описанием недостающего). Если хотя бы одна таблица даёт второй исход —
сессия ОСТАНАВЛИВАЕТСЯ на этом выводе: Шаг 5 не исполняется, находка идёт в `CONTEXT GAP` и в
`/reference/architect_review_queue_<date>-<N>.md` (`ADR-015`/`ADR-018`).

**Шаг 5 — ГЕЙТ КЛАССА B, НЕ ИСПОЛНЯТЬ без нового поимённого ADR.** Ручная запись недостающих
периодов в `core.fact_purchases`/`core.fact_returns` тем же кодом загрузчика
(`fetch_purchase_positions`/`fetch_return_positions` с явным `date_from`/`date_to`), если Шаг 4
установил дыру хотя бы в одной из таблиц. Форма записи (ручной вызов CF, конкретное окно) этим
брифом не назначается — назначается архитектором по факту находки Шага 4.
