## Роль

Ты — исполнитель проекта. Законы — `CLAUDE.md`, стандарты — `05_CONVENTIONS.md` Части I и II.
Модель исполнения: ты исполняешь сам (`ADR-082 §2`). Не-идемпотентное — `deploy`, `run`, `update`,
прод-`bq query`, `git push` — только отдельным действием после явного подтверждения владельца,
никогда в связке с диагностикой (`ADR-055 §2`). В этой задаче не-идемпотентных шагов нет по
построению: всё, что она делает в облаке, — `list`, `describe`, `bq show`, `gcloud storage cp` на
чтение. Если шаг вдруг требует записи в облако — это выход за бриф, стоп и вопрос владельцу.
`Done` — только по подтверждённому логу, не по `rc=0` (`05` Часть I ★ Успех инструмента ≠ факт).
Работаешь в СВОЁМ рабочем дереве и коммитишь в СВОЮ ветку (`ADR-081 §6`). `07_STATE`,
`06_DECISIONS_LOG` и `06_INDEX` не правишь: session-блок кладёшь одним новым файлом в
`reference/_inbox/`.

**Ты не выводишь карту из данных.** Форма добычи назначена владельцем (`ADR-079 §8`, вариант (a) из
трёх): карта снимается **с живого кода**. Сравнение содержимого `core` с ответами API без чтения
кода даёт гипотезы, а не карту, и воспроизводит ровно тот класс ошибки, против которого стоит
`ADR-076 §5.2`.

## Цель

Снять и зафиксировать в репо карту происхождения оставшихся четырёх поверхностей (`ADR-079 §7b`):
1. документ МойСклада → `core.fact_purchases` → `marts.in_transit`
2. документ МойСклада → `core.fact_customer_invoices` → `marts.customer_invoices_ar`
3. документ МойСклада → `core.fact_inventory` → `stock`-компонент `marts.inventory_health`
4. источник `msklad_counterparty_returns` (LS custom query, страница «Операционка») — установить,
   существует ли SQL-объект вообще, и если да — откуда он берёт данные

— по живому коду обслуживающих Cloud Functions, а не по догадке о нём.

Карта обязана называть по каждой сверяемой величине (`ADR-079 §2`): документ-источник МойСклада,
поле этого документа, правило конвертации в KGS (`ADR-010`, там где применимо), фильтр периода
(либо признак «состояние на текущий момент», `ADR-079 §3`) и зерно строки. Без этого мост паритета
не считается выведенным для этих четырёх пар (`Q-79`/`Q-80`/`Q-81`/`Q-82`).

**Важное отличие от `SOURCE-MAP-SALES`:** документация репо (`01_ARCHITECTURE §топология`,
`03_PIPELINE_SPEC §режимы cf-facts`) утверждает, что `core.fact_purchases` грузит `cf-facts`
(режим `purchases`), а `core.fact_inventory` — отдельная CF `cf-inventory` (ежедневный снэпшот,

## Входы (факты из репо — использовать, не перевыводить)

1. **Порядок владельца (`ADR-079 §7`): эта задача идёт ПОСЛЕ `SOURCE-MAP-SALES`.** Если на момент
   старта `SOURCE-MAP-SALES` не DONE (проверяется по `07_STATE §Текущий фокус` и наличию
   `reference/code/cf-facts/MANIFEST.md`) — это не жёсткий блокер по зависимости данных (обе задачи
   класса A, независимо читают код), но расхождение с назначенным порядком — см. Шаг 0в: остановиться
   и подтвердить у владельца, что запуск вне порядка согласован, прежде чем продолжать.
2. **Слот `cf-inventory` в `11_INFRA_FACTS §CF` не существует.** Ни URL, ни ревизия, ни регион этой
   функции в репо не зафиксированы — даже placeholder-строки нет (в отличие от `cf-facts`, у которой
   пустая строка уже была). Регион снимается `list`-командой, как в `SOURCE-MAP-SALES` Шаг 1.
3. **CF, обслуживающая `core.fact_customer_invoices`, не названа нигде в репо.** Догадка о имени
   (например «раз есть `cf-facts`, значит и invoices там же») запрещена (`_METHOD §6`) — источник
   устанавливается инвентарём + чтением кода (Шаг 1/2), не по аналогии.
4. **Проект:** `msklad-bi-prod` (`00_CHARTER §миссия`). Секрет не нужен: задача не ходит в API
   МойСклада (`ADR-079 §7a` основание переносится на `§7b` тем же классом A) — съём имён полей на
   стороне МойСклада вынесен в `REPORT-FIELDS` (класс B) и эту задачу не гейтит.
5. **`marts.in_transit` и `marts.inventory_health` — снимочные витрины** (`ADR-079 §3`): эталон,
   если бы сверка производилась, обязан сниматься в том же окне, что и пересборка витрины. Эта
   задача сверку не производит (см. «Вне scope»), но карта обязана назвать зерно строки как
   «состояние на текущий момент», а не подставлять оконный фильтр по аналогии со `sales_profit`.
6. **`msklad_counterparty_returns` может не быть BigQuery-объектом вообще.** В отличие от прочих
   трёх мартов (все — `transferConfig` с каноническим SQL в `reference/sql/`), для этой поверхности
   ни SQL-файла, ни Config ID в репо нет. Гипотеза, не факт: источник может быть custom-SQL,
   встроенным непосредственно в Looker Studio (Data Source типа BigQuery Custom Query), а не
   scheduled-query-объектом — тогда `bq ls --transfer_config` его в принципе не найдёт. Это
   устанавливается Шагом 5, не предполагается заранее.

### Шаг 1 — инвентарь Cloud Functions и определение обслуживающих CF (read-only)

Цель шага — закрыть Вход 2 (регион `cf-inventory`) и Вход 3 (CF для `fact_customer_invoices`)
фактом, не подстановкой.

```bash
#!/usr/bin/env bash
set -uo pipefail
date -u
gcloud auth list

PROJECT=msklad-bi-prod

echo "=== 1. инвентарь Cloud Functions (все регионы) ==="
gcloud functions list --project="$PROJECT" --format="table(name,state,environment,updateTime)" 2>&1

echo "=== 2. инвентарь Cloud Run (gen2-функции видны и здесь) ==="
gcloud run services list --project="$PROJECT" --format="table(metadata.name,status.url,metadata.namespace)" 2>&1

gcloud auth list
date -u
```

Из выдачи взять точное имя и регион `cf-inventory`. Если функции с именем `cf-inventory` в
инвентаре нет — `CONTEXT GAP`, не повод выбрать похожую по имени.

**Для `fact_customer_invoices`:** полный список CF из этого шага — единственный источник кандидатов.
Ни одно имя не подставляется по аналогии (`ADR-079 §8`). Если полный список CF совпадает с тем, что
уже назван в `01_ARCHITECTURE §топология` (`cf-dim`, `cf-facts`, `cf-fx`, `cf-inventory`, `cf-dq`,
`cf-finance`, `cf-alert`) — источник ищется чтением кода `cf-facts` (Шаг 2), как наиболее вероятного
кандидата по семейству «facts», но это гипотеза для проверки чтением, не вывод из имени. Если в
инвентаре есть функция, не названная нигде в `01`/`03`/`11` — это факт расхождения дока с
реальностью, фиксируется отдельно и код читается и оттуда.

Затем — `describe` по обеим найденным функциям (`cf-inventory`, и, если это отдельная CF, той, что
обслуживает счета):

```bash
gcloud functions describe cf-inventory --gen2 --region="<РЕГИОН ИЗ ШАГА 1>" \
  --project=msklad-bi-prod --format=yaml 2>&1
```

Зафиксировать дословно: `serviceConfig.revision`, `buildConfig.entryPoint`,
`buildConfig.source.storageSource` (`bucket`, `object`, `generation`), `updateTime`, `state`,
`serviceConfig.serviceAccountEmail`, `serviceConfig.uri`, `serviceConfig.timeoutSeconds`,
`availableMemory`, `environmentVariables`/`secretEnvironmentVariables` (имена, не значения),
триггер и его конфигурацию (Scheduler-джоба `cf-inventory-trigger` уже известна из `11 §CF`
cf-finance строка 27 — сверить, что триггер описания совпадает).

Пустая или непарсимая выдача при `rc=0` — гэп наблюдения, не факт (`05` Часть I ★).

## Критерии приёмки (Acceptance)

Проверяемые условия, не «работает»:

1. **Ревизия `cf-inventory` названа фактом.** `reference/code/cf-inventory/MANIFEST.md` несёт
   конкретную ревизию, `source.storageSource` с `generation`, `updateTime`, `state`,
   `serviceAccountEmail`, `uri` — из вывода `describe`. Регион получен `list`-командой и совпадает
   с тем, по которому исполнен `describe`.
2. **CF, обслуживающая `core.fact_customer_invoices`, установлена фактом инвентаря + чтения кода**,
   не подстановкой имени по аналогии. Если это `cf-facts` — цитата из уже снятого снапшота; если
   отдельная CF — собственный `MANIFEST.md` с теми же реквизитами, что п.1.
3. **Снапшоты побайтово происходят из задеплоенных архивов.** sha256 по каждому файлу, метод
   извлечения назван. Транскрипция кода вручную приёмку не проходит (`ADR-017 §5`).
4. **Карта полей полна по всем трём мартовым парам.** Для `marts.in_transit` (`quantity_in_transit`,
   `in_transit_sum_kgs`), `marts.customer_invoices_ar` (`sum_kgs`, `payed_sum_kgs`, `unpaid_sum_kgs`),
   `stock`-компонента `marts.inventory_health` (`stock`, `reserve`, `in_transit`,
   `quantity_available`, `cost_kgs`) — в артефакте есть документ-источник, поле документа, правило
   конвертации в KGS, признак периода/снимка, зерно строки. Расчётные величины без источника в
   документе (`cost_kgs` COGS-метод, `coverage_days_*`/флаги) помечены явно.
5. **Каждое утверждение о коде трассируется к строке файла снапшота** (`файл:строка` + цитата).
   Вердикт, опирающийся на текстовый поиск, печатает совпавшие строки с номерами (`ADR-044`).
6. **Валютный вопрос закрыт однозначно по каждой из трёх денежных величин** (`price_kgs`/`sum_kgs`
   заказов поставщику; `sum_kgs`/`payed_sum_kgs`/`unpaid_sum_kgs` счетов; `cost_kgs` остатков) —
   есть `× rate.value` или нет, с печатью строк.
7. **Правило `MERGE`/загрузки зафиксировано для каждой из трёх ветвей кода** (форма, ключ,
   идемпотентность, триггер пересборки марта).
8. **Судьба `msklad_counterparty_returns` установлена одним из трёх исходов:** (a) найден SQL/VIEW —
   карта снята тем же методом, что три прочих; (b) объект не найден инструментами BigQuery CLI —
   зафиксирован как исчерпанный discovery этой сессии с явным `CONTEXT GAP` на продолжение;

## Вне scope этой задачи

- **Любые обращения к API МойСклада** и чтение секрета `msklad-token`. Это `REPORT-FIELDS`, класс B
  (`ADR-079 §9`). Попытка «заодно дёрнуть один GET» переводит задачу в класс B и есть нарушение
  мандата.
- **Построчная численная сверка** `in_transit_sum_kgs`/`unpaid_sum_kgs`/`stock` с отчётами МойСклада
  и любой вердикт о сходимости. Сверка идёт ПОСЛЕ карты (`ADR-079 §4`).
- **Формулировка правила моста** для `reference/parity_registry.md`. Файл реестра этой задачей не
  правится.
- **`core.fact_sales_profit`/`marts.sales_overview` и различитель `Q-83`** — это `SOURCE-MAP-SALES`,
  не эта задача. Если код `cf-facts` попадётся при чтении purchases-ветки — фиксировать одной
  строкой «уже снято `SOURCE-MAP-SALES`» или кросс-ссылкой, не повторять анализ.
- **Слот `cf-facts` в `11_INFRA_FACTS §CF`.** Правит `SOURCE-MAP-SALES`, эта задача его не трогает
  даже если снимает свой собственный снапшот `cf-facts` в аварийном случае (Шаг 2б) — в этом случае
  факты о самой CF `cf-facts` (ревизия/uri/etc) в `11` не пишутся этой сессией, только используются
  из снапшота для чтения кода.
- **Любой фикс.** Найденный дефект (отсутствие `× rate.value`, `INSERT ROW`, ненадёжность
  `is_in_transit`, расхождение дока с кодом) фиксируется фактом и уходит отдельной задачей —
  фикс-форвард в нужный слой (`CLAUDE.md §Граница контракта`). Эта задача ничего не чинит, включая
  правку комментариев/доков.
- **Расследование курса USD** и всё, что тянет `Q-69`/`Q-70`/`ADR-062` за пределы констатации
  «какая форма курса используется» в марте.
- **Правки `01_ARCHITECTURE`/`02_ERP_CONTRACTS`/`03_PIPELINE_SPEC`** по найденным расхождениям
  (включая добавление схемы `fact_customer_invoices` в `02`): STABLE/SEMI-STABLE доки, меняются
  только через ADR. Расхождение → факт в артефакте + `proposed` в `NEW_DECISIONS`.
- **Доступ к конфигурации Looker Studio** (если Шаг 6 упирается в custom-SQL внутри LS, не в
  BigQuery) — вне инструментов CLI этой сессии, вне мандата класса A по построению (не секрет и не
  деплой, а просто другой продукт без доступа отсюда).
- **Деплой, правка конфигураций, запись в BigQuery** — класс B, вне мандата этой задачи целиком.
