## Шаги

Всё исполняемое доставляется **только через файл** (`ADR-055 §1`): heredoc-запись скрипта, запуск
`bash script.sh > run.log 2>&1; cat run.log`. Прямая вставка блока в интерактивный шелл формой доставки не
является. Временные файлы не удалять, путь печатать последней строкой (`ADR-043`).

**Шаг 0 — якорь и личность (первой командой скрипта, `ADR-055 §3` + `ADR-063 §4`).**
`date -u`; затем активный аккаунт вызывающего: `gcloud auth list --filter=status:ACTIVE --format='value(account)'`
и `gcloud config get-value project`. Оба значения — в артефакт дословно. Если аккаунт не тот, под которым
велась работа, или пусто — остановись: это класс `Q-68`/`ADR-063 §2` (тихий отказ читается как «данных нет»).

**Шаг 1 — листинг заданий за сутки, все пользователи.**
Окно считать от `date -u` шага 0, не от локальной даты. Форма:
`MIN_MS=$(( ( $(date -u +%s) - 86400 ) * 1000 ))`, затем
`bq --project_id=msklad-bi-prod ls -j --all_users --min_creation_time=$MIN_MS -n 1000 --format=prettyjson > jobs.json`.
Скрипт **только выгружает** JSON и печатает его; вердикт по каденции скриптом не выносить (`ADR-044`:
автовердикт на текстовом поиске — не факт). Из `jobs.json` тебе нужны по каждому заданию:
`jobReference.jobId`, `user_email`, `statistics.creationTime` (перевести в UTC-строку с `Z`),
`configuration.query.destinationTable` (интересуют `marts.expenses`, `marts.sales_overview`, попутно любые
`marts.*`), `status.state`.

**Шаг 2 — снять расписания двух конфигураций дословно.**
Сначала полные resource-name: `bq ls --transfer_config --transfer_location=asia-east1 --format=prettyjson > tc_list.json`.
Из него взять поле `name` для обоих ID **дословно** (форма `projects/<num>/locations/asia-east1/transferConfigs/<id>`),
имя не конструировать из догадки о номере проекта. Затем по каждому:
`bq show --format=prettyjson --transfer_config '<полный name>'`. В артефакт — поля `schedule`,
`scheduleOptions`, `nextRunTime`, `state`, `disabled`, `destinationDatasetId`, `updateTime` дословно.
Пустое `schedule` фиксируется как **«поле присутствует и пусто»**, а не как «неизвестно» — это разные факты.

**Шаг 3 — сопоставление, без выбора гипотезы.**
Свести три вещи: задокументированное (`11 §SQ` стр.49–50) · снятое расписание (шаг 2) · фактические слоты
из листинга (шаг 1). Для наблюдения `Q-64` (14:41 и двухчасовая каденция) допустимы ровно три вывода:
(а) объясняется прогонами DTS — тогда с указанием `user_email` и совпадающих слотов; (б) объясняется ручными
прогонами конкретного пользователя — так же с `user_email`; (в) **не различено** — и тогда так и написано.
Вариант «списать на ручные прогоны диагностической сессии» без `user_email`-фактуры прямо ОТКЛОНЁН
`ADR-045 §1`. Пустой или противоречивый результат любого шага = гэп наблюдения, не факт
(`05` Часть I ★, `ADR-021 §2`).

**Шаг 4 — артефакт в репо.**
`/reference/sq_cadence_<YYYY-MM-DD>.md`, дата — **локальная Бишкека** (`ADR-046 §1`); все временны́е факты
внутри — UTC с суффиксом `Z` (`ADR-046 §3`). Состав: `git rev-parse HEAD`, `date -u` начала и конца, аккаунт
начала и конца, точные команды, сырые выдержки полей, таблица сопоставления шага 3, явная строка «прод не
тронут: ни одного `bq update`/`bq mk`/`StartManualTransferRuns`».

**Шаг 5 — предложить патч `11 §SQ` стр.49–50, строго по снятому.**
`ADR-045 §6`: `11 §SQ` патчится ТОЛЬКО по факту замера. Патч предлагается в session-блоке (запись в репо —
через владельца, `_METHOD §10`), затрагивает только поля, снятые шагом 2, и ссылается на артефакт шага 4 как
на провенанс. Ничего сверх снятого в патч не попадает.

**Шаг 6 — закрытие якоря.** `date -u` **последней** командой скрипта плюс повторный
`gcloud auth list --filter=status:ACTIVE` (`ADR-063 §4`). Расхождение личности между началом и концом —
инцидент, фиксируется, вывод шага 3 при этом считается неподтверждённым.

2. Поле `schedule` снято дословно по **обоим** Config ID (`6a22a243-…`, `6a23f3ea-…`); для каждого явно
   сказано «пусто» либо приведено значение. Остаток `Q-21` этим закрыт.
3. Фактические слоты пересборки `marts.expenses` за сутки перечислены с `creationTime` в UTC (`…Z`) и
   `user_email`; сказано, совпадает ли это с `11 §SQ` стр.49 — да или нет, без «примерно».
4. Наблюдение `Q-64` (14:41 UTC · двухчасовая каденция `sales_overview`) получило один из трёх выводов
   шага 3, причём (а)/(б) — только с `user_email`-фактурой.
5. Патч `11 §SQ` стр.49–50 предложен и не выходит за снятые поля.
6. Ни одной команды записи: в `run.log` отсутствуют `bq update`, `bq mk`, `bq rm`, `bq query` с записью,
   `gcloud … run`, `StartManualTransferRuns`. Проверяется просмотром лога, а не заявлением.
7. Ноль инцидентов транспортного класса `Q-62`/`Q-68`; если инцидент был — он **зафиксирован**
   (`ADR-071 §2`: статус «тренировка» не отменяет фиксацию).
