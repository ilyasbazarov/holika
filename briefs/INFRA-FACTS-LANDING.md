Порядок шагов недельного (из последовательности шагов файла, не из комментариев):
`init → step_dim → step_fx → step_facts(mode=weekly) → step_purchases(mode=purchases) →
step_returns(mode=returns, window_days=90) → step_perimeter(mode=perimeter, window_days=90) →
step_dq → parse_dq_result → check_dq → step_promote(mode=promote, window_days=90) →
step_perimeter_promote(mode=perimeter_promote, window_days=90) → done`.

Порядок шагов часового:
`init → step_dim → step_fx → step_facts(mode=hourly) → step_purchases(mode=purchases,
window_days=90) → step_dq → parse_dq_result → check_dq → step_promote(mode=promote, window_days=7)
→ done`.

Два отличия от того, что живые доки утверждают сегодня:
- `01_ARCHITECTURE.md:84` ставит `step_purchases` ПОСЛЕ `step_promote` — неверно с `2026-08-05`
  (разделение периметра гейта, `DQ-GATE-SCOPE-SPLIT`): закупки исполняются ДО гейта.
- `01_ARCHITECTURE.md:100` объявляет состав недельного незадокументированным (`GAP Q-13`).

Блокирующая семантика РАЗНАЯ у двух конвейеров, и берётся из текста, а не по аналогии:
- часовой `step_purchases` — non-blocking: в `except` только `sys.log severity=WARNING`, шага `raise`
  нет (`workflow_hourly.yaml:88-95`). Утверждение `01_ARCHITECTURE.md:98` для часового остаётся
  верным, но обязано быть явно ограничено часовым.
- недельные `step_purchases`, `step_returns`, `step_perimeter`, `step_perimeter_promote` — блокирующие:
  у каждого свой `raise_*`, роняющий прогон (`workflow_weekly.yaml`, блоки `except`).

**Комментарии внутри `.yaml` отстают от порядка** — наблюдённый пример: комментарий у `step_returns`
говорит «После promote — независимая таблица», тогда как сам шаг стоит ДО гейта. Порядок берётся из
последовательности шагов; комментарий источником порядка не является.
