## Цель
Закрыть первую волну построчных сверок реестра паритета (`reference/parity_registry.md`) для двух
пар, объединённых одним заходом по основанию `ADR-085 §1`/`ADR-088 §9` (нетто-выручка — производная
двух валовых величин, обе обязаны сверяться по одним и тем же часам): «Продажи»
(`core.fact_sales_profit.revenue_kgs` против `report/profit/byproduct` и `report/profit/bycounterparty`)
и «Возвраты покупателей» (`core.fact_returns` против `entity/salesreturn`). Перед содержательной
сверкой снять два ещё не измеренных факта, от которых зависит корректность самого замера: зону
интерпретации границ `momentFrom`/`momentTo` (`Q-93`) и количество документов мая-2026 в «ночных
полосах», где московские и бишкекские сутки расходятся (`ADR-088 §5/§6`).

## Входы
- Секрет `msklad-token` в Secret Manager проекта `msklad-bi-prod`.
- Форма заголовка (дословно, `reference/code/cf-finance/main.py:39`):
  `{"Authorization": f"Bearer {token}", "Accept-Encoding": "gzip"}`. Метод — `curl --compressed`
  (декодирует `gzip`); без флага прошлая сессия получила непарсимые тела — untrusted-вывод, не факт.
- Известная точка для различителя `Q-93` и второго замера сдвига: документ `entity/salesreturn`
  №00008 (`id = 0d9650b7-7549-11f1-0a80-19c400103fb5`), `moment` в ответе API = `2026-07-01
  15:33:00.000`, интерфейс МойСклад по тому же документу = `01.07.2026 18:33` (факт снят
  `REPORT-FIELDS`, повторно не проверять).
- Правило суток по веткам (`ADR-088 §3`, уже адъюдицировано, не переоткрывать): интерфейс и ручные
  выгрузки = `DATE(M+3ч)`; `core.fact_sales_profit` = `DATE(M+6ч)`; `core.fact_returns` (и остальные
  три CF-ветки) = `DATE(M)` — то есть UTC-дата документа без сдвига.
- Полосы расхождения календарей (`ADR-088 §5`, уже посчитаны как формула, не как число документов):
  интерфейс/продажи `M ∈ [18:00; 21:00)` UTC; интерфейс/возвраты `M ∈ [21:00; 24:00)` UTC;
  продажи/возвраты `M ∈ [18:00; 24:00)` UTC (по Бишкеку 00:00–06:00). Число документов мая-2026 в
  каждой полосе — то, что снимает эта сессия (Шаг 2), сейчас не известно.

## Шаги

1. **Объявление действия класса B** (`ADR-077 §6.ii`, отдельным сообщением ДО ask): назвать, что
   будет исполнено (`gcloud secrets versions access` на секрете `msklad-token`, проект
   `msklad-bi-prod`, далее серия `GET`-запросов к `api.moysklad.ru` тем же токеном), что откатывать
   не нужно (операция read-only, МойСклад не изменяется). Прочитать токен ОДНОЙ командой в
   переменную окружения; `set -x` запрещён; значение нигде не печатается, не попадает в
   session-блок и в текст коммита. Перед `git add` — `grep -rF -- "$MSKLAD_TOKEN" <каталог сессии>`,
   любое совпадение есть стоп (`ADR-076 §5.1/§5.3`).

2. **Различитель `Q-93`** (зона интерпретации `momentFrom`/`momentTo`, включение верхней границы) —
   ДО содержательных замеров. Метод, назначенный `07_STATE.md:180`: запрос узким окном вокруг
   документа с известным `M` (документ №00008, `M = 2026-07-01 15:33:00.000` по показаниям API).
   Например: `entity/salesreturn?momentFrom=2026-07-01 15:33:00&momentTo=2026-07-01 15:33:00&limit=100`
   (документ включён при включающих обеих границах в той же зоне, что и `moment`) в сравнении с
   окном, сдвинутым на предполагаемую разницу зон (+3ч/-3ч), чтобы отличить «границы в зоне API
   (UTC)» от «границы в зоне аккаунта (Москва)». Зафиксировать: попадает ли документ в узкое окно,
   включена ли верхняя граница (документ с `moment` РОВНО на границе — если такой найдётся среди 11
   документов возврата — либо синтетическая проверка окна нулевой длины). Результат — факт, не
   предположение; если различитель этим методом не снимается однозначно — `CONTEXT GAP`, не гадать.

3. **Замер ночных полос** (`ADR-088 §6`) за май-2026 по обоим типам документов (продажи, возвраты):
   посчитать число документов, чей `moment` (в зоне API, то есть как отдаёт `api.moysklad.ru`,
   с поправкой на снятую на Шаге 2 семантику границ) попадает в каждую из трёх полос `ADR-088 §5`.
   Основание приоритета перед `§7`-развилкой (`Q-92`): при пустой полосе развилка не имеет цены,
   вопрос владельцу об эталонных сутках паритета этой сессией НЕ задаётся ни при каком результате
   замера (`ADR-056`, `07_STATE.md:24`) — только зафиксировать число и передать дальше по цепочке.

4. **Второй замер сдвига** (`ADR-088 §10`) на документе мая-2026: замер `REPORT-FIELDS` подтвердил
   сдвиг +3 часа только на одном документе от 2026-07-01; выбрать документ (продажа или возврат) с
   `moment` в мае-2026, сверить его `moment` по API с отображением в интерфейсе МойСклад через
   владельца (тот же метод, что дал факт по документу №00008: инструмент интерфейсу недоступен,
   вопрос владельцу — один точечный, по конкретному номеру документа и двум числам). Цель —
   подтвердить, что сдвиг +3ч не специфичен для июля (переход на летнее время не предполагается ни
   в какую сторону, `ADR-088 §10`).

5. **Построчная сверка обеих пар** с явно названным правилом суток каждой таблицы (`ADR-088 §3`,
   уже дано во «Входах», не выводить заново). Документы полос `ADR-088 §5` считаются ОТДЕЛЬНО и ДО
   общего вердикта (`ADR-088 §5`, `07_STATE.md:182`): свести общий итог за май-2026 (валовая выручка
   `core.fact_sales_profit.revenue_kgs` против суммы `sellSum` по `report/profit/byproduct`;
   возвраты `core.fact_returns.sum_kgs` против суммы `sum` по `entity/salesreturn`, окно
   `momentFrom`/`momentTo` — май-2026 в зоне, снятой Шагом 2), затем отдельно — итог БЕЗ документов
   ночных полос, чтобы расхождение (если есть) было атрибутируемо к конкретной полосе, а не к
   «сверка не сошлась» без адреса (тот же класс ошибки, что на расходах до `ADR-006`, разрыв ~33 %).
   **Гейт по контрагентам снят:** `PARITY-SCD2-ATTRIBUTION` (`ADR-089`) признал действующий JOIN
   `scd2_is_current = TRUE` корректным по существу — разрез по контрагентам (`bycounterparty`) больше
   ничем не блокирован. Разрез по товарам (`byproduct`) этим гейтом никогда не блокировался и может
   идти первым, если разрез по контрагентам почему-то потребует дополнительного времени.

6. Внести правило суток (`ADR-088 §3`, уже принятое, не переформулировать) и числовой результат
