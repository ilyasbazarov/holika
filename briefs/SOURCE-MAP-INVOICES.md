## Цель

Установить фактом, кто и как загружает `core.fact_customer_invoices` — таблицу, для которой
`SOURCE-MAP-REST` (2026-07-30) установил `CONTEXT GAP`: ни одна из 8 живых Cloud Functions проекта не

фокус`) — поиск исторических `LOAD`/query-заданий, писавших в `core.fact_customer_invoices`, через

(`FX-MAY-WINDOW`, D2).

Результат — один из трёх исходов, не один заранее выбранный:
1. **Найден принципал-загрузчик** (сервис-аккаунт, тип задания `LOAD`/`QUERY`, время, при наличии —
   исходный GCS-объект для `LOAD`-заданий) → это называет, ЧТО грузило таблицу исторически, и открывает
   путь ко второму порядку discovery (какой код стоял за этим принципалом — тем же способом, что
   `CODE-REPO-STANDUP`, но это уже отдельная задача, не эта).
2. **История заданий не находится** (таблица старше горизонта хранения `INFORMATION_SCHEMA`, ~180 дней
   — не факт, а типичный порядок, подтвердить эмпирически Шагом 0) → зафиксировать это фактом с
   границами (какое окно проверено, что вернулось), не как «загрузчика нет».
3. **Найдены задания, но от `user_email` личного аккаунта владельца, а не сервис-аккаунта** → факт о
   разовом ручном/бэкфилл-прогоне, а не задеплоенном CF — сам по себе валидный ответ (одна из трёх

### Шаг 1 — граница по `_loaded_at` (read-only `bq query`)

Цель — получить эмпирическую нижнюю/верхнюю границу загрузок без обращения к `JOBS_BY_PROJECT`,
чтобы Шаг 2 не гадал с размером окна.

```bash
#!/usr/bin/env bash
set -uo pipefail
date -u
gcloud auth list

PROJECT=msklad-bi-prod

bq query --use_legacy_sql=false --project_id="$PROJECT" --format=prettyjson '
SELECT
  COUNT(*) AS row_count,
  MIN(_loaded_at) AS min_loaded_at,
  MAX(_loaded_at) AS max_loaded_at,
  COUNT(DISTINCT DATE(_loaded_at)) AS distinct_load_dates
FROM `msklad-bi-prod.core.fact_customer_invoices`
' 2>&1

gcloud auth list
date -u
```

`rc=0` с пустой/непарсимой выдачей — гэп наблюдения (`ADR-021 §2`), не «таблица пуста»; перезапустить
чисто прежде чем делать вывод. Записать `min_loaded_at`/`max_loaded_at` дословно — это верхняя граница
окна для Шага 2 (искать задания от `min_loaded_at - 1 день` до `max_loaded_at + 1 день`, с запасом).

### Шаг 2 — история заданий (`INFORMATION_SCHEMA.JOBS_BY_PROJECT`, метод D2(б) из `FX-MAY-WINDOW`)

```bash
#!/usr/bin/env bash
set -uo pipefail
date -u
gcloud auth list

PROJECT=msklad-bi-prod

bq query --use_legacy_sql=false --project_id="$PROJECT" --format=prettyjson "
SELECT job_id, user_email, creation_time, job_type, statement_type,
       destination_table.dataset_id, destination_table.table_id,
       SUBSTR(query, 1, 500) AS query_prefix
FROM \`region-asia-east1\`.INFORMATION_SCHEMA.JOBS_BY_PROJECT
WHERE destination_table.dataset_id = 'core'
  AND destination_table.table_id = 'fact_customer_invoices'
ORDER BY creation_time
" 2>&1

gcloud auth list
date -u
```

**Без нижней границы `creation_time` в `WHERE`** — сначала пробуем полный доступный горизонт (обычно
ограничен ретеншном самого `INFORMATION_SCHEMA`, не нашим фильтром); если объём выдачи практически
неуправляем (маловероятно для одной таблицы), сузить окном по Шагу 1. Записать **все** возвращённые
строки — `job_type` (`LOAD` vs `QUERY`), `user_email`, `statement_type` для `QUERY`-заданий
(`MERGE`/`INSERT`), полный `query_prefix` там, где `job_type = QUERY`.

**Пустая выдача при `rc=0` — гэп наблюдения** (`ADR-021 §2`/`ADR-044`), не факт «заданий никогда не
было». Возможные причины пустой выдачи, ни одна не выбирается заранее: (а) горизонт хранения
`INFORMATION_SCHEMA` истёк для нужного периода (Шаг 1 даёт `min_loaded_at`, сравнить с текущей датой);
(б) поле `destination_table` не заполнено для типа задания, которым в реальности была загружена таблица
(редкий случай — фиксировать как наблюдение, не подгонять); (в) таблица была создана иным механизмом
(например, `bq load` из локальной консоли с иным полем назначения) — тогда попробовать тот же запрос без
фильтра по `destination_table.table_id`, только по `dataset_id = 'core'` И `user_email` из уже известных
сервис-аккаунтов проекта (`etl-sa@…`, `bootstrap-sa@…` — оба встречаются в `reference/bq_jobs_2026-07-28.md`),
сузив по времени вокруг `min_loaded_at`/`max_loaded_at` из Шага 1, и просмотреть результат на совпадение
по смыслу (`fact_customer_invoices` в `query_prefix`).

### Шаг 3 — квалификация находки

По результату Шага 2 (и, если понадобилось, расширенного поиска) — один из трёх исходов Цели, ФАКТОМ:

- **Найден `job_type=LOAD`** → зафиксировать `user_email` (сервис-аккаунт или личный?),
  `creation_time` (первое и последнее вхождение), и — если API job details это несёт —
  исходный GCS URI (`bq show -j --format=prettyjson <job_id>` для деталей конкретного задания,
  read-only). Сервис-аккаунт, не входящий в уже известный список (`etl-sa@…`, `bootstrap-sa@…`,
  `ilyasbazarov4@gmail.com`) — отдельно подсветить как новый факт.
- **Найден `job_type=QUERY` с `statement_type IN ('MERGE','INSERT')`** → зафиксировать то же самое плюс
  полный текст запроса (не `SUBSTR`, а `bq show -j --format=prettyjson <job_id>` для полного `query`)
  — это может напрямую показать, из какой staging-таблицы шла загрузка, что сужает следующий шаг
  discovery без необходимости искать сам код.
- **Ничего не найдено ни одним из вариантов запроса** → зафиксировать явно как исчерпанный discovery
  этого порядка, с указанием проверенных окон/фильтров, и явную рекомендацию следующего шага (прямой
  вопрос владельцу: «есть ли где-то ручной скрипт/ноутбук/разовый бэкфилл вне деплой-цикла CF»,
  поскольку BigQuery- и Cloud-Functions-стороны исчерпаны).

### Шаг 4 — сверка с инвентарём CF (не повторный поиск, а перекрёстная проверка)

Если Шаг 3 назвал сервис-аккаунт — сверить его с `serviceAccountEmail` восьми живых CF

сужает круг подозреваемых, не доказывает код. Явно не выдавать совпадение аккаунта за решённую карту
происхождения.

Read-only, без повторного скачивания архивов (это не входит в эту задачу — см. «Вне scope»):

## Критерии приёмки (Acceptance)

Проверяемые условия, не «работает»:

1. **Граница `_loaded_at` установлена фактом** (`min_loaded_at`/`max_loaded_at`/`row_count`/
   `distinct_load_dates`), с полным выводом запроса Шага 1 в артефакте.
2. **Запрос `INFORMATION_SCHEMA.JOBS_BY_PROJECT` исполнен минимум одной формой** (полный горизонт или
   суженный по Шагу 1), полный вывод (все строки, не усечение) приложен в артефакте или в
   `reference/_scratch_.../`, с ссылкой из артефакта.
3. **Квалификация — один из трёх исходов Шага 3, названный явно**, не смешение («вероятно, это X, но
   могло быть и Y» приёмку не проходит — если данных для однозначного вывода недостаточно, это тоже
   явный исход «не найдено», а не размытая догадка).
4. **Если найден принципал** — `user_email`, `job_type`/`statement_type`, диапазон `creation_time`
   зафиксированы дословно из вывода `bq show -j`/`INFORMATION_SCHEMA`, не пересказаны.
5. **Если найден `QUERY`-job с `MERGE`/`INSERT`** — полный текст запроса приложен (не `SUBSTR`-обрезка),
   источник (staging-таблица/подзапрос) назван, если виден в тексте.
6. **Пустая или непарсимая выдача трактуется явно как гэп наблюдения**, не как «загрузчика никогда не
   было» (`ADR-021 §2`) — формулировка в артефакте обязана различать «не нашли» и «не было».
7. **Каждое утверждение трассируется** к конкретному выводу команды (лог в `_scratch_.../`), не к
   пересказу без ссылки.
8. **`11_INFRA_FACTS.md` правится ТОЛЬКО если найден конкретный факт** (принципал/механизм) — если
   Шаг 3 дал исход «ничего не найдено», файл не трогается, это явно названо в session-блоке.
9. **Логи в разделимой форме**, `date -u` и `gcloud auth list` по обоим краям каждого прогона.
   `401`/пустота при `rc=0` — гэп наблюдения, перезапуск, не «данных нет».
10. **Границы соблюдены:** карта полей документ→колонка не выводилась (невозможно без кода), API
    МойСклада не запрашивался, численных сверок не производилось, `reference/parity_registry.md` не
    правился, `07_STATE`/`06`/`06_INDEX` не тронуты напрямую (только через session-блок).
