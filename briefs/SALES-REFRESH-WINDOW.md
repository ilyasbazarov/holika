## Цель
Подготовить (не применять и не деплоить) варианты и текст патча снапшота `reference/code/cf-facts/`,
закрывающие структурную находку `ADR-097 §5`: у `cf-facts` есть только скользящие окна выборки

якорь паритета `2026-05-01` (`ADR-069 §2`) выходит из самого широкого окна к `2026-08-29`, то есть
паритет мая не может быть «поддерживаемым состоянием» без правки (`ADR-067 §5c`). Результат — три
именованных варианта (не выбор одного) с готовым текстом патча/диффа против файлов снапшота, каждый
явно разбирающий ловушку задвоения `ADR-097 §5`, и артефакт `reference/sales_refresh_window_2026-08-01.md`,
самодостаточный для последующего решения владельца/архитектора и для отдельной задачи класса B

## Шаги

1. Процитировать себе дословно строку GAP-реестра `SALES-REFRESH-WINDOW` (`07_STATE.md`) и `ADR-097 §5`
   — зафиксировать в артефакте как открывающий блок, не пересказывать.

2. **Вариант 1 — досев отдельным режимом с раздельными окнами выборки и `MERGE`.** Задача: сутки,
   выпавшие из скользящего окна `WEEKLY_WINDOW_DAYS=90`, обязаны попадать в `core` без задвоения при
   повторном промоуте. Разработать текст патча (не применять):
   - новый `mode` (например `topoff`) или параметризация существующего `promote`, принимающая ДВА
     разных числа: окно выборки из API (`select_window_days`/явные `date_from`/`date_to`, передаваемые
     в `fetch_demand_positions`) и окно `MERGE`-фильтра в `ON`-клаузе (`merge_window_days`), которое
     обязано ПОКРЫВАТЬ весь диапазон выборки, а не совпадать с ним по построению — это и есть снятие
     ловушки `ADR-097 §5` (сейчас оба смысла несёт одна переменная `window_days`);
   - явно выписать изменённую сигнатуру `_run_promote`/`_build_merge_sql`/`promote_to_core` (два
     параметра вместо одного) и изменённую строку `ON` в SQL;
   - назвать источник COGS (`cogs_source`) для диапазона шире 90 суток: текущая логика (`window_days
     >= 90` → `STG_BYVARIANT`, иначе `CORE_BYVARIANT_BCK`) не рассчитана на произвольный исторический
     диапазон — назвать это явно как открытый вопрос варианта, не домысливать значение.

3. **Вариант 2 — разовый пересев мая.** Задача: один неповторяющийся прогон, покрывающий ровно
   2026-05-01…2026-05-31, без превращения в постоянный режим. Разработать текст патча/инструкции:
   - конкретные параметры вызова (`date_from=2026-05-01`, `date_to=2026-05-31`) через ту же форму
     раздельных окон варианта 1 (переиспользовать, не изобретать вторую механику) — или, если
     архитектурно проще, отдельный однократный скрипт вне `main.py`, вызывающий
     `fetch_demand_positions`/`promote_to_core` напрямую с явными датами;
   - явно разобрать ловушку задвоения на этом конкретном диапазоне: `MERGE`-фильтр обязан быть
     `T.transaction_date >= '2026-05-01' AND T.transaction_date <= '2026-05-31'` (или шире), не
     `DATE_SUB(CURRENT_DATE(), INTERVAL window_days DAY)` — иначе майские строки не найдут пары по
     `ON` и задвоятся;
   - назвать источник COGS для мая тем же способом, что в варианте 1 (тот же открытый вопрос).

4. **Вариант 3 — объявление мая датированным снимком с плашкой.** Задача: без правки кода `cf-facts`
   зафиксировать, что данные мая в `core.fact_sales_profit` — снимок на дату последней загрузки
   (наблюдение `Q-98`/`ADR-097`: пример `_loaded_at` майских строк из уже проведённой сверки), не
   поддерживаемое состояние. Подготовить текст плашки/предупреждения — кандидат размещения:
   `02_ERP_CONTRACTS.md §core.fact_sales_profit` и/или `reference/parity_registry.md` (только текст
   формулировки здесь, применение в сами файлы — вне scope этой сессии, см. ниже). Явно назвать: этот
   вариант НЕ требует деплоя и НЕ снимает находку `ADR-097 §5` по существу — он документирует
   ограничение, а не устраняет его.

5. Для всех трёх вариантов — единая таблица сравнения (что снимает / чего не снимает / цена / класс
   исполнения / зависимости) в конце артефакта. Не ранжировать и не рекомендовать один вариант как
   решение — выбор `owner`/архитектора (задача не содержит суждения об этом выборе, только его
   материал; строка GAP-реестра требует именно «вариантов», во множественном числе).

6. Собрать всё в `reference/sales_refresh_window_2026-08-01.md`: открывающий блок (шаг 1), три
   раздела-варианта с текстом патча/диффа (шаги 2–4) и сравнительная таблица (шаг 5).
