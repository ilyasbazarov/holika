## Шаги
1. Шесть оговорок `ADR-076 §5` подтверждены буквально: токен не печатается (переменная окружения,
   без `set -x`, без `echo` значения); форма заголовка авторизации взята из `reference/code/cf-finance/main.py:39`;
   `grep -rF -- "$MSKLAD_TOKEN" reference/_scratch_PARITY-STOCK-ROWWISE_<date>/` перед `git add`, любое
   совпадение — стоп; эталон датируется снимком (зафиксировать `date_snapshot`/UTC-момент живого
   запроса); поведение инструмента на непере­численной сетевой команде фиксируется в session-блоке,
   если проявится. Форма логирования HTTP-полей — `ADR-079 §6`: в лог/артефакт идут имена полей
   (ключи первого элемента `rows[]`), не первые N символов тела.
2. UTC-якорь и подтверждение личности вызывающего первой командой сессии: `date -u` + `gcloud auth
   list` (`ADR-055 §3/§4`).
3. `bq query` — определить текущий `MAX(date_snapshot)` в `core.fact_inventory` (та же партиция,
   что и наша сторона сравнения); сохранить сырой результат.
4. Живой `GET report/stock/all` (`stockMode=all`, `quantityMode=all`, форма — `reference/code/cf-facts/helpers.py:62-67`),
   постранично при необходимости (`expand`/`limit` — по правилам поведения API, `02_ERP_CONTRACTS §поведение-API`,
   если секция наполнена; иначе `limit≤100` по прецеденту `ADR-076`/PR-16). **Сохранить ВСЕ сырые
   строки ответа** (не только агрегат) в `reference/_scratch_PARITY-STOCK-ROWWISE_<date>/` — это то,
   чего не хватило прошлой сессии.
5. `bq query` — выгрузить построчно `core.fact_inventory` за партицию из шага 3 (все колонки, не
   агрегат). Сохранить сырой результат. **Явно указать `-n`/`--max_rows` больше ожидаемого числа
   строк** (прецедент ловушки — дефолтный лимит `bq` в 100 строк тихо обрезал результат в прошлой
   сессии, `reference/parity_stock_intransit_2026-08-04.md §Ловушка`).
6. Построить ключ сопоставления строк между источником и нашей стороной (вероятный кандидат —
   товар/номенклатура + склад; точные имена полей взять из схемы `core.fact_inventory`, а не
   угадывать; если ключ не очевиден из схемы — `CONTEXT GAP`, не изобретать). Выполнить полный
   внешний джойн по этому ключу: сироты источника, сироты нашей стороны, расхождения на совпавшем
   ключе — три отдельных множества, форма отчёта как в `reference/parity_intransit_close_2026-08-04.md`
   (таблица «Множество / строк / величина»).
7. Из результата джойна установить конкретную причину разности `4,00 KGS-штук` (какая строка/товар/склад
   её даёт) — не «объяснение достаточное», а измеренная причина (`ADR-120 §2` — тот же класс различия
   уже проведён для строки 22, использовать ту же дисциплину).
8. Если причина требует данных вне доступа этой сессии (например, состояние конкретного товара в
   источнике на другую дату) — зафиксировать как `CONTEXT GAP`/остаток, не досочинять.
9. UTC-якорь и подтверждение личности вызывающего последней командой сессии (`ADR-055 §4`).
10. Обновить `reference/parity_registry.md` строку 21, колонку «Статус сходимости» — приписка с

## Критерии приёмки (Acceptance)
- Сырые построчные данные ОБЕИХ сторон (источник `report/stock/all`, наша сторона
  `core.fact_inventory`) сохранены в `reference/_scratch_PARITY-STOCK-ROWWISE_<date>/` — это
  единственное, что делает результат воспроизводимым офлайн (в отличие от прошлой сессии).
- Построчный джойн выполнен по явно названному ключу; три множества (сироты источника / сироты
  нашей стороны / расхождения на совпавшем ключе) посчитаны и засвидетельствованы логом, а не
  вычитанием агрегатов (`★ Успех инструмента ≠ факт`, `ADR-021 §2`).
- Причина разности `4,00 KGS-штук` либо установлена конкретно (строка/товар/склад с провенансом),
  либо зафиксирована как неустановимая с названной, а не предполагаемой причиной невозможности
  (например: «источник за эти сутки недоступен к повторному снятию» — только если это факт, не
  догадка).
- `reference/parity_registry.md` строка 21 обновлена ровно найденным результатом; остальной файл
  без изменений (проверяется `git diff` перед коммитом).
