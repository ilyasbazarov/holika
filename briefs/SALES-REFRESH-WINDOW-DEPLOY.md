## Шаги

1. **Read-only сверка дрейфа.** Снять текущую задеплоенную ревизию `cf-facts` и сверить с `master`
   код-репо `holika-prod` — расхождение есть стоп по процедуре варианта Б (деплой поверх дрейфа
   затирает чужую правку молча).

2. **Ветка деплоя.** Завести `deploy/cf-facts-<YYYY-MM-DD>-refresh-window` от актуального `master`;
   перенести в неё `cf-facts/` из снапшота (три файла, тронутых узкой формой: как минимум
   `config.py`, `bq_ops.py`; `main.py` — если правки предохранителя его касаются, сверить по факту).
   Сверить `sha256` перенесённых файлов ветки против снапшота `reference/code/cf-facts/`.

3. **Гигиена и секреты.** Проверить `.gcloudignore` (чистый, `ADR-040`) и прогнать сплошной поиск
   секретов по патчу с печатью совпавших строк (`ADR-044`, пустая выдача не есть факт отсутствия).

4. **Объявление действия (`ADR-077 §6`) + подтверждение владельца, затем снимок.** Отдельным
   сообщением назвать: что исполняется («`CREATE SNAPSHOT TABLE core.fact_sales_profit_snap_<YYYYMMDD>
   CLONE core.fact_sales_profit`»), на каком объекте (`core.fact_sales_profit`, прод), чем откатывается
   (сам снимок — источник восстановления; операция сама по себе безопасна и обратима, но пишет в прод).
   После явного «да» — выполнить, напечатать число строк и `SUM(revenue_kgs)` снимка.

5. **Объявление действия + подтверждение, затем деплой.** Отдельным сообщением: деплой `cf-facts`
   из ветки `deploy/...` (`--source` только на `cf-facts/`), откат — повторный деплой именем ревизии
   `cf-facts-00011-mab`. После «да» — деплой; зафиксировать новую ревизию.

6. **Read-back архива.** Сверить содержимое задеплоенного архива (`ADR-021 §2`: успех команды
   деплоя ≠ факт). Записать секцию в `reference/code/cf-facts/MANIFEST.md` по результату read-back
   (`sha256`, затронутые/незатронутые файлы, `generation`/`updateTime`).

7. **Вычислить `window_days` первого прогона** по формуле `window_days >= (дата прогона −
   2026-05-01 в сутках) + 3` на ФАКТИЧЕСКУЮ дату прогона (не по ориентиру из брифа).

8. **Объявление действия + подтверждение, затем первый боевой прогон.** Отдельным сообщением: режим
   и объект (промоут продаж `mode=weekly`/`promote` с вычисленным `window_days`; промоут периметра —
   staging периметра ОБЯЗАНА быть загружена тем же прогоном, т.к. на `2026-08-11` отставала на восемь
   суток), чем откатывается (снимок шага 4 + time travel `168`ч, код — ревизия `cf-facts-00011-mab`).
   После «да» — исполнить ОДНИМ прогоном (staging + `MERGE`, одно значение `window_days`) для ОБОИХ
   промоутов (продажи и периметр). **В логе обязана присутствовать строка «предохранитель пройден»
   с обеими датами для КАЖДОГО из двух промоутов** — отсутствие есть провал приёмки (мандат `§6(i)`),
   не мелочь для разбора постфактум.

9. **Замер «до/после».** `COUNT(*)` и `SUM(revenue_kgs)` за май-2026 и июль-2026 в
   `core.fact_sales_profit`, до (снимок шага 4) и после (шаг 8). Ожидание, названное мандатом заранее:
   удаляются семь строк-сирот (`1 630 239,81` KGS) и документ `04235` (`1 980 000,00` KGS); майская
   выручка ядра падает с `96 844 445,61` примерно до `93 234 205,80` KGS; июльское завышение
   `127 621,20` KGS/месяц прекращается. Расхождение с этим ожиданием — печатается числом, НЕ
   примиряется исполнителем (`00_CHARTER §главный принцип`), уходит архитектору как открытый вопрос.

10. **Пересчёт разности пары «Продажи».** По той же формуле моста, что дала вердикт `ADR-157`
    (`sales_parity_verdict_adj_2026-08-10.md`), пересчитать расхождение с эталоном на новых числах
    шага 9; напечатать разность явно.

11. **Слияние ветки в `master` код-репо** — только после успешного read-back (шаг 6) и приёмки шагов
    8-10 (условие 8 процедуры варианта Б: при неуспехе ветка не сливается, откат идёт на названную
    ревизию, попытка записывается в `MANIFEST.md` наравне с удачной).

12. Собрать `reference/sales_refresh_window_deploy_2026-08-11.md`: снимок (число/сумма), sha256
    ветки, обе строки «предохранитель пройден», замеры до/после (май и июль), пересчитанная разность,
    ссылки на коммиты код-репо (ветка + merge).
